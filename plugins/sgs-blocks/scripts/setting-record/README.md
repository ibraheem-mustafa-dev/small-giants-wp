# setting-record: what each block setting changes, checked against the block's own code

Each block gets a written record of where every setting paints: the part, the CSS properties, the state and the media conditions. `check.py` runs the block's real `render.php` offline for every setting (no site, no browser), compares what changes with the record both ways, and proves each placement with a CSS cascade. It is the cloning route's source for where each setting paints (plan `.claude/plans/archive/2026-11-21-setting-record.md`); the browser measurement it replaced is retired.

## Use

```
python check.py sgs/button --record path/button.json          compare: exit 1 on any add, remove, change, parts order or schema error
python check.py sgs/button --write path/button.json           write the record from the code (entries marked runner are kept)
python check.py sgs/button sgs/cart --record-dir DIR          several blocks at once, one process each (--write-dir DIR to write)
python check.py --all --record-dir DIR --out DIR2 --jobs N    every block under src/blocks, N at once (the library's first fill; also --write-dir)
python check.py --changed [--no-proof]                        the build gate: only the blocks a change touches, against scripts/data/setting-records
python check.py --changed --restamp                           the same, refreshing the stamp of each record that passes (with the proof)
python check.py sgs/button --write F --fresh                  prove every entry again, ignoring the record's saved proof outcomes
python check.py --self-test                                   plant four faults in copies of sgs/button and prove each is caught
python summarise.py REPORTS_DIR [--json OUT.json]             read a library run's reports into one table of causes
python accept.py DIR                                          mark every record's unproven entries proved in the same shape on another block
python seed_fixtures.py [--check]                             give every block without one a fixture in fixtures.json
python split_fixtures.py --check [--against REV]              each fixture's plain attributes still render the block; --against: the split moves no plan
python -m pytest tests                                        unit tests (each rule has a must-fail case)
```

Options: `--plugin P` checks another copy of the plugin; `--fixtures F` another fixtures file; `--instances PLAN.json` / `--instances-dir DIR` replays a saved instance plan instead of generating one from block.json; `--no-proof` skips the cascade proof (kinds are then left out); `--strict-parts` also fails on block.json part declarations that do not match the render; `--out DIR` is where `<block>.check.json` reports go; `--all` takes every block from its `block.json` under `src/blocks`, and `--jobs N` bounds how many blocks are checked at once (default: a quarter of the cores, at least 2; a library run with the proof took about an hour at `--jobs 10`). `--all` is for filling the library the first time, never a gate, a plugin-round step or a reseed step: after the fill, only the blocks a change touches are checked again (`check.py --changed`: `changed.py::plan` reads every record's stamp through `stamp.py::select`; a block with an own change is checked in full, a change to a file every block loads, to the check or to the runner re-renders the canaries `changed.py::CANARIES` and checks one only if its output moved; a block with no record fails unless `scripts/data/setting-record-pending.json` names it with an owner and an `until` date, and a record whose block is gone fails; each finding prints the entry and the command that rewrites the record). Renders are cached under `SGS_SETTING_RECORD_CACHE` (default `~/.cache/sgs-setting-record`, outside the checkout, so a gate run in a temporary worktree starts warm), keyed per block on a hash of the files its renders can read (its own folder and its fixture's blocks, which block folders exist and which hold a `render.php`, `includes/`, `assets/`, `schemas/`, `templates/`, `src/shared`, the runner), so an unchanged block re-checks in seconds and another block's files never throw its renders away; an `includes/` edit re-renders every block. A render that reads another block's file anyway (a block type its PHP looks up in the registry, a block its content renders: the runner lists every block.json it reads in `SGS_SETTING_RECORD_READS`) keeps each such file's content hash (`outside`), and its cached copy is used only while they are unchanged (`render.py::Renderer._outside_current`), so one block's block.json edit re-renders only the renders that read it. The proof itself is not cached: about 10 s (button) to 7 min (form) a block. `SGS_SETTING_RECORD_WORKERS` sets the parallel renders.

## Reading a report

- `add`: the code changes this, the record lacks it. `remove`: the record has it, the code no longer changes it. `change`: same setting, part and properties, other state or media condition.
- `skippedRunnerCannotSee`: record entries marked `runner` (a paint the offline runner cannot see yet: a `render_block` filter, `wp_footer`), listed, never passed silently.
- `partNotNamed`: placements whose part the selector reader cannot name (`block-source-scan/selector_eval.py::analyse_selector`); kept out of records.
- Every setting is accounted for in one of four places: an entry of the record; `testedNoPaint` (its renders changed no CSS, class, attribute or style anywhere); `replacesBlock` (it removes the block or swaps it for other markup, such as a visibility condition or a broken-reference notice: the changed render keeps none of the block's parts, or drops the block's root element while markup the block queued for the footer survives, `check.py::replaces_block`; no placement is read from it); or `unvalued` (the generator could not value it, with the reason).
- `coverageFloor`: a block whose default render is empty or lacks the block root, or a setting whose every render failed, tests nothing, so the check fails it (`check.py::check_block`) until its fixture renders it.
- `parts`: `order` is the block's printed parts in markup order (the record's `parts` must equal it); `declaredNotPrinted`, `declaredScriptBuilt` and `printedNotDeclared` compare block.json `supports.sgs.elements` with the render. These are block faults, reported always and failing only with `--strict-parts`.
- `proof`: every entry's verdict. `proved` (a property differs between the plain and the changed render on that part, or, for the underlay test, over sentinel rules), `refiled` (it differs on another part, where the entry moves), `removed` (the part is drawn and the entry's own rule matches it, yet nothing differs and the winning declaration is the same text with and without the setting; or the part's class is printed by no source, see `deadParts`), `blind` (the proof cannot see what decides it; the entry is kept and its cause named, see the table under "The record"). Also in the proof report: `deadParts` (classes no source prints: a block fault for the plugin round, each with the evidence and the number of entries removed), `completions` (the extra renders that printed a missing part, class or attribute, and the settings moved to do it), `theme` (whether the theme sheet loaded, and the error if not), `frame` (the container width at each screen width), and `counts.byCause` (the unproved entries per cause).

## The record

`record.schema.json`: `{block, schemaVersion: 1 or 2, parts: [...], entries: [{setting, part, props, state, tiers, kind, unproved?, runner?, selector?, values?, symbolic?}], stamp?, proofKeys?, accounted?}`. Format 2 (what `check.py --write` writes now; format 1 is still read) adds: `stamp` (`stamp.py::make_stamp`: the hash of every file the renders and the proof read, the hash of the renders' output, the theme hash, and the classes and tags the renders print), `proofKeys` (the entry keys before the proof removes or re-files any, so `--no-proof` is exact against the record), `accounted` (`testedNoPaint`, `replacesBlock`, `unvalued`, `partNotNamed`: every setting not in an entry, so an unaccounted setting is visible) and, on each entry, `values` (the setting values that produce it) and `symbolic` (an annotation the writer attaches, for a setting that names a breakpoint). The key is (setting, part, props, state, tiers); `selector` is for people and never compared. A setting's free custom CSS (`sgsCustomCss`) is accounted for as `unvalued` with the reason that it paints whatever its text says, which counts as fully accounted. `kind` is `value` when the property takes the setting's value and `switched-on` when moving the setting off its default turns the declaration on with a value of its own; the proof decides it. `state` is null at rest, else `hover`, `focus`, `current`, `open`, `disabled`, `active`, `checked`, `filled` (an input that holds a value: `:not(:placeholder-shown)`; `vocab.py::norm_state` names it, the proof holds it by giving every text input and textarea a value), or a selector token such as `.is-detached` (the proof holds it by giving the element that class). A blind entry carries `unproved` naming why; its kind is then only a reading (`switched-on` for a true/false setting, else `value`), and a reader that acts on kind must treat it as unproven.

Before an entry is called blind the proof applies, in this order, the mechanisms below. Each is general (it reads the block's own code, the scanner's reading of it and the theme, never a block's name), and each has a must-fail test in `tests/test_lane_d.py` (`SETREC_MUTATE=<mechanism>` switches one off to show its tests fail). An entry that none of them settles keeps its cause, and the table says who owns the next step.

| `unproved` | Meaning | Mechanism that settles it, or the owner of the remaining cases |
|---|---|---|
| `theme-value` | The value reads a custom property that neither the block's sheets nor the theme define | The theme's CSS (`theme.py::theme_css`) is the lowest author sheet of every page (`proof.py::Pages`). Every custom property the winning declaration reads, at any depth (a property defined as another variable is followed), that nothing on the page defines gets its own placeholder value on the page root (`proof.py::token_test`, `outside_vars`), the block's own properties included when this page leaves them undefined (another setting of the block defines them): a setting that switches which token is read is `proved` (`switched-on`) whatever a site's token holds. A token a front-end script writes gets `script-set-token` instead. Otherwise the placeholders are dropped and the entry is judged as any other: both pages reading the same token through the same declaration change nothing |
| `script-set-token` | The value reads a custom property a front-end script sets (`proof.py::script_set_tokens`) | The browser pass, which opens the page the way a visitor does (`browser/README.md`) |
| `same-value-here` | The setting's declaration changes but computes to the plain value (`inherit` under a root with no radius, `none`, a floor, a test value equal to the block's own) | In order: screen widths between the sampled ones (`proof.py::probe_widths`: the midpoint of every stretch between two breakpoints, media or container, inside the entry's tiers; a container breakpoint becomes the screen width whose container first passes it); the setting's other test values (`sibling_pairs`); a second value from the generator itself, asked for a value other than the first (`second_values`: a font weight of 700 that equals the block's own gets 300); the underlay test (`underlay_test`, `computed.py::Page._apply_underlay`: two lowest-priority sentinel rules, one on the part and one on its ancestors, so a declaration the setting switches on differs). Then removal, only with evidence: a per-device override (`fooTablet`, `fooMobile`) swept over every value of the setting it overrides (`override_sweep`) that never moves the part; or a rule that restates what the plain page already declares, on every element and width, var() judged by the longhand's own text (`restated_value`), and only when the setting was seen at two values (`other_value_tried`). What still has this cause computes alike in every one of these |
| `rule-needs-absent-markup` | The entry's rule needs a class or attribute no render here carries | Completion (`proof.py::completion`, `instances.py::switching_attrs` and `switching_values`; asked for only when no render, on either side of any pair, matches the rule, and then demanding the rule's whole condition, every class it requires, each from the settings that print it): the setting the scanner says prints it (`switchClasses`, a part's `conditionAttrs`, `dataAttrs`) is moved to each of its test values, then together, as an extra pair of renders (generated in code, never a `fixtures.json` line); the first pair whose markup the rule matches is the pair the entry is proved on. What still has this cause is printed by something no setting switches (a script, the visitor, content the fixture lacks): the browser pass |
| `part-not-rendered` | The class is printed by this block's PHP or a shared helper, but not in the renders here | Completion first (the setting that switches it on). Every render also runs with the runner's opt-in flags (`render.py::RUNNER_FIDELITY_FLAGS`): `--print-footer` (`wp_footer` listeners, such as the scrim and the detached menu chip), `--render-block-filters` (the plugin's `render_block` filters), `--wp-fidelity` (WordPress's wrapper classes and spacing styles) and `--interactivity-state` (the Interactivity state, applied to the markup by `render.py::apply_directives`). What still has this cause is content the fixture leaves off |
| `script-built-part` | The class is built by the block's front-end script, or assembled from pieces no render prints | The browser pass (`browser/prove_script_parts.py`), whose verdicts are kept in `browser/verdicts/<block>.json` with a hash of the block's front end (`check.py::script_hash`: the front-end scripts `proof.py::front_end_reachable` finds, the render, the stylesheets and block.json, plus `src/shared`; not the editor's entries, stylesheets or editor-only scripts, so an editor change stales nothing); `check.py::apply_browser_verdicts` applies them while the hash matches, so a verdict measured on older code settles nothing and the entry keeps this cause until the pass is run again. A block whose record still holds browser kinds from older code is listed by `changed.py::stale_verdicts`: the full tier fails on it and the fast tier warns, naming the pass or the rewrite that turns those entries unproven |
| `part-printed-elsewhere` | Another block or the theme prints the class (the block's CSS styles it as context) | The browser pass, on a mirror that has the theme and the other block |
| `state-not-holdable` | The rule holds in a state the proof cannot hold: `:user-invalid`, `:target`, `:visited` and the other states only a visitor or the browser sets | `filled` and a class token (`.is-detached`) are held (`proof.py::holdable`); `checked`, `disabled`, `:placeholder-shown`, `:required` and `:empty` follow the markup. What still has this cause goes to the browser pass |
| `container-query` | The rule sits under `@container` | Evaluated at the block's content width at each screen width: the page frame's content width (`theme.py::layout`: the content size, or the screen less the root padding on both sides) less the container's own padding and border (`computed.py::Page._container_px`), at the three sampled screens and at the probe widths between them (`proof.py::probe_widths`). What still has this cause tests more than the width (`style()`, height, aspect ratio) or the theme has no layout |
| `part-printed-nowhere` | (not written by the proof any more) | A class no source prints is dead CSS: its entries are `removed` and the class is listed in `deadParts` as a block fault for Task 5. The slug stays in the schema so earlier records validate |
| `other` | None of the above | Read the proof report's evidence |

A class is dead only when the scanner finds no print and no family or helper assembles its name, and every front-end PHP, JS and HTML file of the plugin and the theme holds it only inside a selector (a leading dot) or not at all (`proof.py::part_source`; the editor's code, stylesheets, build output and tests are not searched).

## Known limits

Under `--render-block-filters` the runner loads every plugin file that registers a `render_block`, `render_block_data` or `render_block_<name>` filter (`render-css-harness.php::sgs_qa_render_block_filter_files`), less those `SGS_QA_RENDER_BLOCK_FILTER_SKIPPED` names with the reason each cannot change a block's markup offline (asset delivery, the plugin bootstrap, WooCommerce or core blocks only, JSON-LD only, `pre_render_block` only); a block passes through `render_block_data`, then `render_block` and `render_block_<name>` as `WP_Block::render()` runs them, and the CSS that `wp_enqueue_scripts`, `enqueue_block_assets` and the render itself attach with `wp_add_inline_style` joins `css`. Under `--wp-fidelity` it defines the WordPress and WooCommerce functions the plugin calls that a plain render never needed (attachment URLs and files, image sizes, the queried object, global styles, `WP_Block_List`, the product attribute and term reads) and loads the plugin classes renders call by name. Named button presets reach `css` only when a fixture passes a global settings file holding them. A setting that still paints only through a route the runner does not take reads as painting nothing, which `summarise.py` lists under `noPaintButPlaced` where the scanner finds CSS written from it. The renders carry no theme CSS; the proof adds the theme's sheet (`theme.py`). Layout results (what `auto` works out to) are compared as declared values, and a container query is evaluated at the page frame's content width less the container's own padding (a container nested deeper than the block root is approximated by it).
