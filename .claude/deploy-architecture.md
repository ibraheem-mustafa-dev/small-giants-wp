# Deploy architecture

How a change gets from `main` to a live site, which file does which job, how the speed mechanisms work, and how to add to each part without breaking the others. The commands to run live in `.claude/dev-setup.md` "Deployment process" and the `/wp-sgs-deploy` skill; this page is the map behind them. Stale-prone numbers are marked with the date they were measured.

## The one rule

`python plugins/sgs-blocks/scripts/build-deploy.py` is the only deploy path. It builds, gates, ships, verifies, purges caches and rotates a `.bak`. Never hand-roll `tar`, `scp` or `rm -rf` on a server, and never use `--allow-dirty` or `--skip-verify` to get past a red result: a skipped check is a check that did not run.

## Where the time goes (measured 2026-10-17, canary, 75b80ffb3, before the speed-ups)

A canary deploy took 1333s: the fast gate tier 206s (inside `npm run build`), the full gate tier 345s, the live motion QA 735s, everything else about 47s. A deploy to a non-canary target (no live motion QA) took 631s. After the speed-ups on a clean tree: fast tier 69s and full tier 132s (4 gates at a time, longest first), and the live motion QA runs a smoke set of about 242s unless the full set is required, which gives roughly 9 to 10 minutes on the canary and 5 to 6 minutes elsewhere; a full motion QA adds about 8 minutes. Every deploy now prints these numbers itself (see Stage timings), so trust the latest `[time]` table over this paragraph. The first deploy with the new setup (2026-10-17, commit 97935b6ee, canary, blocks and theme) took 907.5s: live motion QA 655.0s (full set, because no full pass was on record yet; all 8 probes passed serially), build 117.3s (webpack plus the fast gate tier), `gate:full` 96.6s, cache purge 14.4s, upload 7.4s, stored-content audit 5.6s, packaging 4.6s, everything else under 2s each. Taking the 655s motion QA down to the smoke set's roughly 242s puts the next canary deploy at about 495s (8 minutes). The second deploy (commit 6d2ff6893, 944.3s, motion QA 668.5s) ran the full set again on purpose: two of the 78 files changed since the first deploy, `plugins/sgs-blocks/src/blocks/container/style.css` and `plugins/sgs-blocks/src/blocks/responsive-logo/style.scss`, match full-tier globs, so expect a full run whenever a container or logo block stylesheet changes, which is often while the focus and motion work continues.

## Module map

All files are in `plugins/sgs-blocks/scripts/`. One job per file; the command file stays small.

| File | Job |
|---|---|
| `build-deploy.py` | The command: flags, `main()` (the stage order), `build_and_gate()`, `step_gate_full()`. Keep it a thin sequencer; new logic goes in a module. |
| `deploy_common.py` | `TARGETS` (every deploy site), paths, run ID, tar and dirty-gate rules, `log()`, `err()`, `run()`, SSH and composer helpers. Scripts that need `TARGETS` or the SSH helpers import this. |
| `deploy_guards.py` | Checks before anything ships: scoped dirty-file gate, client `theme.json` payload and guard, ownership marker, stored-content (old-shape) audit, the isolation decision. |
| `deploy_ship.py` | `npm run build`, `step_collect()` (the payload, inside the composer `--no-dev` window), `step_ship()` (list the live tree, send nothing, a delta or the full package, apply, check the live tree again), the upload (`upload_resumable()`: sftp `put`, then `reput` from the bytes the host holds after a dropped connection, verified by remote size, up to 8 attempts; a larger leftover file is overwritten), local cleanup, and `run_isolated()` (the throwaway git worktree at `HEAD`). |
| `deploy_delta.py` | The partial upload's pure parts: `collect_payload()`, the live listing and its parser, `plan_delta()`, `write_package()`, `build_remote_apply_cmd()` (stage, check, swap with undo), `dev_autoload_leaks()`. Its own `--self-test` (case 25). |
| `deploy_verify.py` | After the files land: cache purge, `theme.json` and payload checks, the smoke test, the live motion probes (`step_motion_qa`), the scoped-selector audit. |
| `deploy_cache.py` | Remembers a commit that already built and passed `gate:full`; also the machine-wide packaging lock. |
| `deploy_multi.py` | `--target a,b` or `all`: one build and gate, then every site at once. |
| `deploy_timing.py` | Per-stage seconds, the summary table, the history file. |
| `deploy_qa_tier.py` | Chooses the motion QA tier (smoke or full) and keeps the last-full-pass record. |
| `deploy_selftest.py` | `build-deploy.py --self-test`: numbered cases, each proven red on a planted fault. |
| `run-gates.py`, `gates.json` | The gate runner and its roster (see Gate tiers). |
| `run-motion-gates.py` | Runs every motion gate it finds by filename glob (see the glob warning below). |
| `motion-qa/run-live-probes.mjs`, `probe-scheduler.mjs`, `full-tier-paths.json` | The live motion QA runner, its scheduler and the list of paths that force the full set. |

## Stage order

`main()` runs these in order; each is wrapped in `deploy_timing.timed()` or `stage()` and appears in the timing table under the name shown.

1. Isolation: `run_isolated()` creates a worktree at `HEAD` and re-runs the script from it, so a concurrent session's uncommitted files cannot reach the deploy. `--no-isolate` and `--payload` deploys run from the shared checkout instead.
2. `oldshape-audit`: reads stored post content from the target and refuses a deploy whose schemas would strand or delete it. `media-guard` (`deploy_media_guard.py`, blocks deploys only): when the build is post-cutover (a block declares media `kinds`), exports the target's saved content over SSH and refuses the deploy while the Spec 49 detector finds old media attributes; a pre-cutover build skips it.
3. `build`: `npm run build` (`prebuild` runs the generators, then `scripts/build-with-gates.mjs` runs the fast gate tier and webpack at the same time, webpack writing to a temp folder outside the repo that becomes `build/` only when both pass, so fast-gate time is inside this stage; measured 2026-11-11 at one commit: 447s one after the other, 270s side by side, identical output; the full-tier gate `assert-gate-wiring` fails if `npm run build` stops running the fast tier this way, and a killed build's temp folder is swept after a day), or a restore from the deploy cache.
4. `gate-full`: `npm run gate:full` (the full gate tier), skipped and logged as `gate-full (cached)` when this commit and framework DB already passed.
5. `deploy-ownership`, `theme-json-guard`: refuse to overwrite a newer deploy by another session (`--takeover` overrides) and ship the target client's own `theme.json`.
6. `package` (collect the payload), `live-listing`, `package-write`, `scp` (the stage keeps its name; the transfer is a resumable sftp upload, because the Hostinger link resets connections about every 1 to 2 minutes), `remote-apply`, `verify-tree`, `deploy-marker`, `local-cleanup`. With nothing to send, `package-write`, `scp`, `remote-apply` and `verify-tree` do not run. See Partial upload.
7. `purge-caches`, `verify-theme-json`, `verify`, `verify-payload`: caches purged, then the live site is fetched and the deployed `block.json` files are checksummed against the payload.
8. `motion-qa`: live probes against the canary, canary target only, and only when asked for (`--motion-qa-tier smoke|full|auto`; the default `none` runs none).
9. `first-paint`: the live first-paint gate (`scripts/check-first-paint.mjs`), only when asked for (`--first-paint`); it runs for any target with an entry in `scripts/data/first-paint.json`.
10. `page-weight`: the live page-weight gate (`scripts/check-page-weight.mjs`), when asked for (`--page-weight`) and on every release run (`--motion-qa-tier full`); it runs for any target with an entry in `scripts/data/page-weight.json`.
11. `scoped-selector-audit`: only when `--audit-scoped-page` is given.
12. The timing summary, then `[DONE] sgs-deploy completed in <N>s`. Prove a deploy by the host's marker (`ssh hd "cat ~/.sgs-deploy-marker-<target>.json"`), never by an exit code.

## Mechanisms

**Isolation.** The worktree at `HEAD` links `node_modules` and `scripts/computed-route/node_modules` from the shared checkout, and builds a real `vendor/` (`deploy_ship.vendor_shell()`: its own copy of `composer/` and `autoload.php`, each package folder linked). Before 2026-11-11 `vendor/` was one link, so the deploy's composer runs wrote the shared checkout's autoloader with a base path into the temp worktree, and that path also shipped. A stopped deploy leaks its `sgs-deploy-wt-*` worktree; remove it with `git worktree remove --force <path>`.

**Deploy cache.** After `gate:full` passes, the build and every generated file are stored in `~/.cache/sgs-deploy/<key>/`, keyed on the commit's tree hash plus the framework DB's sha256. A repeat deploy of the same commit restores them and skips both steps. Only isolated runs use it. `--no-cache` forces a rebuild. **Run the full tier once per commit with `python plugins/sgs-blocks/scripts/build-deploy.py --gate-only --blocks-only`** (any scope flag) instead of a hand-run `npm run gate:full`: it builds and runs `gate:full` in the isolated worktree at HEAD, records the pass, and stops before any target is contacted; the deploy of that commit then logs `gate:full PASSED for this commit` and runs neither. Measured 2026-11-04: first run 742s (build 417s, `gate:full` 324s, with reseeds running alongside), second run of the same commit 14s. A hand-run `npm run gate:full` in a working tree records nothing, because uncommitted edits would make the pass untrustworthy. **`ship.py` runs the whole flow below as one command** (`python plugins/sgs-blocks/scripts/ship.py --target <site>`): a reseed only when a `block.json` or a seeder changed since the last generated-files commit, then one `build-deploy.py` pass that both gates and deploys (with `ship.py --editor-check`, also the editor check on the target's `editor_mirror` from `deploy_common.TARGETS`; off by default, Bean 2026-11-11), so no separate `--gate-only` run, then `publish` (reseeded runs only) and push. **Private reseed flow.** The key hashes the DB `framework_db_path()` names, so a session that reseeds a private copy gates with `SGS_FRAMEWORK_DB=<copy>` (the isolated worktree inherits the variable, so its gates read the copy and the pass is keyed on the copy's sha256). In order: `publish-framework-db.py begin --copy <copy>`, reseed the copy, `regenerate --copy <copy> --restore-first`, commit the generated files (rebasing onto `origin/main` first if it moved: a rebase after gating changes the tree and the pass stops matching HEAD), `SGS_FRAMEWORK_DB=<copy> python plugins/sgs-blocks/scripts/build-deploy.py --gate-only --blocks-only` (with `--editor-check local-<site>` here, once), `publish --copy <copy>`, push, deploy. `publish` refuses unless the pass for (HEAD's tree, the copy's sha256) is recorded and no tracked file differs from HEAD, printing the gate command; after replacing the shared DB it copies the entry to the key for (same tree, published sha256), because the published DB is a SQLite backup of the gated copy with identical content. The deploy then logs `gate:full PASSED for this commit`, restores the build and runs neither step; pass no `--editor-check` again. The isolated worktree links `node_modules` and `vendor` from the checkout it is started in, so a worktree needs `npm ci` in `plugins/sgs-blocks` and `scripts/computed-route`, and a copy of the shared `vendor/` (PHPStan lives there), first. **Editor check.** `--editor-check local-<mirror>` (with `--gate-only` or a deploy) syncs this tree's build into that local mirror and opens the mirror's real pages, posts, templates and template parts in the block editor (`editor-crash/check-editor-loads.mjs`), aborting before anything is uploaded on a crashed block or a console error; it also checks every named import from a runtime-provided `@wordpress/*` package against the live `wp.*` global. It overwrites the mirror's plugin and theme (shared with other sessions: message them first) and takes only a `local-*` mirror. Proved on 2026-11-04 against `local-indus` (57 targets): with the per-device `flexDirection` crash of `3b47804e6` reverted, 21 pages failed with `c.indexOf is not a function`; on current code 56 of 57 targets pass. `check-wp-package-exports.mjs --check` is the build-time half for packages installed in `node_modules`.

**Partial upload.** A deploy sends only what the site lacks (`deploy_delta.py`, wired in `deploy_ship.step_ship()`).
- *What ships.* `collect_payload()` walks `theme/sgs-theme` and `plugins/sgs-blocks` in Python with `TAR_EXCLUDES` matched as tar's `--exclude` did (a pattern matches a run of whole path components), follows symlinks, leaves out empty folders and Windows device names (a stray `nul`), and puts the target's client `theme.json` at `themes/sgs-theme/theme.json` (a theme payload without it is refused). It runs inside the composer `--no-dev` window and holds every file's bytes in memory, so a fallback ships exactly the same files; `dev_autoload_leaks()` refuses a payload whose Composer autoloader still names a dev-only package (the D849 fatal). On 2026-11-11 its file list matched the old `tar` output file for file on the shared checkout (3,345 files) apart from that stray `nul`. Following symlinks fixed a fault the old tar had: Windows `tar` stored the worktree's linked `vendor/` as a link, so sandybrown, eye-care-test and eye-care-clone-test held a `vendor` pointing at a Windows path (harmless only because `sgs-blocks.php` guards the require and nothing calls the Spatie colour helpers). Only `plugins/sgs-blocks/vendor` may link outside the checkout; any other such link, or a loop, is refused.
- *What the site holds.* There is no manifest file on the server: the live tree is the manifest. One SSH call (`live_listing_cmd()`) prints the type, mode and sha256 of every node under the deployed folders, gzipped, ending with `END <count>` (1.1 s for 2,107 files on sandybrown, 2026-11-11). A listing that is missing, unreadable, cut off, inconsistent or holds a symlink or special file gives a full upload, never an empty site.
- *The plan.* `plan_delta()` returns `nothing` (the site already holds this payload: no upload, no swap), `delta` (the changed and new files plus a delete list) or `full` (no usable listing, `--full-upload`, or a difference above half the payload).
- *The package.* One gzipped tar: the files to send (stamped with the deploy time, because asset URLs carry `filemtime()` as `?ver=`) and `.sgs-delta/` holding `delete.list`, `expected.sha256` for every payload file and `expected.tree` (sorted `type mode path` of the finished tree). It goes through `upload_resumable()` unchanged.
- *The remote apply.* `build_remote_apply_cmd()` is one line of POSIX shell that ignores hangups (a dropped SSH connection cannot stop it mid-swap). In a per-run staging folder it copies the live folders (delta only), applies the delete list before extracting (so a path that changes between file and folder works), prunes empty folders, sets modes to 644/755 (five-digit `chmod` so a setgid bit cannot survive), checks every sha256 and the whole tree shape, and only then swaps each folder in with the `.bak` rotation. A failed move puts back that folder and every folder already swapped. Exit 10 means nothing was swapped; 20 means a swap failed and was undone; 30 means the files are live but the `touch`/`sgs-css` step failed. Staging folders and packages of interrupted runs older than 3 hours are swept at the start.
- *Fallback.* Only exit 10 from a delta leads to sending the full package once; any other failure stops, because a second apply would replace the `.bak`, the only rollback copy. After the swap, `verify-tree` lists the live tree again and fails the deploy with `[DEPLOYED-BUT-STALE]` (after purging the caches) if it is not the payload file for file.
- *Records.* The timing history line gains `upload_mode` and `upload_bytes` (and `upload_fallback` when the full package followed a failed delta).
- *Measured 2026-11-11.* Before: every deploy sent a 45 MB uncompressed tar (uploads of 157, 148, 179 and 599 s on the last four full Eye Care deploys in `~/.sgs-deploy-timings.jsonl`, the last with six dropped connections). After, on sandybrown: a full package of the whole 48.4 MB payload was 11.7 MB gzipped (421 s through five drops on a very poor link that morning); the same payload after a fresh build, 5 files and 176 KB in 9 s (those five were Composer autoload files, fixed since by the real `vendor/`); one changed theme CSS file, 8,952 bytes in 6 s, whole theme deploy 111 s; its revert 8,910 bytes in 5 s. On mamas-test: a full package of 11.7 MB in 84 s, then a repeat of the same commit sent nothing and the whole deploy took 86 s. The `.sgs-delta/expected.sha256` list is most of a small package (nearly all of the 8,952 bytes for the theme's 147 files; more for the plugin's 3,231).

**Multi-site.** `deploy_multi.py` builds and gates once, then starts one child deploy per site from the same worktree with `--built-by-parent`. Only the canary child runs the live motion probes.

**Gate tiers.** `gates.json` holds one record per gate: `{id, cmd, tier, tier_reason, added_D, added_commit, budget_ms, order}`; `run-gates.py::load_gates` refuses a record with no valid tier, and a `generator` record whose `cmd` contains `--check`. Tiers: `fast` (every build, run by `scripts/build-with-gates.mjs` beside webpack, after `prebuild`'s generators), `full` (pre-deploy, run by `step_gate_full()`), `generator` (never run in parallel; they must run in order and a failure must stop the build). `run-gates.py --tier fast|full|all` runs gates side by side by default (half the logical CPUs, at most 6; `--jobs N` overrides, `--jobs 1` runs them one at a time for debugging), submitted longest `budget_ms` first, with results printed in roster order and every gate always run; the npm scripts and `build-with-gates.mjs` pass no `--jobs`, so a hand run and the build use the same count. On 2026-11-04 a full-tier run on one tree took 720s at 1, 242s at 4 and 151s at 6 at once with identical verdicts. `--assert-wired` proves the deploy still calls the full tier. `--time` measures every gate serially and rewrites `budget_ms`; rerun it when gates are added, because the schedule is only as good as the budgets. Serial and parallel runs were compared on one clean tree on 2026-10-17 and returned identical verdicts.

**Motion gates are discovered by filename.** `run-motion-gates.py` runs every `check-motion-*.py` (with `--check` and `--self-test`), `migrate-motion-*.py` (`--check`) and `migrate-easing-*.js` in the scripts folder, and it is part of the full tier. A new script with one of those names becomes a live gate the moment it is committed. If it must stay red until a sweep, baseline it in `scripts/data/motion-gate-allowlist.json` in the same commit (entries `{gate, pattern, reason, delete_in_unit}`; an entry fails once its unit is recorded in `motion-units-landed.json`). Run `python plugins/sgs-blocks/scripts/run-motion-gates.py` before committing such a script. (On 2026-10-17 `check-motion-literals.py` skipped this and failed `gate:full` for two hours.)

**Live motion QA tiers.** `npm run qa:motion` runs the probes in `run-live-probes.mjs` against the canary after the deploy. Each probe lists the tiers that run it. Smoke is every probe except the four full-only ones (`probe-marquee.mjs`, `probe-looping-media.mjs`, `probe-motion-per-device.mjs` and `probe-motion-a11y.mjs`): 15 of 19 probes, about 350s; the full set is about 950s serial, and marquee and looping-media are 494s of it. The step runs only when asked for: `--motion-qa-tier none` (the default since Spec 38A closed, `deploy_qa_tier.py::motion_qa_action`) runs no probes; `--motion-qa-tier auto` picks full when there is no recorded full pass, the record is over 24 hours old (`max_age_hours` in `full-tier-paths.json`), the recorded commit is unreachable, or any file changed since that commit (including uncommitted files the run ships) matches a glob in `full-tier-paths.json`; otherwise smoke. The record is `~/.sgs-motion-qa-full.json` (override with `SGS_MOTION_QA_FULL_FILE`), written only after a full run passes on committed code with the verify step run. `--motion-qa-tier smoke|full` names the set; `--skip-motion-qa` also skips the step. Run `--motion-qa-tier full` (or `npm run qa:motion` by hand) before any release that touches motion, shared effects or the theme tokens. `--motion-qa-parallel N` and `run-live-probes.mjs --parallel N` exist but must stay at 1 on the Hostinger canary: four at a time on 2026-10-17 made two probes fail on non-200 responses and the CDN then answered 403 to every request for about seven minutes. Probes take turns on the canary by message with other sessions for the same reason (`.claude/rules/motion-qa.md`).

**Live first-paint gate.** `node scripts/check-first-paint.mjs --site <target> [--check] [--update-baseline] [--json out] [--only cls,css,look,name]` measures a live site at 375, 768 and 1440 and `deploy_verify.py::step_first_paint` runs it after the upload (opt-in, `--first-paint`), because a pre-deploy tier would measure the old live code. CLS is the larger of the median of 3 unthrottled loads and one throttled load (CPU 4x, 150ms latency, 1.6 Mbps), scoring the largest session window; a page fails above max(`cls.limit`, its baseline + `cls.tolerance`). The late-CSS check reads the raw delivered HTML and fails on a stylesheet or `<style>` after `</head>` and on any `onload` swap, unless `lateCssAllowlist` names the page and handle with a reason. The stylesheet-name check fetches each page twice and fails when the collected file name differs. The JS-off look check only reports. Pages, baselines and the allowlist live in `scripts/data/first-paint.json`; `--update-baseline` only lowers baselines. `--selftest` runs the offline cases for the window, late-CSS and file-name logic.

**Live page-weight gate.** `node scripts/check-page-weight.mjs --site <target> [--check] [--update-baseline] [--json out] [--pages /,/shop/] [--runs 3]` loads each page cold at 1440 px (scrolling once to the bottom so lazy files count), sums the transferred (compressed) bytes of the site's own CSS and JS responses (own = the origin the page finally loaded from, plus any `assetOrigins` the site lists, such as a CDN host), and takes the median of 3 loads. A page answering 400 or above stops the run with exit code 2, so an error page is never measured or baselined. Third-party files (a payment provider's form, a captcha) are reported in their own column and never judged, because SGS cannot shrink them. The budget is the project's < 100 KB CSS and < 50 KB JS per page. A page over budget fails only above its baseline + `toleranceKb`, so known debt stays green while any regression fails; once a page is under budget, going over fails. `deploy_verify.py::step_page_weight` runs it after the upload, for any scope including theme-only (`--page-weight`, and always with `--motion-qa-tier full`), because a pre-deploy tier would measure the old live code. Pages, budgets and baselines (bytes, dated) live in `scripts/data/page-weight.json`; `--update-baseline` only lowers them, and only at the data file's width and 3 runs; a deliberate rise (a feature that must cost bytes) is set by hand with a `raised` line giving the reason. `--selftest` runs the offline cases for classification, summing and the ratchet; `build-deploy.py --self-test` case 24 covers the wiring.

**Stage timings.** Each stage prints `[time] <name> <seconds>s`; a slowest-first table with percentages precedes `[DONE]`; each real deploy appends one JSON line (`when`, `commit`, `target`, `scope`, `total_s`, `stages`, `dry_run`) to `~/.sgs-deploy-timings.jsonl` (override with `SGS_DEPLOY_TIMINGS_FILE`). The fast gate tier is inside `build`. A multi-site run writes one line from the parent and one per child. The live probe runner prints each probe's seconds and a closing table.

**Guards.** The scoped dirty-file gate (refuses uncommitted deploy-relevant files unless declared with `--payload`), the ownership check, the `theme.json` guard, the old-shape audit, the 55 MB payload size guard (the log's last line then says only `payload-failed (exit 2)`), the dev-autoloader refusal, the staged-tree check and `verify-tree`, and the post-deploy verify. Each has a case in `--self-test`.

## How to add to it

- **Before optimising anything,** read the latest `[time]` table in the deploy log or the last lines of `~/.sgs-deploy-timings.jsonl`; the self-test cases for the timing, motion QA flags and tier choice are 19, 20 and 21 in `deploy_selftest.py`, the partial upload 25 (`deploy_delta.self_test`) and 26 (`step_ship` end to end).
- **The partial upload.** A new kind of file in the payload needs nothing: the listing and the checks cover every file. A change to the remote apply goes in `deploy_delta.stage_steps()` or `build_remote_apply_cmd()`, keeps it one line of POSIX shell, keeps the check before the first `mv`, and adds a case to `deploy_delta.self_test()` whose planted fault is the old command.
- **A deploy stage.** Write a `step_*` function in the module that matches its job (`deploy_guards` before shipping, `deploy_ship` for shipping, `deploy_verify` after), return `0` or a non-zero exit code, call it from `build-deploy.py::main()` through `timed("<stage-name>", step_fn, ...)`, and add a `--self-test` case with a planted fault. Keep `build-deploy.py` under about 500 lines by putting logic in the module.
- **A flag.** Add it in `build-deploy.py::parse_args`, thread it to the step, and give it a self-test case that proves the default leaves the old behaviour byte-identical.
- **A deploy target.** Add an entry to `TARGETS` in `deploy_common.py` (`host`, `wp_content`, `explicit_opt_in_required`, `client`), create its secrets file under `.claude/secrets/`, make sure `sites/<client>/theme-snapshot.json` exists (or name the target's own file in an optional `snapshot` key, as eye-care-test does, when two sites of one client need different theme.json files; `deploy_common.target_snapshot_rel`), and run `--self-test` (case 13b proves a target's own snapshot wins, case 16 that every target's snapshot prepares). SSH is shared: every target lives on one Hostinger account behind the `hd` alias (`SSH_ALIAS` in `deploy_common.py`), so a site on a different account needs the SSH helpers extended first. The live motion probes stay canary-only.
- **A gate.** Add a record to `gates.json` (`tier` `fast` unless it is slow or needs a build, then `full`), run `python plugins/sgs-blocks/scripts/run-gates.py --only <id>`, then `--time` to set its budget. A gate that writes files must write only to temp folders or have exactly one writer, because gates run side by side. A new `check-motion-*.py` also needs the glob check above. A gate command is one program and its arguments: the runner refuses `&&`, `||` and `;` (it runs without a shell, so a joined second command would silently never run); give each step its own record. After a failed tier run, `run-gates.py --only-failed` re-runs just the gates that failed (recorded in the repo's shared `.git/sgs-run-gates-last.json`, so a deploy's temporary worktree records it too) to check a fix in minutes; it is diagnostic only, and the release still needs the full run.
- **A motion probe.** Put it in `scripts/motion-qa/`, give it a stable fixture page (add the page ID to `.claude/rules/motion-qa.md` and `CLAUDE.md`'s fixture list) and a negative control that must come out red, add it to `REAL_PROBES` in `run-live-probes.mjs` (`PROBES` is derived from it) with its `tiers` (both `smoke` and `full` unless it is slow and narrow) and `serial: true` if its timing tolerance is tight, since a serial probe never runs alongside another in parallel mode (the two full-only probes set it), and if it tests code that smoke would not otherwise exercise add that code's paths to `full-tier-paths.json`. Time it in a serial run first; a probe over about a minute belongs in the full tier only. To test the runner without the canary, point `SGS_MOTION_QA_PROBES_JSON` at a JSON file of stub probes (`node plugins/sgs-blocks/scripts/motion-qa/run-live-probes.selftest.mjs` does this); never leave it set during a real deploy.

## Known limits and next speed-ups (2026-10-17)

- The live motion QA is opt-in (Bean ruled 2026-10-17, built when Spec 38A milestone M6.7 closed): motion no longer changes from deploy to deploy, so a routine deploy skips it; a release that touches motion, shared effects or the theme tokens runs the full set first.
- The marquee probe is 367s, mostly fixed waits (a 2s settle after each of about 32 page opens, repeated re-measurement in its reduced-motion pass and 1s measurement windows). Trimming those while keeping the 2% rate judge could save about 100s on full runs; it needs a live canary to verify and a negative-control check, so it is not done yet.
- `run-motion-gates.py --jobs N` runs its 42 script runs N at a time (identical verdicts; 234s serial against 92s wall clock six at a time, timed by hand on 2026-11-11). The default stays 1: inside `gate:full`, which already runs six gates at once, four at a time pushed `check-motion-entrance-cascade.py --self-test` past its 600s timeout on a loaded machine. The tier's wall clock is set by `check-dead-api-calls` in any case (619s in the sandybrown trial-2 run, 1,187s in the run that timed out).
- The editor check (`--editor-check`, about 15 minutes for 50 targets on local-mamas under load, 2026-11-11) is opt-in on `ship.py` as on `build-deploy.py`; `ship.py` ran it on every ship from 2026-11-10 to 2026-11-11. Two speed-ups are built and parked, not shipped: opening only the targets that draw a changed block, and running the check beside `gate:full` (`.claude/plans/2026-11-11-deploy-speed.md`). Opening three editors at once was measured and left off by default: about 10% faster than serial (13m11s against 14m39s for 50 targets on local-mamas) but the mirror dropped two of the requests, which leaves targets unanswered.
- A gate result is not cached per input hash: `check-render-undefined-vars` and `check-dead-api-calls` read whole-tree inputs that are not declared, so a stale pass would be worse than the time saved.
- The oldshape audit (a read of every stored post over SSH) has no timing of its own until it appears in the first `[time]` table.
