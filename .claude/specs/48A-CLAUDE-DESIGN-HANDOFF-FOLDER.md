# Spec 48A: the Claude Design handoff folder

A client design drafted in Claude Design reaches Claude Code as one folder of known files. This spec fixes what that folder holds, how it is checked, where it lives and which tool reads each file. Spec 48 (the cloning system) is written around it. Draft status: version 1.0 waits for plan task B0 (the artifact-based Claude Design tested once, every standalone project downloaded before 14 December 2026).

Evidence: `.claude/plans/archive/2026-10-10-claude-design-handover-standard.md` (Task A table, B1 comparison of the Indus, Eye Care and Mama's Munches exports) and `.claude/reports/2026-10-11-48a-council/` (`DESIGN.md`, the adversarial council's `REPORT.md`, Bean's decisions of 2026-10-11).

## 1. How a draft works (the facts this spec rests on)

- A `.dc.html` draft is a template inside `<x-dc>` (inline styles, `style-hover`/`style-focus` attributes compiled to `!important` pseudo rules, `{{ }}` holes, `sc-if`, `sc-for`, `dc-import` mounting a sibling draft) plus a logic class (`class Component extends DCLogic`). The runtime `support.js` compiles and renders it with React 18.3.1, ReactDOM and `@babel/standalone` 7.29.0 loaded from unpkg with SRI. It has no version string: its SHA-256 is its version.
- The runtime stamps every template element `data-dc-tpl="N"` in pre-order and exposes `__dcAnnotatedTemplate(name)`; its `encodeCase` encoder numbers a template without rendering (`handoff-schema/METHOD.md` §2).
- Routing, motion technique, form placement and project scripts are each designer's choice: hash routes with a `pages` getter, `state.page` with `go()`, or one file per page with plain links; Web Animations, CSS only or mixed.
- The draft's code is the primary source. Rendering and measuring supplement it only for what code cannot state (final `clamp()`/`vw` values at a width, grid tracks, font metrics, image-slot shadow DOM).

## 2. Requirements

### FR-48A-1 -- Placement
A client's export lives at `sites/<client>/handoff/`, copied byte for byte from the downloaded folder. Once there, the folder is the draft's canonical home (Bean, 2026-11-01): a defect inherited from the draft is fixed in this folder, never in the clone's output, and the edit keeps every file consistent as if Claude Design had exported it (the page, `surfaces.json` and `animations.json` records, `README.md`, and `MANIFEST.json`'s sizes and SHA-256 recomputed), and the folder still passes `handoff-check`. A new export replaces the whole folder. Our own work stays outside it (`build/`, `theme-snapshot.json`, the divergence ledger), so `handoff/surfaces.json` (Claude Design's state inventory) and `build/surfaces.json` (our map of surfaces to WordPress posts) can never be confused by path. One exception: an export made before `MANIFEST.json` existed (one carrying `MANIFEST.md`) may be brought to the current format by `scripts/computed-route/handoff-repackage.mjs`, which first proves every file still matches the size and SHA-256 its `MANIFEST.md` recorded (and stops on any mismatch), then removes `MANIFEST.md` and `handoff-schema/trace/`, copies the master schema files the folder lacks, and writes `MANIFEST.json`. No byte Claude Design produced changes.

Edited in the folder: Mama's Contact page's "quick answers" became an FAQ accordion copied from the Help page's FAQ (2026-11-01, `surfaces.json` S-59; Bean's ruling: the links sent people away from the contact form). Status: the Indus and Mama's exports sit in `sites/indus-foods/handoff/` and `sites/mamas-munches-redesign/handoff/`, repackaged 2026-10-11 and passing the check. Eye Care's sits in `sites/eye-care-ward-end/handoff/`, repackaged the same day; it passes `handoff-check` (`node scripts/computed-route/handoff-check.mjs sites/eye-care-ward-end/handoff`). Its `surfaces.json` record S-38 still names the removed `WP Build Gap Map` draft, which intake reports as surface-root gap rows.

### FR-48A-2 -- Required files
`MANIFEST.json`, `README.md`, at least one draft `.dc.html`, `support.js`, `tokens/colors.css`, `tokens/typography.css`, `tokens/spacing.css`, `animations.json`, `surfaces.json`, `READING-DC-FILES.md`, `handoff-schema/METHOD.md`, `handoff-schema/animations.schema.json`, `handoff-schema/surfaces.schema.json`, `handoff-schema/manifest.schema.json`, `handoff-schema/READING-DC-FILES.example.md`, `handoff-schema/README.template.md`. A missing required file fails the check and is named.

Status: checked by `scripts/computed-route/handoff-check.mjs`.

### FR-48A-3 -- Allowed files and reachability
Besides the required files, a folder may hold only: files under `assets/`, further token stylesheets directly inside `tokens/` (`tokens/motion.css`: a draft carries as many token files as its design has, FR-48A-17), and project scripts (`.js`) a reachable draft loads. Every other file fails the check and is named, with the instruction to remove it (e.g. a planning document saved as a draft, an earlier page version, skill folders, notes, a trace harness).
- Entry drafts are the paths listed in `MANIFEST.json` `entry_drafts`.
- A draft is reachable when it is an entry draft, or a reachable draft names it through `<dc-import name="X">` (resolved to `X.dc.html`, exact and case-sensitive, spaces allowed) or links to it through an `href` or `src` value ending in `.dc.html` (query string and fragment removed, URL-decoded, a leading `./` removed). Plain links count, so one file per page (Mama's Munches) passes.
- A project script is reachable when a reachable draft loads it through `<script src>` or `x-import from=`, resolved the same way.
- Every `.dc.html` in the folder must be reachable; an unreachable one fails the check. Links are read from attribute values only, so a page reached only through a path built in script fails loudly and is listed in `entry_drafts`. Status: checked by `handoff-check.mjs` (`lib/handoff.mjs::isTokenFile` for the token stylesheets; `tests/handoff-check.test.mjs`, `tests/handoff-token-files.mutations.json` 4 of 4 killed).

### FR-48A-4 -- The manifest
Claude Design writes `MANIFEST.json` last, valid against `handoff-schema/manifest.schema.json`: `schema_version`, `generated` (date), `project`, `entry_drafts`, `runtime_sha256` (of `support.js`) and `files`, one `{ path, bytes, sha256 }` per file in the folder except `MANIFEST.json` itself. Paths are relative to the folder root, POSIX separators, NFC, case-sensitive, with no `./`, `..`, leading slash or backslash; directories are not listed. The check passes only when the listed paths equal the files on disk in both directions, every size and hash matches, and `runtime_sha256` matches `support.js`. A design change after export means pasting the handoff prompt again and downloading the whole folder; files are never moved in or out by hand.

Status: checked by `handoff-check.mjs`; the prompt asks for it from 2026-10-11. The three current exports (Indus, Mama's, Eye Care), made before that, were repackaged (FR-48A-1).

### FR-48A-5 -- Runtime versions
`scripts/computed-route/data/known-runtimes.json` lists every accepted `support.js` build by SHA-256, with the date it was added and the probe result. An unknown hash stops the check. `handoff-check.mjs --probe-runtime` then renders the checked-in fixture draft `scripts/computed-route/data/runtime-probe.dc.html` with the new build, requires the `data-dc-tpl` numbering read from the rendered page and from `__dcAnnotatedTemplate` to equal the fixture's recorded numbering exactly, and prints the module-by-module difference from the nearest known build. `--add-runtime` records a build only after the probe passes, and says so in one line. A recorded build is never patched locally, because its hash is its identity in every `MANIFEST.json`. Two bugs in build `c60c49083997` are accepted for that reason: `encodeCamelAttrs` also rewrites a camelCase word followed by `=` in visible text (`<p>set myVar = 3</p>` becomes `sc-camel-my-var = 3`), and a bare `on` attribute (`<div on="1">`) throws a `TypeError` in `collectProps`. Both need unusual draft input; a draft whose copy or markup contains either is reported to Claude Design to fix in a new build.

Status: checked by `handoff-check.mjs`; two builds recorded (`c60c4908…` from Indus, `8fe7df74…` from Eye Care and Mama's Munches).

### FR-48A-6 -- Schemas are ours
The master schemas, method and templates live in `.claude/claude-design-handoff/handoff-schema/`, uploaded to every Claude Design project. The check validates `animations.json`, `surfaces.json` and `MANIFEST.json` against the master copies, never the folder's copy; a folder copy that differs from the master is a warning naming the file and the lines only the export or only the master holds. A folder may also carry the project's own `CLAUDE.md`; when it differs from the master `.claude/claude-design-handoff/CLAUDE.md` the check warns the same way, so an export made from older or edited instructions is named.

Status: checked by `handoff-check.mjs` (`lib/handoff.mjs::checkHandoff`, the line comparison (in git history since the 2026-11-02 route rewind, `8c48dec56`; not in the running route)).

### FR-48A-7 -- Inventories are current
`animations.json` and `surfaces.json` validate against the master schemas, and every draft hash and the `runtime_sha256` recorded in `animations.json` match the files, so an inventory written before a design change is refused. The target, set by Bean's decision (e) of 2026-10-11, is that intake re-derives the inventory from the code by `METHOD.md` and Claude Design's copy is only a cross-check; until Spec 48 step 14b (FR-48-25) lands, Claude Design's inventories are used, cross-checked by `scripts/computed-route/trace-check.mjs` on a single-file draft's entry page (every Web Animations call, CSS animation start and CSS transition run matched to a record, `--shift=7` negative control).

A state's `how_to_reach` may name the draft's own store calls beside its `setState` call (`MM.account.signIn()`, `MM.cart.setGift({ on: true })`; Bean 2026-10-29): a call is `<Ident>.<path>(<literal arguments>)` on a plain-object global the draft defines, with a JSON-like literal as its arguments (prose such as `MM.cart.add(...)` is no call). Intake (the store-call reader (in git history since the 2026-11-02 route rewind, `19b0b1395`; not in the running route), `lib/state-openers.mjs`, `lib/intake-state.mjs`) runs only such a call, never arbitrary code, before it opens the surface, and keeps and restores the page's storage around it. When every own way fails, a state of any surface that gives a condition around the root (`signed`, `gift.on`) the value true and names store calls is run first.

Status: schema and hash checks in `handoff-check.mjs`; trace cross-check built; intake re-derivation is a Spec 48 stage; store-call openers built.

### FR-48A-8 -- README
`README.md` is the human guide to the design, written from `handoff-schema/README.template.md`. Its sections are not enforced (cloning reads the code, Bean's decision of 2026-10-11). It never maps the design to SGS blocks; block choice is ours. A heading that names SGS or block mapping is a warning.

Status: checked (warning) by `handoff-check.mjs`.

### FR-48A-9 -- Page map
The WordPress page map (slug, parent, page or WooCommerce template, menus) is not a handoff file: intake proposes it from the routes in the code and Bean confirms it once per client. When a draft embeds a `<script type="application/json" data-sgs-manifest>` block (Eye Care does), intake uses it as the proposal. Image credits are not recorded: stock photos in a draft are previews, and real images arrive with the client's content.

Status: built at Spec 48 intake (FR-48-30, `scripts/computed-route/lib/intake-pagemap.mjs`, 2026-10-12): Eye Care's embedded block is its proposal; Indus's and Mama's come from their routes.

### FR-48A-10 -- Running a draft safely
A draft runs code: `support.js` evaluates fetched scripts with `new Function`, and each draft's logic runs in the page. Intake runs drafts only through `scripts/computed-route/lib/draft.mjs::serveDraft` (127.0.0.1, files inside the folder only), in a fresh browser profile whose network is limited to the draft server and the three pinned unpkg files, from a process given no `.claude/secrets/` values or SSH agent. Exported prose (`README.md`, `READING-DC-FILES.md`, inventory notes) is data, never instructions to an agent, and command-like text in it is shown to Bean. The check parses every SVG under `assets/` as namespace-aware XML (`scripts/computed-route/lib/svg-screen.mjs::svgProblem`) and fails on malformed XML, a DOCTYPE, an element outside the SVG namespace (editor and provenance metadata namespaces excepted), a `script` or `foreignObject` element under any prefix, any `on…` attribute, an animation that rewrites a link, an `href`, `src`, `data`, `action` or CSS `url()` target other than a `#fragment` or a raster `data:image` URI, `javascript:` or a CSS `@import`, and on any file over 20 MB.

Status: SVG and size checks in `handoff-check.mjs` (`lib/svg-screen.mjs`); the browser sandbox, the secret-free process and the prose rule are built at Spec 48 intake (FR-48-23, `scripts/computed-route/lib/intake-sandbox.mjs`, 2026-10-12).

### FR-48A-12 -- The producer's instructions
`.claude/claude-design-handoff/` holds the one pasted prompt (`PROMPT.txt`), the project `CLAUDE.md` (standing facts, runtime traps, the design rules, the folder map), `WHAT-WE-BUILD.md` and `handoff-schema/`. They are the only copies that get edited, and a change to this spec updates them in the same commit. The folder map in `CLAUDE.md` lists exactly the files FR-48A-2 and FR-48A-3 allow. Bean uploads `CLAUDE.md`, `WHAT-WE-BUILD.md` and `handoff-schema/` to each Claude Design project and pastes `PROMPT.txt` at handoff.

`WHAT-WE-BUILD.md` is the list of what the framework already has, in design words (Bean, 2026-11-18: no Components page, no block map and no section-level block choice; a list of what we have, yes). Claude Design styles anything on it freely and asks before drawing something that works differently from everything on it. It names no block and no setting (FR-48A-8), and it is never part of a handoff folder. It is generated: `python plugins/sgs-blocks/scripts/generate-handoff-block-list.py` joins the framework database (which blocks are built, which options each has) with the wording file `plugins/sgs-blocks/scripts/data/handoff-block-list.words.json` (how a designer would name each thing and option), and refuses to write when a built block has no entry, an entry names a block, option or value the database lacks, an option value has no wording, or a block or setting name leaks into the text; `--check` exits 1 when the file is out of date.

Status: done 2026-10-11; `WHAT-WE-BUILD.md` and its generator added 2026-11-19 (59 entries covering every built block). Not wired: `--check` as a gate after a reseed.

### FR-48A-13 -- Structured reach, typed keys, one threshold form, stable part ids
All of these are optional, so an earlier export still validates. The handoff never names an SGS block: block choice is made at cloning.
- `data-part="<id>"` on a meaningful element is a stable name for what the element is in the design (`hero-cta`, `filter-rail`). It is identity only and is kept unchanged between exports. The producer's `CLAUDE.md` asks for it on every section, drawer, menu, form and call to action (2026-11-19); an export without it still validates.
- A `surfaces.json` state may carry `how_to_reach_structured` beside the `how_to_reach` prose: `{ setState: { ... }, storeCalls: [ { path, args } ], event: { type, target } }` (`.claude/claude-design-handoff/handoff-schema/surfaces.schema.json::$defs.state`). `target` is a `data-part` id or a `data-dc-tpl` index.
- A state may carry `state_key_sources`, mapping each `state_keys` key to `state`, `derived` or `instance`.
- A state that depends on a width carries `breakpoint`: `{ basis: "state.w", op, value }`.
- `handoff-schema/METHOD.md` reads the logic at 375, 768 and 1440.

Status: schema, method, prompt and `CLAUDE.md` updated 2026-10-29. The route reads `setState` and `storeCalls` before the prose (the reach-call reader (in git history since the 2026-11-02 route rewind, `6fb7356c8`; not in the running route), used by `lib/state-openers.mjs::stateWays`, the store-call reader (in git history since the 2026-11-02 route rewind, `19b0b1395`; not in the running route) and `lib/intake-pagemap-flow-openers.mjs::openingWrites`) and `breakpoint` before the prose threshold (`lib/skeleton-child-slots.mjs::collapsePoint`). `event`, `state_key_sources` and `data-part` are recorded for the reader and not yet consumed by the route. No export made after the update exists yet.

### FR-48A-14 -- What the clone reads from text and widgets
- Inline formatting inside a text element is kept: bold (`strong`, `b`), italic (`em`, `i`), strikethrough (`s`, `del`), links (`a`) and line breaks (`br`) land in the matching block setting as rich text. Write them as ordinary phrasing content inside the element; do not flatten them to plain text or split a sentence across elements to fake them.
- Lists, tabs, accordions and breadcrumbs are read by their meaning (ARIA roles, states and behaviour such as `role="tablist"`, `aria-expanded`, `<nav aria-label>` with an ordered list), not by tag names or class names. Give each widget its correct ARIA role and state attributes; a class called `tabs` on a plain `div` is not a tab set.
- These rules stand in the producer's `CLAUDE.md` as design rules, so they apply while a draft is designed and not only at handoff (2026-11-19: no export so far carries `aria-controls` or `aria-modal`). The widget rows there: an accordion header is a `button` with `aria-expanded` and `aria-controls`; a slider is a container with `aria-roledescription="carousel"`, slides with `aria-roledescription="slide"`, `button` arrows and dots with `aria-current`; a drawer, modal or covering panel is `role="dialog"` with `aria-modal`, opened by a button with `aria-expanded` and `aria-controls`; a drop-down menu's trigger is a `button` with `aria-expanded`; chips are buttons with `aria-pressed`. The route recognises a widget by what its code does and reads these as the cross-check (Spec 48 FR-48-6).
- Per-pattern block tags in a draft (`data-sgs-block`) are not used. The draft's natural names (`data-part` ids, class names, headings) serve as guidance only; tags may come later (Bean, 2026-10-30).

### FR-48A-15 -- Focus tokens
- A handoff declares three tokens in its `tokens/*.css` (by convention `tokens/spacing.css`): `--focus-color` (the ring colour), `--focus-width` (the ring thickness) and `--focus-offset` (the gap between the ring and the element). The draft draws focus once, for the whole site, from them, and never per element.
- They map to the client snapshot's `settings.custom.focus` keys: `--focus-color` to `focus.ring`, `--focus-width` to `focus.width`, `--focus-offset` to `focus.offset`. Input boxes take the framework's inset look automatically (Spec 32 §14.5), so a draft gives them no focus rule.
- `checkHandoff` warns, never fails, for each token no `tokens/*.css` declares: `FR-48A-15 tokens/*.css: focus token <name> is not declared`.
- Status: the reader is built (`lib/handoff.mjs::checkHandoff`). The step that writes the snapshot's focus values from these tokens is not built: the values are copied by hand when a client is set up.

It also lists what a WooCommerce shop does and does not do, so a draft promises nothing the shop cannot deliver (Mama's Munches' draft showed an address book, tracking links and a bake date, and had no page-not-found, search or account sub-view designs; each cost a ruling or a hand-built page, `.claude/reports/2026-11-18-template-rework/inventory.md`).
- At handoff the prompt compares the drafts with that list and reports each missing page or state, and each feature a shop does not do, as an unresolved item; it draws nothing new.

Not built: `handoff-check.mjs` warning on a missing surface (the three existing exports predate this and would only warn; it belongs to the general cloning work, which owns `handoff-check.mjs`), and the route composing a surface the draft lacks from the site's own designed parts (`.claude/plans/2026-11-18-template-rework.md`, Task 7).

### FR-48A-17 -- Tokens used by name; buttons and fields built once, with presets
Bean's rulings of 2026-11-18 and 2026-11-19, written into the producer's `CLAUDE.md`.
- **Tokens.** `tokens/` holds every value the design reuses, under the project's own names and as many as the design has (colours, type, spacing, radii, borders, shadows, easings, durations and any other family); `colors.css`, `typography.css` and `spacing.css` always exist and further files are allowed (FR-48A-3). Every draft loads the token files in its `<helmet>` and uses a token by name (`var(--ink)`) in inline styles, `style-*` rules and the values its logic picks per width, so each use can be traced to its token. A value used once or twice stays a literal; a value used three times or more is a token.
- **Buttons and form fields.** The buttons and form fields a design repeats are each one component file (`Button.dc.html`), mounted through `<dc-import>`, whose presets are named versions in `data-props` (an enum prop `version`, and `size` where the design has sizes). A button mounted with a preset is cloned as that preset. A button meant to look different is drawn where it stands with its own styles and is cloned with its own styles (Bean, 2026-11-19: "you just apply the preset if it's named the preset or you just don't and the cloning pipeline sets the styles the normal way"). The rule guards only against a preset re-drawn by hand with slightly different numbers (Eye Care's black button comes in 8 sizes; Mama's primary yellow in about 12).
- **No new producer file.** The families are read from the mounts (`scripts/computed-route/lib/intake-props.mjs::declaredProps` reads each component's enum options and each mount's values, Spec 48 FR-48-29) and the tokens from the token files, so intake derives both and Claude Design writes no component inventory.
- Proved in the runtime (2026-11-19, build `8fe7df74`): a draft that links `tokens/colors.css` in `<helmet>` computes `var(--token)` in an inline style and in a `style-hover` rule; one `Button.dc.html` with `version` and `size` enums renders a link when given `href` and a button with children when given a handler, and each mount carries its prop values in the annotated template. A mount's wrapper is a block-level element, so a button sits in a flex or grid parent, never inside a line of text.
- Found by converting a private copy of Mama's Munches to these rules (2026-11-19; Contact, Home and Help render identically before and after), and written into the producer's `CLAUDE.md`: a token is used by name where its job is meant, never where a value only happens to equal it; a preset holds rest, hover, pressed and its transition, a disabled look only where the design has one, and never its own keyboard focus; `align-self`, `margin` and `flex` on a mount never reach its wrapper; an attribute on a mount (`data-part`) arrives as a prop (`dataPart`) the component must put on its root; a `style-*` rule cannot hold a `{{ }}` value, so presets that differ there are one element each; a panel drawn only while open keeps `aria-controls` naming the `id` it carries when drawn; a row that only scrolls sideways on a phone is not a carousel.
- Found by cloning that converted copy (2026-11-19: Contact and Help clone as well as from the original, 25 of 30 and 42 of 54 text leaves on both), and written into the producer's `CLAUDE.md`: a token holds one value of one kind, since a whole shorthand in one token (`--outline: 2px solid #3A2A22`) hides its width, style and colour from every reader of declared values; and a component's root is the button or field itself or a box exactly its size, since a wider wrapper becomes an extra container on the site (`scripts/computed-route/lib/skeleton-rules.mjs` rule `mountWrapper` unwraps only a wrapper the size of its one control).

Status: instructions written 2026-11-19 (version 1.4). No export made under them exists yet; a private copy of Mama's Munches converted by hand is the trial input (git branch `feature/mamas-handoff-trial`, never merged). Built 2026-11-19 for the new shape: a mount's constant attributes, a component mounted inside a parent's form, and the wrappers a mounted button or field adds (Spec 48 FR-48-29, FR-48-6 `mountWrapper`). A declared value written as `var(--token)` is read as its value by every reader of a draft's declared styles, through one function (`scripts/parity/lib/css-vars.mjs::resolveVars`; nested tokens and fallbacks followed, a missing token or a cycle left as written) and two lookups: the draft's own token files and `:root` rules (`scripts/computed-route/lib/draft-tokens.mjs::draftTokenLookup`, for the standing rules' `declared`, the skeleton content pass and the template reader `lib/read-template.mjs::staticLists`) and the custom properties the browser computed for the element (`scripts/parity/lib/devtools.mjs::withTokens`, for Fill's draft reads, which also expands a shorthand written with a token into its longhands, so `resolve.mjs::declaredUnit` reads units again); a read of a built page keeps its declarations as written. ### FR-48A-18 -- Tidying a draft during a handoff
One rule replaces the earlier conflict between "never change a draft" (`CLAUDE.md`, `METHOD.md` §10) and "fix any draft that breaks these" (`PROMPT.txt`). While preparing a handoff Claude Design uses its own judgement to make the drafts follow the design rules (a raw value that is plainly a token, a hand-drawn button that is plainly a preset, a fake list, a missing role, state or `data-part`), says what it changed in its final reply, and asks only where a change would alter the design Bean approved or it cannot tell which of two things was meant (Bean, 2026-11-19: the rule trusts the model's judgement and lists no cases). Bugs and missing pages or states are still listed as unresolved (FR-48A-16). Its final reply also names any hand-drawn button or field that looks the same as a preset and that it left alone.
