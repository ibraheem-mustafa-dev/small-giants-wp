# SGS Button Architecture

> **Styling model: read [Spec 32](32-COMPONENT-STYLING-TOKEN-CONTRACT.md).** A button paints through a semantic BEM variant class plus custom properties fed by per-client tokens. This spec holds the two-block pair, the composition pattern and the button-specific rulings. The attribute surface is `plugins/sgs-blocks/src/blocks/button/block.json` and the framework DB (`/wp-blocks schema sgs/button`, `python ~/.claude/skills/sgs-wp-engine/scripts/sgs-db.py block sgs/button`); never copy it into a doc.

**Implements:** `sgs/button` (the canonical button block) and `sgs/multi-button` (its container).

**Replaces:** every use of `core/button` inside SGS blocks, and the hand-coded CTA rendering that composite blocks (`sgs/hero`, `sgs/feature-grid`) once carried.

---

## 1. Purpose

One canonical button block and one flexible container replace every CTA implementation in the framework. The pair gives:

- **A full attribute surface** (content, per-device typography, padding and width, hover and focus states, icon, shadow, transition) matching or exceeding Spectra and Kadence. Read it from `block.json`.
- **Variant binding.** The site owner sets primary, secondary and outline styling once (as per-client tokens) and every button using that variant follows.
- **WordPress-native composition.** Composite blocks accept buttons through InnerBlocks rather than rendering CTAs internally, so button rendering has one source of truth.

## 2. Why not extend `core/button`

`core/button` has no per-breakpoint typography or padding, no hover-state attributes, no icon support, no link to site-level defaults, no `download`/`tagName`/`isSubmit` and limited transition and shadow controls. Extending it would mean maintaining a Gutenberg fork or fragile filter overrides, so the framework owns its button, as every serious page builder does.

## 3. The two-block pair

### `sgs/button` (atomic)

A single button. Dynamic block: `plugins/sgs-blocks/src/blocks/button/render.php` drives the output and `save` returns `null`. Rulings the schema cannot state:

- **`inheritStyle`** (`primary` | `secondary` | `outline` | `link` | `custom`, plus every preset name a site's snapshot carries on a site that sets `settings.custom.namedButtonPresets`, Spec 32 FR-32-33, so `block.json` holds no enum for it) selects the BEM variant class `.sgs-button--{preset}`, which sets the six `--sgs-btn-*` custom properties from that client's `--wp--custom--button-presets--{preset}--*` tokens (`plugins/sgs-blocks/src/blocks/button/style.css`). A `custom` or unknown value emits no modifier. The editor emits the same class, so WordPress's native "Transform to variation" control (the primary, secondary and outline block variations declared in `block.json`) visibly applies in the canvas.
- **Presets seed, they do not lock.** Every button paints colour, border, hover, typography and shadow entirely from its own attributes; `inheritStyle` gates no styling. `plugins/sgs-blocks/src/blocks/button/presets.js` holds the seed values used by the built-in CTA "Apply preset" control of `sgs/product-card`, and `sgs/multi-button` offers a "Style preset" select that applies a preset to every child button at once (D283).
- **Built-in buttons** (a button a block renders itself because it is tied to shop or flow behaviour) are not `sgs/button` blocks; they take the built-in button kit below.
- **Content and hover.** `contentAlign`, `iconGap`, `note` and `textDecorationHover` are button-owned; their behaviour is described in `02-SGS-BLOCKS.md` (Button architecture). The hover lift, scale and opacity are the button's `sgsMotion` Hover panel (Spec 38A). `note` is rendered by `plugins/sgs-blocks/includes/helpers-button-note.php::sgs_button_note_html`. `iconBackground` and `iconShapeSize` draw a filled circle behind the icon; with `labelFromSiteInfo` the label is the Site Info value when the link source is phone, email or WhatsApp (an email obscured by `antispambot()`, `includes/helpers-button-site-info-label.php`).
- **Per-device width** (`widthType`, `customWidth` and its unit are tier objects) renders in a uid-scoped `<style>` at the 768/1024 device tiers, so a button can be full width on mobile only (D280).
- **Full width** is `plugins/sgs-blocks/src/blocks/button/style.css::.sgs-button--full`: `width:100%; flex:0 0 auto; align-self:stretch`. It fills the line as a flex-row item and keeps its content height in a flex column; a percentage flex-basis is never used because in a column it resolves against the parent's height.
- **Label hardening (XS-9.2).** The label renders through `wp_kses` with an allowlist of `<br>`, `<strong>`, `<b>`, `<em>`, `<i>`, `<span class>` and `<code>`, which deliberately EXCLUDES `<a>`: the wrapper anchor is the block's own, and a nested anchor is invalid HTML and a phishing vector. The URL goes through `esc_url`, which blocks `javascript:`, `data:` and `vbscript:` schemes.

### `sgs/multi-button` (container)

Holds 0..N `sgs/button` instances through InnerBlocks, restricted to `sgs/button` children. It provides layout direction, alignment, wrap and gap per breakpoint (the gap is the shared `ContainerWrapperControls` gap control) and a default template of two buttons when first inserted. It mirrors how `core/buttons` wraps `core/button`, with the per-breakpoint controls the core pair lacks.

### Built-in buttons: the kit (Bean, 2026-11-20, option A)

A content button is a nested `sgs/button` (the composition pattern below). A built-in button is one a block prints itself because it is tied to shop or flow behaviour: a buy box's Add to Cart and flow opener, a choice flow's footer buttons, the account's sign-in, register and empty-state buttons, the product card's CTAs, product search's submit button, carousel arrows. Every built-in button takes one standard, so the cloning route can match any client's draft from settings alone and every site that sets nothing renders as before.

- **Declaration.** A block lists its built-in buttons in `block.json` `supports.sgs.builtinButtons`: `{ prefix, part, label, groups?, elements?, follows?, showWhen?, showWhenNote? }`. `follows` names the button whose rules also reach this one (the buy box's flow opener wears Add to Cart's class, so every setting it leaves unset takes Add to Cart's): the route then writes this button's own content alignment and lift wherever the followed button gets one and this button's draft differs, its centre or `0px` included (`scripts/computed-route/lib/fill-builtin-button.mjs::applyBuiltinButtons`). `part` is the `css_element` the framework database gives every look setting of the button, which the route's part locators key on.
- **Generated settings.** `plugins/sgs-blocks/scripts/generate-button-attributes.mjs` (prebuild; gate `check-button-attributes-parity`) writes `{prefix}{Base}` attributes with `"_generated": "button-kit"` from `plugins/sgs-blocks/src/components/button-kit/registry.json`, and their database rows into `scripts/attr-classification-overrides.json`. The groups are the preset choice (`{prefix}Style`, open preset names per Spec 32 FR-32-33, database role `button-preset`), colours with hover, optional gradients, border style and width, per-device padding and radius (registry `value_shape`), width (`fit` prints `width:fit-content`), per-device min height, shadow with hover, typography (the `TypographyControls` key set) and, for square controls, a per-device size. Two groups position the button's content and its movement: `contentAlign` (opt-in; `{prefix}ContentAlign`, a per-device `justify-content` of flex-start, center, flex-end or space-between, for a button that draws its label at one end and a price or note at the other; declared for `sgs/buybox` `addToCart` and `flowOpener`, `sgs/product-card` `cta` and `cta2`, and `sgs/choice-flow` `continue`, `addToBasket` and `buyNow`) and `hoverLift` (a default group; `{prefix}HoverLiftDistance`, one px length stored as a string such as `2px`, named so it cannot meet `sgs/buybox`'s boolean `addToCartHoverLift`). Generated settings carry no default: unset means the block's own look. The generator refuses an own attribute whose stored shape disagrees with the registry's.
- **CSS.** `plugins/sgs-blocks/includes/helpers-button-style.php::sgs_button_kit_css` prints a button's settings through the shared helpers only (`sgs_button_element_style_css` for colours and borders, `sgs_typography_css_rule`, `sgs_emit_responsive_css`, `sgs_border_element_decls`, `sgs_shadow_decls`, `sgs_button_press_rule_for`, `sgs_button_focus_host_border`). A chosen preset prints as one shared rule a page (`::sgs_button_kit_shared`, worn through `::sgs_button_kit_classes`) carrying the key set `sgs/button`'s variant classes paint, with hover and lift behind the touch guard, a keyboard-focus twin, and the lift and timing falling back to `default` (Spec 32 FR-32-19). `{prefix}HoverLiftDistance` makes the hovered button's total movement exactly that distance whatever lift the site's button token or the chosen preset adds: `sgs_hover_lift_distance_rule` (`includes/helpers-hover-lift.php`) prints an unconditional hover and keyboard-focus `transform:none` that cancels the stylesheet's own lift, plus `translate:0 -Npx` inside `@media (prefers-reduced-motion:no-preference)`, so reduced motion gets no movement at all; `0` prints `transform:none;translate:none` (no movement even where the site lifts) and unset prints nothing; the canvas draws no hover state, so it has no preview twin. Options keep an adopter's own behaviour: `preset => false` (the block keeps its own variant class), `state_guard` (for example `:not([disabled])`), `shadow_lift`. With nothing set it prints nothing. An adopter scopes its selector with `:where()` on the part class so the block's own hover and pressed rules still out-rank the resting rule.
- **Editor.** One panel, `plugins/sgs-blocks/src/components/BuiltinButtonPanel.js`, mounted once per declared button in the block's Styles inspector, built from the shared controls (the colour rows, `SgsBorderControl`, `SgsBoxControl`, `SgsLengthControl`, `TypographyControls`, the shadow control). The canvas previews a button through `src/components/button-kit/button-kit-style.js::buttonKitStyle`, the JS twin of the PHP. **Colour rows and the gate (Stage E2, 2026-11-26).** Neither kit body mounts a Colour panel. A block with 12 or fewer base colours (`scripts/check-colour-count.py`) spreads `plugins/sgs-blocks/src/components/BuiltinButtonPanel.js::builtinButtonColourRows` (and `plugins/sgs-blocks/src/components/CarouselDotsPanel.js::carouselDotsColourRows`, or `plugins/sgs-blocks/src/components/CarouselControls.js::carouselControlsColourRows` for both) into its one `SgsColourPanel` and passes `colourInMainPanel` to the kit mount, so the button's Background and Text rows sit there under a heading with its label; a block over 12 mounts the kit without that prop and the kit draws its colour rows in its own Colour panel (`plugins/sgs-blocks/src/components/KitColourPanel.js`), which Stage E3 places per part. `showWhen`, declared once in the entry, is the condition under which the PHP prints the button (`plugins/sgs-blocks/src/components/kitShown.js::kitShown`, condition kinds in `plugins/sgs-blocks/src/components/kit-show-when.json`, validated by both generators through `plugins/sgs-blocks/scripts/lib/kit-show-when.mjs`): while it does not hold, the kit's panel and colour rows are not offered. A gate that is a site setting or product data the editor cannot read is an empty list with a `showWhenNote`. Status: BUILT (Stage E2).
- **Carousel dots** take a sibling kit: `supports.sgs.carouselDots`, `src/components/carousel-dots/registry.json`, `scripts/generate-carousel-dots-attributes.mjs`, `includes/helpers-carousel-dots.php::sgs_carousel_dots_css` (arrows and dots together through `::sgs_carousel_controls_css`) and `CarouselDotsPanel` (which takes the same `showWhen` and `colourInMainPanel`). An arrow with no size set draws its icon at 22px, whatever size a site's own CSS gives the arrow; `arrowSize` is printed on the arrow selectors as `--sgs-carousel-arrow-size`, and half of it as `--sgs-carousel-arrow-icon` (`::sgs_carousel_arrow_icon_transform`), so a slider nested in one with `arrowSize` set does not inherit them (its arrows still take the outer block's part rules, which are descendant selectors). **The carousel package** is these two kits plus the front-end runtime: `src/components/CarouselControls.js` mounts the `arrow` button panel and the `dot` panel together, `sgs_carousel_controls_css` prints both, and `src/shared/carousel/index.js` (`createCarousel` and its primitives) moves the track, keeps the dots and arrows in step with the scroll position, loops, handles the arrow keys and runs autoplay on the shared pause. `sgs/trustpilot-reviews`, `sgs/post-grid` and `sgs/google-reviews` run their views on it; trustpilot-reviews and post-grid declare both kits; google-reviews declares the arrow kit (its arrow settings kept their names and saved values) and keeps its own dot colour panel and CSS until the dots kit can paint a gradient and a resting colour on the current dot (Status: built for arrows and views, dots open). `sgs/gallery`, `sgs/testimonial-slider` and the container's scroll row keep their own view scripts. `plugins/sgs-blocks/scripts/check-carousel-package.py` (`--survey`, `--check`, `--self-test`) lists every carousel block that builds arrows, dots or a view outside the package; its named exclusions are the only way out.
- **Adopters.** `sgs/buybox` (`addToCart`, `flowOpener`, on every product it renders: a simple product goes through the same buy box markup as a variable one, so both buttons and all their settings reach it; Bean, 2026-11-21), `sgs/choice-flow` (`back`, `skip`, `continue`, `addToBasket`, `buyNow`, `closeButton`), `sgs/account` (`loginButton`, `registerButton`, `signedOutSignIn`, `signedOutRegister`, `emptyState`), `sgs/product-card` (`cta`, `cta2`), `sgs/product-search` (`submit`), and the arrows (`arrow`) and dots (`dot`) of `sgs/testimonial-slider`, `sgs/container` and `sgs/gallery`. The theme's shop "Load more" button is not a block: it wears the preset a site names in `settings.custom.shopButtonPreset`, else primary.
- **Older settings.** Add to Cart's, the product card's and the account form's own settings were renamed to the kit's names (map `plugins/sgs-blocks/scripts/data/builtin-button-renames.json`); saved content is moved by `plugins/sgs-blocks/scripts/sweep-builtin-button-attrs.php` (WP-CLI, dry run by default), never by `deprecated.js` (FP-14).
- **The route** matches a draft's built-in button against the site's presets, resting and hovered, and writes `{prefix}Style` on a match, else the draft's own look into the prefixed settings (`scripts/computed-route/lib/fill-builtin-button.mjs`, Spec 48 FR-48-51). Whether or not a preset matched, it also writes `{prefix}ContentAlign` from the draft button's computed `justify-content` (per device; the block's own centre or `normal` writes nothing) and `{prefix}HoverLiftDistance` from how far the hovered button moves up (whole px; a still or sinking button writes nothing), each only where the block declares the attribute; and the buy box's `addToCartShowIcon` is written false when the draft's Add to Cart draws no svg (`data/part-look-modes.json`, locator `add-to-cart-icon`).
- **Detector.** `plugins/sgs-blocks/scripts/check-styled-part-has-setting.py` (passes `buttons`, `parts`, `unmapped`) finds a styled part, a hard-wired preset or a look setting the database cannot place; its baselines only shrink.

### Composition pattern in composite blocks

Every block that renders CTAs (`sgs/hero`, `sgs/feature-grid` and so on) exposes an `<InnerBlocks>` slot whose default template is `sgs/multi-button` holding two `sgs/button` instances. The user can delete one button (a one-CTA block), delete both (text and image only), add a third, and choose each button's variant independently. There is no "Match Style" extension: the variant lives once on `sgs/button` and every instance inherits it. New SGS blocks with CTAs MUST use this pattern; the one recorded exception, `sgs/product-card`, is described in `02-SGS-BLOCKS.md`.

A dynamic block with an InnerBlocks slot must `save` as `<InnerBlocks.Content />`, never `null`, or the nested blocks are lost on save (`.claude/specs/common-wp-styling-errors.md` B4).

## 4. Button presets are native theme.json

Per-client preset values live in `settings.custom.buttonPresets` of the client's `sites/<client>/theme-snapshot.json` (Spec 32 Part C), pushed by `plugins/sgs-blocks/scripts/push-theme-snapshot.py`, and in the Customiser panel `plugins/sgs-blocks/includes/class-button-presets-customiser.php`. WordPress generates the `--wp--custom--button-presets--*` properties itself; the framework emits no bridge and has no Settings page for them. WooCommerce's primary buttons (the mini-cart checkout button, Proceed to checkout and Place order, `theme/sgs-theme/assets/css/woocommerce.css`) follow every key of the `primary` preset: `font-size`, `font-weight`, `letter-spacing`, `text-transform`, `min-height`, `padding`, `border-radius` (falling back to the `border-radius.medium` token) and its optional `shadow` and `hover-shadow` keys (a box-shadow value each; absent means no shadow), so the client's button look reaches the shop's own buttons (Spec 27 FR-30-18).

| Path | Audience | UX |
|---|---|---|
| Site Editor, Styles, Buttons | Site owners and power users | Native WordPress UI with live preview and pseudo-element support |
| `sites/<client>/theme-snapshot.json` | Developers shipping a client | Code-first, version-controlled, per-site push CLI |

Each preset (primary, secondary, outline) carries the full per-state set: background, text, border, border width, radius, padding, font size and weight, letter spacing and text transform (optional: the base theme leaves them unset so a preset button inherits its surroundings' case and spacing; a client snapshot sets them, e.g. Eye Care's uppercase 1.3px primary), minimum height, and the `:hover` background, text and border.

## 5. Rulings

- **Decision 22:** button presets are native theme.json `settings.custom.buttonPresets` (plus the Customiser panel). There is no Settings page and no `wp_options` bridge (`sgs_button_presets` names only a Customiser panel). Bean-approved.
- **Decision 24:** WordPress natively generates every consumed `--wp--custom--button-presets--*` property from `theme.json` `settings.custom.buttonPresets`, so no PHP bridge exists. The coverage audit is `.claude/reports/phase-5b-button-property-coverage.md`.
- **D283:** the locked inline-preset system is removed; presets seed attributes and every value stays editable. Bean-approved.
- **D280:** per-device button width and the hover underline (`textDecorationHover`) are part of the surface.
- **D270, D271, D293:** no `deprecated.js` and no version bumps pre-production; an attribute change ships without a deprecation path (`.claude/rules/block-authoring.md`).

## 6. Gaps deliberately skipped

Visibility controls are not button-specific: the universal visibility extension (`02-SGS-BLOCKS.md`, Visibility Extension) covers them.

## 7. Requirements

- **FR-11-1 — Signature keyboard focus on the commerce CTAs.** The animated, client-coloured Signature focus look (`sgs-focus--signature`, Spec 32 §14.5) reaches the buybox add-to-cart button, the product-card CTA and the pricing-table CTA, through the same "Keyboard focus" control `sgs/button` carries (`focusStyle`), refused on the same two conditions (a gradient border, a motion effect that owns `::before`). Owner ruling 2026-10-17 (Q3): `sgs/button` is the only block with the control, so these three CTAs, which render their own markup, take the site's default focus look until this requirement is built. *Done when:* each of the three CTAs offers the Keyboard focus control or inherits it from an `sgs/button` it composes, a focused Signature CTA shows the conic band with a `::before` carrying `animation-name: sgs-focus-spin` (and `none` under `prefers-reduced-motion: reduce`), and the Spec 32 §14.5 probe reports the stop as `signature` on the fixture page. Status: NOT BUILT.

- **FR-11-2 — WooCommerce primary buttons follow the whole `primary` preset (COM-6, Bean 2026-11-05).** The mini-cart checkout button, Proceed to checkout and Place order in `theme/sgs-theme/assets/css/woocommerce.css` read each `--wp--custom--button-presets--primary--{font-size,font-weight,letter-spacing,text-transform,min-height,padding,border-radius,shadow,hover-shadow}` property, with the pre-COM-6 value as the fallback for a key a site leaves unset. *Done when:* a site whose `primary` preset sets a key renders that value on all three buttons. Status: BUILT.

- **FR-11-3 — Every built-in button takes the built-in button kit (Bean, 2026-11-20, option A).** A button a block prints itself declares itself in `supports.sgs.builtinButtons`, gets the generated preset choice and look set, the one shared panel and canvas preview, and prints through `sgs_button_kit_css`; with nothing set it renders as before; the route writes a matching preset or the draft's own look (section 3, "Built-in buttons: the kit"). *Done when:* `node plugins/sgs-blocks/scripts/generate-button-attributes.mjs --check` and `--self-test` pass; `python plugins/sgs-blocks/scripts/check-styled-part-has-setting.py --check` passes and fails on a planted hard-wired button; `php vendor/phpunit/phpunit/phpunit --filter 'ButtonKit|ButtonElementStyle|BuyboxKeepFlow|ChoiceFlowButtonKit|AccountButtonKit|ProductSearchSubmitKit|ShopLoadMoreButton|CarouselControls|ButtonMigrationSweep'` passes (in `plugins/sgs-blocks/`); on a scratch copy of Eye Care the route writes the product page's flow opener solid and Add to Cart outlined, as the draft draws them, at 375 and 1440; and the render check shows Mama's, Indus and Eye Care unchanged with the rename sweep run. Status: BUILT (2026-11-21). Not built: the editor canvas of `sgs/choice-flow` does not draw Continue, Add to basket, Buy now or Skip, and the carousels' canvases draw no arrows or dots, so those settings have no canvas preview (accepted as wiring-fingerprint L3 gaps); the choice flow's Back button has no typography group yet.
