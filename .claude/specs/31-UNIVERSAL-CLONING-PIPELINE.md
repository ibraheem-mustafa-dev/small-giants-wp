## 0. Plain English (what this is, why it exists)

**What.** Every cloned page section renders through ONE engine — `sgs/container` and its PHP wrapper (`SGS_Container_Wrapper`), which the composite blocks share. The cloning converter (`converter/`) reads a draft mockup's CSS and puts every value the draft holds into the right block setting, at the right screen size (mobile / tablet / desktop). Anything it cannot place is logged as an honest gap, never dropped silently.

**Why a full architecture, not patches.** This stage has failed repeatedly because fixes were local: one block made to work in one context, score inflated by a cheat, then collapse everywhere else. This spec defines the *whole* target system — every block type, every layer, every screen tier, every child-shape — plus the completion goals and the cheat-detection that make a partial or cheated implementation **impossible to mistake for done**.

**The one-sentence target.** A single DB-driven, name-free routing engine reads any draft routing unit — a CSS property OR a content node (text/media/array) — and places it on the correct block attribute (or child InnerBlock) at the correct responsive tier, for `sgs/container` and every container-bearing composite identically — with completeness measured against a live coverage ledger and cheats caught by structural gates, not by eye.

> **SCOPE — content extraction is IN, and UNIFIED with CSS.** Despite the title saying "CSS-Transfer", this spec governs the WHOLE draft→block transfer through the one container dispatch: **CSS routing AND content routing (scalar text lift, scalar media object-shaping, array/repeater lift, child-block emission)**. Content is NOT a separate engine, NOT a separate stage, NOT out-of-scope. The content fork (which child becomes a block vs a scalar attr — FR-31-2/2.1/2.2/2.5, §13.3) is INCORPORATED here as part of the same name-free DB dispatch; CSS simply adds the L1–L4 layers + more DB columns on top of the SAME recognise→resolve-destination→tier→serialise pipeline. Spec 22's content logic is absorbed into §13. **Do not infer content is excluded because the title or §8 says "container-CSS transfer."**

## 1. System map — where CSS transfer happens

The pipeline (Appendix D stage index, below) touches CSS transfer at exactly these points. Spec 31 governs all of them as ONE system:

| Stage | Role in CSS transfer |
|-------|---------------------|
| **0.7 `css_router.py`** | Splits the draft `<style>` into destinations: **D0** global/reset, **D1** typed-attr lift → block attrs (token-snapped), **D2** wrapper-CSS scoped `.page-id-N`. |
| **Stage 2** block-match | Picks the block for a section; no confident match → `sgs/container`. Composite recognition (`.sgs-hero`→`sgs/hero`, `.sgs-trust-bar`→`sgs/trust-bar` with `variant` set) lives in the `converter/` recognition module. Sections with no registered composite block (featured-product, brand, ingredients, gift, social-proof) correctly emit `sgs/container`. |
| **Stage 3** slot list | Annotates each attr with `canonical_slot`/`role` from block.json — metadata only, not the structural router. |
| **Stage 4 `converter/`** | **PRIMARY lift engine** — entry `converter/entry.py::convert_section`; the universal walker folds wrappers and lifts box/grid/typography CSS onto attrs at 3 viewports through ONE dispatch. |
| **Stage 4.5 / 0.8** | Token-snap (ΔE≤1 / ≤1px) + theme-width detection; the literal is kept and a gap logged on a miss. |
| **Stage 11.6** | Computed-parity (Spec 20 — effective values matched by CONTENT at 375/768/1440) — the verification floor and the sole automated fidelity signal, paired with Bean's eye per R-31-13. |
| **Stage 9** | 5-bucket leftover router; the "honest gap" mechanism is in-memory ledger tracking (there is no DB-backed gap-candidate table). |

**Architectural principle #1 — ONE lift path. CONTENT AND CSS ARE THE SAME DISPATCH — do not build them separately.** Every lift (root supports, wrapper box, typography, content band, uniform grid-item CSS, scalar content, scalar styling, scalar media) is a resolver inside ONE DB-driven `(block, layer, property/role, tier) → resolver` dispatch (§12.4). The lifts have genuinely DIFFERENT destinations (WP supports / container box / typography / grid-item / scalar content / scalar media), so any change to the dispatch MUST gate on both conformance suites. Two paths that can disagree is itself a defect class (Family K duplicate-emit is a symptom). **`css_router.py` rule:** Stage 0.7 routes CSS to D1, and Stage 4 must consume that output (or the D1 path must not exist) — a dead stage that silently strands properties is forbidden.

> **MODULARISE, do not RECREATE.** Scalar CONTENT lift and scalar MEDIA lift are resolvers inside the ONE `(block, layer, property/role, tier) → resolver` dispatch (§12.4), alongside the CSS resolvers — content does NOT get a separate engine, new `run_mechanism_*` logic, or new DB columns. The existing DB data (`derived_selector`, `canonical_slot`, `standalone_block`, `parent_block`, `accepts_allowed_blocks`, `slots.aliases`) already drives content routing — query it, do not duplicate it.

## 2. THE CORE PIPELINE MECHANISM — one recursive stream, content + CSS together

**Mini-glossary (terms used below).** *Container-equivalent block* = any block wired to the shared `SGS_Container_Wrapper` PHP helper (§2.1). *InnerBlocks* = nested child blocks inside a parent block (WordPress Gutenberg). *Scalar attr* = a plain data field on a block (a string/number), as opposed to a nested child block. *Atomic block* = the smallest single-purpose block a bare tag maps to (`p→sgs/text`). *Fold* = absorb a wrapper's CSS onto the container's attributes and drop the wrapper div (it does NOT survive as its own block). *L1/L2* = the OUTER box layer / the CONTENT (inner-band) layer (§2.3). *`container_kind`* = a DB value (`section`/`layout`/`content`) that gates which editor panels + render layers a container-equivalent exposes — NOT a routing input. *Variant* = a named structural preset of a block (e.g. hero `split`) selected from its class modifier.

> **This section is the heart of the spec. Read it first; everything else is detail beneath it.** If you understand this section you understand how a draft becomes SGS blocks. It is written to be self-explanatory — you should never need it explained in conversation.

### 2.0 Plain English — what the pipeline does

The pipeline **recursively** walks the draft. It processes every node the same way, migrating **CONTENT and CSS together in ONE pass per element** — there is no separate "CSS route" and "content route". The unified stream is `build_block_markup` → `process_element` (CSS) + `extract_content` (content) in one traversal, not two document sweeps.

Every node that is a section or a wrapper renders through a **container-equivalent block** — `sgs/container` itself or a composite that has the shared container helper built in. There is no "sometimes a container, sometimes something else."

### 2.1 Container-equivalent blocks — the universal render surface (DB-identified, at ANY level)

A **container-equivalent block** is any block with the shared `SGS_Container_Wrapper` helper built in, identified in the DB (never a hardcoded list):

```sql
SELECT block_slug, container_kind FROM block_composition
WHERE wraps_block = 'sgs/container' AND container_kind IS NOT NULL;
```

`block_composition.container_kind` (∈ `section`/`layout`/`content`) is the converter's roster axis. It gates **panel/render-layer exposure** (which editor controls + PHP layers the block shows) — it is **NOT** a routing input (§2, §8 below). A couple of blocks have render-side wrapper nuances — e.g. `sgs/modal` and `sgs/nav-drawer` are excluded from the wrapper-mirror (`containerMirror:false`, §13.6.1 below) — but that render-side axis is **separate** and does not remove a block from the converter roster (`container_kind`). Full roster + KIND meanings: §13.6.1 below (canonical).

**Container-equivalent blocks appear at BOTH levels, treated identically:**
- **Section-class level** — a top-level page section (`sgs/hero`, or a slug-None `<section>` → `sgs/container`).
- **Div-class level** — a nested `<div>` deeper in the tree (`.sgs-feature-grid` → `sgs/feature-grid`; `__cards` → a grid container; `.sgs-products` → its own grid container).

There is **NO** "class-section vs div-section" distinction (R-31-9 universal — a carve-out for one or the other is a break). The recursion (§2.0) means a container-equivalent block nested three levels deep is decomposed by the exact same rules as a top-level section. When this section talks about "the container," it means whichever container-equivalent block is being processed at that point in the recursion — at any depth.

### 2.2 The per-node pipeline order (recognition → variant → layers → content)

For **every** node, in this order:

1. **Recognise the block by BEM name** (§13.2). The `sgs-<block>` root class resolves to a block slug via the DB (`slots`/`blocks`), name-free per R-31-2; a slug-None node **at any depth** defaults to `sgs/container` (FR-31-4). This decides *which* container-equivalent block the node becomes.
2. **Variant lookup — AT THIS RECOGNITION STAGE (load-bearing).** If the recognised block declares variants (`blocks.variant_attr IS NOT NULL`), read its variant from the node's **class modifier** (`--split`, `--featured`, `--trial`) against the **variants table** (`variant_slots` + `blocks.variant_attr`, FR-31-20) — DB-driven, query never guess (R-31-1/R-31-8). **Two complementary variant mechanisms exist, at different times.** (a) THIS step — recognition-time **modifier application** (`variant_detect.detect_variant_for_node`, reads the `--modifier`) which can pre-empt the layer pass; (b) a post-content-lift **fingerprint reconciliation** (`db_lookup.detect_variant(slug, assembled_attrs)` — counts which discriminating `variant_slots` POPULATED from the draft THIS run, §13.5), which structurally CANNOT run before the lift. Neither replaces the other (a modifier-less draft still gets its variant from the fingerprint; a fingerprint-ambiguous draft still gets it from the modifier). **The variant can change the block's structure — including whether it is a grid, which slots exist, and the layout.** So the variant is resolved *before* the generic layer pass and can pre-empt it: e.g. `sgs/hero --split` **IS** a 2-column grid *by variant definition* (`variant_slots`: `gridTemplateColumns`/`splitMediaImageUrl`/`splitMediaImageUrlMobile`), not by generic `display:grid` detection. The hero's split media is the decomposed `splitMediaImageId`/`Url`/`Alt` (+Tablet/Mobile) shape. The generic layer decomposition (§2.3) only runs for what the variant does not already define. Variant lookup runs at recognition for a node at **any depth** — including a grid item that is itself a variant composite (a `sgs/product-card--featured` inside a grid is recognised as that variant *first*, never reduced to a generic grid cell — §2.5).
3. **Layer decomposition** (§2.3–§2.4) — for the CSS the variant didn't define.
4. **Content extraction** (§2.6) — in the same pass.

### 2.3 The layer decomposition — name-free, by CSS signature + structural position

A container-equivalent block decomposes the draft it wraps into **layers**, detected by **CSS signature + structural position, NEVER class name** (DEC-1/2/3 — matching `__inner`/`__content` names causes wrong collapse and is banned):

| Layer | Physically lives on | Detected by (CSS signature) | Container destination |
|-------|--------------------|-----------------------------|-----------------------|
| **OUTER box (L1)** | the container's own root element | it is the root | `style.spacing.*`, `background*`, `border*`, `align`/`maxWidth` |
| **CONTENT band (L2)** | a **pass-through** inner wrapper (see §2.4 for "pass-through") | `max-width` + `margin:auto` (± padding), NO grid/flex, NO block identity | `contentWidth`, `contentPadding*` |
| **ARRANGEMENT (grid/flex)** | the **direct parent of the arranged items** (see the rule below) | `display:grid` OR `display:flex` (row/column layout) | grid → `layoutType:grid` + `gridTemplateColumns`/`gap`; flex → `layoutType:flex` + `gap` (+ justify/align) — the container's layout attrs |
| **PER-ITEM** | the arranged items (direct children of the ARRANGEMENT element) | box-CSS shared by the items | `gridItem*` defaults (§2.5) |

**The load-bearing ARRANGEMENT rule:** `display:grid` (or `display:flex`) **always sits on the immediate parent of the items**, because grid/flex only lay out an element's *direct* children. So the arrangement property is on whatever element directly parents the items — it is **NOT** a separate nested "grid layer" div, and it is **never** on the items. When you see `display:grid`/`display:flex`, that element **is** the arrangement level, and its direct children are the items. (Below, "grid item" is shorthand for an arranged item under either `display:grid` or `display:flex`.)

### 2.4 The recursive fold — what folds into the container vs what becomes its own container

The layers collapse onto **ONE** container-equivalent block. Apply the **grid-item test first**, then the **fold/recurse test**:

**Grid-item test (first).** A **grid item** = a direct child of an element carrying `display:grid`/`display:flex`. If the container itself carries the arrangement — on its root (brand), or folded up from a sole arrangement inner (trust-bar) — then its **direct children are grid items**: they go straight to §2.5 (become the container's InnerBlocks, each recognised variant-first, uniform box-CSS → `gridItem*`). **Grid items are NOT subject to the fold/recurse test below, even though they are siblings** — that is exactly how brand's two columns (`__content`/`__image`) are grid items of the section grid, not separate own-containers. The fold/recurse test applies **only to children that are not grid items** (i.e. the container is not itself an arrangement, or the child sits *beside* the arrangement, not inside it).

**Fold/recurse test (for non-grid-item children):**
- **A sole pass-through child folds in.** If the container's root has a **single** real child that is a *pass-through wrapper* — a `<div>` with **no block identity** (its BEM class resolves to no registered block) — that child **folds into the container**: its content-band CSS → `contentWidth`, its arrangement CSS → the container's layout attrs, and **its** children become the container's children (re-apply the grid-item test to them). Repeat while there is a sole pass-through child. (Trust-bar's sole `__inner` carries the grid → folds → badges become the container's grid items; gift's sole `__card-inner`, a content-band with no grid → folds to `contentWidth`.)
- **A sibling'd child, or a child with block identity, does NOT fold — it recurses as its own container.** When the container has **more than one** real child (a heading beside an arrangement, etc.), or a child resolves to a registered roster block, that child is its **own** container-equivalent block, processed by this same §2.2 procedure recursively — **not** flattened. (Gift's `__cards`, a grid beside the heading, stays its own grid container; `.sgs-feature-grid`/`.sgs-products` resolve to their own registered grid containers — **slug per DB recognition, never the literal class name**.)

**Consequence — where the arrangement CSS lands:** always on the **direct parent of the items**, which is either **this** container (arrangement on the root, or folded up from a sole arrangement inner — brand, trust-bar) **or** a **nested own-container** (arrangement beside siblings or with its own block identity — gift `__cards`, featured `.sgs-products`, ingredients `.sgs-feature-grid`). Same §2.3 rule at whatever depth; the only difference is nesting.

**Definitions.** *Pass-through* = a `<div>` whose BEM class resolves to no registered block (a bare structural wrapper), carrying only content-band and/or arrangement CSS. *Real child* = a direct child **element** that is content or a container-equivalent block, **plus** any non-whitespace text node (whitespace-only text is ignored). *Sole* = the container's root has exactly **one** real child and it is a pass-through wrapper; any sibling (element or non-whitespace text) makes it non-sole and blocks the fold.

> **Fold/recurse guard:** do not add a margin/gap/padding disqualifier to the fold/recurse test — such a rule rejects the exact `max-width`+`margin:0 auto` pattern that IS the L2 CONTENT band above. A relational L2 qualifier — `converter/services/l2_qualify.py` — is BUILT but NOT WIRED. Its trigger is RELATIONAL, not per-element: the direct PARENT being a recognised container-kind block is what makes the child a fold candidate; the child's own identity is never the input. It reproduces the §2.7 acceptance table 5/5 on the real homepage draft. Do not build a second, competing qualifier — wire this one in.

### 2.5 Grid items fold into the container

The grid items become the container's **direct InnerBlocks**. Their box-CSS folds **per property**: any CSS property whose value is **the same on every item** folds into the container's `gridItem*` default attrs; any property that **differs on even one item** stays on that individual child block. *(Non-normative: with only two items, expect most properties to stay.)* A **heading** or any recognised content sibling of the grid is **content, not a grid item** — emitted as its own content block, never swept into the grid.

**A grid item that is itself a variant composite is recognised first (precedence over folding).** If a grid item is a variant composite (a `sgs/product-card--featured`), §2.2 step 2 recognises it as that block+variant **before** any `gridItem*` folding — it keeps its full variant identity and is **never** reduced to generic `gridItem*` box-CSS.

### 2.6 Content extraction runs in the same single pass

In the same traversal, per element, content migrates alongside its CSS — never as a second pass. **The one rule for "attribute vs child block":** a piece of content becomes a **typed scalar attr** when the target block renders that element itself (element-based blocks), or a **child InnerBlock** when the target block composes children (InnerBlocks blocks). That fork is the DB-driven content fork (§13.3 — `equivalent_block_for`, read with `role` + `attr_type`; `canonical_slot` drives *only* this content fork, never layout). Bare content tags resolve to their atomic block via `blocks.replaces` / `atomic_tag_map` (`p→sgs/text`, `h2→sgs/heading`, `a→sgs/button`, `img→sgs/media`, `blockquote→sgs/quote`).

### 2.9 Reference: the four orthogonal axes (detail beneath §2)

Every container-bearing block is described by four independent axes. The routing engine must handle **every combination**, with no per-block code.

### Axis 1 — LAYERS (where in the box a property lives)
Per FR-31-21 + the design-gate doc. A draft wrapper decomposes into at most four layers; each has a distinct attr destination, detected by **CSS signature + structural position, NEVER by class name** (DEC-1/DEC-3):

> **Box-property SHAPE note:** within any layer, a **box-family** property does NOT land as N flat per-side/per-corner attrs — it lands as ONE named-object attribute. **4-side families** (`padding`/`margin`/`borderWidth`/`contentPadding`/`mediaPadding`/`contentBandPadding`/`imagePadding`/`imageBorderWidth`) → `{top,right,bottom,left}`. **4-corner families** (`borderRadius`/`imageBorderRadius`) → `{topLeft,topRight,bottomLeft,bottomRight}`. Root padding/margin/border-radius keep routing to the WP-native `style.spacing.*`/`style.border.radius` object (already object-shaped); per-area families (contentBandPadding etc.) use an equivalent SGS custom object attr, both consumed via WP's `BoxControl`/corner-radius editor component. **Non-box properties stay scalar**: `max-width`/`min-height`/`gap`/`background*` and the single-side families (`attributionMarginTop`, `shapeDivider{Top,Bottom}` + sub-properties, etc. — see Spec 32 §6.1 for the full keep-scalar list). The categorisation guard is the DB `block_attributes.box_family` column (§4) — there is no separate `box_side` column; per-side/per-corner identity comes from the flat attr's name — never a name regex for the family assignment itself.

| Layer | Detected by | Attr destination |
|-------|-------------|------------------|
| **L1 OUTER box** | the section-root element itself | native `style.*` + **`maxWidth`**/`padding*`/`background*`/`min-height`. **`max-width` rule:** ABSENT → **emit NOTHING** (`maxWidth` defaults to `{}` = no cap = full-bleed, so absence is the honest translation of absence); PRESENT → `maxWidth` (string **literal**, exact draft value — decimals+unit preserved, no 5% theme-snap, no `int()` truncation) + responsive `maxWidthTablet/Mobile` at 767/1023. There is no `widthMode`/`customWidth`. ⛔ **`align` is NOT emitted at this layer.** Measured on the live canary: stripping `.alignfull` from an element in a real `.wp-block-post-content` context changes nothing — left, width and all four margins are identical, and an A/B against an unaligned sibling is byte-identical. Core's breakout rule resolves `calc(var(--wp--style--root--padding-left) * -1)` against a variable that is EMPTY at `:root`, so the declaration is invalid and dropped. `align:"wide"` has no matching rule at all (its only rule needs `.is-layout-constrained`, which `sgs/container` never emits). No SGS-BEM draft can express either — there is no such CSS property — so emitting `align` would invent a WordPress idiom the draft never stated, failing the R-1 honest-mapping test. `supports.align` is not declared on `sgs/container`; the DB-driven gates in `outer_box.py::align_finalise()` and `assembly.py` self-disable when `block_supports` carries no such row. The native WP `style.*` lift lives in `converter/services/root_supports.py`: `padding`/`background-color`/`border-radius` emit nested `style.spacing.padding`/`style.color.background`/`style.border.radius`; the conductor partitions block-supported props out of the per-declaration Decl stream before handing off to outer_box. |
| **L2 CONTENT-WIDTH (inner band)** | `--content-width` custom-prop decl (deterministic) OR `max-width`+`margin:auto` signature (scraped fallback) | `contentWidth` (token `normal`→content-size / `wide`→wide-size / `full`→no cap, OR a **literal**; **default `normal`** (~content-size); `full` resolves to `''` = no cap. A container that is NOT page content (a `<main>`, a sidebar `<aside>`, a flex cluster) must say `full` EXPLICITLY or it silently gains a band + gutter) + `contentBandPadding*` (via the `max-width ≡ width` CONTENT-layer suffix equivalence) + an inheritable **`text-align`** on the band → the block's WP-native `textAlign` support (see FR-31-5.1a; cascades to the band content, child-overrideable) |
| **L3 GRID + PER-ITEM** | the level carrying `display:grid`/columns | `gridTemplateColumns`/`gap`/`gridItem*`. UNIFORM child box-CSS → `gridItem*` defaults; UNIQUE per-item CSS → that child block's own CSS |
| **L4 GRID-PER-AREA** (FR-31-21.3) | named grid areas — `<areaName>+<Suffix>` families (object-shaped) | `contentPadding*`, `mediaBackground`, … via `db.attr_for_area_property( block, area, prop )`. ⛔ **Areas are DERIVED FROM THE DRAFT, never declared on the block** — `assembly.py` step 3d walks the section root's children and reads each one's BEM ELEMENT TOKEN (`db_lookup.parse_sgs_bem( cls ).element`, so `sgs-hero__content` → area `content`). `supports.sgs.gridAreas` does not exist — declaring it fails the build. See Spec 35A §F.2. The per-area lift is `assembly.build_block_markup` **step 3d**: for every named-BEM-element child of any block's section root, `fold_helpers.route_area_css_to_block_attrs` (with a `residual_sink`) routes the child's box-CSS to `<area>+<suffix>` per-area attrs (`content`→`contentPadding*`, `media`→`mediaPadding*/mediaBackground`) and drains non-device residuals to `sgsCustomCss`; it is universal/DB-gated (`attr_for_area_property` → None → gap-track, no per-block literal) and recursive (fires per `build_block_markup` call, i.e. every block and nesting level). **Band-alias guard:** `attr_for_area_property` SKIPS `Band*` suffixes — the L4 per-area resolver must never bind to an L2 container-band attr (`contentBandPadding*`), or a nested `__content` column's padding lands on the outer band. |

Rules that bind every layer: the container **NEVER imposes alignment on children** (step 5); any property with no attr destination is **FLAGGED, never silent-dropped** (step 6); `display`/`grid-template-*` are **EXCLUDED from cross-node inline lift** (GAP-3 — inline beats `@media` and collapses grids). On a section root, properties in `dispatch_table._GRID_LAYOUT_PROPS` now route PRE-LAYER directly to the grid resolver (a section root is simultaneously OUTER for box CSS and GRID for child-track declarations); this resolves the ambiguity where the layer-detector could not distinguish an OUTER `max-width` from a GRID `grid-template-columns` on the same root element.

### Axis 2 — KIND (which layers a block exposes)
`block_composition.container_kind` : **section** (all layers + background/overlay/SVG/shape), **layout** (L1–L4 width+grid, no background layer), **content** (L1+L2 width+padding only, no grid, no background). KIND **gates which attrs exist as a destination**; it does NOT change routing logic (§13.6.1 below).

### Axis 3 — CHILD-SHAPE (where per-item / child CONTENT **and** CSS goes)
The axis Bean called out explicitly. The CONTENT nested-vs-child shape is decided PER ATTR by the source-derived `block_attributes.emit_shape` (`nested` | `child`), not by a block-level flag — a block-level flag cannot express a MIXED block. The three-way table below illustrates the block *families* (pure-InnerBlocks / pure-scalar / mixed); the routing is per-attr: each `role=content` attr resolves its identity (`equivalent_block_for`) + its `emit_shape`, so a "Mixed" block is simply one whose attrs carry BOTH `emit_shape` values. **This axis governs BOTH the element's CONTENT destination AND where its CSS goes — the SAME per-element dispatch, not separate stages.** Read the "CSS destination" column below as content+CSS destination:

| Child-shape | `emit_shape` of its content attrs | Per-item / child CSS destination |
|-------------|------------------|----------------------------------|
| **InnerBlocks** (card-grid, feature-grid, accordion, tabs, multi-button…) | `child` | Each grid item IS a child block → that child block's own CSS attrs. UNIFORM item CSS → parent `gridItem*` defaults |
| **Scalar** (testimonial, team-member, trust-bar, option-picker…) | `nested` | Child content/style lives in the parent's typed scalar attrs (e.g. per-area `content*`/`media*`) |
| **Mixed** (hero, cta-section…) | both | Full wrapper attrs (L1–L4) **plus** per-area scalar attrs (`headline`, `contentPadding*`, `mediaBackground`) — routed by L4 area lookup. The cross-node predicate `slot_has_equivalent_block(block, slot)` forks: TRUE → CSS to child block; FALSE → lift to parent box attrs |

#### Child-block CONTENT resolution

The table above answers "where does child **CSS** go". Which **child block** a draft child element becomes is a distinct mechanism from the `slot_has_equivalent_block` CSS-fork: `slot_has_equivalent_block(parent, slot)` checks the parent's own content **attributes**, which a LAYOUT container legitimately has none of — so keying child-block emission off it would produce zero children for every layout-container composite. The DB-driven resolution (the same forced-parentage mechanism as **§13.3 / FR-31-5.3**):

> For a draft child element carrying a BEM token under an `InnerBlocks` parent, resolve its child block by: (1) **`blocks.parent_block` (forced-parentage)** — if the parent has a registered child whose identity matches the element's token, that child wins (`sgs/accordion __item → sgs/accordion-item`; `sgs/tabs __tab → sgs/tab`; `sgs/form __step → sgs/form-step`), overriding the global alias (so `__item` under accordion does NOT mis-resolve to the global `card`-alias `sgs/info-box`); (2) otherwise **`slots.(aliases, standalone_block)`** — the token → canonical slot → `standalone_block` (`__button → button → sgs/button`); (3) **`block_composition.accepts_allowed_blocks`** is the VALIDATION gate — the resolved child must be in the parent's allowed-blocks list, else it is a flagged GAP (never silently dropped, never a per-block carve-out, R-31-9). `slot_has_equivalent_block` is the CSS-fork ONLY; it is NEVER the child-block-emission predicate. `wraps_block` names the parent's own built-in wrapper (e.g. `sgs/container`), NOT its content children — do not confuse the two.

### Axis 4 — VARIANT (which extra slots exist this run)
`blocks.variant_attr` names the selector attr; `variant_slots(block_slug, variant_value, unique_slot)` holds each variant's **discriminating** slots (set-difference vs siblings). The detector counts how many of each variant's `variant_slots` were populated **from the draft extract THIS run** (never the block's stored attrs) and sets the highest-count variant. Code is universal (`detect_variant`, `variant_attr_for`). ⛔ **Query, never guess — a prose example in a spec is not a query, and any attr name written here is a snapshot that rots.** Example: `SELECT * FROM variant_slots WHERE block_slug='sgs/hero'` returns `('sgs/hero','split','splitMediaImageUrl')`, `('sgs/hero','split','splitMediaImageUrlMobile')`, `('sgs/hero','standard','backgroundImage')`; there is no Tablet-specific discriminating slot for `split`, and the generic `gap`/`gapTablet`/`gapMobile` cover spacing. Re-run the query before relying on any of those names.

## 3. The routing algorithm (DB-driven, name-free) — the heart of the system

> This section is detailed reference beneath the canonical §2 core mechanism and must not contradict it.

**The dispatch routes a draft ROUTING UNIT to its native destination. A routing unit is EITHER (a) a CSS declaration `(css_property, value)` at a tier, OR (b) a CONTENT payload (an element's text / media / rating, or a child element that becomes a child block).** Both classes go through the SAME `(block, layer/role, property/selector, tier) → resolver` dispatch (§12.4) — content and CSS are branches of one algorithm, NOT separate engines (§1). Per element, route every CSS declaration through the **CSS branch (§3.A)** AND route its content through the **CONTENT branch (§3.B)**; both write into the same emitted block attrs + child InnerBlocks and feed the same conservation ledger.

### 3.B — CONTENT branch (resolvers inside the one dispatch)

These are resolvers inside the one dispatch. All four sub-routes are DB-driven (R-31-1), capability-gated, no-op when their trigger is absent, and name no block.

- **B1 — Scalar CONTENT lift** (block has `scalar-content-lift` capability; a leaf block). For each attr in `block_attrs(slug)` with a non-empty `derived_selector`, find the FIRST descendant matching the selector (comma-separated BEM classes, first-non-None wins — handles `__text`↔`__quote` drift), and lift by `(role, attr_type)`: `text-content`/`content`+`string` → `_rich_text_content(el)` → scalar text attr; `rating`+`number` → star count (`aria-label` digit, else ★/⭐ glyph count, 0–5) → rating attr; `image-object`+`object` → first `<img>` → `_lift_scalar_media_from_img` → `{url: resolve_media_url(src), id:0, alt}`. `showRating` coupled to a positive rating. An attr whose selector matches nothing emits NO key (strict no-op). Implemented in `converter/resolvers/scalar_content.py::lift_scalar_content` (+ helpers in `converter/services/lift_helpers.py`), wired via the thin wrapper `run_mechanism_a` (`extraction.py`); the strict-no-op behaviour above is a contract. Media resolution is live end-to-end: the orchestrator loads the media-map JSON itself (`sgs-clone-orchestrator.py`), threading the dict through `convert_section` → `build_block_markup` → `extract_content` → `extract_field_value` → `resolve_media_url` (`converter/services/lift_helpers.py::resolve_media_url`), so image srcs ARE remapped to uploaded WP URLs.
- **B2 — Scalar STYLING lift** (block has `scalar-styling-lift` capability) — the **CSS-on-content** route. For each attr with `role∈{color,typography}` + non-empty `derived_selector` + a non-NULL `css_property` (peeled longest-suffix vs `property_suffixes`), collect the matched element's CSS declarations and normalise per `css_property` (colour→token/hex, font-weight→numeric, font-size→raw or split+Unit companion). Implemented in `converter/resolvers/styling_content.py`. **STATE STYLING LIFTS.** Dropping state styling would break the universal "every element's CSS routes to its OWN attr" principle (§3.B.0) (R-31-9): a state-keyed attr (hover / persistent-selected — e.g. `hoverBackgroundColour`, `pillSelectedBgColour`) simply carries a state `derived_selector` and lifts that selector's declarations onto its own state attr, exactly like every non-state attr. **Do NOT introduce a state-selector exclusion.**
- **B3 — Child-block CONTENT resolution** (a composite block). For each content-leaf child element, resolve which child block it becomes: (1) `blocks.parent_block` forced-parentage (`sgs/accordion __item → sgs/accordion-item`) overriding the global alias; (2) else `slots.(aliases, standalone_block)`; (3) validate against `block_composition.accepts_allowed_blocks`, else a flagged GAP — never silent. Emit a child InnerBlock + recurse into its own content. (The Axis-3 child-routing; the token-match predicate, the recursion rule and the NULL-`accepts_allowed_blocks` case are defined in §13.3.)
- **B4 — Array / repeater** (`attr_type=array` — FR-31-2.5). Sibling-class DOM traversal of the array container; emit one child block per item; per-item attrs lift via B1's role-aware mechanism.

**The content fork (scalar-attr vs child-InnerBlock) is a source-derived per-attr `emit_shape` fact (FR-31-2.6) — NOT `equivalent_block_for`'s result.** For each `role=content` attr (FR-31-2.2 filter): resolve its IDENTITY (`equivalent_block_for` → `standalone_block`), read its `emit_shape` (`nested` → scalar/array lift per identity; `child` → child InnerBlock of the identity + recurse). The B1–B4 LIFT logic above (text / media / rating / array processing) is the per-identity processor; the per-attr `emit_shape` walk (§13.3 FR-31-2.6) chooses between B1 (leaf) and B3 (composite). `equivalent_block_for` is the IDENTITY resolver — never confused with the CSS layer fork nor with the nested-vs-child shape.

#### 3.B.0 — UNIVERSAL element extraction: ONE shared recognise→content→CSS machinery for EVERY element (load-bearing universal principle)

> **The recognise → extract-content → extract-CSS machinery is UNIVERSAL across EVERY element on the page, regardless of its OUTPUT form.** The block-vs-element fork (§3.B above) decides ONLY the DESTINATION; the recognition + content-value extraction + per-element CSS lift is the SAME shared mechanism whether the element becomes:
> - a standalone **section block**,
> - a **nested child block** (B3 — emitted as InnerBlocks),
> - a **BUILT-IN element / scalar attr** — the same content the block renders ITSELF instead of as a nested child block (e.g. a testimonial's avatar/quote, a card's built-in heading, an icon-list item's icon),
> - an **array-item field** (B4).
>
> The SAME draft `<h3>` / `<a>` / `<img>` / icon / `<span>` — by CONTEXT — becomes EITHER a nested child block OR a built-in scalar element OR an array-item field; but its content AND its CSS are recognised + lifted by the SAME shared extractors either way (**R-31-2:** tag is shape, context is meaning; the bare-tag→block/element map `html_tag_to_core_block` is that shape layer. **R-31-9:** one universal mechanism). Example: a `<p>` inside a `sgs/container` becomes a `sgs/text` child block; the SAME `<p>` inside a `sgs/button` is the button's built-in text element — different output, identical recognition+extraction.
>
> **Binding consequences:**
> 1. The **role-handler library** (the per-element value extractors: `text-content`, `image-object`, `rating`, `icon-slug`, `url-href`, `link-href`, `link-content`, `plain-integer`, …) MUST live in ONE shared module used by B1 / B2 / B3 / B4 + the atomic-tag swap.
>    - **`link-content` .** A role whose value is a CONCATENATED FRAGMENT of a URL the block assembles around it — not a whole href. `sgs/whatsapp-cta.phoneNumber` and `.message` are both fragments of the single `https://wa.me/<phone>?text=<message>` the block's own render builds (`whatsapp-cta/render.php`). Handled by the SAME shared entry point as every other role — `services/field_extractors.extract_field_value()`, which dispatches `role == "link-content"` to `extract_link_fragment()`. The block's captured URL template arrives as a **4th keyword-DEFAULTED parameter** (`link_template=`), so both call paths keep their 3 positional arguments — the shared signature is extended, not forked (R-31-9). The template itself is DB-declared: `block_attributes.output_signature`'s `link_template` key, read via `db_lookup.link_template_for()` (§4). **Fail-closed by design:** no captured template, no single `{value}` placeholder, a non-allowlisted scheme, or an href missing the template's literals ⇒ `None`, never a guessed fragment. **Why not `link-href`:** every other content-bearing role extracts a WHOLE value, so storing the assembled href in `phoneNumber` would have render.php re-prefix it (`https://wa.me/httpswame447700900123texthi`) — a corrupted phone number that still LOOKS like a successful clone. Two call sites, both in `walk.py`: NESTED leg 1b (the block's OWN root `<a href>`) and `_typed_value_for_role` (a link hanging off a BEM-tokened descendant). Building a handler block-private or array-private is an **R-31-9 violation to refactor into the shared library** — content extraction for a built-in element and for an array item is the SAME operation.
> 2. The shared **recognition primitives** (`icon_resolver.resolve_icon` for icon identity, `html_tag_to_core_block` for tag shape, `_safe_href` for hrefs, `lift_styling_content` for per-element CSS) MUST be reusable from EVERY extraction path. The `import_ban` gate's allowlist therefore extends beyond `db_lookup` to these shared recognition modules (`icon_resolver` etc.) — walling them off forces per-path duplication, the exact R-31-9 break this principle forbids.
>    - **Icon content resolves to one of `sgs/icon`'s FOUR real sources :** a **Lucide slug**, a **bare emoji glyph**, a **Dashicons name** (`dashicons-<name>` class), or a **WordPress-icon name** (explicit `data-wp-icon` / `wp-icon-<name>` marker) — via the shared `field_extractors.resolve_icon_kind(element)`. These are exactly `sgs/icon`'s `iconSource` enum in `block.json`: `lucide | wp-icon | dashicon | emoji`. There is **NO raw-svg source** — a raw `<svg>` the fingerprinter cannot map to a Lucide slug returns `(None, None)` and becomes a LOUD content gap upstream, never a silent default-star. A wp-icon authored as an inline `<svg>` from `@wordpress/icons` folds into `('lucide', slug)` via the shared fingerprint chain (visually identical). Emoji + all source detection live in this ONE shared resolver, so every icon path (leaf, array item, nested child) gets it uniformly — not a per-block case. A resolved icon sets its block's attrs by kind: `iconName`+`iconSource='lucide'`, `emojiChar`+`iconSource='emoji'`, `dashiconName`+`iconSource='dashicon'`, or `wpIconName`+`iconSource='wp-icon'` (each guarded on the block declaring that attr).
>    - **The named-leaf arm (`run_mechanism_leaf`) covers the icon-source role, not only text/image/link .** An **icon-source leaf** — a leaf block DECLARING an icon-source attr (`emojiChar`/`iconName`/`dashiconName`/`wpIconName`, e.g. `sgs/icon`, whose `primary_content_attr` is NULL) — routes through the named-leaf arm (DB signal = the block declares an icon-source attr, a self-sufficient schema fact, never a slug literal, and NOT the broader `identity` role, which `sgs/button` carries WITHOUT any icon-source attr), where the icon arm lifts its icon via `resolve_icon_kind`. Without this, an icon leaf child (e.g. an info-box's first child) would emit EMPTY. An icon-source leaf whose draft icon resolves to no supported source emits a LOUD gap (even when a link on the same leaf was lifted). Decorative leaves (no primary + no icon source) still fall through to the Case-4 loud gap.
> 3. **CSS follows content at EVERY granularity** (§3 unification): every recognised element — built-in, nested-block, or array-item — carries its own typography/colour/box CSS that the per-element styling-lift (B2 `lift_styling_content`) must transfer. Array items get the same per-item CSS lift after their content. This is not array-specific — it is the universal per-element content+CSS pairing.

### 3.A — CSS branch
For each draft CSS declaration `(css_property, value)` resolved for an element at a given tier:

1. **Detect the LAYER** (L1–L4) by CSS signature + structural position (§2 Axis 1). Never the class name. **Structural-position guard:** a layer detector that sees only CSS declarations cannot tell whether the node is the section ROOT or an inner band — a section-root that legitimately declares `max-width:1200px;margin:0 auto` would misroute its `max-width` to `contentWidth` instead of the OUTER `maxWidth`. The detector MUST be passed (and enforce) the node's structural position: **CONTENT-WIDTH (L2) detection fires ONLY on a non-root, direct-descendant inner element.** This precondition is a build requirement, not an assumption — document it at the detector + add a guard that rejects a root node.
2. **Resolve the destination attr** via a per-block lookup `(block_slug, layer, css_property) → attr_name` (`db.attr_for_layer_property` / `attr_for_area_property`). The declarative routing columns on `block_attributes` — `css_property`, `css_layer`, plus `css_element`/`css_state`/`css_tier` — are seeded and load-bearing (`css_property` is populated on a large minority of rows — **query `/sgs-db` for the live count, never cache one here**); `css_element`/`css_state`/`css_tier` drive `db_lookup.py::_base_domain_attrs_for_css_property`. The resolver keys on the base domain (`css_element IN ('','root','self')`, `css_tier IN (NULL,'desktop')`, `css_state IS NULL`) and fails loud (`AmbiguousCssPropAttrError`) on a genuine multi-candidate tie rather than rowid-picking. The fallback for attrs without seeded declarative columns **name-builds** the candidate attr from a **CLOSED 3-prefix vocabulary** (`''` OUTER / `content` / `gridItem`; `root_supports.py`, `db_lookup.py::attr_for_layer_property`) concatenated with the `property_suffixes.suffix`, then **DB-existence-checks** the built name against `block_attributes` before accepting it; the seeded-column path is primary for css_property-carrying attrs.
   - **OUTER declarative fallback .** The OUTER name-build capitalises the suffix (OUTER prefix is `''`) → `BackgroundColour`/`BorderColour`/`BorderWidth`/`BorderStyle`, which the DB-existence check MISSES for a block whose attrs are camelCase (`backgroundColour`/`borderColour`/…) — so `attr_for_layer_property('sgs/text','',prop)` returns None and the property would gap, even though `attr_for_property(block, css_property)` (the css_property/declarative route) resolves it correctly. `services/attr_resolve.attr_resolve` therefore FALLS BACK to `attr_for_property` **only when** (a) the layer name-build returned None, (b) `layer == 'OUTER'`, and (c) the fallback's resolved attr actually exists on the block (`block_attrs`). Strictly additive (zero→one, never one-of-two): it cannot change any property that already resolved, so no regression to blocks whose name-build hits. Universal + DB-driven, no slug literal (R-31-1/R-31-9). This is what lets a block's colour/border CUSTOM attrs (used when native `color`/`__experimentalBorder.width/color` support is off — e.g. `sgs/text`) receive the draft's OUTER background/border. `services/root_supports.expand_background_border_shorthand` is shared + also run on `css_pass`'s own decl copy so a native-support-REJECTED longhand still reaches this dispatch instead of being silently stripped.
3. **Disambiguate** where one css_property maps to multiple suffixes (the completeness audit's bite-list). **Ambiguity handling:** `attr_for_layer_property` never rowid-picks; when ≥2 candidate attrs exist for one (block, layer, property) it raises `AmbiguousLayerAttrError`/`AmbiguousCssPropAttrError` (`db_lookup.py::attr_for_layer_property`), and the base-resolver-domain columns (`css_element`/`css_state`/`css_tier`) are the disambiguation key.
   - `max-width` → **by LAYER:** L1 OUTER → `maxWidth` (literal) when present, else nothing is emitted (§2.9 Axis 1); L2 band → `contentWidth` (token or literal). The OUTER never snaps to a token. Resolve by LAYER (structurally guarded per step 1) + the ambiguity handling above.
   - `align-items` → `AlignItems` vs **`VerticalAlign`** — **LOCKED** (memory `converter-attr-must-match-the-attr-render-reads`): container-wrapper blocks render `verticalAlign`, so target `VerticalAlign` for them.
   - `box-shadow` → `Shadow`(role=color) vs `BoxShadow`(role=visual): `converter/resolvers/outer_box.py` resolves `box-shadow` → the block's `shadow` attr (DB-first: Shadow row wins over BoxShadow by rowid) via a token-snap to `design_tokens` shadow presets (sm/md/lg/glow); a raw box-shadow with no matching preset emits an honest `NO_DESTINATION` gap.
   - colour/bg/border-radius spelling aliases → pick the attr the **target block actually declares** (`block_attributes`).
3b. **Object-shape routing (box-object interface contract, FR-31-22).** When the resolved destination attr carries a DB `box_family` value (§4), the CSS branch does NOT write one Decl → one flat attr. It **accumulates** the 4 side-Decls (or 4 corner-Decls) for that `(block, box_family, tier)` into ONE object Write — `paddingTablet = {"top":"10px","right":"20px","bottom":"10px","left":"20px"}` (omit absent sides) — because the converter is otherwise strictly one-Decl→one-Write, and an object destination needs a cross-declaration accumulator (the engineering seam lives in `resolvers/outer_box.py` + `resolvers/content_band.py` + `services/fold_helpers.py`'s shorthand-expansion + `services/css_pass.py`'s per-property consumed-partition, which must mark all 4 sides consumed per tier for the object path). Root padding/margin/border-radius continue routing to the WP-native `style.spacing.*`/`style.border.radius` object (already object-shaped) — object-shape routing there is a passthrough, not new work. **Migration-safety discriminator:** an attr is a legitimate merge/migration TARGET only if (a) it (or the flat attr it replaces) carries a DB `box_family` value, AND (b) for the CSS-signature path, it round-trips through `attr_for_layer_property`'s closed-vocab generator (step 2) — this EXCLUDES `role='layout'` element-selector attrs (the 5 single-side element-margins) and `shapeDivider*` (zero converter references) from ever being treated as merge candidates, even accidentally. The migration/seed script MUST filter on `box_family`, never a name regex (`.*Top$|.*Bottom$|.*TL$` is the anti-pattern this rule exists to prevent) — enforced by the static AST collision gate (§13.4 FR-31-22.2): it FAILS the build if any per-side/per-corner grouping or migration operation runs without a `box_family` DB check in its call path, and is plant-tested to fire on a planted name-regex merge while staying silent on the correct `box_family`-gated one.
4. **Resolve the TIER attr.** Tier siblings (`…Mobile/…Tablet/…Desktop`) have **NULL `canonical_slot`/`role`** and `is_responsive` is unreliable. So: resolve the BASE attr via slot/role, then **re-append the breakpoint modifier suffix** from `modifier_suffixes(kind='breakpoint')`. Never slot-lookup a tier attr directly.
4a. **Resolve the STATE attr (universal hover).** An interaction-state (`:hover`/`:focus`/`:active`) declaration routes IDENTICALLY to a tier — resolve the base attr, then **re-append the state modifier suffix** from `modifier_suffixes(kind='state')` (`Hover`/`Focus`/`Active`), AFTER any tier suffix (v1 hover is base-tier only). No `property_suffixes` derivation; the recognition signal is simply whether the block DECLARES the `{attr}{State}` companion (`block_attributes`, from block.json source) — else an honest gap (R-31-9). State declarations are collected by `collect_state_decls_for_element` (styling_helpers), which reuses the base matcher on a per-state pseudo-STRIPPED copy of the rules, so a `:hover` decl is structurally isolated from the resting base and can never leak into it. Carried by BOTH families: `css_pass` (the node's own CSS) + `styling_content` (derived-selector-matched element). Hover attr naming is standardised to the suffix form `{base}Hover` (matching the tier grammar) so routing needs zero per-convention code. Note: §3.B B2's `derived_selector` state-lift only ever resolves persistent `--active`/`--selected` classes (its hover selectors are synthetic placeholders that never exist in real markup) — genuine `:hover` is resolved by THIS mechanism, not B2. **Per-ELEMENT (non-root) extension:** the base state resolver `attr_for_state_property` restricts to `css_element IN ('',root,self)`, so a `:hover` transform/filter on a NAMED CHILD element (post-grid `scaleHover` on `card`; `imageZoomHover` on `image` across card-grid/gallery/team-member/post-grid) needs its own route. `styling_content.lift_per_element_state` (driven by `db_lookup.per_element_state_attrs`) is the per-child SIBLING of the base state-lift: same `collect_state_decls_for_element` isolation, gated on the transform/filter parser set, child resolved by its stored `derived_selector` else the synthesised `.sgs-<short>__<element>` BEM class — ONE universal mechanism landing every such attr, disjoint from base (no double-emit), no slug literal. Reduced-motion (Spec 35 E5) stays the block's render responsibility.
5. **Parse + serialise** the value by `property_suffixes.kind_override` (`number_unitless`/`number_px_or_em`/`string`) + `block_attributes.attr_type`. (Family B = the `unitless` sentinel must round-trip and be stripped at render — verify render.php.)
6. **Token-snap** when `property_suffixes.is_token_matched=1`: snap to the nearest `design_tokens.css_var` (ΔE≤1 / ≤1px) else keep literal + log gap. Per-client divergences only emit as raw instance values (FR-26-C6); repeated values are candidates for derived globals (deferred).
   - **Slug-validation on a colour `var()` .** When resolving a draft `var(--X)` colour, `styling_helpers.extract_token_or_hex` emits a bare token slug **only when** it is (a) an explicit `var(--wp--preset--color--X)` reference, or (b) a `var(--X)` whose `X` (after draft-`:root`→theme-palette snap) is a REAL theme-palette slug (`_theme_palette_slugs()`). Any other bare draft var falls through to the concrete hex / rgb / honest gap — it MUST NOT emit the raw capture `X` as if it were a slug, because `sgs_colour_value('X')` → `var(--wp--preset--color--X)`, and an undefined preset var falls to `currentColor` (dark). The same guarantee holds on the WP-native border-color path and the custom-attr colour path (`backgroundColour`/`borderColour`). Example: draft `--border:#E8D5C0` snaps to `border-subtle`; an unmapped var gaps honestly rather than painting dark.
   - **Cross-reference — bootstrap dependency on Spec 33 .** The theme-palette this step exact-hex-snaps a draft colour against (`settings.color.palette`) is GENERATED, not hand-authored: the Spec 33 draft global-styles extractor (`plugins/sgs-blocks/scripts/theme-extractor/`) measures the draft's rendered computed styles and writes `sites/<client>/theme-snapshot.json`, which this step's palette load reads (`styling_helpers.py::_load_theme_palette_map`). The extractor MUST run and validate for the current draft BEFORE conversion — enforced fail-closed by FR-33-12 (Spec 33, `.claude/specs/33-DRAFT-GLOBAL-STYLES-EXTRACTOR.md`).
7. **Validate** against `block_attributes.enum_values` (reject `contentWidth='banana'`) and `block_supports` (gate L1 full-bleed on the block declaring `align:["full"]`).
8. **No destination?** → log to the in-memory honest-gap ledger (in-memory tracking; there is no DB-backed gap-candidate table). NEVER silent-drop, NEVER emit as inline `@media` (responsive values go to tier attrs — §3 F-fork), NEVER fall to D2 scoped CSS when a D1 attr destination exists (R-31-15c).

### Responsive: device-tier vs visual breakpoint (the F-fork)
- **Device-tier system** = the SGS Mobile/Tablet/Desktop attrs, rendered by the wrapper + mapped by the converter, fixed at **768/1024**. ONE vocabulary: delete the parallel hardcoded `_GRID_TABLET_BP`/`_GRID_DESKTOP_BP` constants; route grid through the same `db.breakpoint_suffix_rules()` every other lift path uses.
- **Arbitrary visual breakpoint** = a single draft rule at 600/640/781 for a design reason. **These are DISTINCT and must NOT be coerced into a device tier.** Family F is the converter *remapping* a draft 640 onto 768 — the forbidden conflation.
- **Resolution — F-ii (preserve), Bean-mandated; per FR-31-5.2:** map draft `@media` thresholds that ARE device-tier values (767/768/1023/1024) to the tier attrs; **faithfully preserve** any non-device-tier threshold as a raw uid-scoped rule (passthrough) — **never snap, never drop**. **WHOLE-TIER FOLDING + `sgsCustomCss` residual passthrough (§13.4 FR-31-5.2):** `collect_css_decls_for_element` computes each tier's effective value by folding base + every `@media` rule that applies across the tier's ENTIRE `[lo, hi]` range (`db_lookup.device_tier_ranges`). A non-device threshold that splits a tier is captured as a `ResidualBand` and routed to the owning block's `sgsCustomCss` (Additional-CSS) field via the `&selector` convention — the client-editable, STOP-52-compliant destination. **Render-precedence + bounding:** the residual is (1) BOUNDED to the device tier its threshold falls inside (symmetric min/max — so it never bleeds into an adjacent tier), (2) relies on whole-tier FOLDING to carry a value up through an unset tier, (3) emitted at EQUAL class-level specificity + APPENDED LAST so it wins by source order (NOT an ID — the WP-6.6 / Kadence / Spectra / GenerateBlocks idiom; ID/`!important` escalation is the banned anti-pattern), and (4) every block's per-instance styling is normalised to one class-level specificity. Full architecture in §13.4 FR-31-5.2. Open: a NO-WIDTH media condition (`@media print`/`prefers-color-scheme`/`orientation`) still folds into the screen base; overlapping residual bands resolve by emission order.

## 5. Coverage matrix — the completeness instrument

The matrix is the artefact that makes "everything accounted for" measurable. **§12.2.1's draft-derived CSS Accounting Ledger is the PRIMARY completeness instrument — the matrix only sees cells it already knows about (it cannot see the ~15 no-suffix-row property classes), whereas the ledger accounts for the whole draft declaration stream. The matrix is a secondary validation/dashboard, not the completeness gate.** **Rows** = every container-bearing block (the composites + `sgs/container` + `sgs/media`). **Columns** = every capability × layer × tier × child-shape destination. **The matrix MUST be an auto-generated artefact (`generate-coverage-matrix.py`)** — rows enumerated from `block_composition`, columns from the DB — so it can never silently under-count. **BUILT** in `scripts/coverage-matrix/`; the COVERED/CHEAT classification is **PARTIAL** — pending the F3-RUNTIME LANDED leg.

For each cell the state is one of:
- **COVERED** — a draft value for this (block, layer, property, tier) round-trips to the live clone via the universal path, live-verified per §7b (element present, draft value ≠ wrapper default).
- **GAP** — no destination attr or no property_suffixes row (→ seed via the canonical path; tracked in the in-memory ledger).
- **BLOCKED** — destination attr exists but is unreachable on a real clone until a sibling phase lands (e.g. L4 per-area + scalar composite attrs are unreachable until Method-2 routes sections to native composites — see §6 goal 7).
- **UNVERIFIED** — not live-probed on a fixture that actually exercises it (block absent from the canary, or only tested where the draft value equals the default). NOT the same as COVERED.
- **CHEAT** — the cell "passes" only via a forbidden mechanism. **CHEAT is classified from the §7a gate OUTPUT, not human/LLM judgment** — a cell is CHEAT iff a gate flagged the mechanism that produced its value (per-block branch / hardcoded dict / `!important` / mirror-emit / D2-when-D1). This removes a gameable judgment call. **A CHEAT cell scores ZERO**, never partial — this is what stops score inflation.
- **N/A** — the KIND doesn't expose this layer (e.g. grid on a content-KIND block).

**Completion = every non-N/A cell is COVERED or explicitly BLOCKED-with-sibling-phase, with zero CHEAT cells, zero UNVERIFIED cells, and the open GAP set explicitly listed** (each GAP either fixed or logged with a reason).

### Known property GAPs to seed (from the live ledger + audit)
HIGH-impact missing `property_suffixes` rows the container/grid system needs: `order`, `grid-area`, `grid-template-areas`, `grid-row`, `grid-column`, `overflow`(+x/y), `object-fit`, `object-position`, `position`/`inset`/`top`/`right`/`bottom`/`left`/`z-index`, `background-size`/`-position`/`-repeat`/`-attachment`, `flex` shorthand, `aspect-ratio`. Each seeds via block.json `supports.sgs` OR a `migrations/*.py` row + a full `/sgs-update` reseed — **never a code branch, never a manual DB edit**.

**ALL LISTED PROPERTIES ARE SEEDED** (`migrations/2026-06-30-property-suffixes-grid-position-bg-flex.py`: 20 `property_suffixes` rows; role `'position'` + `CssPosition` suffix for the inset/top/right/bottom/left/z-index family). ## 7. Anti-cheat detection — making cheats impossible to hide

Bean's core requirement: a cheat must be **structurally obvious**, not score-inflating. Two complementary defences.

### 7a. Cheat-detection gate — `scripts/cheat-gate/` (Python not JS)

The gate is the `plugins/sgs-blocks/scripts/cheat-gate/` PACKAGE — `run.py` plus the `check_*.py` modules — wired into `plugins/sgs-blocks/scripts/gates.json` as `cheat-gate-run`. There is no single `check-converter-cheats.py` file.
Naive grep signatures have HIGH-severity bypasses, so the gate is a **Python script that queries the DB**, scans the WHOLE `orchestrator/` tree (not one function), and **scans the PHP/CSS render surface, not just converter output**. It fails the build on any of:

1. **Per-block literal — WHOLE-tree + indirect forms.** Not just `if slug == 'sgs/`. Scan every `.py` under `orchestrator/` for: `slug ==`/`slug in`/`slug.startswith('sgs/`/`.get(slug)` against slug strings; dict/`frozenset`/`set`/`list` literals whose keys/members match `"sgs/[a-z-]+"`. Allowlist carries **function scope**.
2. **Hardcoded property→attr dict — R-31-1.** No `_SUFFIX_ATTR_OVERRIDES`- or `prop_map`-shaped dict in the converter; property→attr routing is DB-sourced (`check_hardcoded_dicts.py`).
3. **`!important` over a faithful property — scan PHP/CSS, NOT converter output.** The converter already strips `!important` (`_strip_important`), so the real cheat lives in `class-sgs-container-wrapper.php` + block `style.css`/`editor.css`. The gate queries `property_suffixes.css_property`, then greps those render files for `<prop>...!important`. `check_important_render.py` is SELECTOR-AWARE — it skips variant-scoped or state-scoped `!important` rules (selectors containing `--modifier` or `:pseudo`-class variants) and only flags base-selector `!important`. This removes false positives on legitimate modifier/state overrides while still catching the real cheat pattern.
4. **Parallel breakpoint vocabulary — numeric-literal scan + dict-ban.** Ban integer literals 640–1100 in the converter outside a `db.breakpoint_suffix_rules()` call (a name-scan misses coincidental literals); AND no in-code breakpoint-suffix map — it must derive from `modifier_suffixes`.
5. **Mirror-emit / `sourceMode='bound'` / BEM-element className — gate wired.** `check_no_mirror.py` auto-runs post-clone via the orchestrator (after `stage_9_report()`, pre-deploy) and HARD-HALTS on a NEW mirror violation; existing violations are grandfathered via `orchestrator/check-no-mirror-baseline.json`. A commit-time static `sourceMode='bound'` AST tripwire (`scripts/cheat-gate/check_bound_emit.py`) also runs.
6. **D2-when-D1-exists — DB cross-join at pipeline close, not grep.** A Python check at pipeline end: for each property stranded in `variation-d0-d2.css`, query `property_suffixes`+`block_attributes`; if a D1 destination exists for that (block, property), FAIL.
7. **Sentinel leakage.** Scan emitted block attrs for the literal `"unitless"` (and any parse sentinel) AND scan the live rendered DOM. Family B's render-side strip must be confirmed per block.

### 7b. The structural-insufficiency rule (R-31-11 + R-31-13 — load-bearing)
**Rendered-DOM structural parity is necessary but NOT sufficient as a closing gate** — a faithful *mirror* (the cheat) satisfies structural parity by construction, so structure-match alone would pass the very cheat the rules ban. Therefore:
- the **closing gate is the live-homepage per-section visual check vs the DRAFT** (R-31-11: compare to ground truth, not internal tree shape) **+ Bean's co-authoritative eye** (R-31-13).
- **The canonical automated fidelity instrument is [Spec 20 — Clone Fidelity Measurement (computed-parity)](20-CLONE-FIDELITY-MEASUREMENT.md)** — the tool `plugins/sgs-blocks/scripts/parity/computed-parity.js`, run as pipeline Stage 11.6, compares the EFFECTIVE (computed) value on each rendered element matched by CONTENT (CLAUDE.md rule 4a / STOP-42). It is universal/draft-agnostic. It PAIRS with Bean's eye; the number alone does not close (Spec 20 §FR-20-7).
- internal metrics (emit-green, conformance-green, "mechanism fires", aggregate parity %) are **progress signals, never closing gates**. A cell is COVERED only when a live computed-style read equals the draft.
- Input-side counts (`leftover-buckets.json`, a debug aid) are NOT a per-clone fidelity signal (Spec 20 §FR-20-7). The rendered signal is Stage 11.6. The "honest gap" concept lives in the in-memory ledger.

**Three live-probe false-win guards the closing gate MUST add:**
- **Empty-section false-win** (known trap): an empty/soft-failed section contributes no DOM, so a computed-style probe trivially "matches". Gate every probe on `el.innerText.length > 0` (and element-present) FIRST — a missing element is a FAIL, never a match.
- **Single-canary blind spot**: one live page (the Mama's homepage) does NOT contain every block × variant (tabs, accordion, gallery, the `sgs/media` image family E may be absent). A single-page match does NOT prove the universal engine. The coverage matrix's live-verify must run across **a fixture set that exercises every block × variant × layer**, not one page — blocks absent from any live page are `UNVERIFIED`, never `COVERED`.
- **Coincidental-default match**: a clone value can match the draft because the wrapper's hardcoded default happens to equal it (transfer never tested). Each COVERED cell must be verified on a section whose draft value **differs from the wrapper default** — otherwise the cell is `UNVERIFIED`.

## 11. Build strategy — STAGE-BY-STAGE, no deferrals

The build is sequenced by **pipeline STAGE, not by route**. Rationale: building one route at a time bakes in route-specific decisions that harm other routes and forces countless rebuilds + hides cheats. Instead:

1. **Start at the pipeline's beginning.** Take the first stage; make it handle **every** block, variable, and possible outcome universally — proven reachable via the logic + DB-data matching, and cheat-checked by the §7 gates — *before* touching the next stage. Example: recognition + routing for ALL blocks (including composite/native routing) is completed and proven universal at its stage before any CSS-lift stage begins.
2. **Universality is proven per stage**, not per route — so progress can't be undone by a later route's needs.
3. **No "later phase" deferrals** — every routing choice that a stage owns is decided when that stage is built, with all routes in view.

**Prerequisite to ALL building: the exhaustive pipeline routing/logic HTML chart** (`.claude/reports/pipeline-routing-map-2026-06-17.html`). It maps the WHOLE pipeline start→every finish point: every routing choice, branch/if, DB table/column check, and terminal outcome, with an explanation of each. The chart is the ground truth the stage-by-stage build is sequenced against and checked for completeness against. Building begins only after the chart proves every stage's every-route reachability.

## 12. Clean modular architecture — authoritative build direction


### 12.0 Locked decisions
- **CLEAN MODULAR ARCHITECTURE, not spot-fixes.** Mama's=100% is a METRIC of pipeline effectiveness, not the goal. The holes are systemic (sgs/container, composites with scalar/child elements, blocks with child blocks), not hero-only; a fix that works for one block does not generalise and can regress others.
- **MODULAR FILE ARCHITECTURE.** The converter is split into per-resolver files dispatched by branch logic. Rationale: in giant scripts, functions/cheats/DB-calls get missed by humans AND subagents; small single-purpose files = locatable failures, visible cheats, wirable gates.
- **STAGE-BY-STAGE = BUILD ORDER + per-stage universality test.** Build + test each pipeline stage is universal across ALL block-shapes; do not start stage N+1 until stage N passes; if stage 4 fails, only stage 4 needs fixing. Never build on a flawed lower stage. Stage-by-stage is the build ORDER; the draft-derived ledger + render-oracle (12.2) is the cross-stage TEST that gates each stage's universality claim. A stage passes only when its declarations are end-to-end accounted on a multi-shape fixture set.

### 12.2 TIER-1 FOUNDATION — the spine, in place before any stage rebuild
The build does not start a pipeline stage until this foundation exists and is armed.

1. **Draft-derived CSS Accounting Ledger (the keystone).** `declare_input` = the draft's parsed `(selector, property, value)` stream captured at Stage 0.7 BEFORE any routing — NOT the converter's recognised set / the `property_suffixes` table. `UNACCOUNTED = draft_decls − (transferred ∪ excluded-with-reason ∪ gap)`. Any UNACCOUNTED = hard fail. This is what makes the no-suffix-row classes (background-image, filter, opacity, transform, object-fit, pseudo-elements, font shorthand) impossible to silently drop. It is the primary completeness instrument — the §5 matrix only sees cells it knows about; the ledger sees the whole draft. **Content-conservation ledger:** `ledger/content_coverage_check.py` (+ its baseline, wired into the gate chain) accounts for CONTENT routing units so a dropped scalar content node is UNACCOUNTED, not silent; the lift itself stays a strict no-op (§3.B1) — completeness is caught by this ONE ledger, never by a second per-attr tracker.
2. **WRITTEN vs LANDED.** WRITTEN = attr emitted (progress signal, never a gate). LANDED = live computed-style on a NON-DEFAULT fixture equals the draft (the only "done"). WRITTEN-not-LANDED count >0 = hard fail (catches wrong-layer transfer in the ledger, not the eye).
3. **Differential render-oracle + metamorphic relations.** Render-diff oracle (DIAGNOSTIC — the closing gate is computed-style-vs-draft per R-31-4 / §7b): render the DRAFT and render the CLONE, pixel-diff the two renders at 375/768/1440 per section (the draft is its own exact non-circular oracle). Plus metamorphic tests: source-order permutation → identical output; BEM-synonym rename → identical output (tests name-free routing); px-scaling by k → all transferred values scale by k.
4. **Closed, audited EXCLUDED set.** `excluded_properties(css_property, reason, decided_by, date)` DB table; a gate fails the build on any in-code exclusion literal or any growth without a migration+reason. Excluded-from-lift ≠ excluded-from-clone (must still D2-passthrough for fidelity).
5. **Gates EXIST + WIRED as prerequisites.** The cheat gate (`plugins/sgs-blocks/scripts/cheat-gate/`, §7a), `generate-coverage-matrix.py` and the ledger pipeline-close check exist; `check_no_mirror.py --enforce` and the cheat gate are wired into `package.json prebuild`; a `PreToolUse` git-commit hook (`.claude/hooks/f5-commit-gate.py` + `.githooks/pre-commit`) closes the commit-without-build bypass. Failure messages are plain English for a non-coder QC owner. BUILT — see the §12.7 F5 row.
6. **The ledger is the build spine.** A stage is "done" only when, for the declaration classes it owns, the end-to-end ledger shows zero UNACCOUNTED AND zero WRITTEN-not-LANDED on the multi-shape fixture set — not an in-stage conformance suite, not a single page alone.

### 13.2 Recognition + the single-recursive walker contract (FR-31-1 / FR-31-3 / FR-31-16 / FR-31-15)

- **FR-31-1 — BEM recognition.** The walker reads the `class` attr, parses BEM, and resolves a block slug via the DB (`slots scope='element'`, `blocks`). No hardcoded class→block dict (R-31-1); the HTML tag is shape only (R-31-2).
- **FR-31-3 — exactly three permitted walker exceptions.** The walker is ONE recursive function whose only branching surface is three conditionals: **(1)** atomic-tag swap (`not sgs_classes and node.name in atomic_tag_map`); **(2)** chrome-skip at top level (`is_top_level and node.name in SKIP_TOP_LEVEL_TAGS`); **(3)** top-level container wrap (`is_top_level and resolved_slug != 'sgs/container'`). All other divergence comes from DB row variation, never code. A 4th branch fails the contract (R-31-3).
- **FR-31-4 — section base is always `sgs/container`** — the load-bearing DEFAULT (see the **DEFAULT-IS-CONTAINER** box in §12.6): a top-level class-section emits `sgs/container` with its children recursed, UNLESS its root class is registered `blocks.tier='class-section'` (hero, cta-section, trust-bar), which returns from the voter at confidence 1.0 and emits its composite directly. A no-name-match section is the COMMON case, never a failure. **FR-31-4.1** is the universal fold/recurse procedure, in precedence order: block-match wins → a direct-descendant slug-None wrapper FOLDS its CSS into the container (grid/flex descendant → the container absorbs the layout, its items become grid items) → a block-resolved direct-descendant becomes its block (and IS the grid item) → a non-direct wrapper gets its own `sgs/container` → a text-only sgs-classed leaf becomes a CONTENT block (text-capable target), NEVER a `sgs/container` wrapping raw text (which fails block validation).
- **Classless boundary.** A top-level boundary with ZERO BEM classes takes the FR-31-4 container default (it does not stay `unrecognised`): `converter/recognition.py::recognise_section` takes an `is_boundary_root` parameter (default `False`, preserving the FR-31-11 pass-through behaviour for a nested classless node inside an already-recognised composite); only the boundary's own top-level root passes `True`.
- **FR-31-16 — voter tier-driven recognition.** Recognition consults `blocks.tier='class-section'` (a DB signal, not a slug literal) via `is_class_section_block()`; class-section blocks emit their composite, all others fall to the FR-31-4 default.
- **FR-31-15 — multi-root disambiguation: dedupe, then LOUD.** When one node carries ≥2 bare block-root classes, the candidates are first DEDUPED (a bare class and its own `--modifier` class parse to the same block — not ambiguity). A residual tie between DISTINCT blocks is a draft-authoring ambiguity: the resolver goes LOUD (`bem_resolve_ambiguous_loud` trace) and returns no match, so the node falls to the FR-31-4 container-default/pass-through path — the correct response is to fix the draft or strengthen the intended block's recognition data, never a silent rank.

- **FR-31-11 — non-sgs pass-through.** A DOM node with NO `sgs-` classes (not an atomic-tag swap) emits NO block of its own: its children recurse into the nearest emitting ancestor's InnerBlocks, any non-sgs classes are preserved on that ancestor, at unlimited depth. Preserving a draft BEM *element* class on an emitted block is a LAST-RESORT only and MUST raise a FAIL-able warning when the node's CSS could not be lifted (R-31-15(a)) — never the success path.
- **FR-31-12 — Stage-2 artefact preservation.** Stage 2 writes a `stage-2.json` entry for EVERY section boundary even when the BEM resolves unambiguously (so a recognition decision is never silently un-recorded). PASS: every section in `extract.json` has a `stage-2.json` entry. (Artefact catalogue: Spec 20 — Spec 21 was archived into it.)

### 13.3 The content fork — scalar attr vs child block (FR-31-2 family; canonical mechanism)

This is the **single authoritative content fork** for §3.B.

> **The nested-vs-child decision is FR-31-2.6's `emit_shape`, not `equivalent_block_for`'s NULL/non-NULL result.** Three roles split cleanly: **`role`** = the content-vs-styling FILTER (does this attr represent content at all); **`equivalent_block_for`** = the universal FUNCTIONAL IDENTITY (what KIND of content — text/heading/media/button — via `canonical_slot → slots.standalone_block`, so a block-inconsistent attr name anchors to ONE identity); **`emit_shape`** = the nested-vs-child decision (a source-derived per-attr fact, FR-31-2.6). FR-31-2/2.2 below are read through this split. FR-31-2.1/2.1a/2.5/2.5a (identity derivation, ownership-from-code, array schema) stand as written.

- **FR-31-2 — every content attr has a universal functional IDENTITY; the nested-vs-child shape is a SEPARATE source-derived fact (FR-31-2.6).** `equivalent_block_for(parent, attr)` resolves the attr's **identity** (`canonical_slot → slots.standalone_block`): e.g. product-card `description`→`sgs/text`, hero `headline`→`sgs/heading`, `price`→`sgs/text`, `link`→`sgs/button`. This is the processing anchor — text-identity → rich-text lift, media-identity → image lift, button-identity → link lift — used whether the attr emits nested OR as a child block. The SAME `equivalent_block_for` is the only identity call-site for BOTH the CSS-D1 child-attribution (FR-31-5) and the content walk — one authoritative implementation in `db_lookup.py`. It is an IDENTITY resolver, NOT the nested-vs-child fork.
- **FR-31-2.1 — two-tier derivation** (the G1 token-match predicate): **Tier A** = direct join on `canonical_slot` + `role` + `attr_type`; **Tier B** = BEM-element segment from `derived_selector` (strip the `sgs/<parent>-` prefix so `accordion-item` matches `__item`).
- **FR-31-2.1a — PARTIAL: known-open violation + sequenced closure (do NOT flip the reader in one shot).** The seeder `behavioural-analyser/assign-canonical.py::detect_role_from_block_json` still derives `role` from an attr-NAME regex (`_ATTR_NAME_RULES`) and IGNORES the authored `"role"` key in block.json — the name-parsing this FR forbids. It is INERT: the name-regex currently produces CORRECT roles (the "danger" attrs are correctly upgraded from the bulk marker to their specific role). A NAIVE "read the declaration first" fix REGRESSES load-bearing attrs, because **every top-level declaration is the identical bulk value `"role": "content"`** — the generic catch-all the pipeline deliberately UPGRADES AWAY FROM (`assign-canonical.py`); reading it first would make `sgs/button.url` (`link-href`) take the button's LABEL TEXT as its href, and break `sgs/media.imageUrl`/`imageAlt`. **⛔ CRITICAL — the block.json `"role": "content"` key is WP 7.0's `contentOnly` PATTERN-EDITABILITY marker (WP core's own attribute property; see parking `P-WP7-PLATFORM-ALIGNMENT` item 1), NOT the converter's role vocabulary. An attr WITHOUT `"role": "content"` becomes non-editable inside a WP 7.0 pattern → locks client editing. So the DANGER attrs MUST keep `"role": "content"` — do NOT change it to `link-href`/`image-object` (that breaks client pattern-editing). The converter's `link-href`/`image-object`/`image-alt` values are SGS-DB-only; the two vocabularies merely collide on the key name `role`.** The FR-31-2.1a-compliant closure therefore reads the converter role from a SEPARATE, SGS-OWNED declaration channel that does not collide with WP core's `role` — exactly as array-item fields already do (`block.json items.properties.<field>.role`, an SGS namespace, FR-31-2.5). Sequenced, gated by `scripts/audit-declared-vs-seeded-roles.py` (measures the WP-core-vs-SGS-derived gap; run it for the live AGREE/NULL/BENIGN/DANGER split): **(1)** add an SGS-owned per-attr role channel (e.g. `supports.sgs.attrRoles: {url:"link-href", imageUrl:"image-object", …}`) declaring the SPECIFIC converter role — WP core's `"role":"content"` stays untouched; **(2)** the seeder reads that channel COLUMN-FIRST-ELSE-name-regex-fallback + wire an audit `--check` to prebuild; **(3)** ONLY once every derived role is declared there + the audit proves the SGS channel == the seeded role, DELETE `_ATTR_NAME_RULES`, verified live (R-31-11). Parking: `P-FR-31-2.1A-CLOSURE`. Fixes made through the FR-blessed `ATTR_CLASSIFICATION_OVERRIDES` channel do NOT close this — the regex tier survives. **FR-31-2.1a below is the target end-state, not a description of current behaviour.**
- **FR-31-2.1a — attr/field → (role, element) ownership comes from the CODE or an explicit DECLARATION, never from parsing the identifier name.** An attribute's owning element is stated three times in the block's own source — `render.php` applies the attr to a specific element, `edit.js` groups its control under that element's `PanelBody`, `style.css` selects it — so it must be READ from there (or declared), not reverse-engineered from the attr name. Name-parsing (peel-suffix → last-camelCase-segment → global-slot lookup) is rejected: it both mis-guesses the element (`titleColour`'s real element is `__name`, not the name-formula `__heading`) and over-resolves bare boolean/state attrs (`showIcon`→icon, `isLink`→link) whose last segment coincidentally matches a slot. Concretely:
  - **Top-level attr → element/selector:** this is `assign-canonical.py`'s `derived_selector`. Do not use the `fingerprints.json`/`tools/recogniser` builder — the engine does not recognise through it. When a top-level style attr's selector is wrong/NULL, fix it via `ATTR_CLASSIFICATION_OVERRIDES` (the live Stage-1 sub-step C) or by reading the block code, NOT a name-derivation and NOT by reviving the fingerprint builder. (Array-item content lift does not depend on this at all.)
  - **Array-item field → role:** DECLARED per field in `block.json items.properties.<field>.role`, seeded into `array_item_schema.role` by the existing Stage-1 seeder (`sgs-update-v2.py`). The resolver reads that role; it never name-parses the field key. A field whose grammatical head isn't its semantic target (`iconName` identifies an icon, not a name) is exactly why the role is declared, not derived.
  - Draft-side, the owning element is the DOM parent/selector — already known at convert-time, never guessed.
- **FR-31-2.2 — role is the content-vs-styling FILTER** (the gate INTO the content walk), not the nested-vs-child decision. An attr enters the content walk ONLY when its `role` is in the content-bearing positive allowlist (`text-content`/`identity`/`image-object`/`content`/`rating`); the ~16 styling/behaviour roles are NOT content. `scalar-media`: `SELECT block_slug, attr_name FROM block_attributes WHERE role='scalar-media'` returns a single row, `('sgs/hero', 'splitMediaType')` — the attribute render.php reads to select the media family (re-run the query rather than citing this snapshot). The role must exist: without it a hero clone puts the MOBILE crop in the DESKTOP attribute and drops the desktop image. The roster lives in a git-tracked seed (`scripts/data/scalar-media-roles.json`) re-asserted at module load. `sgs/testimonial-slider.sideImage` is deliberately NOT in the scalar-media roster: it carries role `image-object` (content-bearing) and `emit_shape='nested'` — it IS content-walked, lifted as the parent's own scalar attr via the FR-31-2.6 `nested` path. (`equivalent_block_for` yields an identity only for a content-role attr — a non-content role returns NULL; the scalar-vs-child fork is FR-31-2.6 `emit_shape`.)
- **FR-31-2.5 — array/repeater resolution** (the B4 mechanism): an `attr_type=array` attr resolves its item schema from `array_item_schema` (field_key + declared `role`, seeded from `block.json items.properties.<field>.role` by `sgs-update-v2.py`); sibling-class DOM traversal of the array container emits one entry per item, each item's fields lifting via the shared role-aware mechanism (FR-31-2.2) — matched by canonical-slot name, then BEM-element-segment (FR-31-2.1a), then role. **BUILT.** (`array_item_slot_for()` remains the Tier-A per-block-attr slot resolver.)
- **FR-31-2.5a — array RECOGNITION uses the item-field signature, not just "largest repeating group".** Array-item recognition is not purely structural (largest group of ≥2 same-BEM-token siblings, no identity check): the block's declared item-field schema (`array_item_schema` field keys + their `(slot, role)` from FR-31-2.1a) is an **item SIGNATURE** the recogniser scores candidate repeating groups against — the same "recognise by what the DB says it should be" principle the other stages already use (BEM→block, tag→atomic, selector+role→CSS; §3.B.0). Binding: (1) a candidate repeating group is the array only when its items' children match the expected field roles above a threshold — a non-matching group is rejected, not blindly accepted; (2) among multiple candidate groups, the recogniser picks the **best signature-match**, not merely the largest; (3) the array container is the parent whose repeating children fit the signature. This does not add a new mechanism — it reuses the same schema-role data built for the content lift, bringing array recognition to parity with the child-block / nested-element / CSS stages.
- **Recursion rule (G2):** an emitted child block recurses into its own content via the same dispatch (a child can itself be an InnerBlocks parent — accordion-item's `__title`/`__content`). **NULL `accepts_allowed_blocks` (G3):** treated as permissive (admit + trace), never a silent drop.
- **FR-31-2.6 — the nested-vs-child fork is a source-derived `emit_shape` fact; ONE universal per-attr walk (CANONICAL).**
  - **Why per-attr.** A block-level flag CANNOT express a MIXED block that renders SOME content as its own nested elements AND hands the rest to `$content` child InnerBlocks: product-card renders title/price/description itself; accordion-item renders `title` itself but its panel is `$content`; hero renders `badges` itself but its headline is `$content`. A static block-level flag mis-routes these (the empty-slides class of bug).
  - **The signal (per content attr, source-derived).** A block renders a content attr as its OWN nested element when its `render.php` (+ require'd helpers) EMITS that attr's value inside/as an element (`echo $attributes['x']` into element content / `<img src>`); it delegates to a child InnerBlock when the attr is NOT render-emitted and the content lives in the `$content` region.  `block-files-are-ground-truth`: the block SOURCE, not a derived DB flag, states the shape.
  - **The channel (DB-first, R-31-1 — NOT a live scan).** `/sgs-update` has a stage that computes this per content attr from block source and seeds **`block_attributes.emit_shape`** value (`nested` | `child`). The walk reads the seeded column via `db_lookup`, exactly like every other routing fact — no runtime PHP scan. The seeding stage FAILS LOUD on any block whose render it cannot confidently parse (no silent misclassification — Rule 4). A drift-guard test asserts the derivation is stable across reseeds.
  - **The walk.** For each draft content routing unit resolving to a `role=content` attr (FR-31-2.2 filter): (1) resolve its **identity** (`equivalent_block_for` → `standalone_block`, FR-31-2 + the FR-31-2.1 two-tier + the agnostic-term ladder); (2) read its **`emit_shape`**; (3) **`nested`** → lift into the parent's scalar/array attr, processed per identity (text / media / rating / button / array); **`child`** → emit a child InnerBlock of the identity's `standalone_block` + recurse via the SAME walk. `sgs/container` and other pure layout blocks are untouched — they carry NO `role=content` attrs, so nothing enters the walk for them.
  - **Guards.** The invariants are explicit per-attr checks in the ONE walk, each with a test: the mutual-exclusion (an attr cannot be both nested and child), per-unit conservation (every content unit yields ≥1 of {scalar-lift, child-block, tracked-gap} — no silent drop), G3 `accepts_allowed_blocks` validation on emitted children, and the `sgs/container` default-recurse. **Art-directed `*Mobile`/`*Tablet` media routing is a SHIPPED invariant.** `db_lookup.py::content_attr_for_element` resolves purely on the draft's BEM element token and never inspects a `--mobile`/`--desktop` modifier; the device-tier routing is the scalar-media mechanism instead (Branch A, `extraction.py`), covering all 3 device tiers (desktop/tablet/mobile) and all 3 media types (image/video/SVG), so a draft's `--mobile`/`--tablet` art-directed image routes correctly. The type-selector attr (`splitMediaType`/`…Tablet`/`…Mobile`) must be written alongside the media value — stored video/SVG content with no type selector is never selected for render.
  - **Verification (the closing gate).** A LANDED before/after diff of the ACTUAL emitted block markup on the real drafts + computed-parity 11.6 (R-31-11) — NOT a source-vs-DB-role classification count. The `emit_shape` classification accuracy (PoC-verified) is necessary but NOT sufficient; the walk's rendered output must match.

- **FR-31-2.7 — the container-vs-composite classifier.** BEFORE the emit-shape gate, every recognised node is classified **arbitrary holder vs typed composite** by a COMPOSED signal of DB facts — `slug == db_lookup.container_default_slug()` (name-free), `blocks.tier`, `block_composition` roster membership — NEVER a slug/slot/role literal (STOP-38/41). An arbitrary holder (`sgs/container` is the ONLY one; `card-grid`/`gallery`/`post-grid` are TYPED composites) recurses its children independently; a typed block enters the per-attr `emit_shape` walk. The classifier lives at the RECOGNITION stage (a dispatch-key computation), NOT as a 4th walker conditional — R-31-3's three-exception contract holds.

- **FR-31-2.8 — the registry + destination contract for the unified walk.**
  1. **ONE walker owns recursion** (unconditional descent — a node cloned into an attribute still has its children walked). `recognise()` computes the dispatch key ONCE; `unrecognised` is a PRE-registry loud gate, never a signature.
  2. **Registry keyed by STRUCTURAL signature only** — {recognition kind, per-attr `emit_shape`, `container_kind`, `role`, tier, capability} — never `block_slug` (a slug-keyed entry is an R-31-9 carve-out; gate scope: `no_slug_literal.py` extended to `dispatch_table.py`/`orchestrator.py`/`walk.py`).
  3. **ADDITIVE multi-handler emission per node** — the mechanism arms COMPOSE (scalar + styling + array; B + array); a one-handler-per-node registry re-introduces the hero.badges silent drop. Handlers declare **explicit priority** (CSS-cascade style), never elif source-order.
  4. **Destination-parametric dispatch** — `Ctx` (or the dispatch signature) carries a DESTINATION (owning block + target attr-dict), defaulted to self; EVERY node's full declaration stream — root, folded band, grid item — runs the SAME cascade, only the destination differs. The reduced band-fold paths (max-width-only fallback; hand-rolled prop→layer ladder) are R-31-9/Rule-4 violations to DELETE. Semantics: `layer_detect`-first; the old fold ladder re-expressed as explicit registry priorities. The structural-position guard (L2 detection rejects a root node) and the ambiguity rule (≥2 candidate attrs for one (block, layer, property) → FAIL LOUD, never rowid-pick) are binding on this dispatch.
  5. **Coverage test** enumerates the producible signature space from the DB MINUS validity constraints (forbidden combos raise, they are not registry entries); every guard re-homed from the deleted case-fork is a `raise`, never `assert` (STOP-27).

- **FR-31-2.9 — tag-identity: the source HTML tag is preserved as an attr VALUE when a block declares an attr for it.** R-31-2 says the tag is *shape* (it picks the block, not the recognition), but some blocks declare an enum attr whose VALUE *is* that tag — `sgs/heading.level` (`h1`..`h6`), `sgs/media.mediaType` (`image`/`video`/`svg`). Without this rule the tag chooses the block and is then discarded, so `level` is never written and render defaults to `h2` (0 `<h1>` on a cloned page — an SEO + WCAG-hierarchy defect). **The rule:** an attr the block declares with `role='tag-identity'` (declared per FR-31-2.1a via the `ATTR_CLASSIFICATION_OVERRIDES` channel, NEVER derived from the attr name, and NEVER from bare enum-contains — `sgs/hero.variant` contains `"video"`, `sgs/quote.attributionTag` contains `"div"`, both must be excluded) receives the source node's tag as its value **when that tag is a member of the attr's `enum_values`** (an `<img>` is outside `mediaType`'s enum → the block default stands). Written by `assembly.build_block_markup` step 3a2 via `db_lookup.tag_identity_attrs(slug)` (cached, role-gated, enum-membership write-gate), `setdefault` so an explicit variant/CSS/content value wins. Universal (DB signal, no slug literal — R-31-9); the same mechanism covers every future tag-valued attr. `role='tag-identity'` has `classification='styling-behaviour'` so it NEVER enters the content walk (FR-31-2.2). Registered by `migrations/2026-07-05-register-tag-identity-role.py`.

### 13.4 CSS routing completions (FR-31-5 / FR-31-5.1 / FR-31-5.2 / FR-31-5.3)

- **FR-31-5 — three-destination CSS router (D0/D1/D2):** D0 global tokens → theme.json; **D1** typed-attr lift → block attr (when a `property_suffixes` row matches an attr the emitted block declares); D2 scoped variation CSS (`variation-d0-d2.css`, inline at Stage 10). The D1 child-attribution rule routes a `.sgs-X__Y` rule to the CHILD block when `equivalent_block_for(X, Y)` is non-NULL (the FR-31-2 fork).
- **FR-31-5.1 — inherited / absent-value resolution:** an inheritable CSS property (e.g. `text-align`) absent on an element resolves by walking the ancestor chain; a genuinely-absent inheritable value defaults to its CSS initial (LTR `start`), never invented.
- **FR-31-5.1a — inheritable band `text-align` folds to the block's WP-native `textAlign` support, rendered EXPLICITLY.** When a pass-through content band (L2) carries an inheritable `text-align` (e.g. a centred section band), it folds to the owning container-equivalent's WP-native `textAlign` support — NOT a new attr — gated on the block declaring `supports.typography.textAlign` (`db_lookup.block_supports_for`, DB-universal, no slug literal); a base-tier value only (WP `textAlign` is not responsive), else a tracked gap. **The render side MUST emit `has-text-align-{value}` EXPLICITLY** in the block's dynamic wrapper: WP core does NOT reliably merge `has-text-align-*` into `get_block_wrapper_attributes()` for a DYNAMIC (render.php) block — a folded `textAlign` attr renders NOTHING unless `SGS_Container_Wrapper` emits the class itself. This is **STOP-44** — a schema-valid emitted attr can be a RENDER no-op; verify the class/style paints on the LIVE element, never assume WP-core applies a native support for a dynamic block. The fold uses the FR-31-5.3 interior router (`route_interior_css_to_parent_slot`), applied in BOTH the default-container fold and the composite `build_block_markup` step-3c (a composite's content mechanisms — array/scalar — do not fold its sole pass-through inner; step-3c is the universal composite seam).
- **FR-31-5.2 — responsive `@media` → device-tier WHOLE-TIER FOLDING + `sgsCustomCss` residual (the F-fork implementation).** A draft `@media (min-width|max-width)` rule resolves to the SGS device-tier attrs by **whole-tier folding**, NOT by matching the raw threshold string to a marker table (a substring match would SILENTLY DROP any non-marker threshold, e.g. `min-width:600`). The device system is fixed at **768/1024** (Mobile `<768`, Tablet `768–1023`, Desktop `≥1024`); the SGS **base (unsuffixed) attr IS the Desktop value**. Algorithm (`collect_css_decls_for_element`, `db_lookup.device_tier_ranges`):
  1. For each tier's inclusive width range — **Desktop `[1024, ∞)` / Tablet `[768, 1023]` / Mobile `[1, 767]`** — compute the effective value by folding the element's non-media cascade + every `@media` rule that applies across the **ENTIRE range (tested at BOTH `lo` and `hi`)**. A rule that covers only PART of a tier is NOT folded in. This is direction-agnostic: `min-width:X` folds where the whole tier is ≥ X; `max-width:X` where the whole tier is ≤ X. **Whole-tier (not single-interior-width) is what prevents a threshold nested inside a tier from being absorbed into that tier's base** — a single interior-width sample (Desktop=1440) would wrongly fold `min-width:1280` into the Desktop base; folding only rules that span all of `[1024, ∞)` excludes it (it fails at 1024) → the base is the correct 1024-1279 value and 1280 becomes a residual (step 3).
  2. Map **Desktop → the base attr** (A-collapse — there is no `…Desktop` attr), **Tablet → `…Tablet`**, **Mobile → `…Mobile`**; a tier that matches base inherits it (no redundant tier attr). This correctly **inverts a mobile-first draft** (base CSS = mobile + a `min-width` desktop override → the desktop value becomes the base attr, the mobile value lands on `…Mobile`).
  3. A threshold **outside the canonical device set {767,768,1023,1024}** splits a tier → a sub-tier band the 3-tier attr model cannot represent (an "arbitrary visual breakpoint"). Per the §3 F-ii lock it is **captured (never snapped, never dropped) as a `ResidualBand`** (`models.ResidualBand`, scoped by the element's OWN SGS-BEM class via `_residual_selector_for` — the rendered clone preserves the draft class by construction, so no hardcoded selector / DB lookup, R-31-1) and **serialised to the owning block's `sgsCustomCss` (Additional-CSS) field** by `serialise_residual_bands` at the per-block CSS pass (`css_pass._build_css_attrs`, drained ONCE per block — `root_supports` re-collects the same node without a sink to avoid double-capture). `includes/custom-css.php` renders `sgsCustomCss` APPENDED after the block (so an Additional-CSS override wins at equal specificity, matching WP-core Additional-CSS semantics), replacing `&selector` with the block's scoped class. **This is the built passthrough channel.** The device-tier suffix vocabulary (Mobile/Tablet/Desktop) stays DB-owned via `modifier_suffixes('breakpoint')`; only the 768/1024 boundary widths (and the derived `device_tier_ranges`) are the R-31-1 permitted-constant (same class as `SKIP_TOP_LEVEL_TAGS` — no DB table of CSS pixel boundaries).

  - **RESIDUAL RENDER PRECEDENCE + BOUNDING.** The residual is the arbitrary-custom-breakpoint case the leading block plugins (WP-core, Kadence, Spectra, GenerateBlocks) deliberately do NOT support — so SGS resolves it with a FOUR-part universal architecture, NOT specificity escalation (no ID, no `!important` — that is the anti-pattern WordPress 6.6 moved away from and the `wrapper-class-residual-cannot-beat-id-scoped-block-rule` lesson warns against):
    1. **BOUND — a residual is confined to the DEVICE TIER its threshold falls inside** (`serialise_residual_bands` / the F-ii capture): a single `min-width:X` → `[X, upper-edge-of-the-tier-containing-X]`; a single `max-width:X` → `[lower-edge-of-the-tier-containing-X, X]`. Symmetric. So `min-width:600` (in Mobile) emits `@media (min-width:600px) and (max-width:767px)`; `min-width:1280` (in Desktop, the top tier — nothing above) stays open-ended `@media (min-width:1280px)`; `max-width:1200` (in Desktop) → `@media (min-width:1024px) and (max-width:1200px)`. A residual can therefore NEVER bleed past its tier into an adjacent tier that legitimately differs. (Tier edges from `db_lookup.device_tier_ranges()`; the boundary widths are the R-31-1 permitted-constant.)
    2. **FOLD — a value spanning a WHOLE tier is folded into that tier's attr** (existing whole-tier folding). This is what carries a value up through an UNSET intermediate tier: the residual only ever holds the sub-tier REMAINDER; the tier attrs + folding deliver "extend until the next explicitly-set value takes over" for free (a `min-width:600` value with no draft tablet rule folds 24px into the Tablet attr because it spans all of `[768,1023]`, while the residual holds only the `[600,767]` Mobile slice).
    3. **MATCH SPECIFICITY + WRITE LAST — equal class-level specificity + source order, NOT ID.** `custom-css.php` emits the residual at the SAME class-level specificity as the block's own scoped rule (the generated scope class is doubled, `.sgs-c-XXXX.sgs-c-XXXX` = 0,2,0) and keeps it APPENDED LAST, so it wins by cascade order at equal specificity — the WordPress-core idiom (6.6 `:root :where()` low-specificity + source order) and the pattern Kadence/Spectra/GenerateBlocks all use.
    4. **NORMALISE — every block's per-instance styling emits at ONE class-level specificity** (see FR-31-22.3 reconciliation): blocks that emit typography (e.g. collapsible-text) do so at class-level so the match-and-source-order rule holds universally. No block emits per-instance styling at ID specificity.

    Known limits (untriggered by current mockups): a NO-WIDTH media condition (`@media print`/`prefers-color-scheme`/`orientation`) still folds into the screen base rather than being captured as a residual; two residuals whose bands overlap resolve by emission order (bound them ascending).
- **FR-31-5.3 — cross-node interior box-CSS → parent per-slot attr group:** a direct child's box-CSS (padding/max-width/min-height/gap/margin) folds onto the parent's per-slot/area attrs when `slot_has_equivalent_block(parent, slot)` is FALSE (no child block owns it); when TRUE the CSS goes to the child block. (`slot_has_equivalent_block` is the CSS-fork ONLY; never the child-block-emission predicate.)

  - **Per-side border-width longhand transfer:** a draft's `border-{top,right,bottom,left}-width` ACCUMULATES into the `borderWidth` box-object `{top,right,bottom,left}` on the blocks declaring it — exactly as per-side padding accumulates into `contentBandPadding` (§3.A step 3b accumulator). Gated on `box_family_for(block,attr)==attr` (DB classification, never a name regex — passes the FR-31-22.2 AST collision gate); name-free (`attr_resolve`+`box_family_for`); base-only (a Tablet/Mobile longhand honestly gaps — no `borderWidthTablet`); no render.php change (render already reads the 4-side object). Known edge (loud, not silent): `border-width` shorthand + a per-side longhand on one element collide on a shared key → hard conservation error; resolving cleanly needs shorthand→longhand expansion at extraction (NOT BUILT).
  - **Pattern selector:** a **content-KIND composite** that uses only box+width migrates **block-private** (like `sgs/quote` — own scoped `<style>`, no `SGS_Container_Wrapper`), because the converter routes CSS by `block_attributes` keyed on `block_slug`, NOT by `wraps_block`/`container_kind` (zero walker impact — dropping the wrapper is safe, no DB change). **section/layout-KIND composites KEEP the wrapper** (like `sgs/hero`). See FR-31-21.1.
  - **FR-31-22.1 — reseed-durable DECLARATIVE categorisation:** the `block_attributes.box_family` column (§4; there is no separate `box_side` column) is seeded ONLY for the genuine box families, DECLARATIVELY from each block's `block.json supports.sgs.boxFamilies` (via `_collect_boxfamily_overrides` in `sgs-update-v2.py`) — NOT from the `ATTR_CLASSIFICATION_OVERRIDES` dict. A full `/sgs-update` re-run reproduces the seed byte-identically from the block.json declarations; the 10 scalar families get no row (NULL `box_family`) by construction (they carry no `boxFamilies` declaration), never by exclusion logic. Adding a box family = declare it in the block's block.json, never grow a dict.
  - **FR-31-22.2 — structural AST collision gate:** a static gate (same shape as the existing cheat-gate scanner) FAILS the build if any per-side/per-corner grouping or migration operation runs without a `box_family` DB check in its call path. Plant-tested: fires on a planted name-regex merge (`.*Top$`), silent on the correct `box_family`-gated merge, and asserts the 5 element-margin attrs + `shapeDivider*` remain untouched by any migration pass. Without this gate the `box_family` guard is mere convention, not enforcement — "by construction" is not enough on its own.
  - **FR-31-22.3 — no-inline base serialisation (the sibling mechanism to the box-object merge):** the base tier of a box-family attr serialises via WP's stable `wp_style_engine_get_styles($style, ['selector' => $scoped_selector])['css']` combined with `__experimentalSkipSerialization` (per-property, on the shared helpers — `SGS_Container_Wrapper`, `sgs_typography_css_rule`, `sgs_button_element_style_css`, `sgs_responsive_css_rule`) into the block's own scoped `<style>`, NEVER inline `style="…"`. **The `$scoped_selector` is CLASS-LEVEL — `.{$uid}.{block-root-class}` (specificity 0,2,0), NOT `#{$uid}` (the reference blocks emit at `.{uid}.block`, e.g. `sgs/heading`'s `$root_sel`).** Per-instance styling at class-level (never ID) is the load-bearing precondition for the FR-31-5.2 residual to override it by equal-specificity + source order (WP-6.6 idiom); any block emitting per-instance styling at `#uid` is normalised to class-level. `skipSerialization` suppresses only WP's *auto-inline output*; the `style` attribute is still populated so render.php can still read it.

- **FR-31-23 — preset-absence transfer (AUTO-DERIVE).** Without it a cloned card-like block keeps its `block.json` default preset value (`cardStyle=elevated` / `effectHover=lift`) regardless of the draft — painting a shadow/hover the draft never had. These **preset-selector** attrs are un-routed by the normal attrMap (no `css_property`), so the converter resolves them from the cloned element's COLLECTED CSS.
  - **FR-31-23.1 — auto-derive seed (R-31-1, reseed-durable):** `/sgs-update` (`sgs-update-v2.py::_populate_preset_implications`) parses each block's OWN `style.css` — for each preset attr named in `block.json supports.sgs.presetSelectors`, it reads each enum value's class rule (the class prefix + resting/hover state are derived from the block's `render.php`, the authority: `.sgs-{block}--{value}` for `cardStyle`, `.sgs-{block}--hover-{value}:hover` for `effectHover`; google-reviews' descendant-scoped `.sgs-{block}--card-{value} .{child}` is handled by the generalised selector-token matcher), classifies the implied signal property (box-shadow / border / transform present-or-absent), and seeds one row per `(block, preset_attr, enum_value)` into the **`preset_implications`** table `(block_slug, preset_attr, enum_value, implied_property, presence, is_neutral)`. No dict, no manual SQL — a full re-run reproduces the seed from the block.json declarations. The convention dicts `_PRESET_STATE_BY_ATTR` / `_PRESET_NEUTRAL_FALLBACK_NAME` are per-ATTR-NAME (universal, R-31-1-acceptable); move to a DB column only when a 3rd preset-selector attr beyond `cardStyle`/`effectHover` is added.
  - **FR-31-23.2 — resolver + reconciliation:** `converter/resolvers/preset_absence.py::apply_preset_absence` runs in `services/css_pass.py` AFTER the per-element resolvers, picks the enum value whose implied properties are all present (priority box-shadow > border > transform on an equal-count tie, else the `is_neutral` value), and RECONCILES with any companion attr the element already wrote for that property — DEFER to its write, NEVER re-derive, NEVER write the underlying shadow/transform attr (the two mechanisms stay disjoint; no double-paint). Universal + DB-driven (R-31-9), no slug literal (`converter/gates/check_preset_absence_no_slug_literal.py`).
  - **FR-31-23.3 — fidelity floor:** a real draft shadow whose value the box-shadow token-snap (§3 step 3, `outer_box.py`) cannot match to a `design_tokens` preset — so `cardShadow` gaps + stays unwritten — still resolves to `elevated` via the raw-decl fallback. A real shadow must never silently become the neutral (no shadow) on the clone.
  - **FR-31-23.4 — reconciliation scoping:** `db_lookup.attrs_for_css_property_state` returns ≤1 companion attr unchanged (preserves e.g. card-grid's `card-tile`-scoped `cardShadow` byte-identical) but narrows a ≥2-match ambiguity by the same `_BASE_ELEMENTS`∪`css_layer=OUTER`+base-tier predicate as the sibling lookups — so a per-child `imageZoomHover` cannot leak into the card's `effectHover`.
  - **Roster:** 5 blocks (info-box / team-member / card-grid / testimonial / google-reviews). `post-grid` is OUT (dynamic query block — its `cardStyle` is a JS-consumed layout choice with no `.sgs-post-grid--{value}` CSS rule; not a static clone target). A 6th block joins by declaring `supports.sgs.presetSelectors` + reseeding — zero converter code.

### 13.5 Variant detection (FR-31-20)

`blocks.variant_attr` names the selector attr; `variant_slots(block_slug, variant_value, unique_slot)` holds each variant's **discriminating** slots (set-difference vs siblings). The detector (`detect_variant` / `variant_attr_for`) counts how many of each variant's `variant_slots` were populated **from the draft extract THIS run** (never the block's stored attrs — the banned `$is_split` cheat) and sets the highest-count variant. Universal + DB-driven (R-31-1/R-31-9), gated by `blocks.variant_attr IS NOT NULL`, NOT a 4th walker branch (R-31-3). For class-modifier-encoded style presets (e.g. `sgs/button` `inheritStyle` primary/secondary/outline), the BEM `--modifier` maps to the enum attr gated on a string-typed `inheritStyle`/`variantStyle` (not the slot-set-difference path, which cannot discriminate structurally-identical variants).

**Composition-based tiebreaker.** Some variants cannot be told apart by attribute values alone (two `sgs/nav-drawer` variants, `split-zone-serif` and `two-column-editorial`, share every attribute value with a sibling and would score 0 with no rivals). A SECOND discriminating table, `variant_composition_slots(block_slug, variant_value, unique_child_slug)`, holds each variant's discriminating InnerBlocks CHILD-BLOCK-NAME set (same set-difference methodology, seeded from `variations.js`'s `innerBlocks` arrays via a JS AST extractor, `variant-value-extractor/extract-variation-values.js`). `detect_variant` takes an optional `child_slugs: list[str] | None = None` parameter, consulted ONLY as a TIEBREAKER when the attribute-value pass genuinely ties (including a 0-count tie/miss) — never additive, never able to override a clean attribute-only win, and completely inert (zero cost, zero behaviour change) for any caller that omits it. The one call site, `assembly.py` step 4, builds `child_slugs` from the already-resolved `results` list (`[r.slug for r in results if isinstance(r, ChildBlock)]`) — content extraction has already run by that point in `build_block_markup`, so the recognised child slugs are free to read. **A block only benefits if it also has a real content-extraction path** (`derive_delegates_content()==1`, an `array-content-lift` capability, or a `block_attributes emit_shape='child'` row); `has_inner.py`'s `$content`-consumption regex must recognise a bare trailing function argument (e.g. `printf(..., $content)`) for such blocks to qualify. Db-consistency check "Check #10 — Dead Composition Discriminator" (`db-consistency/check_dead_composition_signal.py`) flags any block that has `variant_composition_slots` rows without a working content-extraction path.

**Composition-signal guards and the column-count destination.** A grid column-count destination resolves DB-first via `db_lookup.attr_for_grid_column_count`; a block opts in via a `"css:grid-template-columns:count"` attrMap pseudo-property (e.g. `"attrMap": {"css:gap": "gap", "css:grid-template-columns:count": "listColumns"}`) instead of relying on a hardcoded `"columns"` literal. Two further db-consistency checks guard the "child-attribute-value composition signal": **Check #11** (`db-consistency/check_fx_qualifying_blocks_stale.py`) flags a stale `fx*`-qualifying-block roster; **Check #12 — order-dependent role-resolution guard** (`db-consistency/check_role_resolution_guess.py`) flags an array-content slot whose extraction role is resolved by DB insertion order rather than an explicit declaration (the `_slot_extraction_role()` fallback). A slot answers to several related names through the `canonical_slot_aliases` mechanism, and a resolver rule recognises whole-instance "container marker" slots and skips scalar-attribute guessing rather than forcing a wrong owner.

### 13.6 Composite-mirror + render.php migration (FR-31-21.1 / FR-31-21.2 / FR-31-6)

- **FR-31-21.1 — composite-mirror rule:** every composite with a built-in wrapper (`block_composition.wraps_block='sgs/container'`) MIRRORS `sgs/container`'s wrapper capabilities per its `container_kind` (section/layout/content) — never diverges with per-block CSS hacks. Missing capabilities are design gaps to add to the composite (via DB seeding), never converter workarounds.
  - **"Mirror capabilities" ≠ "must call `SGS_Container_Wrapper::render()`".** The rule forbids per-block CSS *hacks that DIVERGE* from the wrapper's computed behaviour (examples: a `wrap_inner=false` opt-out, a `max-width:100%!important` containment, a `margin-inline:-24px` breakout) — NOT a clean block-private implementation that reproduces the same capability set with identical computed output. A **content-KIND composite that uses only box+width** (quote, info-box, testimonial, team-member, product-faq-item…) MAY render **block-private** (own scoped `<style>`, no wrapper call): it never used the wrapper's grid/section/background machinery, and — decisively — the converter routes CSS by `block_attributes` keyed on `block_slug` (block.json-derived), NEVER by `wraps_block`/`container_kind` (the column has "zero walker impact"), so dropping the wrapper is safe and needs no DB change (the roster classifier re-derives `wraps_block` from InnerBlocks presence regardless). **section/layout-KIND composites KEEP the wrapper** (genuine grid/section — e.g. hero), which is itself fully no-inline (base spacing, max-width/contentWidth/band and grid/flex all scoped). One residual cost of the block-private path: a block that drops the wrapper falls out of FR-31-21.2 auto-propagation of FUTURE container capabilities (informational). This is the no-inline-rollout pattern selector; apply it, do not re-litigate per block.
- **FR-31-21.2 — auto-propagation:** `/sgs-update` Stage 11 propagates a new container capability to every composite in the roster (writer + scanner BUILT, including `--write-block-json --apply`).
- **FR-31-6 — hybrid render.php migration:** a composite whose content was scalar attrs migrates to emit `<InnerBlocks.Content />` + a `deprecated.js` covering the old shape; **never** a server-side legacy fallback (R-31-14). The roster is DB/report-derived (query `/sgs-db`, never hardcode).

- **FR-31-6.1 — parallel-session migration protocol.** When render.php migrations are dispatched across parallel subagents: each agent is confined to its own block directory; an agent that needs a shared helper HALTS and RETURNS rather than editing a shared file (STOP-2 / `subagents-must-not-write-shared-files`); agents have NO git-commit authority (the main session reviews + commits); the legacy-cleanup phase is BLOCKED until every agent has closed. This prevents the `rater-agents-must-never-git-revert-shared-tree` failure class.
- **R-31-14 correct path (not a fallback hack):** the sanctioned way to give a migrated block backwards-compat is the FULL FR-31-6 roster migration (deprecated.js for the old shape) + a WP-CLI batch sweep of existing posts — never a server-side `if empty($content)` legacy-scalar-render branch in render.php.

### 13.6.1 Container-equivalent roster + KINDs

**The model.** `sgs/container` is the canonical wrapper block (background image/video/parallax/ken-burns/SVG/overlay, shape dividers, width/content-width capping, grid/flex layout, responsive gap, min-height, grid-item defaults, shadow). Every composite with a built-in outer wrapper mirrors it via the shared PHP helper `plugins/sgs-blocks/includes/class-sgs-container-wrapper.php` (`SGS_Container_Wrapper::render( $attributes, $block, $inner_html, $kind, $opts )` — pass `$attributes` VERBATIM, no merge/reorder, or the responsive-CSS uid `md5(wp_json_encode($attributes).anchor)` breaks scoped-selector targeting) and the shared editor component `src/blocks/container/components/ContainerWrapperControls.js` (`kind` prop matches `block_composition.container_kind`; its `KIND_PANELS` map decides which sub-panels render). See §13.6 above for what "mirror" does/doesn't mean and the block-private exception.

**The three KINDs** (`block_composition.container_kind`, gates panel exposure + PHP render layers — never routing, per §2 Axis 2 / §13.8 below):
- **`section`** — full-bleed outer page wrapper; background spans edge-to-edge, `contentWidth` adds the inner centring wrapper. For top-level page sections (hero, CTA strip, trust-bar). Exposes: layout, width, min-height, grid-item defaults, background, shadow, shape dividers.
- **`layout`** — inner grid/flex arrangement of children, width/contentWidth capping, no background layer. For blocks whose job is arranging children (card-grid, feature-grid, gallery) inside a parent section.
- **`content`** — self-contained content unit with its own chrome, width cap + inner padding, no grid/background engine. For blocks that are a card/box/unit inside someone else's grid (info-box, quote, team-member).

**Excluded from mirroring** (`supports.sgs.containerMirror: false`) despite structurally wrapping `sgs/container`: `sgs/modal` (outer shell is a `<dialog>`, no background/grid/gap layers) and `sgs/nav-drawer` (off-canvas Popover overlay, container mapping doesn't apply to fixed-position overlays).

**Live roster (DB-authoritative, do not hardcode a count or list here):**
```bash
python plugins/sgs-blocks/scripts/sgs-db.py query \
  "SELECT block_slug, container_kind FROM block_composition WHERE container_kind IS NOT NULL ORDER BY container_kind, block_slug"
```

**Auto-propagation:** a new `sgs/container` attr propagates to the whole roster via `/sgs-update` Stage 11 (`sync-container-wrapping-blocks.py`), diffing the KIND-scoped attr set and writing missing attrs into roster `block.json` files (report-only unless `--apply` is passed — see FR-31-21.2 above).

**Container-bearing vs styles-directly.** The Stage-11 mirror roster (which blocks RECEIVE the sgs/container attr-mirror) is NOT the same test as "renders via `SGS_Container_Wrapper`". A block can use the wrapper for its outer shell yet have its own colour/border/typography supports + no `sgs/container` InnerBlocks — it then styles directly and is excluded from the roster (`sgs/product-card`, `sgs/team-member`). Roster detection currently keys on `sgs/container` InnerBlocks presence, so wrapper-attr scalar blocks must be hand-curated out; `container_kind` (the converter's composite-mirror source) is a separate axis and both blocks above remain `content` there.

### 13.7.1 Content-role vocabulary + detectors (FR-31-24, Spec 35 Track 1b)

**Purpose.** `block_attributes.role` is the DB column the converter routes content extraction and CSS emission on (§3.A/§3.B). A `role IS NULL` row is ambiguous by construction — it reads identically whether nobody has examined the attribute yet, or someone has and concluded it is neither content nor styling. The mechanisms below make every row an explicit, evidence-backed verdict rather than a silent gap. Row counts are DB-authoritative — query `role`/`roles` via `/sgs-db`, never trust prose for a current count.

**Role vocabulary (`plugins/sgs-blocks/scripts/data/roles.json`).** Every role carries a `classification` (`content-bearing` or `styling-behaviour`) that the converter's content walk gates on. Two generic backstop roles sit alongside the named-family roles (layout/typography/color/visual/motion/position/text-content/svg/…):

- **`styling`** — classification `styling-behaviour`. The GENERIC BACKSTOP: a structural mechanism has proven the row paints CSS, but no more specific family was established. TWO assigning passes, both in `assign-canonical.apply_role_detection_inline()`:
  - **TIER 3** — fills `role IS NULL AND css_property IS NOT NULL`, structurally LAST among the css_property passes; it can only fill a NULL, never pre-empt a content-bearing or family-specific verdict.
  - **TIER 2.4 (`_apply_wrapper_styling_tier()`)** — fills a NULL row whose ONLY consumer is `class-sgs-container-wrapper.php`. The wrapper is a CSS-rendering engine by construction, so everything it reads off the attributes bag it reads in order to PAINT: positive evidence of the same class as the D1 veto behind `technical`, not an absence argument. Ordered BEFORE TIER 2.5 on purpose — a veto says only "not content", a wrapper-only read says positively what the value IS, which is the precedence TIER 3 already encodes for `css_property`.
  - It is not a terminal verdict — TIER 3.15 upgrades OFF it (below).
- **`technical`** — classification `styling-behaviour`. A machine-facing value (form key, element ref, `rel`, taxonomy/query key, enum dispatch key) that a draft mockup carries no signal to lift. Assigned ONLY from positive evidence — a Detector-1 veto (the row's every usage site was walked and none was content-bearing) or a Detector-4 referenced-not-output finding (below) — **never** from "nothing else claimed it". An unreached row stays `NULL`; conflating "unreached" with "proven technical" would rebuild the exact ambiguity this role exists to remove.

**Precedence (enforced structurally by pass ordering in `apply_role_detection_inline`, not by a priority field):** content tiers (D1/D2/D3 structural detectors) > wrapper-only paint (`styling`, TIER 2.4) > evidence-of-not-content (`technical`, TIER 2.5 — a D1 veto or Detector 4) > `css_property` (`styling`, TIER 3) > `NULL`. A veto only says "not content"; positive paint evidence (a wrapper-only read, or a `css_property`) says what the value IS, so `styling` wins a row that qualifies for both.

**⛔ THE GOVERNING RULE ON `NULL`. A NULL role means the row is UNREACHED or UNSEEDABLE — never "reached, understood, and filed nowhere".** A mechanism that examines a row, forms a verdict, and then leaves the column NULL rebuilds the exact ambiguity this vocabulary exists to remove. It is the test any detector bucket must pass before it is allowed to report rather than seed.

**Role-vocabulary integrity — three families that LOOK like bloat and are NOT.** An empty or near-empty role is not evidence of a dead role:
- **`spacing-token` / `colour-text`** are PROVISIONED by `property_suffixes.role` (`BlockGap`/`Spacing` → `spacing-token`, `LinkColor` → `colour-text`) and describe the **WordPress-NATIVE** half of the vocabulary (theme.json `settings.spacing.blockGap`/`spacingSizes`, block.json `supports.color.link`). They are empty only because no SGS block declares a custom attr for those. `spacing-token` also has a live branch in `db_lookup.py`. Deleting either leaves suffix derivation resolving to a role that does not exist.
- **The four `icon-*` roles are a ROUTING KEY, not four spellings of one idea.** `services/extraction.py` builds a `{role: attr_name}` dict for every role starting `icon-` and then looks up `icon_source_attrs.get("icon-" + kind)`. All four sit on `sgs/icon` (`dashiconName`/`emojiChar`/`iconName`/`wpIconName`). Merging them collapses that dict to ONE entry and breaks icon cloning outright.
- **`content`→`text-content` and the `number-css-*` merge** are documented aliases resolving identically; merging delivers ZERO functional change and would need `property_suffixes` repointed too.
- **Before proposing any role deletion, check `property_suffixes.role` for provisioning AND grep for a prefix-keyed dict lookup — a row count of 0 proves neither.**

**Detector 4 — `content-role-detect/detector4_referenced_not_output.py`.** D1/D2/D3 all hunt for evidence a value IS content. D4 hunts the opposite positive evidence: an attribute the block demonstrably READS (a structured access pattern, never a bare-word match) that never reaches an output-escaping call (D1 walked every escaping call site and found none) and paints no CSS property (the emission parser found no declaration). All three facts are measured, not inferred from absence. D4 splits its findings three ways — read its module docstring for the authoritative definitions:

- **`referenced-not-output`** → assigned role `technical`. The dominant case is the form conditional-visibility trio (`conditionalField`/`conditionalOperator`/`conditionalValue`) consumed by `includes/forms/` to decide field visibility — configuration, not copy.
- **`wrapper-rendered-styling`** → assigned role `styling`, via TIER 2.4. The decorative families (`overlayGradientFrom`/`To`, `shapeDividerTop`/`Bottom`, `bgSvgContent`) are ones `sgs/container` — the block every composite mirrors (R-31-9) — deliberately declines to map: its `decorative` element declares `"clusters": []` with a written note that these are governed by dedicated controls outside the style clusters (`container/block.json`). Declaring attrMaps for them would REVERSE a standing architectural decision to close a reporting nuisance. An opt-out declaration does not by itself discharge a row: the only thing that removes a row is a non-NULL `css_property`, which the decorative families never carry, because the emission scanner reads each block's own render.php/style.css and never the shared wrapper.
- **`d4-needs-review`** → a human call. A bare `$x = $attributes['x'] ?? ''` whose paint site can't be resolved without variable-flow analysis (D1's job, D4 does not attempt it).

An attribute nothing reads at all is a DIFFERENT finding (a dead attribute — delete it) and belongs to `check-dead-controls.js` CHECK 4, not D4. D4's known blind spots (dynamic/computed reads, sibling-block consumption, theme-pattern-only reads) are enumerated in the module docstring and are bounded to false NEGATIVES — they cannot manufacture a false positive.

**D4 tie-break — a RENDER-side read outranks an EDITOR-side one.** `find_reference()` collects both kinds and PREFERS the render-side read, falling back to the editor-side hit only when nothing renders the value — so the answer never depends on DIRECTORY LAYOUT (the iterator yields the block's OWN directory before the shared trees). Example: `sgs/container.shapeDividerTop`/`Bottom` must resolve to `class-sgs-container-wrapper.php` (wrapper-painted), exactly as the same attribute does on hero / cta-section / trust-bar / site-header / site-footer / physics-canvas, not to a block-local `SelectControl value={…}` binding. **The rule, stated once: what RENDERS a value decides its role; an editor control merely AUTHORS it.** This is a tie-break, not a new classification: it must not change `technical_refs`.

**Detectors resolve to the SPECIFIC role, not the coarsest that fits.** Reasoning in three broad buckets and seeding the widest one that fits is a defect, not a safe default. Two examples: `enum-class-probe` (*"a BEM `--modifier` class carries this attr's value, never a CSS declaration"*) has a real cloning consumer in `db_lookup.py` that matches the modifier against the draft's actual BEM class — filing such a row as generic `styling` measures the right thing and then discards the consumer that made it worth measuring; likewise `color` (consumer `attr_is_colour_role()`) on the separator gradients. Narrowing a detector's rule also makes it more correct: tightening "appears in a class context" to "IS the `'…--' . $var` modifier suffix" excludes `separator.contentIconName` (a content-bearing `icon-lucide`) and `mega-panel.viewAllPlacement` (an `enum-mode`, not a modifier) with no special-casing.

**TIER 3.15 — GENERIC-STYLING UPGRADE. The ONLY pass in `assign-canonical` that OVERWRITES an existing role**, and narrow to match: its `WHERE` pins `role = 'styling'` exactly, so it can never touch a content verdict, an already-specific family, or a NULL. It re-runs D7 over backstop rows and upgrades where the PAINT SITE proves a specific role. It exists because `styling` rows are invisible to `eligible_pool()` (which is `role IS NULL`), so nothing else re-examines them after assignment. **Motivating case and permanent negative control:** `border-color` is filed TWO ways — most rows on `color`, a handful on the backstop. Reading each CONSUMER splits them cleanly: `button.colourBorder`/`Hover` and `product-card.ctaColourBorder`/`Hover` reach `sgs_colour_value()` (genuine colours, the latter through a SHARED helper — D7's documented single-file blind spot), whereas `gridItemBorder` is a border SHORTHAND (`1px solid #ccc`) sanitised by a regex that deliberately permits spaces and emitted raw into a custom property. **`color` would be WRONG there: it would hand `attr_is_colour_role()` a shorthand and call it a colour.** Identical by `css_property`, opposite correct answers — which is why this needs the consumer read, not a `GROUP BY`. The `gridItemBorder` rows are the self-test's negative control (a real row, not a fixture); dropping the `role = 'styling'` guard turns it red.

**Detectors 6 / 7 / 8.** All three run over exactly what Detector 4 could NOT decide — the `d4-needs-review` bucket — and answer its open question ("technical, or styling painted later?") with a SPECIFIC role. Scoping them to D4's leftovers is the structural ordering guarantee: they never get a chance to re-decide a row a trusted detector already assigned.

- **Detector 6 — `content-role-detect/detector6_native_support_and_style_emission.py`.** Two mechanisms, both by-construction rather than inferential: (a) an attribute WordPress core injects because the block declares the matching `supports` key is `technical`; (b) a value written into the CONTENTS of a `<style>` element is `styling`. **Gotcha (a detector keyed the obvious way is silently INERT):** `sgs/button` has no `supports.className` key at all — the backing key is `customClassName`.
- **Detector 7 — `content-role-detect/detector7_css_paint_flow.php`.** Forward variable-flow to a PAINT site — the gap D4's own module comment names. It does NOT re-implement PHP statement splitting: it `require`s `detector1_render_escaping.php` and reuses its tokeniser. Two paint shapes, both derived from real code: **CSS_VALUE** (reaches a CSS helper / custom property) and **CSS_CLASS** (concatenated into a class list — a BEM modifier IS a paint instruction, mapping to `enum-class-probe`, never generic `styling`).
  - **Two structural guards any flow analysis needs:** **(1) COMBINATION DILUTES** — an RHS mentioning more than one variable owns no single value; **(2) A PREDICATE IS NOT ITS SUBJECT** — a comparison yields a boolean ABOUT the value, not the value. Without them, naive transitive carrier tracking launders DERIVED values back into evidence about their source (`option-picker.defaultSelected` chained through an `is_checked` boolean and then "landed in a class"). A generic "declaration shape" regex is not used: it claims `post-grid.orderBy`, a WP_Query key that paints nothing.
- **Wiring:** D6 + D7 verdicts ARE consumed — `fingerprint_content_roles.compute()` runs both over `d4_review`, first-verdict-wins per key, and returns them as `specific_roles`, which `assign-canonical` merges UNDER the content verdicts (`{**specific, **content}`) so a content verdict can never be overwritten by a styling/technical one. Auto-seeding over a considered human verdict is the failure this vocabulary exists to prevent: where D7 contradicts a considered human verdict (e.g. `separator.contentIconName`, `site-header-row`/`site-footer-row.rowSlot`), the resolution is a human call, not the detector's.
- **Detector 8 — `content-role-detect/detector8_undeclared_enum.php`. Reports a SCHEMA gap; it seeds no role, deliberately.** `eligible_pool()` excludes `enum_values IS NOT NULL`, so every unclassified row by construction has no `enum` in its block.json — yet several ENFORCE one in PHP (`in_array( $attributes['source'], array('typed','menu'), true )`). D8 reports the block as owing an `enum` DECLARATION, because `/sgs-update` Stage 1 already reads block.json enums into `enum_values` and TIER 3.5 already seeds `enum-mode` from that column. Declaring it fixes three things with **no new role logic**: the row classifies via existing tested machinery, WordPress validates the value, and the client gets a real select control instead of a free-text box — which is Spec 35's whole point. **Documented blind spot:** a closed set expressed as a comparison CHAIN (rather than an `in_array` set) is not reported — proving a chain exhaustive is a much weaker inference.
- **D4's evidence gate is the limit.** Widening D4's candidate pool (so a D2-only report does not veto it) gains no roles: D4 awards `technical` only when the reference sits in a subsystem proven to emit no CSS, and the decisive reference is typically the block's OWN render.php. Do not re-derive this.

**Tier-inheritance rule (`behavioural-analyser/extract-signatures.py`).** An attribute named `<base><Tier>` (`Tablet`/`Mobile`/`Desktop` suffix — the framework's universal device-tier convention, see §13.4's responsive-breakpoint discipline) whose `<base>` carries a `css_property` inherits that property with `css_tier` set, plus the base's `css_layer`/`css_element`/`css_state` selector context so the sibling routes to the right element, not merely to the right property. The base must itself carry a real `css_property` — inheriting from an unclassified base would manufacture a classification out of two unknowns, so those rows correctly stay open. **This rule requires the property to already be declared somewhere on the base** — a block relying purely on the bare-prefix convention with an EMPTY prefix (candidate name `"" + "Gap" = "Gap"`, which never matches a real lowercase `gap`) is invisible to it and needs an explicit `attrMap`/`css:` declaration instead (`sgs/google-reviews` and `sgs/trustpilot-reviews` both need this because they render their grid through the shared wrapper rather than declaring `gap` themselves).

**Consuming this:** never write a new hardcoded attribute-name dict for "is this technical/styling" — check `roles.json` first, and if a row is genuinely unclassified, run the detectors (`content-role-detect/`, D1–D8, aggregated by `fingerprint_content_roles.compute()`) rather than guessing from the attribute's name (R-31-1/R-31-2 apply equally to this data layer). **And resolve to the SPECIFIC role the evidence supports, not the coarsest one that fits** — a generic verdict discards the very consumer that made the measurement worth taking.

### 13.9 `block_render_composition` — render-time block composition

A block can compose ANOTHER registered block at render time by calling WordPress's own `render_block(['blockName' => '<slug>', ...])` from inside its own PHP — distinct from `block_composition.accepts_allowed_blocks` (§13, Axis 3), which only knows about a child block the EDITOR stored (InnerBlocks). Real instances (found by running the seeder): `sgs/buybox` → `sgs/option-picker` (one axis-picker per WooCommerce variation axis), `sgs/card-grid` → `sgs/product-card` (twice — a collection-mode branch and a wc-product-mode branch), `sgs/product-card` → `sgs/option-picker` (three call sites — two in its own `render.php`, one in a required partial, `product-card-builtin-render.php`, found because the seeder follows the same `require()` resolution `render_repeater_seeder.py` uses).

**Why this lives in Spec 31.** The classless-repeater scanner (Spec 44 §4.2) only sees a block's own `render.php` + its `require()`'d PHP partials — it has no path to a composed CHILD block's own identity when the composition happens via `render_block()` rather than a PHP include. That is a Spec-31 data-layer fact: Spec 44 is a consumer of it, the same way it consumes `block_composition`/`block_attributes` (§3.1). Spec 45's Tier 3 (nested child-block matching) is a second, independent consumer.

```sql
CREATE TABLE block_render_composition (
    block_slug   TEXT NOT NULL,   -- the block doing the composing, e.g. sgs/buybox
    child_slug   TEXT NOT NULL,   -- the block being composed, e.g. sgs/option-picker
    call_order   INTEGER NOT NULL, -- position among this block's own render_block() calls
    source_file  TEXT NOT NULL,
    source_sha   TEXT NOT NULL,   -- same staleness discipline as block_render_repeaters
    PRIMARY KEY (block_slug, child_slug, source_file, call_order)
);
```

**Detection is source-derived, R-31-1 compliant — no hand-typed block-to-block dict.** `seed-render-composition.py` reads a `render_block()` call's blockName straight out of the block's real PHP; only a LITERAL string counts. A call whose blockName is built from a variable or expression is flagged (WARN, never silently skipped or guessed) — the same fail-loud discipline `render_repeater_seeder.py` applies to an unparseable `foreach`. Its masking/source-resolution primitives (`mask_php`, `resolve_sources`, `source_sha`) are REUSED from `recogniser.render_repeater_seeder` rather than re-implemented, so a masking bug fixed once fixes both consumers. **Negative control:** three blocks (`before-after`, `nav-drawer`, `text`) mention `render_block()` only in a PHP *comment* documenting a call that lives elsewhere — the seeder produces zero rows for all three, because its detection view blanks comment spans before scanning (same `mask_php(text, comments_out=...)` side-channel `markup_view()` uses for the identical reason in `render_repeater_seeder.py`).

Wired as a Stage 1 tail step in `sgs-update-v2.py`
(`_run_render_composition_seed`), same idempotent/WARN-not-fail/subprocess contract as
every sibling seeder — survives every `/sgs-update` reseed automatically.

**Consumer BUILT — a Step-0 narrowing signal, not a spliced sequence.** `render_repeater_recogniser.ParentContext` has `required_composed_children: frozenset[str]`, checked in `narrow_candidates()` at Step 0 via the `composes_child(conn, slug, child_slug)` helper — exclusion-only, exactly like the `required_capabilities` check it sits beside (`NarrowingResult.composition_conclusive` records whether it ever fired). **Status: PARTIAL.** The signal is real and tested (a candidate genuinely missing a required composed child is genuinely excluded — `test_composition_narrowing_excludes_a_non_composing_candidate`), but it is INERT in production, for the same reason `required_capabilities` is — nothing derives "this draft group's parent embeds an X-shaped widget" from real draft markup yet. `classless_draft_adapter.build_stage_a_group()` always leaves it empty. The slot exists for Spec 45 Tier 3 (§9.2) and a future draft-side detector to populate; it changes zero real match outcomes.

### 13.10 `block_render_singletons` — static/singleton structural elements

A STATIC/SINGLETON structural element is content that renders EXACTLY ONCE — not
inside a `foreach` (`block_render_repeaters`, §4.2) and not a child block composed at
render time via `render_block()` (`block_render_composition`, §13.9) — but still
carries a real, matchable structural role per §3.1 (action-trigger /
image-or-fallback / current-state-indicator / label). This is the third and final
table in the structural-facts trio.

**Concrete case:** `sgs/buybox`'s main product image (`plugins/sgs-blocks/src/blocks/buybox/gallery-col.php`) sits OUTSIDE its thumbnail `foreach` loop and OUTSIDE its one `render_block()` call to `sgs/option-picker`, yet has a genuine `image-or-fallback` conditional (a real `<img>` vs. an SVG placeholder — `if ( '' !== $buybox_img_src ) : <img> else : <svg> endif;`). It is invisible to both sibling tables, and for a minimal single-image/single-variant product, buybox's thumbnail gallery AND price-ladder AND axis-picker composition all degrade to empty/absent — so the static parts are the ONLY reliably-present signal for the most common real case. Check: `seed-render-singletons.py --survey --block sgs/buybox` seeds `image-or-fallback` for `gallery-col.php`, outside that file's own thumbnail `foreach` body span.

```sql
CREATE TABLE IF NOT EXISTS block_render_singletons (
    block_slug   TEXT NOT NULL,
    role         TEXT NOT NULL,   -- same 4-value vocabulary: action-trigger,
                                  -- image-or-fallback, current-state-indicator, label
    role_order   INTEGER NOT NULL,
    source_file  TEXT NOT NULL,
    source_sha   TEXT NOT NULL,
    PRIMARY KEY (block_slug, role, role_order)
);
```

**Detection is REUSE-NOT-REIMPLEMENT, R-31-1 compliant.** `seed-render-singletons.py`
adds no new PHP masking or role-detection logic of its own. For each live block it
calls both sibling detectors to learn which byte spans they already claimed —
`render_repeater_seeder.detect_repeaters()`'s `foreach` body spans, via a purely
additive `spans_out` parameter that ALL existing callers ignore by default (ALL
spans, including attribute-backed ones excluded from `block_render_repeaters`
itself, because that markup is still "repeated, not static") — and its own
`render_block()` call spans, found by reusing `_match_pair()` over the reused
`mask_php()` mask, so a paren inside a string-literal call argument (e.g. a URL) can
never be miscounted as call structure. Both claimed-span sets are blanked
(offset-preserving, spaces only) out of BOTH the file's `markup_view()` and its
original text, and the reused `derive_roles()` runs on what's left with an EMPTY
`loop_vars` tuple — there is no loop to bind an item-variable from at top level, so
the echoed-loop-var label signal correctly never fires for singleton content.

**Fail-loud, matching every sibling seeder:** if EITHER `detect_repeaters()` or
`detect_composition()` already flagged a WARN for a block, singleton seeding is
skipped too and the equivalent WARN is printed. A block whose repeater/composition
boundaries are already known-unreliable must never have its "everything else"
region guessed at — "everything else" is only correct when the two subtractions it
depends on were.

**Disjointness is the load-bearing correctness property**, proven as a named
negative control in `test_render_singleton_seeder.py`
(`test_singleton_spans_never_overlap_sibling_claimed_spans`): for `sgs/buybox`, every
byte offset `block_render_singletons` seeds is asserted to fall outside every span
`block_render_repeaters`/`block_render_composition` already claimed for the same
block+file, checked against real offsets, not role-name spot-checking. A silent
overlap would double-count the same markup as both "repeated" and "static",
corrupting any future consumer's fingerprint.

Wired as a Stage 1 tail step in `sgs-update-v2.py` (`_run_render_singleton_seed`), immediately after `_run_render_composition_seed`, same idempotent/WARN-not-fail/subprocess contract as both sibling seeds.

**Consumer BUILT — a SEPARATE evidence dimension, never spliced into the repeater role sequence.** `render_repeater_recogniser.RenderMatchResult` has `static_leaf`, computed for the WINNING repeater candidate only: the draft boundary's own non-repeated content (`classless_draft_adapter.derive_static_draft_roles()` — excludes every `<sc-for>` subtree, the same span-subtraction idea `seed-render-singletons.py` uses on the PHP side, applied to the draft's DOM) compared against the winning slug's `block_render_singletons` rows via the SAME `match_leaf()` function Stage A uses for repeaters (zero new matching logic). Spec 45 Tier 4's `resolve_tier4()` has the mirror: an optional `static_roles` parameter, compared against the classifier-guessed slug's singleton rows, attached as `Tier4Resolution.static_corroboration`.

**Deliberately INFORMATIONAL ONLY, both sites:** `test_static_leaf_never_changes_clause_a_or_the_outcome` shows FR-44-1(a)'s clause and the trust gate's outcome are byte-identical whether `static_leaf` is `None`, a real EXACT match, or a fabricated mismatch; only the review-page `signal` text differs. Tier 4's `confidence`/`review_pending` are likewise untouched. It is informational by design: a real measurement, not a design guess, decides whether it should ever gate.

**Measurement (`measure-classless-baseline.py`, real Eye Care Birmingham draft): 0 of 39 real groups carried a static-shape corroboration signal.** Every matched boundary on this draft either has no static content of its own adjacent to its repeated group (the real `thumbs` boundary tests empty — `test_derive_static_draft_roles_on_the_real_thumbs_boundary_is_empty`) or matched no candidate at all. This is a null result for THIS draft, not proof the mechanism is dead — the synthetic + real-buybox-fixture tests both confirm it detects a real corroboration when one exists (`test_static_leaf_is_computed_for_the_winning_candidate`, `test_tier4_static_corroboration_against_real_buybox_singleton`). A measurement against a draft that DOES exercise it decides whether to promote this signal into the gate.

The companion `required_composed_children` slot above (§13.9) shares the exact same
"built, tested, inert-in-production-today" status for the same underlying reason: no
draft-side detector observes it from real markup yet.

### 14.2 R8 — motion recognition from raw CSS

**The problem.** Every other extraction family in this pipeline reads a structural or textual
signal (a BEM class, a CSS property value) and routes it to a block attribute. Motion is
different: a draft site's `@keyframes` block or `transition` shorthand encodes an *intent* — fade,
slide, reveal, stagger — that has to be recognised as a SHAPE, not read as a literal value, then
matched to one of the framework's own named `fxPreset`/`sgsAnimation` slugs. R8 is that
recognition layer. It reads a draft's real CSS and infers `sgsAnimation` + `fxTrigger` (+, for
grouped siblings, `fxStagger`) — it never touches the `data-sgs-fx-*` authoring grammar Spec 38
governs (see §14.2.4).

**Architecture — four tiers, each a separate concern:**

| Tier | What it recognises | Entry point |
|---|---|---|
| 1 | Shape — the CSS declares an unconditional or hover-scoped `@keyframes` animation, or a `transition` with a resolvable resting value | `motion_shape.py::classify_css_motion()` |
| 2 | Trigger — WHEN the shape fires: `scroll` (CSS `animation-timeline: scroll()` or an IntersectionObserver JS signal) / `hover` (an owning `:hover`/`:focus` selector) / `load` (the documented fallback — never a silent guess) | `motion_trigger.py::classify_css_motion_with_trigger()` |
| 3 | Stagger — a group of shape-alike siblings whose `animation-delay` values form a strictly monotonic sequence | `motion_stagger.py::detect_stagger()` |
| 4a/4b/4c | Live-DOM signals static CSS reading cannot reach (library detection, page-load-settle sampling, WebGL draw-call probing) | `sgs-clone-orchestrator.py::stage_neg1_motion_probe()` |

Tiers 1–3 run inline inside the converter (Stage 4, `assembly.py` step 3a1b / `extraction.py`'s
sibling-stagger adapter). Tier 4 runs once per clone job, before Stage 0, because it needs a real
browser (`source_url`), which the per-section converter pass does not have.

### 14.5 Routing mechanism, and why Spec 38's Tier G/H/W never enter it

R8's output is a `sgsAnimation` preset slug plus an `fxTrigger`. **Every preset R8 can ever match
is Tier V** — `motion_shape_signatures.tier` carries a hard `CHECK(tier = 'V')` constraint, so
Tier G (GSAP)/Tier H (helper library)/Tier W (WebGL) are structurally unreachable from this
mechanism, not merely unselected by convention. This is a deliberate, narrower scope than Spec
38's full four-tier doctrine: Spec 38 §11.4 independently states "live-scrape ingestion NEVER
emits fx attrs... an inferred effect is a guess, and guesses are banned" — that rule governs the
`data-sgs-fx-*` AUTHORING grammar (a Bean-controlled draft declaring its own effect), a different
vocabulary from `sgsAnimation` (a Tier V CSS preset R8 infers from real, present CSS declarations,
never from JS behaviour). The two systems do not overlap: R8 never emits an `fx*` attribute, and
the `data-sgs-fx-*` lift (`db_lookup.lift_behavioural_attrs()`, FR-38-22) never runs CSS shape
inference. A cloned page therefore never silently acquires a GSAP or WebGL bundle it didn't
already declare — R8 cannot select a tier capable of doing that.

### 14.6 Known limits

- **`%`-unit transform magnitudes** are not normalised against a reference viewport — the largest
  remaining code-fixable gap, NOT BUILT.
- **Fade direction is not preserved** — `parse_opacity_change()` uses `abs()`, so a fade-OUT (the actual shape of Locomotive's `.c-preloader`) resolves as `sgsAnimation: "fade-in"`.
- **JS-state/interaction-toggled effects with no timing signal** (a hover-triggered tooltip, a scroll-triggered library widget with no `IntersectionObserver` call) are out of scope by design — Tier 4b only watches for a load-timing diff; simulating an arbitrary interaction to probe for one would mean guessing which interaction applies, which this system's whole discipline (decline rather than guess) refuses to do.

## 15. JS-array-sourced repeated content resolution (FR-31-26)

**Problem.** A boundary's real content can live ONLY in a JS class property such as `static TICKER = [['text', 'iconPath'], ...]` (Eye Care Birmingham's ticker), never as static text in the DOM; the `<sc-for list="{{ ticker }}">` item template's `{{ t.text }}`/`{{ t.icon }}` bindings resolve only via a separate `.map(t => ({text:t[0], icon:t[1]}))` transform elsewhere in the file. The same draft has many such `static ARRAY = [...]` declarations, so this is a draft-wide authoring pattern, not a per-boundary case. Every extraction signal this pipeline has (role derivation §13.2, Spec 44 Stage A/B, the text-leaf ladder) operates purely on DOM text — a boundary whose content is JS-array-sourced has zero usable signal, inflating Spec 44/45's own review/no-match buckets for reasons neither spec's own mechanism can see or fix.

**No custom JS-array-literal parser.** The array body is inside `<script type="text/x-dc">` — inert to a real browser. Parsing the array literal, plus a second parser for the `.map(...)` field-correlation expression that declares which array index maps to which `{{ t.field }}` binding, duplicates, unreliably, what the draft's OWN runtime already does correctly, and risks the general-purpose-JS-interpreter scope creep this spec's R-31-1/R-31-9 discipline exists to prevent.

**Approach: render the draft with its own runtime, read the resolved DOM.** The draft ships two REAL `<script src="./support.js">`/`image-slot.js` includes. `support.js` is a genuine client-side renderer for the whole `<sc-for>`/`<sc-if>`/`{{ }}`/`dc-import` DSL (`DCLogic`-based, React 18.3.1 via `unpkg`). Serve the draft over a real local HTTP server (NOT `file://` — the runtime's own `fetch()` calls for self-loading and sibling `dc-import` components are blocked under `file://` by browser security) and let `support.js` execute: the resulting DOM's `document.body.innerText` contains the real, exact ticker strings verbatim — zero custom JS parsing. This is the SAME pattern Spec 33's `theme-extractor/measure.js` uses for the CSS side (render in a real headless browser, read what the runtime actually produced, never parse the source) — this FR extends it to content, not computed style.

### FR-31-26.1 — non-destructive splice, never a full-document swap

The live-rendered DOM is NOT used as the pipeline's new mockup wholesale. React does not preserve the source's exact markup shape (attribute casing/order, custom `<sc-for>`/`<sc-if>` tags are consumed and vanish, class ordering can shift) — using the full rendered DOM directly risks the corruption a BeautifulSoup whole-document round-trip causes. Instead: for each `<sc-for>` in the ORIGINAL raw HTML with no static placeholder content, find its resolved counterpart in the live DOM and splice the resolved text back into the ORIGINAL draft's `<sc-for>...</sc-for>` body as literal markup — pure string/regex patching, matching `dc_import_resolver.py`'s own discipline (byte-identical outside the patched span). Runs on the mockup AFTER `<dc-import>` resolution (Stage -2), so a JS-array-sourced group inside an imported component is covered too.

### FR-31-26.2 — marker-based correlation, not document order

Matching resolved content back to the correct `<sc-for>` by DOCUMENT ORDER (Nth source `<sc-for>` = Nth resolved group) is fragile: ordering/count can shift under viewport-conditional logic (`ticker: (mob ? TICKER.concat(TICKER) : TICKER.slice(...))`) and `sc-if` branching. Instead: inject a unique marker attribute (`data-sgs-resolve-id="rN"`) onto each `<sc-for>`'s item-template element in a TEMPORARY served copy before rendering (pure string insertion — never touches the pipeline-bound mockup); since the runtime clones that template element once per array item, every rendered instance carries the same marker. Query the live DOM by marker, not position — a stable anchor tied to the specific `<sc-for>`, immune to how many items resolved or in what order.

### FR-31-26.3 — regression-safety, three independent stacking guarantees

1. **Scope-narrowed by construction.** Only `<sc-for>` groups with NO usable static content today
   (no `hint-placeholder-count` fallback, no literal text) are touched at all. A group that
   already extracts something is skipped entirely, byte-identical — this mechanism cannot
   regress anything already working because it never reads or writes it.
2. **Opt-in, not default-on.** Ships behind a flag, mirroring Spec 44's own rollout
   discipline (`--classless-match`/`--classless-auto-complete`, both `default=False` until
   measured across real runs) — promote to default only once verified across more than one
   draft.
3. **Fail-soft, never fail-hard.** Any failure (server won't start, Playwright unavailable, timeout, a genuinely dynamic array the runtime can't resolve) degrades to a no-op — the `<sc-for>` is left untouched, producing whatever gap it would produce without this mechanism. Matches `dc_import_resolver.py`'s own "unresolvable import left as-is, non-fatal" discipline — never a new failure mode, only ever a no-op.

### FR-31-26.4 — interaction with Spec 44/Spec 45 (no change to either)

This FR is a pure upstream content precondition. Spec 44's Stage A/B and Spec 45's field-tier resolution do not change at all — they simply receive real DOM text for a class of boundary that would otherwise hand them nothing. See Spec 44 §11 and Spec 45 §4.1.0 for the cross-reference notes recording this relationship.

## 16. Draft manifest, entity references and build order (FR-31-27)

### FR-31-27 — Draft manifest — BUILT (read-only; nothing consumes it yet)

**Behaviour.** `plugins/sgs-blocks/scripts/draft-manifest/manifest.py` reads a draft and the README beside it and writes a JSON manifest (and a markdown report) that lists:
- the **screens**: each `<main data-screen-label>` gated by an `isX` flag (`dc_template.py::find_screens`), matched to the README routes table (`readme_routes.py::read_readme_routes`) and given a kind (page, wc-archive, single-template, wc-cart, wc-checkout, wc-order-received, choice-flow) by `manifest_vocab.py::SCREEN_KIND_RULES`, with the target it is built as;
- **header and footer**;
- **entities** other things point at: modal, drawer, cart drawer (`sgs/cart` with `displayMode` drawer), mega menu, choice flow, and one form per page screen. An overlay is found from the script, not from names: a handler that sets state (`setState({modal:'size'})`) is tied to the flag that reads it (`sizeModalOpen: S.modal === 'size'`) by `dc_script.py::opens`. A name pairing (`openLens` with `lensOpen`) is the fallback and is marked `resolved_by: name`. Kind comes from the region's geometry (`manifest_vocab.py::GEOMETRY_RULES`). A region inside a screen is a state of that screen (`in_screen_regions`), not an entity;
- the **reference graph**: which screen, chrome piece or entity opens or links to which, with counts;
- a **build order** (`build_order.py::order`): global styles and Site Info; page shells (an empty page or template that only reserves the slug, so every link target exists); leaf entities; header and footer; page content. A reference edge always overrides the tier, and a cycle is reported instead of looped on.

A draft with no labelled screens yields one page and no entities, so a static draft such as Mama's homepage is unaffected.

**Not built.** No stage consumes the manifest. There is no per-client entity registry (kind, draft name, slug, post ID), no step that creates the entities, and no step that resolves a later reference to an entity that already exists. ### FR-31-28 — Screen route: clone one screen of a multi-screen draft — BUILT

### FR-31-29 — An unresolved template binding is never lifted into a block attribute — BUILT

**Behaviour.** A Claude Design draft's style values such as `padding: {{ secPad }}` are resolved by the draft's own runtime, so the static HTML the converter reads still carries the raw text. `converter/services/template_binding.py::drop_unresolved_bindings` runs at the one place the converter first reads a node's inline `style` (`converter/services/styling_helpers.py::collect_css_decls_for_element`, which also filters declarations from stylesheet rules). A declaration whose value contains `{{` or `}}` is dropped whole, before it can be tokenised into box sides or snapped to a design token, and is recorded as `kind: "dropped"` through the existing content-gap channel (`converter/services/content_gap_collector.py::record_declaration_gap`; reason "unresolved template binding"). Text and content bindings are not touched. A draft with no `{{` in a style value is unchanged.

**Why.** Without it a shorthand became four junk sides (`{"top":"{{","left":"secPad","bottom":"}}"}`), and `font-size: {{ h2 }}` was snapped to `var(--wp--preset--font-size--h2)`, a preset the site does not define, so the live heading rendered at 16px instead of 46px.

**Done when (met).** Eye Care homepage sections b2, b5, b7, b8 and b9: style-derived raw-binding attributes 18, then 0; boundary statuses unchanged; Mama's homepage markup byte-identical (32,767 characters); 874 converter tests pass.

**Not done.** About 13 content bindings (`{{ r.title }}` in button labels, a heading, a quote attribution, three `sgs/text` `text` values) still reach attributes: a different problem.

### FR-31-30 — Script-computed layout bindings as per-device values — BUILT and WIRED (A1, D1132)

**Behaviour built.** `orchestrator/script_bindings.py::resolve_tier_bindings` (with `orchestrator/script-bindings-eval.js`, a Node `vm` evaluator with an empty context and timeouts) reads the draft's script and evaluates every style binding that depends only on the draft's width flags. It reads the flag definitions from the script (`const mob = effW < 760, narrow = effW < 1024, wide = effW >= 1280`), never assumes them, and returns `{name: {mobile, tablet, desktop}}` for the device tiers, sampled at 375, the converter's tablet sample (800, `converter/db/db_lookup.py::device_tier_samples`; the evaluator's own default is 768, used only if that lookup fails, which the stage now reports) and 1440. A threshold is snapped as a FLIP POINT (`orchestrator/breakpoint_snap.py::flip_point`): `effW <= 767` already sits on the 768 edge and is left alone. Anything that depends on state, data or a loop item is returned as unresolved with its reason and never guessed; a draft whose flags cannot be read resolves nothing.

**Proof.** Eye Care: 140 names in style values, 75 resolved, 65 unresolved (37 loop-item fields, 28 state or data driven).
