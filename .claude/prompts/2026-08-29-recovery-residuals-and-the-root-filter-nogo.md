## ⛔ THE FOUR PITFALLS THAT COST REAL WORK ON 2026-08-28

### 1. A false completion claim is how work gets lost — not the stash

At 20:29Z the prior session told Bean the classifier was "fixed and **committed**". `git log`
still showed a commit from five days earlier. Nothing protected the file, so the stash took it.
**Before writing "committed" anywhere, run `git log -1 -- <path>` and read the date.** The
stash was the proximate cause; the false claim was the root cause.

### 2. FOUR too-narrow greps each produced a confident FALSE answer

Every one would have caused a wrong action. This was the dominant failure mode of the day:

| Grep | False answer it gave | Truth |
|---|---|---|
| `gridTemplateColumns` in `render.php`/`edit.js` → 0 | "dead on 10 blocks, delete it" | The **shared wrapper** reads it. Live, client-reachable. Nearly deleted from 9 blocks. |
| flat key against nested JSON | every lookup `None`; negative control "passed" | `css_element` is nested under `fields`. |
| `import.*SgsBorderControl` → 0 in 4 files | "peer shipped undefined refs" | Multi-line import lists. Imports were present. |
| `find -name "style.css"` on the server | "not deployed" | webpack emits `style-index.css`. |

**A grep returning 0 is a hypothesis, not a finding.** Before acting on absence, add a
POSITIVE CONTROL — grep something you know exists, in the same file, the same way. If the
control also returns 0, your pattern is wrong, not the world.

### 3. A test can pass for the wrong reason — build the control first

`extract-signatures.py --self-test` returned 8/8 PASS on the file with Cause A/B **removed**.
It passes with or without the feature, so it could not gate the recovery. Separately, a
fidelity check "passed" only because a broken lookup returned `None` for everything, including
the negative control. **A negative control that passes while every positive control fails is
not a control — it is the same bug twice.**

### 4. `--dry-run` before any shared-DB write, and read what it says

`sgs-update-v2.py --stage 1 --dry-run` revealed the ordering trap: the derived layer had been
regenerated by an already-reverted classifier, so reseeding would have written poisoned values
into the DB five tracks share. **Order: restore the generator → regenerate the derived layer →
reseed → commit.** Getting it wrong bakes in a regression that every gate passes.
