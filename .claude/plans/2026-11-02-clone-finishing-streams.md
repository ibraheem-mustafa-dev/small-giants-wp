# Finishing the three client sites, one stream (Indus first)

**Goal (Bean, 2026-11-02):** three sites good enough to present to prospective clients and start selling, each matching its Claude Design draft visually and functionally at 375, 768 and 1440. Speed matters more than pipeline purity: the sites are finished by hand with real SGS blocks and settings, and every fix on the two cloned sites is catalogued so the pipeline's remaining gaps can be found and fixed afterwards.

Rules every stream keeps:
- Fix with real SGS blocks and their settings first; a one-off effect with no setting goes in the block's Custom CSS box (Bean 2026-11-01). Never fake content (static copies of live data, screenshots as content).
- Indus and Mama's: edit on the client's mirror, then copy with `bash scripts/local-wp/push-to-remote.sh local-<client> <client>-test` (dry run first). Never run the clone route (`site-run.mjs`, `fill.mjs`, `intake.mjs`, `site-build.mjs --apply`) for a stream's client: a route run rebuilds the posts and erases the hand fixes.
- A framework defect (a block that cannot do what the draft shows) is fixed in the block itself, deployed with `build-deploy.py --target <site>` before any push to that site, and catalogued as a framework gap.
- Wrap-up stage (every stream, before Bean's presentation approval; Bean 2026-11-05): a lean parity walk of each page, `node scripts/parity/draft-live-walk.mjs <page config> --lean --widths 1440,768,375` (read-only: styles, boxes, hover end states, structure and scroll-ins), with the client's `divergences.json` as the accepted differences so it reports only new gaps; every remaining row is then triaged against the client's decided list (Eye Care: `sites/eye-care-ward-end/build/qa/decided.md`) before it is checked live or put to Bean, and the hand-paired configs open the handoff draft served locally (`SGS_DRAFT_URL`). Indus and Mama's configs are `sites/<client>/build/qa/parity/<page>.fill.mjs` (walker configs generated by Fill, pairing each `cr-ref` block with its draft element); Eye Care's are `sites/eye-care-ward-end/build/qa/parity/<page>.mjs`. The draft loads its photos from the internet, so run it on a normal connection (a home-page walk did not finish in 25 minutes at 38 KB/s on 2026-11-05).
- Root-cause rounds (Bean 2026-11-06, every stream; worked example: Indus round 8, `sites/indus-foods/build/qa/r8-root-causes.json` and the fix catalogue's "Round 8 root-cause register"). Bean's review findings go first to a read-only root-cause council, one investigator per area, and each finding gets exactly one class: setting not applied, handoff value the clone dropped, missing capability, framework bug, content, Bean's accepted change, or not reproduced. Count instances, not list lines: a global finding Bean mentions once is every element on every page where the live site differs from the draft. A finding is done only when every instance is fixed by one universal mechanism, measured. A hand sweep of existing settings is a patch: where a setting exists but was never set, the fix is the applier, which takes each live block's paired draft element (`cr-ref` pairing) and writes the setting from the draft's measured value and the handoff files (animations.json, surfaces.json, tokens). A hand patch is only for one of Bean's rulings (a D-n divergence). Priority (Bean): the three sites ready fastest. Do the biggest-impact fixes and the low-effort, low-risk ones first. A fix that is large, risky or hard for tooling to recognise goes to the polish stage, a documented checklist a review agent runs after each clone, rather than a tooling project.
- Each stream compares its page with the draft at 375, 768 and 1440 before and after each fix (`node scripts/computed-route/tools/vision-capture.mjs <client> <ENVKEY> <surfaces>` makes paired full-page captures), and keeps the site's site-check passing (`node scripts/computed-route/site-check.mjs <client> --site <client>-test`).

## Polish stage (after every clone, run once by a review agent)

The checks tooling cannot do reliably: large, risky or hard to recognise (Bean 2026-11-06). A Sonnet review agent runs them read-only on the client's mirror after the applier, writes `findings.json` (page, element, width, draft, live), and each finding is checked on the live DOM before it is fixed by the applier or a universal fix, never by hand. Wait for an entrance to end before any read: an element still moving reads wrong.

1. Page states: force hover and keyboard focus on every interactive element of each page and compare with the draft. Includes the states the applier cannot read: FAQ open icon, active nav underline, nav item hover tint, backdrop fade, menu opening on focus.
2. Drawer: open each accordion at 375 and 768, hover every row and compare per state.
3. Touch: tap ten controls per page group at 375 and 768 with `hasTouch`; a tap shows the hover look (Bean's T1), and a second tap elsewhere clears it.
4. Choice groups: any button row keeping one look after a click is a dead choice control; it must be a real field.
5. Card links: click the card body and the cue on every card; one link, keyboard reachable, no nested anchors, and the card's name read aloud.
6. Composed interactions: hover and focus block controls in place, looking for clipped, covered or stacked results a single-feature gate cannot see.
7. First seconds: frames at 0.5s, 2s and 4s of each hero against the draft, because a still of the end state hides a missing sequence. Check the live hero's source first: Indus's About hero is Bean's own animated SVG and plays, so a finding there was false.

What the Indus Custom CSS audit taught (2026-11-07): an audit that judged a snippet "no setting" from attribute names alone claimed about ten new settings were needed, and most were already possible through shared extensions (child sizing), element toggles, floating layers and parent alignment. Judge "no setting" only after reading the block family's source and trying the existing settings, and verify a patch against the draft, never against the patch itself (before and after the patch compared with each other proves only that nothing moved). Of the 14 gaps a cold re-review examined, 10 were real; Bean will decide next session what is built.

What the first run taught: check each finding against the owner's own issue list item by item and find its root cause before fixing (Indus: 117 issues, each checked on its own example in `E:/sgs-tmp/indus-r8/check117/`); a run that reaches zero applier ops can still fail the owner's check, so the applier's closing gate (`scripts/computed-route/lib/apply-gate.mjs`) fails a run whose no-setting rows name something the block can do.
