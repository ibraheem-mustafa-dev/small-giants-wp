# Clone coverage foundation

**Purpose.** Bean's requirement is that Spec 48 recognises and clones everything a draft can hold and every piece of functionality the SGS framework offers. Spec 48 was written in one direction only, from the draft in: its §10 value matrix lists the kinds of value a draft holds, and its Motion (row 11) and Behaviour (row 12) rows name "presets" and "SGS features" without a list. No document ever enumerated the framework's capabilities and asked how each is recognised and cloned, so every step closed on done-whens that could not fail for an unlisted capability. This plan makes coverage a machine check instead of a memory: a generated capability inventory, a coverage map, and a test that fails while any capability has no clone path or approved exclusion.

**Evidence (five coverage audits, session C, 2026-10-12).**
- Block settings: 13,304 attributes on 219 blocks; on the 97 `sgs/*` blocks, 5,746 are styling (covered by calibration and Fill) and 7,051 are not. Uncovered families: carousel behaviour (autoplay, speed, dots), accordion open state, layout and variant modes without a CSS property, media (background video, Lottie, Ken Burns), icons, product and collection data, parallax, click effects, conditional display. 6,524 of the 7,051 have no description in the framework DB, so no tool can know what a mode means.
- Effects and motion: entrances are covered; entrance stagger is always `null` in the inventory, the entrance trigger has no path, 16 of 22 `fx_effects` have no recogniser even under FR-48-77, and no writer sets an effect's own parameters. Hover tilt, border accent, whole-card links and responsive hide toggles have no path.
- Behaviours: intake records mechanisms (handler, timer, observer) and names surfaces by regex on state and component names, but has no behaviour-identification layer: a draft's timer advancing an index over an `sc-for` is never identified as "carousel, autoplay 5 s, loop, dots". Tabs, counters, countdowns, sticky header, notice banners, table of contents, filters, cart and modal triggers get their block with default options.
- Surfaces and site: no path for search, SEO meta, cookie consent, dark mode, popups and floating CTAs, booking, map embeds (two on Indus), newsletter signup, the 404, search and blog templates, or form conditional fields, file upload, spam protection and consent; the site-build script (FR-48-55) is not built.
- What a draft can hold: video and third-party embeds, `<picture>`, container queries (their conditions are dropped by `lib/intake-inventory-css.mjs::cssBlocks`), native `dialog`/`details`/popover, uncommon input types, scroll-driven CSS animation, dark mode, canvas and WebGL and animated SVG are not seen at all; 11 of 19 construct-registry kinds have no reader.

## Phases

### Phase 0. Standardised motion system (setup before the motion parts of this plan)
- [x] **0.1 Review** (done 2026-10-12, session C): a QC council of the current hover, entrance and fx implementations found fixed presets hiding the real variables, whole-block targeting only, about six reveal and stagger systems and seven hover systems with three incompatible data shapes, no per-device motion values, no usable token layer, flat-order stagger, and a resolver that cannot write a measured duration. Research (research council, gap-analysis C 3.25 with every C+ fix applied): `.claude/reports/2026-10-12-motion-system-research.md`.
- [x] **0.2 Design decisions** (done 2026-10-12, Bean, from `.claude/reports/2026-10-12-motion-system-research.md` section 1): D1 keep the existing `settings.custom` motion token names, extend only (distances, extra springs); D2 a preset stamps a copy whose values point at tokens; D3 one small plain-JS scroll driver in every browser for scroll-linked effects (the FR-38-35 precedent); D4 one framework default token set from the shared core of the Indus, Mama's and Eye Care drafts (hover 200-250ms, cards 300-350ms, reveals 600-900ms, 2-4px lifts, a fast-start gentle-settle curve), each client's exact values from its own draft; D5 the editor shows the final state plus a Replay button; D6 a custom selector for the cloning tool only inside the block root and only when a draft proves the need; D7 stagger restarts per visual row with a total cap, written by the container helper. Fixed inputs: three panels per element (Hover, Entrance and reveal, Effects), values underneath with presets on top, layered UX, explicit stored per-element delays.
- [x] **0.2 Brief** (Bean's target, which the decisions above answer): Bean's target is one standardised panel per motion type (hover, entrance and reveal, motion fx) on every compatible block; an effect type per element, each element customised on its own; picking a type reveals modular controls for every variable a draft can hold (for a fade: direction, distance, duration, delay, easing curve, optional presets); the same controls define site-wide motion tokens; container-level orchestration sets children's motion with an optional stagger and an order (for example row first, left to right). The current preset-heavy model is the problem: it is close to the banned hard-coded setup. Scope (Bean, 2026-10-12, confirmed against the DB): colour and shadow hover VALUES are already compliant (per-element `<slot>ColourHover` and per-element hover shadow settings with a `css_property` and `css_state='hover'`, set through the shared colour and shadow controls' hover state, calibrated and clone-writable) and stay as they are. The redesign owns hover effects (transform, filter, opacity, lift, tilt, zoom), entrance and reveal, motion fx, and the transition timing of every hover, which today is one duration and easing pair per block. `shadowLiftOnHover` (22 blocks) and the hover extension's `sgsHoverShadow` (8 blocks) are lift effects with no CSS property that overlap the compliant hover shadow, so they fold into the redesign; `shadowHoverColour` vs `shadowColourHover` naming is tidied in the same sweep.

### Phase 1. Capability inventory and the failing test (one session)
- [x] **1.1 Framework inventory** (built 2026-10-17, branch `claude/clone-coverage-plan-review-2bbei4`). `scripts/computed-route/capabilities.mjs --write` generates `data/capabilities.json` through `lib/capabilities.mjs::buildInventory`: block settings grouped by role and kind (motion, styling, mode, or attribute type, by `lib/capabilities.mjs::settingKind`), `fx_effects` rows and `motion_presets` families from the framework DB read-only; `supports.sgs` keys, extensions, templates, parts, patterns, post types, plugins and theme-snapshot key paths from the code. No hand-written list. Proof: `node --test scripts/computed-route/tests/capabilities.test.mjs` (9 pass, fixture DB from `dbschema/schema.sql`). The committed file was written without the DB, so its three DB sections read `absent` until step 1.5.
- [x] **1.2 Draft inventory** (built 2026-10-17). The same command lists HTML elements (`html-tag-names`), CSS at-rules and property groups (`mdn-data`) and the construct registry's kinds. Intake's missing-features step raises one row per HTML element or construct kind it sees that the coverage map does not cover (`lib/intake-missing.mjs::coverageMissing`, proof `tests/intake-coverage-rows.test.mjs`, 3 pass). CSS at-rules and property groups are inventoried but intake does not yet report the ones a draft uses (its stylesheet reader `lib/intake-inventory-css.mjs::cssBlocks` keeps only `@media`); that reader belongs to the Phase 4 wave that covers container queries.
- [x] **1.3 Coverage map** (built 2026-10-17). `data/clone-coverage.json` (schema `data/clone-coverage.schema.json`): per capability ID its `recognise`, `write` and `check` references (`construct:<kind>` or a repo path with `#symbol`), or Bean's `excluded` (reason, `signedBy`, date). An entry missing a step is a gap naming its Phase 4 `wave` (`unassigned` until triaged); a motion gap carries `waiting: "phase-0"`. Seeded with a gap stub for every non-DB capability; the eight registry kinds with a reader record it.
- [x] **1.4 The gate** (built 2026-10-17). `tests/clone-coverage.test.mjs` (8 pass) and `node scripts/computed-route/capabilities.mjs --gate` fail on an inventory ID with no entry, an entry for an unknown ID, a reference to a missing file, export or construct reader, an unsigned exclusion, a gap with no wave, and a motion gap not waiting on Phase 0. MUST FAIL controls: a planted block setting, a planted draft tag, a missing writer.
- [ ] **1.5 First run is the definitive gap list.** First run done 2026-10-17 on Bean's PC (`175d693`: every section `ok`, 643 capabilities uncovered). Triage done the same day: every gap names its Phase 4 wave, and four value kinds are recorded as covered end to end because the route already recognises, writes and checks them (CSS styling: `scripts/computed-route/lib/fill-read.mjs#readDraft`, `lib/fill-prop.mjs#resolveProperty`, `lib/triage.mjs#triage`; text, link URLs and show/hide toggles through `lib/fill-presence.mjs`; structural and text HTML elements through the skeleton). Covered: 4,819 of the 9,438 SGS block settings; 1,098 are motion settings waiting on Phase 0. No CSS property group is read in full (`lib/fill-read.mjs::PROPS` holds 68 properties; grid layout 1 of 23). The gap list by wave: `.claude/reports/2026-10-17-clone-coverage-gaps.md` (`node scripts/computed-route/capabilities.mjs --gaps`). **Open:** Bean signs the exclusion candidates (each gap whose wave is `exclusion candidate (awaiting Bean)`); each signed one becomes an `excluded` entry.

**Phase 4 waves (named by the step 1.5 triage; Phase 4 orders them by the Indus gap list):** motion writer (4.0, waits on Phase 0); modes and values with no CSS property; behaviour recognisers; content, media and icons; shop, forms and data; site and surfaces; draft reading (container queries, unread CSS property groups, construct kinds with no reader).
