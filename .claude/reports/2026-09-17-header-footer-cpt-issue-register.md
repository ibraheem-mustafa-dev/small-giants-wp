# Header/footer/nav-drawer builder — issue register

Front D (`LEDGER.md`) closed out 5 visual issues in the header/footer builder. While checking
the admin backend before Mama's/Indus branded content authoring starts, Bean found a larger set
of architecture problems in how the Advanced Header / Advanced Footer / Nav Drawer CPTs work.
This register tracks those, decomposed one issue per row. Full narrative + investigation plan:
`.claude/plans/doc-type-next-session-prompt-project-magical-puppy.md`.

| ID | Issue | Category | Root cause / status | Next action |
|---|---|---|---|---|
| A | What settings exist on the Header Settings / Footer Settings admin pages | Understood | These are the **Header Rules / Footer Rules** admin pages (`class-sgs-header-rules-admin.php`, mirrored for footer): a priority-ordered routing engine — `Show this header/footer when` condition (post type / template / URL regex / user role / device) picks which registered pattern displays where. Not per-header settings. | None — resolved. Feeds into B. |
| B | Should these settings pages unify with the CPT, or be settable per-CPT-post directly | **Concrete proposal, corrected scope** | Bean's actual ask (clarified): merge the "Header Rules" admin page and the "Advanced Headers" CPT-list page into ONE screen — the Rules table (there are only ever a handful) at the top, the CPT's post-instance list below it, on the same page. Same for Footer. This is a pure admin-screen layout change; it does NOT touch the shared header/footer block wrapper mechanics, so it does NOT need the same design-gate as G — pulled out of that session per Bean's decision. | Route to `wp-sgs-developer` — build the merged screen for both Header and Footer. Independent of the G decision. |
| C | Advanced Header/Footer/Nav-Drawer CPT list pages start with zero items | **DESIGNED — Spec 37 v1.2.0 FR-37-48. No seed content, no default active post. | Auto-run the already-built `wp sgs header\|footer\|drawer seed-starter` (FR-37-30) once per site, on plugin activation, guarded against double-seeding, so the list is never empty. |
| D1 | `sgs/site-header` block sits inside the Advanced Header CPT itself | **DESIGNED — Spec 37 v1.2.0 FR-37-46. | D2 | Blocks can exist outside the 3 locked header/footer rows | **DESIGNED — Spec 37 v1.2.0 FR-37-46 + FR-37-49. Council-reviewed, Bean-approved, ready to build (W2-b still needs its own scoping pass first — see FR-37-49).** | `sgs/site-header`/`sgs/site-footer` lock their own top level to exactly 3 rows (`templateLock:'all'`, `allowedBlocks` restricted) — but `sgs/nav-drawer` sits as a **sibling** to `sgs/site-header` in the same CPT post, entirely outside that lock, and more blocks can be added below it with no upper bound. | Template-lock the CPT post itself to exactly one block (FR-37-46) closes the "anything else" half; dropping `sgs/nav-drawer` from patterns (FR-37-49) closes the drawer-specific half — sequenced together with the drawer post-picker (W2-b), never before it, since that's currently the only way to attach drawer content. |
| D3 | These CPTs carry no CPT-specific settings/meta schema of their own | **Investigated — small gap confirmed** | DB queries (`block_attributes`/`block_composition`) confirm styling/behaviour already lives correctly on the blocks themselves (`sgs/site-header`, `sgs/nav-drawer`), and a separate Header/Footer Rules system already handles page-targeting — so B's premise ("unify Rules into the CPT") doesn't hold; they solve genuinely different problems. The real gap is a handful of operational fields with nowhere else to live: `_sgs_is_default` (which header/footer is the fallback), a computed usage-count (which ones are safe to delete), and for drawers, `_sgs_referenced_by` (what currently points at this drawer, so one can't be silently orphaned). Established precedent to follow: `class-sgs-template-part-meta.php`'s `register_post_meta()` shape. | Small, low-risk addition — route to `wp-sgs-developer` for implementation once you confirm you want it. |
| E | Clicking a hyperlinked element in these CPT editors navigates to the link/page instead of selecting the block | **FIXED — diff ready, not committed** | Confirmed and fixed. The real census (via a new detector script, not the assumed list) found **9** unwrapped `<ServerSideRender>` usages, not 3: `before-after`, `brand-strip`, `business-info`, `card-grid`, `nav-bar-menu`, `nav-drawer-menu`, `product-card`, `responsive-logo`, `trustpilot-reviews`. All 9 fixed with `<Disabled>` wrapping. A permanent gate script (`audit-serverside-render-disabled.js`) now fails the build on any future regression — confirmed passing with 0 violations, build compiles clean. One unrelated pre-existing gate failure disclosed (`dbschema-check_schema_drift`, Spec 44 work, not touched). | Needs your review of the diff, then a live Playwright check in the actual block editor before commit. |
| F | Leaving a header row empty shows a large, non-dismissable placeholder | **Confirmed — fix-shape agreed by 2 independent investigators** | It's a custom `RowQuickInsertAppender` component (not vanilla Gutenberg), rendered whenever a row has zero inner blocks, with no dismiss control. It names business-info variants because the row's own hardcoded "promoted quick-insert" button list includes 3 business-info variants for footers, 1 for headers — this is deliberate steering UI (Spec 37 §3.5 / FR-37-34), not a bug in itself, but the lack of any dismiss/escape is. Prior art already exists in the same codebase: `sgs/container` uses the plain default WP appender for its optional empty slot. | Add a dismiss control to `RowQuickInsertAppender` that falls back to the plain default appender, matching `sgs/container`'s existing pattern. Not yet implemented — awaiting your go-ahead. |
| G | Content can exist outside the 3-row hard-set structure (nav-drawer as a sibling block, more addable below it) | **DESIGNED — Spec 37 v1.2.0 FR-37-46, decided: Option 2. Council-reviewed, Bean-approved, ready to build.** | **Option 1** (rejected): the CPT becomes the header block itself — its meta mirrors `sgs/site-header`'s own attributes, holding only the 3 rows; injected into a real block at render time. **Option 2** (chosen): keep `sgs/site-header` visible, template-locked so nothing can exist beside or below it. Option 1 bought nothing Option 2 doesn't already deliver, at real migration cost. | Bean approved Option 2 and confirmed the block already carries its full settings surface (verified: 58/65/48 attrs on header/footer/drawer, no CPT-meta duplicates). A required pre-build check remains: confirm the WP mechanism this depends on actually works the way FR-37-46 assumes (see the spec's own "verification spike" note). |
| H | "SGS Default" nav-drawer preset allegedly forces "Edit Pattern" mode instead of inserting loose, directly-editable blocks | **DESIGNED — Spec 37 v1.2.0 FR-37-46/47, overrides FR-37-7. Council-reviewed, Bean-approved, ready to build.** | Static code reading (2 investigators) correctly found no synced-pattern reference in either pattern file — the mechanism isn't in the file, it's attached by WordPress itself at insertion time. Live-tested on the canary: picking EITHER "Start from Scratch" OR "SGS Default" stamps the inserted block with pattern-provenance metadata that locks child-block editing behind an "Edit pattern" click — **affects BOTH presets identically**, core WordPress's own per-CPT starter-pattern behaviour. Root cause: these 3 CPTs rely on WP's native empty-post picker (FR-37-7, Bean-signed-off 2026-07-24 specifically to avoid bespoke UI) — a template-locked post (FR-37-46) is never empty, so that picker can never fire again, for better or worse. Bean explicitly overrode FR-37-7 for these 3 CPTs rather than accept the friction. | **Corrected 2026-09-17 (was: a bespoke "Load a starter" action — that design was replaced after council review, see D1092):** FR-37-47 makes the starter looks a preset control on the locked block itself, the same shape as the already-built "Layout preset" control (FR-37-28) — no separate action, no new write path. Choosing a preset sets attributes and, where needed, replaces a row's content using the same safe client-side call `RowQuickInsertAppender` already uses. Same 14 starters stay usable; H can't recur because content never goes through WP's pattern-insertion path at all. `sgs_mega_menu` keeps FR-37-7 unchanged. |
| I | Nav Drawer CPT requires inserting `sgs/nav-drawer` into its own content (looks circular) | Explained, deliberate | Confirmed intentional: one editable `sgs/nav-drawer` copy lives in the Drawer CPT, referenced by a global "Active Layout" pointer (an option, not a block attribute) — replacing an older, worse pattern of pasting the block into 8 separate header patterns as a sibling. | No action needed unless the G-session's chosen render mechanism changes how content is wired from CPT to live block — revisit then. |
| J | `sgs/cart` is wrapped in an unnecessary `sgs/container` in the default header | **FIXED — diff ready, not committed** | Found 4 instances (not just the 1 originally spotted): 3 were genuinely redundant single-child wrappers and have been removed (`framework-header-default.php`, `header-search-bar-above.php`, `header-search-bar-below.php`); 1 (`header-search-icon.php`) is a real 2-icon grouping (search + cart) doing genuine flex work and was correctly left alone. | Needs your review of the diff, then a live Playwright check on the deployed canary before commit. |
