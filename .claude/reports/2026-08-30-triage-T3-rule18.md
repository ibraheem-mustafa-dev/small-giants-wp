## 1. The 12 findings — classification rollup

| Bucket | Count | Blocks |
|---|---|---|
| **REAL** | 5 | card-grid, gallery, post-grid, team-member, testimonial |
| **DECORATIVE BY CONSTRUCTION** | 2 | decorative-image, social-icons |
| **ARTEFACT** | 5 | before-after, brand-strip, image-sequence, product-card, responsive-logo |

### DECORATIVE BY CONSTRUCTION (verified, not assumed)

- **`sgs/decorative-image`** (`render.php:174-181,467-482`) — every `<img>` it emits hardcodes `'alt' => ''`, `'aria-hidden' => 'true'`, `'role' => 'presentation'`, unconditionally. The `imageAlt` attribute it declares is read into a legacy `decorMedia` synthesis object but is **never used on the actual rendered tag** — dead value, not a live override. Genuinely decorative by construction; the toggle the rule wants would be redundant.
- **`sgs/social-icons`** (`render.php:455,492`) — a custom-icon `<img>` always gets `alt=""`, and the accessible name comes from the wrapping `<a aria-label="...">` (line 492) that names the platform ("Follow us on Facebook"). Confirmed correct pattern: link carries the name, image is properly decorative.

### ARTEFACT (already has real alt-text control; the rule's regex is too narrow)

The rule's exemption test is `/decorative|arialabel|alttext/i` matched against attribute **names**. It requires the literal substrings "decorative", "arialabel", or "alttext" — it does **not** match the framework's common bare-`Alt`-suffix naming (`imageAlt`, `thumbnailAlt`, `beforeImageAlt`), and it only scans **top-level** attributes, missing attributes nested inside a repeater's item schema.

| Block | What actually exists | Why the regex misses it |
|---|---|---|
| `before-after` | `beforeImageAlt`, `afterImageAlt`, `beforeVideoAlt`, `afterVideoAlt` (block.json top-level, all `type:string`) | Name ends `...ImageAlt`/`...VideoAlt`, not `...AltText` — no `alttext` substring |
| `image-sequence` | `thumbnailAlt` (block.json:80, documented as "alt TEXT" in the block's own `_note`) | Same: `thumbnailAlt` has no `alttext` substring |
| `product-card` | `imageAlt` attribute + resolved alt text threaded through every image branch (`render.php:694,1083,1131,1528`) | Same: `imageAlt` has no `alttext` substring. Product photos are also inherently informative (they represent a real SKU) — a decorative toggle would fight the block's own purpose |
| `responsive-logo` | Top-level `alt` attribute (block.json:157), explicitly documented elsewhere in the codebase as `role: image-alt`, paired to `logoUrl`/`logoIdTablet` etc. | Bare `alt`, no `alttext`/`decorative`/`arialabel` substring at all |
| `brand-strip` | Per-logo `alt` field **nested inside the `logos` repeater's item schema** (`block.json` `items.properties.alt`), plus render-time logic that sets `alt=''` automatically whenever a visible caption/name is shown so the name isn't double-announced (`render.php:530-540`) | Nested attribute — the rule's `attrNames` scan only reads `blockJson.data.attributes` at the **top level**, never repeater item properties |

None of these five need the suggested fix ("add `isDecorative`/`ariaLabel`") as-is — `brand-strip` is the only one with room for a genuine small enhancement (a manual per-logo decorative override, on top of its existing automatic caption-based one), but that is an enhancement, not a fix for a missing control.

### REAL (genuine gap — confirmed no alt-text or decorative attribute exists anywhere)

| Block | Evidence checked | Negative control (paired, same file family) |
|---|---|---|
| `card-grid` | Zero `alt`-matching attribute declared. The only `alt` handling in `render.php:730-737` is `alt=''` hardcoded **only** inside the legacy bare-URL-string normalisation branch (a back-compat fallback), not the primary object-media path — the primary path has no client-facing alt control at all | Contrast with `before-after` (same "media slot" family), which genuinely declares 4 alt attrs — proves the scan can and does find real alt attrs when present |
| `gallery` | Alt is read only from `$img['alt'] ?? ''` — i.e. whatever the Media Library attachment carries (`render.php:178,365,373`) — with **no block-level attribute** letting the operator override it or mark an image decorative | Contrast with `product-card`, which resolves alt the same Media-Library-first way but *additionally* exposes `imageAlt` as an override — gallery has no equivalent |
| `post-grid` | Zero `alt` references anywhere in `render.php`; zero alt-matching attributes in `block.json` | Contrast with `team-member`, which at least auto-fills `alt` from the person's name — post-grid has neither an attribute nor an auto-fill |
| `team-member` | Auto-fallback only: `if (empty($media_for_render['alt'])) { $media_for_render['alt'] = $name; }` (`render.php:245-246`) — no attribute exposes this to the operator, no decorative option | Contrast with `responsive-logo`, which has an equivalent "always-meaningful image" semantics but *does* expose the value as a real attribute — team-member does not |
| `testimonial` | Zero `alt`-matching attributes; the avatar/org-logo media objects are rendered via `sgs_render_media()` with whatever the media library returns, no operator override surfaced | Contrast with `brand-strip` — same "media object with an optional caption" shape, but brand-strip's repeater schema carries a real (if nested/invisible-to-the-rule) alt field; testimonial's does not |

## 2. Task 2 — the detector false-negative (ariaLabel-for-a-link)

**Confirmed real.** The rule's exemption test only checks whether a block **declares an attribute whose name** matches `/decorative|arialabel|alttext/i` — it never checks what that attribute actually labels. Several blocks declare a top-level `ariaLabel` string attribute used exclusively to label the block's own **landmark tag** (`nav`/`aside`) or a **link**, wholly unconnected to any image inside the block. Any such block that also renders an `<img>` in `edit.js` is wrongly cleared.

Full sweep: 10 blocks in the tree declare an attribute matching the exemption regex — `button`, `cart`, `container`, `cta-section`, `hero`, `icon`, `media`, `nav-drawer`, `timeline`, `trust-bar`. Checked each for whether it (a) actually renders an `<img>` in `edit.js`, and (b) what the matched attribute really labels:

| Block | Renders `<img>` in edit.js? | What `ariaLabel` actually labels | Falsely cleared? |
|---|---|---|---|
| `button` | No (no image at all) | The button/link's own accessible name | N/A — not image-bearing |
| `cart` | No (SVG icon via `sgs_get_lucide_icon`) | The cart-icon link | N/A |
| `container` | No (background image is a CSS `background-image` decl, never an `<img>` tag) | The `nav`/`aside` landmark | N/A — correctly not flagged (no `<img>` regardless) |
| `icon` | No (SVG, not `<img>`) | The icon's own `role="img"` wrapper — this is the ONE case where `ariaLabel` legitimately labels image-equivalent content | N/A — not image-bearing per the rule's own `<img>`-tag test |
| **`cta-section`** | **Yes** — `<MediaPicker>` (background image), confirmed on the frontend too (`render.php:74`, real `<img>`-equivalent background image with its own `alt`) | The `nav`/`aside` landmark tag (`render.php:587-589`) — unrelated to the image | **Yes — false negative** |
| **`hero`** | **Yes** — literal `<img>` at `edit.js:1714`, and a real frontend `<img>` with `fetchpriority="high"` for LCP (`render.php:952,987`) | The `nav`/`aside` landmark tag (`render.php:1390-1392`) — unrelated to the image | **Yes — false negative** |
| **`trust-bar`** | **Yes** — `<MediaPicker>` + literal `<img>` at `edit.js:1109`, and a real frontend badge `<img>` (`render.php:506-508`) | The `nav`/`aside` landmark tag OR the fixed `'Trust signals'` region label (`render.php:265,283-284`) — unrelated to the image | **Yes — false negative** |
| `nav-drawer` | Yes — but only a literal `<img>` inside the **editor-only** inspector preview thumbnail (`edit.js:537`), already hardcoded `alt=""`. The real frontend paint is a CSS `::before` background layer, never an `<img>` tag | The drawer's own dialog/landmark label (`render.php:635-636`) — unrelated to the image | Technically yes under the rule's literal logic (edit.js-only scan), but **moot in practice** — the frontend has no `<img>` to need alt/decorative handling, and the one `<img>` that exists is already correctly `alt=""` |
| `media` | Yes | N/A — `media` declares `imageIsDecorative`, which matches `/decorative/i` directly (legitimate exemption, not the ariaLabel path) | No — correctly exempted for the right reason |
| `timeline` | Yes (milestone media) | N/A — declares `milestoneMediaDecorative`, matches `/decorative/i` directly | No — correctly exempted for the right reason |

**Enumerated affected blocks: `cta-section`, `hero`, `trust-bar` (confirmed, high-confidence), plus `nav-drawer` (matches the rule's literal edit.js-scan logic but is a moot/low-severity case since the frontend never renders an `<img>` for that background).** This lands on **3 confirmed + 1 borderline = 4**, matching the plan's working estimate of 4 — but I'm reporting the breakdown rather than a flat "4 confirmed", because `nav-drawer`'s case doesn't carry the same real-world accessibility risk as the other three (no frontend `<img>` exists to fix).

### Negative control — proving a corrected test doesn't overmatch

A corrected test needs to stop treating a bare `ariaLabel` attribute name as sufficient proof of image-decorative coverage. The safest correction: **only exempt via the `arialabel` branch of the regex when there is no independent evidence the attribute is used to label a landmark tag** (i.e. don't blanket-trust the name; or, more simply, drop `arialabel` from the auto-exempt set entirely and require `decorative`/`alttext`-named attributes specifically for image accessibility).

Applying either correction to `sgs/media` (which is NOT one of the 12, and must stay cleared) proves the fix doesn't overmatch:
- `media` renders an `<img>` (would pass the `rendersAnImage` gate).
- `media` declares `imageIsDecorative` — this matches `/decorative/i` directly, independent of the `arialabel` branch.
- Under the corrected test (drop bare `ariaLabel` trust, keep `decorative`/`alttext`), `media` is **still correctly exempted** — the correction only removes false trust in `ariaLabel`, it does not touch blocks that were already exempted for a real reason.

A second negative control on the "does the correction touch non-image blocks" side: `container` has `ariaLabel` (landmark-only, same pattern as the 3 false negatives) but never renders an `<img>` — under both the old and corrected test it is correctly never flagged (the `<img>` gate fails first regardless of the exemption regex). This confirms the correction's blast radius is exactly the 3-4 blocks identified, not wider.

## 3. Task 3 — the naming question

Full-tree search (`grep -rniE 'decorative'` across every `block.json`, cross-checked against nested schemas and the top-level attribute scan) found **exactly two** accessibility decorative-toggle attribute names in use, both boolean, both functionally correct and wired end-to-end (checked/set in `edit.js`, read in `render.php`, actually gating `alt`/`aria-hidden` on the rendered tag):

| Name | Block | Shape |
|---|---|---|
| `imageIsDecorative` | `sgs/media` | `{prefix}` = `image`, pattern = `{element}IsDecorative` |
| `milestoneMediaDecorative` | `sgs/timeline` | `{prefix}` = `milestoneMedia`, pattern = `{element}Decorative` (no "Is") |

**No third variant exists.** A broader sweep for any nested/repeater "decorative" field (in case a block hid one inside an `items[]` schema the way `brand-strip` hides its `alt`) found none — only false-positive matches that are a **different, unrelated namespace**: `container`, `cta-section`, `nav-drawer`, `site-footer`, `site-header` each declare a `"decorative"` key inside `supports.sgs.elements` — this is an **element-manifest grouping label** (Spec 35's per-element style-cluster system, e.g. "the decorative background element" covering `backgroundImage*`/`bgVideo*`/`bgSvg*` as one styling cluster), not an accessibility attribute. Do not conflate the two when settling the name.

**The naming inconsistency to settle:** `imageIsDecorative` (with "Is") vs `milestoneMediaDecorative` (without "Is") are the only two live instances, and they disagree. Every other SGS boolean attribute in the framework reads as a bare adjective, not an "is"-prefixed predicate (`scrolling`, `pauseOnHover`, `showNames`, `fadeEdges`, `dismissible` — none use an "Is" prefix). `milestoneMediaDecorative`'s shape matches that convention; `imageIsDecorative` is the outlier. Recommend settling on the **`{element}Decorative` pattern (no "Is")** as the one name the cloning pipeline reads going forward, and renaming `media`'s `imageIsDecorative` → `imageDecorative` to match — that is a decision for the design gate, not something this triage should apply unilaterally.

## Method notes

- Population (12) was declared from the scan output before any classification began.
- Every REAL classification is paired against a same-family block that DOES have the relevant control, to rule out "the scan just doesn't check for X" as the reason for a zero.
- Every DECORATIVE-BY-CONSTRUCTION claim was verified by reading the actual `render.php` output construction (not inferred from the block's name or its listed purpose), per this project's rule that a claim about rendered behaviour must be checked against the real render path, not assumed from a block's stated intent.
- The false-negative enumeration checked all 10 blocks matching the exemption regex tree-wide, not just ones already suspected — `button`/`cart`/`container`/`icon` were ruled out with evidence (no image, or CSS-background-only, or SVG-only), not assumed clear.
