# Fluid Typography as the Cause of Mobile Clone-Fidelity Loss — Hypothesis Test

**VERDICT: PROVEN.** The exact WordPress fluid `clamp()` formula found in the live global-styles stylesheet reproduces the clone's measured font-size to the pixel at all three tested viewports (375px → 14.00px, 768px → 14.95px≈15px, 1440px → flat 16px), while the draft's declared value is a flat 16px at every width. This is not a correlation — it is the same numeric formula, walked by hand, landing on the exact measured values.

## The decisive 1440px test

**Result: elements affected by fluid clamp() MATCH exactly at 1440px** (above the theme's `maxViewportWidth: 1200px` ceiling, where `clamp()` flattens to its max bound). None of the three traced elements below appear in the 1440px mismatch list — they only appear at 375px and 768px. This is precisely the predicted signature: a gap that shrinks as viewport widens and disappears above 1200px.

A second, unrelated font-size issue also exists at 1440px (see "What this is not" below) — it does not follow the clamp signature and must not be folded into this finding.

It rules out a per-block data bug and points to one shared, theme-level mechanism.

## The mechanism, traced to source

`theme/sgs-theme/theme.json` (lines 96–99) sets global fluid typography:
```json
"fluid": { "minViewportWidth": "375px", "maxViewportWidth": "1200px" }
```
This setting is **global**, at `settings.typography`, not scoped to individual presets. WordPress's typography engine (`wp_get_typography_font_size_value()`) applies it to **any** numeric font-size a block declares — preset or literal custom px — unless that specific value opts out via its own `"fluid": false`.

The registered preset scale (`fontSizes`, lines 155–213) only declares `fluid: false` for two sizes: `x-small` (12px) and `medium` (18px). Every other size — `small` (14, fluid 13–14), `large` (20, fluid 17–20), `x-large`, `xx-large`, `hero` — is fluid. **None of the registered presets has a flat/base size of 16px.** The draft's 16px is therefore not landing on a registered non-fluid token; WordPress is auto-fluiding the raw 16px value against the theme's global min/max viewport settings.

Fetching the live clone's rendered `<head>` (global-styles inline CSS block) confirms the exact formula in use:
```
clamp(14px, 0.875rem + ((1vw - 3.75px) * 0.242), 16px)
```
Walking this by hand at each tested viewport:
- **375px**: `1vw = 3.75px` → `(3.75 − 3.75) × 0.242 = 0` → `14 + 0 = 14.00px` — **exactly matches the clone's measured 14px.**
- **768px**: `1vw = 7.68px` → `(7.68 − 3.75) × 0.242 = 0.951px` → `14 + 0.951 = 14.95px → rounds to 15px` — **exactly matches the clone's measured 15px.**
- **≥1200px (incl. 1440px)**: clamp flattens to its upper bound, `16px` — matches the draft's flat 16px, hence zero mismatch reported.

This is the same clamp family that produces the theme's other registered fluid sizes (`clamp(13px,…,14px)`, `clamp(17px,…,20px)`, `clamp(20px,…,24px)`, `clamp(26px,…,36px)`, `clamp(32px,…,50px)` were all found live in the same stylesheet fetch) — confirming the 14px/16px clamp is generated by the identical engine, just against an ad-hoc 16px input rather than a registered preset.

## Line-height: consequence, not an independent cause

The theme's default paragraph typography (`styles.typography`, line 417) sets `lineHeight: "1.7"` as a **unitless multiplier**, and block-level text styles in this framework follow the same unitless convention. A unitless line-height recomputes automatically whenever the browser resolves the element's `font-size` — no separate fluid mechanism is needed for it.

Check against the traced ratios:
- Draft: `line-height 26px / font-size 16px = 1.625`
- Clone at 375px: `22px / 14px = 1.571` (close; rounding on both the font-size and the line-height pixel outputs stacks small rounding error)
- Clone at 768px: `24px / 15px = 1.60`

The ratio is stable (~1.57–1.63) across all three widths and consistent with a single authored unitless multiplier applied to a shrinking font-size. **Line-height is a downstream consequence of the font-size clamp, not an independently-caused defect.** Fixing font-size fluid-scaling will fix line-height as a side effect, with no separate line-height fix needed.

## What this is NOT (a distinct, smaller finding — do not conflate)

At 1440px, four `<button>` labels ("8pack"/"12pack"/"20pack"/"40pack") and three reviewer-name `<p>` elements ("reham london", "sarah m manchester", "halimah birmingham") show `draft: 13px, clone: 14px` — and this mismatch is present at 1440px, i.e. it does **not** disappear above the 1200px ceiling. This is the `small` preset (registered fluid 13–14px) being used where the draft actually authored a flat 13px. Above the ceiling the clamp holds its **max** bound (14px) which is 1px off the draft's genuine 13px value. This is a separate, minor preset-calibration mismatch (the `small` token's `max` doesn't equal 13), not part of the fluid-typography-vs-fixed-draft defect this hypothesis targets. Flagging it here only so it is not mistakenly folded into the fix for the main finding.

## Which bug class this is

Per this project's fidelity contract (R-31-11/R-31-13: fidelity closes on computed-value match to the draft + Bean's eye — CONVERT, don't improve; zero cheats), **this is a CONVERTER bug, not a desirable improvement and not purely a measurement artefact.**

Reasoning:
- Fluid typography is a legitimate, good CSS practice for a live client site — but that is a decision for the *design system* (theme.json), applied deliberately per-token, not an accidental side effect of *how the converter emits font sizes*.
- The actual defect is narrower than "fluid vs fixed": the converter is emitting a **literal custom px value (16px)** that doesn't correspond to any registered preset, rather than resolving to the nearest matching preset **and respecting that preset's own `fluid` flag**. If the converter instead resolved 16px to a preset the theme author intentionally marked non-fluid — or if theme.json had a `16px` non-fluid preset for the converter to land on — this specific gap would close without disabling fluid typography site-wide (which would be the wrong, blunt fix given fluid scaling is likely wanted on genuinely fluid tokens like `hero`/`xx-large`/`x-large`).
- It is *not* purely a measurement bug: the computed-parity tool is doing exactly what R-31-11/4a mandate (compare live computed values, content-matched) and is correctly reporting a real, visible, on-page difference — mobile text is genuinely rendering 2px smaller than the draft intends. Calling that a false positive would require deciding fluid-shrink-on-mobile is desired, which is a design decision, not something to silently absorb in the scorer.

**Fix direction (not executed — this task was read-only):** the converter's font-size resolution step should snap literal/computed px values to the nearest registered preset slug (which already carries the theme's intended `fluid` setting) rather than emitting a bare custom px value that falls through into WordPress's implicit global-fluid path. Where no preset matches closely enough, add the missing flat size as a new `fluid: false` preset (theme.json is DB/spec-governed per this project's rules — a design-gate change, Rule 7). Separately, the `small` preset's `max` (14px) vs the draft's actual 13px usage should be reconciled (raise `small.fluid.max` to 14→13, or confirm the draft intends 14 and the draft itself is the outlier) — but that is the smaller, cosmetic finding above, not this hypothesis.

## What I could not determine

- Whether the emitted attribute on these specific blocks is literally `style.typography.fontSize: "16px"` (custom) vs. a preset reference that itself lacks a `fluid:false` override — I confirmed the clamp math matches a `clamp(14px,…,16px)` formula live in the stylesheet, but could not locate the exact CSS rule for class `sgs-text-ca1ccd5d` in the specific canary fetch used (the block CSS is lifted to `uploads/sgs-css/<hash>.css` per this project's known gotcha, and the fetched file for that particular canary run didn't contain the class — likely a different/older deployed page than the one the parity run measured). The global-styles clamp formula match is exact to the pixel at all three viewports regardless, so this doesn't weaken the proof, only leaves the precise converter code path (which file emits the raw 16px) unconfirmed without a follow-up code read of the converter's font-size resolution logic.
- Whether other font-size/line-height diffs in the 35/36 mobile mismatch counts follow the identical clamp mechanism versus the separate preset-`max`-mismatch class described above — I traced 3 representative elements plus identified the 7-element exception group at 1440px; a full sweep of all 35 was out of scope for a hypothesis test but would be a cheap follow-up (grep the same clamp-math check against each of the 35).
