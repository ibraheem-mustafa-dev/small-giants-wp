evidence for. It deliberately contains **no verdict** and **no per-row attribution of "explained"**.

`sgs-update-v2.py --stage 1` runs, diffs taken against the captured baseline.

## Consistency suite

`db-consistency/run.py --check`, run **after** the changes: `2 violation(s) total — 1 NEW, 1
baselined`. GATE FAILED.

The NEW violation: `cssprop:undeclared-subelement:sgs/form:formFocusRingOpacity` — "paints
css_property='box-shadow' … but resolved css_element=NULL AND derived_selector=NULL".

Relevant observations:
- `src/blocks/form/render.php:246-249` emits `formFocusRingOpacity` as a CSS custom property
  (`--sgs-focus-ring-opacity`, 0-100 integer divided to a 0-1 decimal), not as a `box-shadow` value.
- `src/blocks/form/style.css:211-217` paints one `box-shadow` whose value composes **two** `--sgs-*`
  custom properties via `color-mix`.
- `sgs/form`'s `focus-ring` element declares no `attrMap`; its `_note` states the attributes
  "surface as ORPHANs (FR-35-4), same treatment as sgs/button's icon element".
- `sgs/form/block.json` is committed and was not modified by this work.
- **The suite was not run before the changes**, so no before/after comparison exists for it.

An attempt was made to fix this by changing the Task A classifier to detect composite-value
attributes. Measured result: violations went 1 → 3 (adding
`cssprop:rogue:sgs/form:formFocusRingOpacity` and
`cssprop:undeclared-subelement:sgs/form:formFocusRingColour`), and `css_layer` fell 354 → 349. That
change was reverted; the revert was verified byte-identical to the pre-change artefact (850 entries,
0 changed) and the gate returned to 1 NEW violation.
