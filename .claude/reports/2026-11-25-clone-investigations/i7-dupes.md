# i7-dupes: settings that paint the same property on the same element

Nothing was changed in the repo, DB, or any site. Scripts and outputs are in `E:\sgs-tmp\general-cloning\investigate\i7-dupes\`: `detect.py` (the detector), `classify.py` (sorts hits into classes), `hits.json` and `classes.json` (every hit), `probe-holds.mjs` (the Fill tie probe).

## Findings first

1. **The DB already has what a name-based scan lacks.** `setting_placements` (24,714 rows, 104 blocks) records, for each setting, the element it painted in a real render: `part`, `selector`, `props`, `state` (hover, focus, current, open, a class modifier), media `tiers`, and `kind` (`value` = the property takes the setting's value; `switched-on` = moving the setting turns a declaration on). So state is a column, not something to guess from names. Evidence: `sqlite_master` schema of `setting_placements`; `plugins/sgs-blocks/scripts/setting-record/README.md` (kind and state definitions). Caveat: 2,833 of the rows are marked `unproved` (blind), and 6,969 distinct settings are placed against 8,361 settings with a declared `css_property`, so the detector cannot see settings the render never moved.
2. **The first scan's 35 triples were a small, name-filtered view.** Run on rendered selectors with shorthand expansion, the detector finds 952 hits (setting pair x state) across 101 blocks, 643 distinct (block, setting-pair) combinations. After sorting, only 14 combinations (24 hits) are class (a) or (b)-candidate residue, and I checked each by reading the render code. The rest are legitimate or false positives, listed in the class counts below.
3. **Mama's footer underline is PROVEN to be a tie at the resolver, with a proven mechanism and one unproven link.**
   - Fill report `sites/mamas-munches-redesign/build/qa/fill/footer/2026-11-24T17-40-00/fill-report.md`: rows for `cr-ref-footer-23/30/31` (all `sgs/button`): "ambiguous: textDecoration, linkUnderline all paint text-decoration-line on ''". Draft value: `underline`.
   - On `sgs/button` the DB says `textDecoration` accepts `["", overline, line-through]` and `linkUnderline` accepts `["", none, always, hover, sweep]`, whose description is "Set, it replaces textDecoration and textDecorationHover." Neither list contains the keyword `underline`.
   - `resolve-enum.mjs::holdsValue` is what should pick `linkUnderline` (the value `always` paints `underline`, which is recorded in `enumReads`). Probe `probe-holds.mjs`: with no `enumReads`, both settings return false, so `lib/resolve.mjs::resolve` keeps the tie (`tied = holding.length ? holding : tied`) and raises the `ambiguous` gap; with an `enumReads` entry for `always`, `linkUnderline` returns true and `textDecoration` false, so the tie breaks.
   - The calibration cache `E:\sgs-route-cache\button.json` (dated 2026-11-15) has no `enumReads` on any of its 4,434 settings across all blocks, although `calibrate.mjs` (commit cb64887be, 2026-11-19) writes them. UNPROVEN: that the 11-24 run read that cache. What would settle it: re-run only the footer calibration for `sgs/button` and check `enumReads` exists, or print which cache directory the 11-24 run used.
   - This contradicts the one-line account in `deep/s1.out` C9 ("ambiguous ties, H1-A/F4"): the tie rule exists and works when readings exist; the readings are missing. Fix layer is calibration freshness, not a merge.

## The underline pair, specifically (class b)

- `textDecoration` writes the plain `text-decoration` keyword on the element. `linkUnderline` (an enum: none, always, hover, sweep) writes different things per value, shown by its placements on `sgs/button`: `always` writes `text-decoration` at rest; `hover` writes it only on `:hover` and `:focus-visible`; `sweep` writes `background-image`, `background-origin`, `background-position`, `background-repeat`, `background-size` (growing on hover and focus) and `transition-*` on the label (`.sgs-button__label`), with `text-decoration` forced off.
- What in the draft tells them apart: a computed `text-decoration-line: underline` at rest means a plain underline (`textDecoration`, or `linkUnderline: always`, which paints the same thing); `none` at rest and `underline` under `:hover` means `hover`; `none` at rest with a gradient `background-image` whose `background-size` changes under `:hover` plus a `transition` on `background-size` (or a pseudo-element doing it) means `sweep`. No Fill reader looks for the sweep today: `grep sweep` across `lib/fill-*.mjs`, `lib/resolve*.mjs` and `lib/apply-*.mjs` finds only the width sweep, and Fill reads only the computed value of the property it asks about.
- Bean's guidance (plain underline is `textDecoration`) conflicts with one block: on `sgs/button` the author removed `underline` from `textDecoration`'s list so the button never ties, and `linkUnderline: always` is the plain underline there (commit b96a34b91, comment in `resolve-enum.mjs`). Across the DB, 180 `*TextDecoration` settings list `underline` and only `sgs/button`'s does not (104 have no list). So the tie exists only where both settings sit on one element: the detector finds it on `sgs/button` and `sgs/icon-list`. On `sgs/text`, `sgs/heading` and the other 10 `linkUnderline` blocks, `textDecoration` paints the root and `linkUnderline` paints `a`, so they do not tie (the Fill report line "no text-decoration-line setting on sgs/text paints ''" is that case: a different problem).

## How Fill picks between tied settings today (item 3)

`lib/resolve.mjs::resolve` order: settings whose calibrated element and state match; nearest ancestor (`resolve-nearest.mjs::nearestHome`); a setting whose value list cannot hold the draft value is dropped if another can (`resolve-enum.mjs::holdsValue`, needs `enumReads`); other-paint side effects against the draft (`resolve-side-effects.mjs::sideEffectFree`, needs the cache's `effects`; both underline settings have `effects: []` in `button.json`); otherwise gap `ambiguous` and nothing is written. Mama's footer ends at the last step because the first four have no data to act on.

## The detector's rule, in plain words

Two settings of one block clash when a placement of each (1) lands on the same element, which means the same normalised selector (wrapper doubling like `.x.wp-block-x` collapsed, the hover guard and state pseudo-classes removed), or a bare tag such as `a` against a class part whose markup tag, read from the block's `render.php` or `save.js`, is that tag and whose selector chain sits under it; (2) in the same state string from the `state` column; (3) on the same value-carrying property, with shorthands expanded to longhands only for edge, corner and axis families (margin, padding, border-radius, inset, gap), and for the one mixed shorthand `text-decoration` where the line is its value; (4) in media tiers that can apply together (a rest rule always can; two media tiers only if equal; forced-colors and reduced-motion rules are ignored). It then drops: same setting family (responsive suffix, state words in the name, a colour and its Gradient companion); two settings whose declared `css_property` values differ; descendant placements of an inherited property that an ancestor placement of the same setting already covers; and a pair where neither setting is declared for the property. What remains is ranked: both declared for it (strongest), one declared and the other a side effect.

Estimated reach of the pattern: the same shape (two settings, same property, same element, same state) appears in 643 combinations before curation, about 14 after. Names to look at first: `sgs/cart`, `sgs/account`, `sgs/nav-bar-menu`, `sgs/nav-drawer-menu`, `sgs/decorative-image`.

## Where the detector is not proof (UNPROVEN)

- Element identity comes from selectors plus a tag alias, not from the rendered DOM. Rendered HTML sits in `~/.cache/sgs-setting-record/` (427 hash folders) but I did not key into it. A DOM-based pass would settle, for example, whether `.sgs-icon-list__item-link` and `a` are one node (the tag alias says yes).
- Blind (`unproved`) placement rows and settings never placed are invisible to it.
- Descendant placements of inherited properties are treated as inheritance; a block that writes an explicit child rule for the same property is missed.
- `sgs/button`'s hover pair (`linkUnderline` / `textDecorationHover`) was labelled "rest value in state" by the rules; it is really a class (b) underline pair.

## Calls I made

- Used `setting_placements` rather than `block_attributes.css_element` as the primary source, because `css_element` names differ from rendered selectors (the cart icon / pill case) and carry no state; `css_state` exists in `block_attributes` but is null for 13,441 of 14,435 rows.
- Treated `kind='switched-on'` and enum-without-declared-property settings as non-owners of a property, so mode switches show as class (b) not (a).
- Merged `X` and `XGradient` into one family and ignored them as duplicates of each other; a solid colour against a differently named gradient setting is class (b).
- Classified cart's `panelSlideDuration` / `scrimFadeDuration` and the nav submenu pair as designed fallbacks rather than true duplicates, from the render comments.
- Did not run any browser, calibration or Fill: the tie mechanism was proved by calling `holdsValue` directly.
- Wrote the detector to read `mdn-data` from `scripts/computed-route/node_modules` for shorthand families (the repo's own `css-families.mjs` approach) instead of a hand list.
