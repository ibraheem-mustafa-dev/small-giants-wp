## 1. G1 — burger width and height set separately

**Problem.** `includes/nav-menu-trigger-css.php` writes `burgerSize` to `width`, `height`,
`min-width` and `min-height`, so the burger is always square. lamalama's is 30 x 36.

**Design.**
- New attribute `sgs/nav-bar-menu::burgerWidth`, a per-tier length object (`{"type":"object","default":{}}`),
  read with `sgs_responsive_normalise_object()`. Empty tier = `burgerSize` (today's square). Name checked
  free: `sgs-db.py sql "SELECT block_slug FROM block_attributes WHERE attr_name='burgerWidth'"` (to run at build).
- `burgerSize` keeps its meaning for height, and for width when `burgerWidth` is empty. The inspector
  label changes from "Size" to "Height" and a "Width" control appears beside it, in the global device toggle.
- `min-width`/`min-height` follow the visible box (so 30 x 36 can exist), and the **touch target moves to
  an invisible `::after`**: `position:absolute; inset:50% auto auto 50%; width:max(100%,44px);
  height:max(100%,44px); transform:translate(-50%,-50%)`, no paint. The button gets `position:relative`
  if not already. So every burger keeps a 44 x 44 tap area whatever it looks like.
- Text-bearing modes (`text`, `icon-and-text`) keep `width:auto` as today.

**Risk.** A `::after` hit area can overlap a neighbour's tap area when the burger sits within 7px of
another control, or be clipped by an ancestor with `overflow`/`clip-path`/`mask`. Both are measured,
not assumed: the live probe runs `elementFromPoint` at the 44px box's four corners and reads every
ancestor's computed `overflow`, `clip-path` and `mask` on pages 4446 and 4465. Files: 
`includes/nav-menu-trigger-css.php`, `nav-bar-menu/block.json` (attribute + `elements.burger` css:width
map), `nav-bar-menu/BurgerPanel.js` (Height + Width controls), `nav-bar-menu/style.css` (`::after`).

## 2. G2 — a drawer that grows out of the header's own box

**Problem.** No `anchor` value lays the drawer over the header. `trigger` hangs below the burger,
right-aligned; `container` aligns to the header's CONTENT box and sits below it. lamalama's closed pill
(343 x 50 at 375) grows downward in place into a 343 x 436 card: same left, same width, same top.

**Design (recommended: option A).** New `anchor` value `header-box` (enum + PHP allow-list in the
same commit, `nav-drawer/render.php::$sgs_nd_allowed_anchors`).

- **Geometry.** `store.js` already measures the header at open time for `header`/`container`. It
  additionally publishes the opener header's border box: `--sgs-drawer-hb-top/-left/-width` and
  `--sgs-drawer-hb-row-h` (the header's own height). The drawer: `position:fixed; top:hb-top;
  left:hb-left; width:hb-width; height:auto; padding-top:hb-row-h`, **z-index one below the header**
  (the `$sgs_nd_z_under_header` stacking), so the header row (logo, message, burger) paints over the
  drawer's top strip and the burger stays the live close control.
- **One surface, not two.** While a `header-box` drawer is open, `store.js` sets
  `data-sgs-drawer-grown` on the opener header, and the header's fill, blur and shadow are dropped for
  that state (`site-header` style.css reads the attribute). The drawer carries the fill (its own
  `drawerBg` + `surfaceOpacity` + `surfaceBlur`, already built), so the top row and the menu read as
  one card with no doubled 60% black strip. Radius: the drawer takes the header's radius.
- **Modality: `header-box` is always non-modal.** A modal drawer (`showModal()`) sits in the browser's
  top layer, which ignores z-index, so it would cover the burger. `render.php` resolves modality to
  `non-modal` whenever the resolved anchor is `header-box`, and the inspector disables the Modal
  choice with a one-line note for that anchor. lamalama is non-modal already.
- **Header stays put while open.** The same `data-sgs-drawer-grown` attribute pauses hide-on-scroll
  (`src/header-behaviours/view.js`) until close, and `store.js` republishes the `--sgs-drawer-hb-*`
  values on resize, so the card never drifts from the pill.
- **No JS.** The drawer never opens without JS (a dialog), so nothing changes without it.

**Option B (not recommended).** Drawer starts at the header's BOTTOM edge, same border-box width,
and the header's bottom corners square while open. Simpler (no header state), but two fills meet at a
seam; with a translucent blurred fill the seam shows as a line where the blur regions join, which
breaks the "one card" reading Bean asked to copy.

**Option C (compared, not recommended).** Make the menu the header row's own expanding surface
(no dialog). One node, one fill by construction, no stacking question. It loses what `<dialog>` gives
for free and Spec 36 FR-36-6 relies on (Escape, focus handling, the undeletable close chrome), and it
would be a second drawer system beside `sgs/nav-drawer`. Option A reuses the drawer everyone already
builds with.

**Risk.** The header state attribute is a new coupling from `sgs/nav-drawer` to `sgs/site-header`.
Mitigation: it is a data attribute on the opener's closest `header.sgs-site-header`, removed on close
and on `pagehide`, and styled only by `site-header`'s own stylesheet; a non-SGS header simply keeps its
fill (option B's look, still usable).

## 3. G4 — a panel narrower than its wrap centres on the page

**Problem.** `mega-disclosure.js::repositionPanel` measures `[data-sgs-mega-panel]` (the wrap), whose
width is `--sgs-mm-panel-width`, default `min(1120px, calc(100vw - 56px))`. The `sgs/mega-panel`
inside has its own `maxWidth` (620, 300, 1080 on the Indus copy), so the placement centres a 1120 box
and the real panel sits at the wrap's left edge.

**Design.** No new attribute. Three changes, all in the placement code:
1. The mega branch clears `--sgs-mm-panel-width` at the start of every open (today only the dropdown
   branch does), so a width from another tier or panel never leaks into a re-open.
2. It measures the panel's own width as the widest element child of the wrap, skipping `style`,
   `script` and `template` (the wrap holds whatever the mega-menu post renders, so the first child is
   not guaranteed to be the panel).
3. `panel-bounds.js::placePanel` takes that `contentWidth`; for a mega panel narrower than its box it
   returns `width: contentWidth` (today it returns `null` unless the header is a floating pill, and
   `repositionPanel` then deletes the width, which would undo the fix). `full-width` is unchanged
   and never measures the child. Centring, `start`/`end` and edge clamping then use the real width.
`scripts/tests/test-panel-bounds.mjs` gains cases for 620 and 300 panels at 1440 and 768, a
content-width panel (no change), `full-width` (no change), and a re-open after a tier change.

**Side benefit.** The wrap no longer holds an invisible 1120px strip over the page beside a narrow
panel, which today catches clicks meant for the page underneath.

**Risk.** A panel whose width comes from its content (no `maxWidth`) measures at the wrap's width,
so nothing changes for it. Proved by the existing full-width fixtures staying byte-identical.
