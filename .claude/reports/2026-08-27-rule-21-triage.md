# Rule 21 triage — 211 findings, all classified

**`21-render-without-control` means: the block paints something the client cannot change.**
It is the most client-facing of the scanner's rules and it states CLAUDE.md's own standard as a
number — *"no block feature is complete until it has full block-editor UI controls"*.

## Verdicts — the counts sum to exactly the measured FLAGGED population

| Verdict | Count | What it means |
|---|---:|---|
| **DETECTOR BUG — fixed** | **128** | The control exists and works; the scanner could not see it. Fixed in `7f3ad8ae4`. |
| **REAL** | **83** | Genuinely no control. The client is stuck with the `block.json` default. |
| **FALSE POSITIVE** | **0** | None. One candidate was investigated and DISPROVED — see the correction below. |
| **Total** | **211** | Matches the measured FLAGGED count before the fix. |

⚠ **Quote 211, never 222.** 222 is FLAGGED + BASELINED; the scanner's `--json` serialises both
while the exit code counts only FLAGGED.

## The 128, and why they were not defects

`ContainerWrapperControls` is a **table-driven dispatcher**: it reads `KIND_PANELS[ kind ]` and
INVOKES each panel as a function. The scanner's recursion followed only JSX tags, so it dead-ended
and reported every attribute those panels own as uncontrolled, across all 16 blocks mounting it.

Three earlier explanations were checked and **disproved** before this one — it is not
`core/components.js` (it indexes the facade correctly), not `exportBody` failing on a default
export (it returns a clean 816 chars), and the facade's six `contentWidth` mentions are all
**comments**, which the source cache strips. Full mechanism: rule 21's own `advisoryReason`.

Measured before/after, keyed by finding key: **211 -> 83, 128 cleared, ZERO new, and no other rule
moved** (all 24 checked). Guarded by fixture `control-via-dispatcher-table`, written and watched
FAILING first.

## CORRECTION — the one candidate false positive was REAL after all

`sgs/nav-drawer.variantPreset` was first classified a known limit, on the grounds that the client
can pick it from the block VARIATION picker. **That was wrong, and Bean's question about the
drawer's CPT builder is what exposed it.**

What the follow-up found:

- The drawer IS CPT-built (`sgs_drawer`), registered deliberately with **no template seed** so
  WordPress's native "Choose a pattern" starter modal fires. That part of the intuition was right.
- But the starter patterns (`drawer-scratch.php`, `framework-drawer-default.php`) **do not set
  `variantPreset`.** The starter picker and the seven looks are separate mechanisms.
- Every variation was `scope: [ 'inserter' ]` — **inserter only**. No `transform` scope, no
  switcher in `edit.js`, no inspector control.

So the look was chosen ONCE at insertion and could never be changed. A drawer created through the
CPT starter picker got the `block.json` default with **no route to the other six looks at all**.
That is exactly what the rule claims, and it contradicted `variations.js`'s own stated principle:
*"every value stays editable after insertion"*.

**Fixed the same day:** all seven variations are now `[ 'inserter', 'transform' ]`, giving the
native toolbar switcher. Every variation already carried `isActive: [ 'variantPreset' ]`, which is
what the switcher needs. Zero custom UI.

⚠ **The method lesson:** the first check asked *"can a client SET this?"* — and at insertion, yes.
The question that mattered was *"can a client CHANGE this?"* For a value persisted in saved
content, only the second one counts, and `scope: [ 'inserter' ]` is precisely the shape where the
two answers diverge.

ℹ `nav-drawer` is the ONLY block in the framework with a `variations.js`, so this is one block and
one decision, not a pattern to sweep.

### Status AFTER the fix — measured, not assumed

Re-scanned once the `transform` scope landed: **rule 21 still reports 83, and
`sgs/nav-drawer.variantPreset` is still among them.** That is correct behaviour, not a failed fix.
The rule asks whether an INSPECTOR control resolves the attribute; a transform-scoped variation is
not one, so it cannot see the new switcher.

The verdict has therefore genuinely FLIPPED as a result of the fix:

| When | Verdict | Why |
|---|---|---|
| Before the `transform` scope | **REAL** | The client could not change it by any route |
| After | **FALSE POSITIVE** | The client CAN change it, via the toolbar switcher — the rule just cannot model that surface |

⛔ **OPEN, and deliberately not actioned unilaterally:** by this project's own doctrine a false
positive is a detector bug, never baseline fodder — so the rule should learn that a
`transform`-scoped variation with `isActive` IS a client-reachable control, which would take the
ceiling 83 -> 82. That is a DEFINITIONAL change to what counts as a control surface, for a
population of one file, so it is Bean's call rather than a mechanical fix. Until then the ceiling
stays at 83 and this single finding is a documented known limit.
