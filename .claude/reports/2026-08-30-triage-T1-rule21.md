# Triage T1 — Rule 21 `render-without-control` (2026-08-30)

**Scope:** every one of the 82 live-flagged findings from
`node scripts/inspector-scan/run.js --check` (rule `21-render-without-control`),
across 18 blocks. Read-only triage — no files edited, no baselines touched.

## Expected population — declared method

The rule's own file header (`rules/21-render-without-control.js:22-33`) carries a
prior independently-derived population of **53**, dated to the 2026-08-07
control-type-contract council audit, composed of: hover values across 9 blocks
(31), lineHeight/letterSpacing tiers (10), physics-canvas (8), heading/text
boxShadow (4).

That number is now **stale as a comparison baseline**, for a reason visible in
the live data itself: physics-canvas contributes **zero** findings in the
current 82, and no lineHeight/letterSpacing tier finding appears anywhere in
the current 82 either. Both families were evidently closed by real control
work done between 2026-08-07 and now (the file's own D810 note records one
such fix, 2026-08-26). So the 53 baseline and the current 82 are not
apples-to-apples — the framework moved. This report does not try to force the
live count back to 53; it reconciles the 82 that exist today, attribute by
attribute, against the actual source (control corpus + render corpus + every
documented rule blind spot), which is a stronger evidence standard than
comparing against a stale headline number.

**Working expectation for this pass**, stated before opening any block's
source: given the rule's own history shows its major false-positive classes
(dispatcher-table, transitive component nesting, extension ownership, core
`supports`, helper-derived keys) were already fixed as of 2026-08-28, the
residual 82 should skew heavily toward genuine gaps, with any detector bugs
appearing only where a NEW resolution shape exists that these fixes don't yet
cover. This expectation was confirmed, not assumed: verified below per
finding.

## Method

For every one of the 82 findings: read the block's `block.json` attribute
definition, grep the block's own `edit.js` for the literal attribute name,
grep every shared component (`src/components/*.js`,
`src/blocks/container/components/*.js`, `src/blocks/extensions/*.js`) the
attribute's name or its known derivation helpers could route through, and
grep `render.php` / the shared PHP includes it calls to confirm real
consumption. Where a sibling block has a working control for the same
attribute, that sibling's file:line is the positive control proving the
mechanism exists and this block's absence is real, not a project-wide gap.

The single biggest fix by findings-cleared is **mounting `ShapeDividersPanel` on
`sgs/site-footer`** (12 findings), closely followed by **mounting `LayoutPanel`

control.

## REAL findings ranked by client impact

Impact ranked on: how visible the missing capability is on a typical page,
how often a client would plausibly want to change it, and whether it blocks a
whole feature category vs one edge value.

1. **Shape dividers completely uncontrolled on `sgs/site-footer`** (12 attrs — top/bottom wave dividers, colour, gradient, flip, scale, invert). Decorative dividers are a highly visible, commonly-requested design feature; the client can see them (converter/import can set them) but never touch them. Needs: mount `ShapeDividersPanel` in `site-footer/edit.js`, same as other section-kind composites.
2. **`cta-section` background colour + hover colour** (2 attrs). CTA background colour is one of the most commonly wanted per-instance customisations, and the block already has a working colour-panel pattern for text/border right next to it. Needs: an `SgsColourPanel` row for `backgroundColour`/`backgroundColourHover`, matching the existing text/border rows.
3. **Hero + site-footer flex/grid layout controls** (10 attrs — align/justify/direction/wrap/grid-rows). Controls the actual arrangement of hero content and footer columns; genuinely paints CSS via `SGS_Container_Wrapper`. Needs: mount `LayoutPanel` (or a scoped subset of it) in both blocks' edit.js.
4. **Hover-effects family gaps across 8 blocks** (27 attrs). Each individual gap is smaller, but the aggregate is large and the pattern is well-established elsewhere (button/gallery/quote already do it). Needs: extend the existing hover-effects UI pattern to card-grid, info-box, team-member, text, heading, hero, cta-section, testimonial (each needs only the specific missing sub-controls, not a rebuild).
5. **`buybox` merchandising toggles** (showLadder, framingMode, decoyEnabled — 3 attrs). These are pricing-psychology/conversion features with descriptive block.json text clearly written for a non-technical operator, and currently have zero editor path. Needs: 1 toggle + 1 radio/select + 1 toggle in buybox/edit.js.

## What I could not fully determine, and why

- **testimonial's `staggerDelay`**: I confirmed testimonial has SOME working
  hover-effects controls (it appears in the `transitionDuration`/
  `transitionEasing` positive-control grep) but did not exhaustively map
  every control testimonial DOES have vs. only `staggerDelay` being absent —
  I verified the specific attribute is absent, but did not rule out a
  dynamically-constructed key on this one attribute the way I did for the
  card-grid/info-box/team-member/gallery hover families. Given time
  constraints this is marked REAL on the strength of "0 literal matches,
  attribute is declared and rendered", but it carries slightly less
  cross-checking than the rest of the table and would benefit from a second
  look before being used to justify a specific commit.
- **Exact client-facing weight of `sgs/site-footer`'s `tagName`**: this is a
  genuine gap (confirmed by the developers' own in-repo comment marking it as
  a deferred feature), but I did not attempt to assess how often clients
  actually need `<div>` instead of `<footer>` — it is included as REAL by the
  rule's own doctrine (declared + rendered + no control), not because I
  judged it high-value; it is ranked low in the impact list above precisely
  because of this uncertainty.
- I did not re-run `--json` to cross-check the 82 against a machine-diffable
  list (the brief flagged it as non-deterministically dropping the last 2-3
  rules); the plain `--check` text output was used throughout and its rollup
  line (`82 flagged · 11 baselined`) matches the literal count of "is declared
  in block.json and IS consumed" occurrences I grepped (82), so the two
  sources agree without needing the JSON path.
