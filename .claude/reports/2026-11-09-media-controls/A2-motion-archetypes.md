## Best archetype for the driver

Motion's `scroll()` (`packages/framer-motion/src/render/dom/scroll/attach-animation.ts::attachToAnimation`, with `utils/can-use-native-timeline.ts::canUseNativeTimeline`, `utils/offset-to-range.ts::offsetToViewTimelineRange`, `track.ts::scrollInfo`). It is the only production library that is native-first with a JS fallback and a per-element range. Its decision logic is: feature test `window.ViewTimeline !== undefined` (element target) or `window.ScrollTimeline !== undefined` (`packages/motion-dom/src/utils/supports/scroll-timeline.ts::supportsViewTimeline`); native only if the offset maps to a named range (`offsetToViewTimelineRange` returns `entry-crossing N%` / `exit-crossing N%` or undefined); otherwise `scrollInfo`, one shared scroll listener per container, measured in `frame.read`, written in a later frame step. The polyfill uses the same gate (`flackr/scroll-timeline src/init-polyfill.js::initPolyfill`: returns early if `window.ViewTimeline !== undefined`) but replaces the global `Animation` and `Element.prototype.animate`, so it is not a model for SGS.

## Findings by area

1. Native-first. Motion as above. Per-element range is expressed by a `ViewTimeline` on the target with `rangeStart`/`rangeEnd` set on the animation (`attachToAnimation::apply`), not by a page-basis expression. Motion's own comment: "Chrome skips that realignment when the range changes in the frame the animation starts, leaving it offset for good, so it's replayed" (`apply`): set `rangeStart`/`rangeEnd` then call `play()`. Q2's `ratio x max(0, scrollY - blockTop)` has no Motion equivalent: Motion has no page-basis-from-block-top form; a ViewTimeline range (`cover` or `entry`/`exit`) is the native form. Direction is re-evaluated on resize when `a*target.clientHeight + b*container.clientHeight < 0` (`update` in `attachToAnimation`).
2. Stacking with other transforms. Motion does not use separate CSS properties: all `x`, `y`, `scale`, `rotate` on one element compose into one `transform` WAAPI animation (`plans/039-independent-transform-acceleration.md`, "transform group"), and the group is demoted to the JS driver when a scroll timeline is attached ("`attachTimeline` (scroll)" is in its demotion table). So Motion's answer is one composed `transform` track per element, not wrapper and not `animation-composition`. Rellax concatenates: it reads the inline `transform` once and appends it after its own `translate3d(...)` (`rellax.js`, the `transform` regex and `translate3d(` write). No archetype uses `animation-composition: add`. SGS's `motion.css` already uses per-property animation lists (`--sgs-me-a-list-name` over `translate`, `rotate`, `scale`, `clip-path`), which is the CSS-native equivalent of independent transforms and is consistent with Q2's choice of a wrapper with replace composition.
3. Layout changes above the element. Motion: `scrollInfo` listens to window `resize`, `resize(container)` (ResizeObserver), and with `trackContentSize` polls `scrollWidth`/`scrollHeight` every frame (`track.ts`); the native path re-measures direction through `resize([target, container], update)`. GSAP ScrollTrigger has no ResizeObserver: it refreshes on `resize` (200 ms delay `_resizeDelay`), `load`, `DOMContentLoaded` and `visibilitychange` (`ScrollTrigger.js::_autoRefresh`, `_onResize`), and layout shifts need a manual `ScrollTrigger.refresh()`. Rellax re-inits on `resize` only. With a native ViewTimeline the browser tracks layout itself, which removes this problem for the native path; only the JS fallback needs the observer.
4. Pixel rounding and layer promotion. Rellax rounds by default (`round: true`, `Math.round` on x and y) and writes `translate3d` (forces a layer). Motion creates `will-change` only through an opt-in `WillChangeMotionValue` (`motion-dom/src/value/will-change/add-will-change.ts`, only when `MotionGlobalConfig.WillChange` is set): no blanket promotion. GSAP: `will-change` not found in `ScrollTrigger.js` (grep, 0 hits). SGS today rounds to 1px in CSS (`fx-parallax.css::--sgs-fx-plx-offset round(...,1px)`), matching Rellax. Nothing read supports promoting every parallax element with permanent `will-change`.
5. Overscan. Rellax has none: the author sets `min`/`max` or `center`; GSAP none (it is a timing library). No archetype to copy; Spec 49's per-side overscan formula is original and stays. (Gutenberg Cover avoids it via `background-attachment: fixed`.)
6. Pinned or fixed-feeling background. Gutenberg Cover (`packages/block-library/src/cover/style.scss`, `.has-parallax`): `background-attachment: fixed`; `@supports (-webkit-touch-callout: inherit)` sets `scroll` (the comment: "Mobile Safari does not support fixed background attachment properly"; Chrome on Android "does not appear to support the attachment at all"); `prefers-reduced-motion: reduce` sets `scroll`. GSAP ScrollTrigger pins with `position: fixed` or transform (`pinType`, default fixed on the viewport scroller; `ignoreMobileResize` and `normalizeScroll` exist for mobile toolbar resizes).
7. Hover zoom, Ken Burns, clip-path reveal compositor-safety: no primary source read for these. Not verified. Local fact only: SGS clip reveal is a keyframed `clip-path: inset()` (`motion.css::sgs-me-clip-path`); `clip-path` is not a compositor-only property in the sources I read (not verified from a source).
8. Reduced motion. Gutenberg: CSS media query switches fixed to scroll. Motion: `matchMedia("(prefers-reduced-motion)")` plus a change listener (`motion-dom/src/render/utils/reduced-motion/index.ts`), consumed by components. Rellax: no handling found (grep, 0 hits). GSAP ScrollTrigger: no reduced-motion handling in the file (grep, 0 hits). SGS handles it in both CSS and driver, which is ahead of the archetypes.
9. `animation-timeline` crashes. Not verified. A web search for Chromium crash reports found nothing matching; searches of GitHub issues in motiondivision/motion and flackr/scroll-timeline for "crash" returned 0 results. Q2's renderer crashes (11 of 14 attempts on a synthetic page, replace mode) remain unexplained by any public report I could find. Only Chromium's tracker (issues.chromium.org, not reachable here) could confirm; treat as an open risk and cause-agnostic: keep the JS path as the default until the crash is reproduced and bisected.

## What Stage C should take straight from an archetype

From Motion: the feature-test gate, the ViewTimeline-with-named-range per-element mapping, setting `rangeStart`/`rangeEnd` then `play()` (Chrome realignment bug), and direction re-evaluation on resize. From Gutenberg Cover: the Pinned recipe. Everything else (overscan, wrapper, reduced motion) stays SGS's own.
