# A1: Rendering archetypes for the SGS media redesign

Source: shallow clones in E:/sgs-tmp/media-a1/ (wordpress-develop, gutenberg, next.js, astro, unpic, unpic-img, Stackable, Kadence). All paths below were read in the clone; nothing was run. "Not verified" marks anything not read in code.

## Findings per area

1. Art direction. No candidate ships per-device art direction in code. Astro `packages/astro/components/Picture.astro` builds `<picture>` with one `<source type>` per format and one `<img>`; it forwards `sizes` to every `<source>` (`sourceAdditionalAttributes.sizes`), puts only the scoped style class on `<picture>` and the user class on `<img>` (comment cites Astro PR 18004: styling `<picture>` broke existing CSS). That is the proven split for "paint targets the img, picture is plumbing", which Spec 49 §7.1 already follows. Next `packages/next/src/shared/lib/get-img-props.ts::getImgProps` returns props for one `<img>`; I did not find a `<source media>` path in the code (docs claim not verified). Width and height on `<source>`: not verified in any repo.
2. Sizes. Unpic `unpic-img/packages/core/src/base.ts::getSizes` returns `(min-width: Wpx) Wpx, 100vw` for constrained, `Wpx` for fixed, `100vw` for full width. WP `wp-includes/media.php::wp_calculate_image_sizes` returns `(max-width: Wpx) 100vw, Wpx`. Next `get-img-props.ts::getWidths` takes the smallest `vw` in `sizes` to drop widths that can never be used and defaults `sizes` to `100vw` for `fill`; `client/image-component.tsx` warns in dev when `fill` has no `sizes`. Crop: Unpic's srcset code derives each breakpoint's height from the aspect ratio (a crop requested per width); Next `fill` has no crop handling. WP `media.php::wp_img_tag_add_auto_sizes` (and the lazy branch in `wp_get_attachment_image`) prefixes `auto, ` to `sizes` on lazy images that carry width and height.
3. Fill. Gutenberg `packages/block-library/src/cover/style.scss`: the container owns the height (`min-height:430px`, flex centre), the media is `position:absolute; top/left/right/bottom:0; width:100%; height:100%; object-fit:cover; max-width:none`. Next `fill` is the same absolute/100% pattern with no floor; `image-component.tsx` only warns when the parent height is 0. So the proven fallback is a container `min-height` (Cover) or a dev warning (Next). I found no pattern that fills a stretched flex item with an in-flow floor and no minimum; none avoids a floor. Spec 49's `::before` 12rem is the same idea as Cover's `min-height`.
4. Caption width. Gutenberg `packages/block-library/src/image/style.scss`: the figure is an ordinary block; only `.aligncenter` (and floats) use `display:table` with `figcaption{display:table-caption; caption-side:bottom}`, so the caption wraps to the image's width through table sizing, not `width:0; min-width:100%`. Also `img{height:auto; max-width:100%; vertical-align:bottom}` and `a{display:inline-block}`. Stackable `src/block/image/style.scss` only sets `figcaption{margin:0}` and takes the full width (no shrink-wrap). WebKit behaviour of table-caption in a narrow parent: not verified.
5. Background element. Gutenberg Cover `save.jsx` and `index.php`: a real `<img class="wp-block-cover__image-background">` (z-index 0), then `<span class="wp-block-cover__background">` overlay (z-index 1), then `__inner-container` (`position:relative`). Only the parallax case swaps to a `role="img"` div with `background-image` and `background-attachment:fixed`, switched off under `@supports (-webkit-touch-callout: inherit)`. The container uses `overflow:hidden` followed by `overflow:clip`, so sticky children keep working.
6. Lead image. WP `media.php::wp_maybe_add_fetchpriority_high_attr` and `wp_high_priority_element_flag`: one static per-request flag; the first non-lazy `<img>` with width times height of at least 50000 (filter `wp_min_priority_img_pixels`) takes `fetchpriority=high`; an explicit `high` is honoured and clears the flag; `low` and `auto` never become high (`auto` marks images hidden by block visibility and also skips the media count). `wp_get_loading_optimization_attributes` forces header contexts to "in viewport" (filter `wp_loading_optimization_force_header_contexts`) and otherwise uses a count threshold. Next `getImgProps` has an explicit `preload`/`priority` prop (a clash with `loading=lazy` warns) and `image-component.tsx` calls `ReactDOM.preload`.
7. Masks and shadow. Stackable `src/block-components/image/style.js` and `get-shape-css.js`: `mask-image` plus `-webkit-mask-image` on `img`, `::before` and `::after` (the overlay is masked too); shadow is `filter:drop-shadow` on the wrapper above the masked node because `box-shadow` fails with `mask-image` (comment in the file); `preserveAspectRatio="none"` only when Stretch is on; flips are done by a `<g transform>` inside the SVG, not a CSS transform, as a Safari fix; `editor.scss` adds `will-change:filter` against drop-shadow flicker in Safari.
8. One source for editor and front end. Stackable `blockStyleGenerator.addBlockStyles` entries carry `renderIn: 'edit' | 'save'`, so one definition emits both surfaces (JS only, no PHP). Gutenberg Cover shares one `style.scss` between editor and front end. I found no repo that shares one resolver between PHP and JS.
