# Spec 49 sizing and CSS design stress test (§6.4, §7.1 to §7.5, §7.9)

Method: Chrome stable, Firefox 1511 and WebKit 2248 (Playwright, standards mode, container 600px, file 1600x900). Raw logs: E:/sgs-tmp/ec-r11/media/s2/out-chrome.txt, out-firefox.txt, out-webkit.txt, out3-chrome.txt, out3-firefox.txt, out3-webkit.txt; scripts s2.mjs, s3.mjs, s4.mjs in the same folder (copied from q/sizing.mjs). Sources: Gutenberg `packages/block-library/src/image` (style.scss `img{height:auto;max-width:100%}`; save.jsx prints `aspectRatio`, `objectFit`, width, height as inline style) and `embed/style.scss` (`.wp-has-aspect-ratio .wp-block-embed__wrapper::before{padding-top:50%}` with an absolutely positioned iframe, the same technique as §7.2 Fill); Kadence `src/blocks/image/style.scss` (`height:0; padding` box with `height:100%; object-fit:cover` child); MDN aspect-ratio ("at least one of the box's sizes needs to be automatic in order for aspect-ratio to have any effect").

Verdict: the model is sound and the 12 Chrome combinations hold for img, video and inline svg in all three browsers, identically. Five required changes (listed under "Required changes"); two wording notes. Nothing needs a mode.

## Q1. Defaults and combination rules (confirmed, with three corrections)

Confirmed identical in Chrome, Firefox and WebKit for `<img>`, `<video>` (with width/height attributes, `height:auto`) and inline `<svg>` (with or without width/height attributes): nothing set 600x337.5 (with `width:auto;max-width:100%`); Ratio 1:1 at 100% width 600x600; Height 300 at 100% width 600x300; Height 300 with width auto 533x300; Ratio 1:1 with Height 300 and width auto 300x300; Ratio 1:1 with Width 200 200x200; Ratio, Width 200 and Height 100 200x100 (ratio loses); Ratio 16:9 at 100% with Max height 300 600x300; Ratio 16:9 at 100% with Min height 500 600x500; Ratio 1:1, Height 300 and Max width 200 200x300; Ratio 1:1, Width 400 and Max height 250 400x250; Ratio 2:1, Width 400 and Min height 300 400x300; Ratio at 100% with Min width 800 800x800. `height:auto` is required: with it the width/height attributes only supply the natural ratio. `aspect-ratio:auto` returns the file's own shape.

Correction 1 (contradiction inside §7.2): the table says "Ratio only, or Height only: Width defaults to 100%" and also "Ratio and Height: 1:1 and 300px tall is 300 by 300". With the default `width:100%`, Ratio 1:1 plus Height 300 measures 600x300 in all three browsers (ratio ignored because neither size is auto). The 300x300 result needs `width:auto`. So the emitter's default width depends on the resolved values at that device: Ratio and Height both set means `width:auto`, otherwise `width:100%`. With `width:auto` and a Ratio taller than the container allows, `max-width:100%` must stay (the base rule) and the box then crops (600x800 for Ratio 1:1, Height 800), which is the crop the owner's model expects.

Correction 2 (iframe, Firefox and WebKit differ from Chrome): an iframe has no intrinsic ratio, so `width:auto` plus a Ratio is honoured only by Chrome. Ratio 16:9, width auto, no height: Chrome 600x337.5, Firefox and WebKit 300x150. Ratio 16:9 with Min height 500 and width auto: Chrome 888.9x500, WebKit 888.9x500, Firefox 1000x500. Ratio 16:9 with Height 300 and width auto works everywhere (533x300), and `width:100%` with any ratio works everywhere. A printed `width="1600"` attribute acts as CSS width on an iframe (bare iframe measures 1600x150; `aspect-ratio:auto` at 100% width measures 600x150). So the embed's default is `width:100%; aspect-ratio:16/9` as explicit CSS on resolved values, the renderer prints no width or height attributes on an iframe, and width auto is allowed on an embed only when both Ratio and Height are set.

Correction 3 (flex and grid items): `min-width:auto` makes a media item refuse to shrink. In a flex row (600px, 100px fixed sibling) a natural-size img with `max-width:100%` measures 600x337.5 in all three browsers and overflows by 100px; with `min-width:0` it shrinks to 500x281. A `width:100%` plus Ratio img with a 50px sibling is 600 in Chrome and WebKit (overflow) and 550 in Firefox; with `min-width:0` all three give 550x309. In a stretched flex row with Ratio set and width auto, WebKit measures 1600x300 (Chrome and Firefox 600x300); with `width:100%` all three give 600x300. A 1fr grid item with a 1600px img and no `max-width` blows the column out to 1600; `max-width:100%` fixes it (300). Stretch in grid or flex does not change the resolved box once `width:100%` and `min-width:0` are printed, so the base stylesheet carries `min-width:0` on the layout box and media element (a user's Min width overrides it).

Edge surprise: percentage width inside a shrink-to-fit parent (a floated or inline-block layout box) is a cyclic percentage. Ratio 1:1 at `width:100%` in a float measures 800x800 (viewport) in all three browsers. Layout boxes are never floated or inline-block in SGS, so this is a note, not a change.

## Q2. §7.9 per-kind rules (confirmed, one improvement)

Video: `object-fit` (cover, contain, fill, none, scale-down) and `object-position` both work on a real mp4 in Chrome, Firefox and WebKit (200x200 box, 160x90 clip: cover at 0% 0% shows red, at 100% 50% shows blue, contain letterboxes, none and scale-down show the clip at natural size). Confirmed.

Inline SVG: `preserveAspectRatio="xMidYMid slice"` crops and `meet` letterboxes identically in all three browsers; `none` stretches. CSS `object-fit` and `object-position` have no effect on an inline `<svg>` in any browser (measured: object-fit:cover with no preserveAspectRatio still letterboxes). So the table's choice (Cover is slice, Contain is meet, only those two) is correct, and `none`/`xMinYMid slice` also work, so Focal could map to the nine alignments (`xMinYMin` to `xMaxYMax`) with slice. Optional improvement, not a defect.

Iframe: `border-radius` on the iframe itself clips its content in all three browsers (corner pixel white, centre red); a wrapper with `overflow:hidden` plus radius also clips; `overflow:hidden` on the iframe changes nothing visible. `object-fit` has no effect on an iframe (inner viewport stays the box size, 300x100, though the computed value reads `cover`), so "Not offered" is right. Confirmed.

Pointer events: an overlay with `pointer-events:none` over an iframe or a video returns the iframe or video from `elementFromPoint` in all three browsers (controls and the embedded player stay clickable); `pointer-events:none` on the iframe itself returns the wrapper. Confirmed. Note the consequence: an Overlay never blocks an embed or video control, which matches the table.

## Q3. Fill technique (fails in two of the required cases)

Measured helper height with `height:100%` + absolute media + `::before{padding-top:66.67%}`, 600px wide (3:2 is 400px, so any other number proves a real fill), identical in all three browsers: definite parent 700px: 700 (works); parent with `aspect-ratio` 600x600: 600 (works); grid item stretched by a 700px sibling: 700 (works); block child of a stretched flex item: 700 (works); helper that is itself a flex item in a row stretched by a 700px sibling: 367 (FAILS: an explicit `height:100%` switches off stretch and the percentage has nothing to resolve against); parent with only `min-height:700px` (block or flex column): 400 (FAILS: a percentage never resolves against a min-height); no height anywhere: 400 (the 3:2 fallback, as the spec says).

The spec's sentence "it stretches in a flex or grid row" is therefore wrong when the helper is the flex item, and "Containers' content bands MUST pass height to children when the container's height comes from a min-height" cannot be met by a percentage at all.

Alternatives tested in all three browsers. `height:stretch` works in Chrome only (Firefox and WebKit compute 0). `-webkit-fill-available` is inconsistent (Chrome fine on definite parents, Firefox 0 under min-height, WebKit 900 everywhere). Both are rejected. What works everywhere: helper `height:auto; min-height:100%; flex:1 1 auto; align-self:stretch` (plus the `::before` 3:2 and the absolutely positioned media), and the parent a flex column or a grid. Results: flex item stretched by a 700 sibling 700; grid item 700; definite parent 700; aspect-ratio parent 600; flex-column parent with `min-height:700px` 700; grid parent with `min-height:700px` 700; flex-column or grid parent inside a row stretched by a 900px sibling 900; no height anywhere 400. It still fails (400) for a plain block parent with only a min-height, which is why the content band of a container that gets its height from min-height, a ratio or a stretched row must be `display:grid` (single column) or a flex column. This is the same shape Gutenberg's embed uses for the 3:2 fallback and is the standard stretch pattern.

## Q4. `<picture>` with `display:contents`

No accessibility risk found in current engines: the accessibility tree is identical in Chrome, Firefox and WebKit (`link "A cat" > img "A cat"` inside the figure, via `ariaSnapshot`); `picture` has no role to lose, and the historic display:contents bugs affected semantic elements (button, table, list). Layout: an img inside the contents `<picture>` resolves `height:100%` against the figure and link as if the picture were absent (400px in a 400px figure, all three browsers). Without `display:contents` an inline `<picture>` adds a line box and baseline gap (about 4px below the img here), which is why the rule is right. Risks the spec must state: the picture generates no box (rect 0x0), so `width`, `overflow`, `border-radius`, `opacity`, `filter`, `transform` and animations set on it do nothing, and IntersectionObserver or motion code that observes the picture never fires. Every paint, motion and observer target is the `<img>`.

## Q5. Anything users expect that the model cannot express or that surprises

Expressible and correct: every combination in the matrix; Max height with Ratio crops (the box stops, Fit/Focal crop the file); Ratio plus Min height crops at 100% width.

Surprising and worth stating: (a) Ratio with Width auto and a Max height narrows the box instead of cropping (img 533x300, not 600x300), because Max height transfers through the ratio; the default width of 100% hides this, so any control that sets Width auto must say so. (b) Ratio with Width auto and no Height takes the file's natural width (1600x900 at Ratio 16:9 with Min height 500), so Ratio-only must never print `width:auto`; correction 1 covers it. (c) Ratio with Min height and a definite width crops rather than widening, which is what the owner's "ratio works like a crop" model predicts. (d) Height as a percentage (`50%`) needs a definite parent, otherwise it computes to auto; offer Fill, not a percentage, for "same height as the row". Not expressible: none of the requested combinations; `Fill` combined with Ratio is already excluded by the spec.

## Required changes

Change 1, §7.2 table, rows 2 and 3 and the line after the table. Replace the table rows and the sentence "`Width: auto` keeps the file's proportions with a Height." with:

| Ratio only, or Height only | Width defaults to 100% of the space; the height follows from the Ratio, or is as set | | Ratio and Height | Width defaults to `auto`, so it follows from the two: 1:1 and 300px tall is 300 by 300. It never exceeds the space (`max-width:100%` stays), and a taller-than-wide Ratio crops |

"The default width is resolved per device from the resolved values: `auto` when both Ratio and Height are set at that device, otherwise 100%. A Width the user sets always wins. Width `auto` with a Height and no Ratio keeps the file's proportions."

Change 2, §7.2, after "Three rules fill the gaps CSS leaves", add a sentence and base-CSS line: "The layout box and the media element are flex and grid items in many rows, where the browser's `min-width:auto` stops them shrinking below their natural size and overflows the row (proved in Chrome, Firefox and WebKit). The base stylesheet therefore sets `min-width:0` on the layout box and the media element; a Min width the user sets replaces it."

Change 3, §7.2, replace "An embed with nothing set is 16:9 at 100% width." with: "An embed with nothing set is `width:100%; aspect-ratio:16/9`, printed as CSS on every embed. The renderer prints no `width` or `height` attribute on an iframe (an attribute acts as a CSS width). An embed never prints `width:auto` unless both Ratio and Height are set, because only Chrome transfers a ratio through an auto width on an iframe. An SVG with nothing set uses its viewBox."

Change 4, §7.2, replace the Fill paragraph with: "Fill means the height the surrounding layout gives the media. The helper prints `height:auto; min-height:100%; flex:1 1 auto; align-self:stretch`, the media is absolutely positioned inside it, and a `::before` with `padding-top:66.667%` gives it a 3:2 height when nothing supplies one. An explicit `height:100%` is never printed on the helper: on a flex item it switches off stretch (measured 367 against a 700 row). Fill takes the height of a definite parent, a stretched flex or grid row, an aspect-ratio parent, and a flex-column or grid parent with a min-height; with no height anywhere it is 3:2. A percentage cannot see a min-height, so a content band whose height comes from a min-height, a Ratio or a stretched row MUST be `display:grid` (one column) or a flex column; the container emitter prints that automatically when any child is Fill. Min height on the media is its floor. Proved in Chrome, Firefox and WebKit for all of these parents; PS-2 repeats it on the 13 layouts. `height:stretch` and `-webkit-fill-available` are not used (Firefox and WebKit do not support them consistently)."

Change 5, §7.2 first paragraph and §14.2 PS-2: replace "proved in real Chrome" with "proved in real Chrome, Firefox and WebKit, for img, video and inline svg (iframe: Width 100% only, per the embed rule)", and add to §7.9's Alt/Loading rows nothing; add to §7.1 after the picture sentence: "The `<picture>` generates no box: every setting that paints, moves or is observed (opacity, filter, transform, motion, observers) targets the `<img>`, never the picture."
