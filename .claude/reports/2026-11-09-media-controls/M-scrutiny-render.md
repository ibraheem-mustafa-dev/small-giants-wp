## 1. Atom framework: registry, 15 JS/PHP twin pairs, parity gates. REWORK

It works and its gates are real: test-media-atom-parity, test-media-attr-parity, test-media-enum-vocabulary and test-media-injection-parity all pass (verified by running them), the PHP twins return declarations with no inline style, and an empty attribute set emits nothing. The concept (atoms emit custom-property values, one shared stylesheet paints) is right and cheap at runtime. Exact changes: (a) `includes/media/atoms/source.php::sgs_media_atom_source_css` prints `--sgs-media-background-image:url("` plus the raw stored URL plus `")` with no escaping. Proved by `src.php`: the URL `https://x/a.jpg");background:red;--y:url("` produced `--sgs-media-background-image:url("https://x/a.jpg");background:red;--y:url("")`, a declaration-injection hole reachable wherever `source` is declared (sgs/media and hero splitMedia are the two adopters). Fix with esc_url_raw plus a `"`, `)`, `\` and newline reject, and add a gate that every atom css() output is run through a declaration validator. (b) Twin code in two languages with a byte-parity gate is a permanent tax (two implementations of every rule); keep the parity gate until the atoms are generated from one declarative table (the registry already holds the data: bases, types, scope, css vars), then generate the PHP and JS emitters. (c) Atoms attach to a box or an element by a hard-coded list; see item 2. (d) 21 of 38 adopting surfaces take only object-fit; adoption, not capability, is the gap, so the new system should make the atom stack the only way to declare a media slot (one `mediaSlots` declaration per block) rather than selective injection.

## 3. includes/helpers-media-element.php (naming, stored-name map, tolerant value reader). REPLACE

Why: the file exists to tolerate legacy. `sgs_media_element_stored_attr` carries a hard-coded STORED_AS map (before-after autoplay, decorative-image `decorMedia`, brand-strip `logoFit`), mirrored again in MediaElementControls.js; `sgs_media_element_value` reads five storage shapes (media object, attachment id, id-or-string union, url string, tri-state) and its own docblock says the census measured TEN shapes for one concept; the header says "ZERO RENAMES" because stored post_content could lose images. The owner's instruction (and FP-14, pre-production, no content to protect) is that the new design must not adapt to these. Instead: one slot object per media (see item 20), one reader, no name derivation by prefix string concatenation (`sgs_media_element_attr` builds names by lcfirst and prefix, which is why a hyphen or a new base can silently produce the wrong key). Only `sgs_media_element_scope_class` (sanitised uid plus `--prefix`) and `sgs_media_element_style` (join declarations, no trailing semicolons) are worth carrying; move them into the replacement class.

## 4. box-shape shape vocabulary (`clip-path` presets: none, square, rounded, circle; PHP `sgs_media_atom_box_shape_clip_paths`, JS CLIP_PATHS; also decorative-image `shape`, hero `splitMediaShape`). REPLACE

Why: it is four fixed clip-path strings, `rounded` is a hard-coded `inset(0 round 12px)`, it is not per-device, and `clip-path` removes the border and the shadow. Proved in real Chrome on injected markup (mask.mjs, screenshot E:/sgs-tmp/ec-r11/media/s/mask.png): case A, the real photo with `clip-path:circle(50%)`, `border:6px solid red` and `box-shadow`, shows only two red border stripes at top and bottom and no shadow at all; `circle(50%)` on a 220 by 160 box also draws a circle sized from the box diagonal, not an ellipse or a true circle. The same defect is stated in the decorative-image source comment ("a shaped layer clips its own shadow") and in the hero shadow comment. What to build instead: a shape registry (JSON, see item 6) and a two-layer render: a frame element carrying `filter:drop-shadow()` (mask does not clip a filter on its parent: case C in mask.mjs shows the shadow following the blob contour) and an inner element carrying `mask: url(data:image/svg+xml...) center/100% 100% no-repeat`. The mask approach worked for an arbitrary 98-point Bezier blob on a real photo (cases B and C). Not proved: a contour-following border. In case B the straight CSS border is simply cut by the mask edge (red slivers at the sides). A contour border needs a third element (a ring: the same mask minus an inset copy using mask-composite exclude, or an SVG stroke); my ring attempt (case D) was a flawed test and shows nothing either way, so treat the contour border as unproven and build it with its own test.

## 5. includes/helpers-end-shape.php and src/utils/end-shape.js (mask-image end cuts on a box, sgs/label only). KEEP, for the label only

Read end to end (273 and 244 lines), JS and PHP return identical strings, and `LabelEndShapeTest` plus `label-end-shape.test.js` pass (verified by running them). It is high quality for what it is: an end cut of a pill using a library path in a data-URI SVG tile with `mask-composite:subtract`, and a separate masked border layer (`z-index:-2`) so the real border follows the cut. It does NOT generalise to images and should not be stretched to: the tile is `auto 100%` of the box height with depth in percent of height, it only cuts left and right ends, and the border layer logic assumes straight sides. It is the proof that the two-layer technique (masked paint layer plus real border) is viable, and its `sgs_end_shape_url` encoder (`%`, `<`, `>`, `#`, `"` escaped) is the right data-URI encoder to reuse. Not run: live Chrome render of a label end shape (no label with an end shape exists on the live site).

It holds five paths (hexagon, diamond, octagon, star, blob) in a fixed `0 0 100 100` box. Note: the earlier census said there is no blob anywhere; this file has one. Live proof: the live hero background `<img>` has srcset, width and height, is eager with fetchpriority high on the first background only, and was the LCP element with CLS of 0.00004 at 1440 and 0 at 375 (fx2.mjs). ## 9. helpers-media.php::sgs_image_loading_attrs, sgs_next_background_image_index, sgs_content_image_claims_priority. REPLACE

Why: three entry points share one static counter but apply three different rules. `sgs_next_background_image_index` gives the high-priority slot to whichever background image renders first, with no fold test. `sgs_content_image_claims_priority` requires the first section (`Sgs_Motion_Renderer::in_first_section()`). `sgs_image_loading_attrs` (used by sgs/media at three sites, decorative-image, product-card, buybox, brand logo) checks neither the first section nor visibility: any call among the first 16 images prints `loading="eager"` and the very first call on the page takes `fetchpriority="high"` even if it sits in section five of a page with no hero. The 16-image eager budget (`apply_filters( 'sgs_eager_image_limit', 16 )`) is far above what any viewport needs, and the decorative-image ornament (`can_lead` false) is eager within it; the live proof of the consequence is the failing test: `DecorativeImageLayerTest` now gets `loading="eager"` where its golden output expects `loading="lazy"` (five stale byte-identity cases, run and read). Also the counters are PHP statics, so they are request-order facts: a cached fragment, a REST re-render or a block rendered out of document order (a template part, the mega panel) gets the wrong answer, and a hero that renders its split image through `sgs_tier_media_render` (item 10) never consults the counter at all. Build instead: one `sgs_media_priority( $slot )` resolver keyed on three facts (is it in the first viewport-sized section; is it inside a hidden surface; is the one high-priority slot already taken), budget of one `high`, at most two eager, every other image lazy with a size hint; and let the editor mark a slot "above the fold" explicitly so the author can override. Not run end to end: the page-order failure (an image-led page with no hero); I read it from the code and the test failure.

## 10. helpers-tier-media.php::sgs_tier_media_render and sgs_tier_media_toggle_css (per-device sibling elements). REPLACE

Why: proved with the stubbed harness (tier.php) on the exact shipped function. With three image tiers and no options, the output is three `<img>` elements each `loading="eager"` and `fetchpriority="high"`; a `display:none` image with eager loading still downloads, so a phone fetches the desktop and tablet files too, all at high priority. Only timeline passes `img_loading => lazy`; the hero calls it with no options. The same run shows the toggle CSS is emitted with duplicates: the desktop element's hide rule appears twice in each of the mobile and tablet-only bands (the function builds `$rendered = array_merge( array( 'desktop' ), $present )` and `$present` already contains desktop), 8 rules where 6 are needed. Other facts: images use `large` and no sizes; alt is per tier (reversing Spec 35 D5's "alt is not tiered"); the video branch is hard-coded `loop muted playsinline` with `source type="video/mp4"` only (no webm, no mime from the attachment, no poster). Replace with one `<picture>` renderer (`<source media>` per tier with its own srcset and sizes, one `<img>` with width, height, alt, loading and priority) so one file downloads, the preload scanner sees it, and the cascade-up is automatic because a tier without a source is simply omitted. Keep only the band-ownership idea, for the genuinely mixed case (image on desktop, video on mobile). Not run live: no live page uses tier images; the PHP harness replaces the attachment lookup with a stub, so the srcset branch is read, not run.

Why: it is the oldest renderer and the weakest. Images are `loading="lazy" decoding="async"` always, with no priority path (so a logo bar above the fold can never be eager), no srcset, no sizes, width and height only from `sgs_image_size_attrs` on the URL; `<picture>` appears only for one `mobile_url` (one source, one breakpoint, no tablet); video is `autoplay loop muted playsinline` by default with `aria-label` "Background video" when there is no alt. Live proof: the brand logos it renders on the home page report `srcset:false` and lazy (live1.mjs), which is acceptable for 65-pixel logos but shows there is no responsive path at all. It also does not use the `sgs-media-el` marker, so the atom stylesheet does not reach it. It should disappear into the single renderer.

## 12. helpers-media.php::sgs_media_cover_crop_plan, _widens, _sizes, _hint_sizes, sgs_media_drop_auto_sizes. REWORK

It works and is tested (MediaCoverCropSizesTest passes, run). It computes a concrete `sizes` string from the box's per-device px width, height or ratio and the image's real ratio, so a cover-cropped image is not over-fetched. Weakness: it is about 170 lines of heuristics that only understand `px` widths; anything in `%`, `vw`, `rem`, `clamp()` or a fluid grid column returns `unknown` and falls back to an empty `sizes` (the browser then assumes 100vw). It also mirrors the same function in no JS twin, so the editor cannot show the chosen candidate. Rework: make it the sizes generator of the single picture renderer; accept layout-derived widths (the container's column width as a custom property the renderer already knows); and add the DPR-aware candidate list. Keep the idea, because most builders ignore cover-crop widening; it is a genuine differentiator.

## 17. Scoped CSS collector use and scope-class stability. KEEP

Scope classes are content hashes: hero `sgs-hero-` plus first 8 hex of md5 of the JSON-encoded attributes and anchor; container `sgs-container-` likewise; decorative-image `sgs-di-` likewise. Two identical blocks produce one identical rule (de-duplicated by the collector), nothing random or time-based, so the collected file name is stable between views (the live collected file is `sgs-css/sgs-2299-aa2697c1c0ffb310f715aaa15b99403d.css`, hash-named). Residual risk: an 8-hex prefix collides at roughly 1 in 4 billion per pair, negligible; but any attribute change renames every class, which is correct. Not run: I did not load the same page twice to compare the collected file hash across requests; the stability claim rests on the code (no random inputs) and the hashed file name.

## 18. The shared atom stylesheet: assets/css/media-element.css (concatenation of assets/css/media-atoms/*.css). REWORK

Measured on the live home page (css.mjs, Chrome, decoded sizes, not transfer sizes): 37 stylesheet files totalling about 1,020 KB decoded, plus about 93 KB of inline style; the project budget is under 100 KB CSS per page. Media-related files alone: media-element.css 47.7 KB, motion.css 34.7 KB, motion-triggers.css 25.0 KB, fx-marquee.css 9.2 KB, fx-parallax.css 3.7 KB. The home page also loads a 330 KB collected block-CSS file and two WooCommerce stylesheets of 155 KB and 93 KB (not media, but they show the budget is not being held; transfer sizes after compression would be smaller and I did not measure them). media-element.css is the build-time concatenation of every atom partial (14.6 KB `_base.css`, 10 KB box-shape, 4 KB svg-presentation, video-behaviour and others), loaded whole on any page with one media element. Rework: load each atom partial only when that atom emitted something on the page (the collector already knows), and move `_base.css` into critical. Second, a correctness defect proved in three browsers: `.sgs-media-el` uses `width: var( --sgs-media-width, attr( width px, auto ) )` and `aspect-ratio: var( --sgs-media-aspect-ratio, auto attr( width type( <number> ) ) / attr( height type( <number> ) ) )`. Typed `attr()` is Chrome-only. In ff.mjs the same declarations on a 300 by 200 image gave Chrome width 300px, height 300px, aspect-ratio `auto 300 / 200`, but Firefox 146 and WebKit 26 gave width 10px, height 10px, aspect-ratio `auto` (the image's intrinsic size, because the whole declaration is invalid at computed-value time). So in Firefox and Safari every `.sgs-media-el` image loses its width and height attributes' reserved space, which is a layout-shift risk the Chrome-only lab data (CLS 0) would never show. Fix: use plain `width:var(--sgs-media-width,auto)` and let the browser's own `img[width][height]` mapping supply aspect-ratio, or emit `width` and `aspect-ratio` as real numbers from PHP (it already knows the attachment size).

## 20. Data shape: flat sibling attributes `x`, `xTablet`, `xMobile` and ten storage shapes. REPLACE

## Missing capabilities a best-in-class system needs (none exist today)

1. One `<picture>` renderer with per-tier crop, art direction, format negotiation (AVIF and WebP via the attachment's generated sizes), explicit width and height, and `fetchpriority` chosen by one resolver. 2. A `<link rel=preload as=image imagesrcset imagesizes media>` emitter for the lead image only (searched: none exists). 3. A shape library with mask shapes, per-device shape, a contour-following border ring and a drop-shadow frame, plus uploadable SVG shapes. 4.
