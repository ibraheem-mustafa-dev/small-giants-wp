## 2. Which gaps close by reading data that already exists, and which need new data

**Close by reading existing data (no new data):**
- **G1:** the footer slotting reads the surfaces.json `kind`/`opened_by` and a computed `position: fixed`, and stops absorbing (`skeleton-inventory.mjs`, `skeleton-footer-slots.mjs`). The spec line in FR-48-6 Footer rows changes in the same commit.
- **G4:** a position reader picks the floating or sticky mode from `block_attributes` (enum and name rows above).
- **G6:** add one `surfaceRoot` entry for `modal`. Data line only; the knowledge is in `block_capabilities` and `states`.
- **G8 + G9:** `surfaceRoots` reads the page-map `parts[].owner`.
- **G10:** read the census tag and the parent chain.
- **G11:** the handoff check reads `MANIFEST.json`.
- **G12:** three reader fixes (`reachCalls`, `judgeKeys`, `openers`) over data already in surfaces.json.
- **G3, partly:** the classifier asks `block_capabilities` (discovery keywords) and `blocks.description` for candidates, as a scored evidence source next to the tag map.

**Need new data (smallest that would do):**
- **G2:** a domain rule for WhatsApp in `brand-registry.json` (`wa.me`, `api.whatsapp.com`), and `siteInfoKinds` accepting `linkSourceForKind` kinds.
- **G3:** a machine-readable recognition signature per block (`supports.sgs.recognise` or a DB column: href hosts, ARIA roles, position, surface kind) for blocks no rule covers, and a `block:<slug>` coverage section so `capabilities.mjs --gaps` names every block nothing recognises. This is the root fix for "ignorant of much of the framework".
- **G4:** a `variant` enum in `sgs/whatsapp-cta/block.json` (`floating`, `card` seen in its source, `inline` named by `elements.card-title.absentIn`; confirm the full list in `edit.js` before adding it), so the DB carries the values.
- **G5:** a `rules.backToTop.floating` handover entry, plus Floating UI options as site-setting coverage entries.
- **G7:** `blockOwnedPart.byTemplate.archive-product`, plus a page-map owner rule that recognises the filter drawer.
- **G13 / G14:** coverage entries that raise missing-features rows. The features themselves are absent from the framework.

## 3. Root cause of each proven case (one line each)

- **Indus WhatsApp button:** Spec 48 FR-48-6 Footer rows tells `skeleton-footer-slots.mjs` to absorb any fixed sibling into the footer's bottom row. There, `pillButton` wins because `siteInfoKinds` drops the `whatsapp` kind (business-info has no such display type and the brand registry does not claim `wa.me`). No rule or score ever consults `sgs/whatsapp-cta` (`block_capabilities` whatsapp/chat, `variant` default floating). Eye Care S-07 hits the same path (`footer …/1158#0` → `sgs/button`, `pillButton`).
- **Eye Care `shop-filter-rail-drawer`:** `surfaceRoots` reads every `drawer` record as its own surface. It ignores the page map, which has the part as `owner: draft-notes`, and `blockOwnedPart.byTemplate` knows only the cart. So the drawer the theme's `sgs-shop-filters.js` already draws (a modal `<dialog>` below 782px) is re-read at 375, where the draft root is closed and unmarked.
- **Mama's checkout `<header>`:** the `CENSUS_CPT` check in `surfaceRoots` demands a surfaces.json header record per component. It never reads the page map, which already owns that header as the checkout page's part (`owner: woocommerce`).
- **Mama's `basket-gift-note-upsell`:** the root (tpl 47) needs `gift.on`. That is a dotted key `judgeKeys` drops, reached by `MM.cart.setGift(...)`, which `reachCalls` cannot parse. The "upsell shown" state alone (`showUpsell`) cannot render a root that is still closed. The content also has no framework equivalent (FR-48-62 extras slot).
- **Mama's `cancel-subscription-confirm` and `address-form-add-edit`:** the only setState calls are written `dcLogic('Account').setState(...)`, which `reachCalls` does not match. The state values are placeholders (`<sub id>`, `new|<address id>`), so no opener exists.
- **Mama's `account-details-change-password`, Eye Care `addresses` and `account-details`:** `openers` applies only the surface's own state, never its parent chain's. For Eye Care that is S-45 → S-42's "signed in" `{page:'account', user:{…}}`. For Mama's, the signed-in precondition comes from localStorage (probable, not traced). These are WooCommerce account forms the page map gives to `woocommerce` anyway (G8).
- **Eye Care `storefront-shell`:** `surfaceRoots` takes a `global` record whose root is the `<sc-helmet>` app shell (the parent of the other surfaces) as a surface to read.
- **Eye Care S-38 report:** surfaces.json lists a draft (`WP Build Gap Map`) that `MANIFEST.json` does not ship. The handoff check does not refuse it, so it reaches skeleton intake as a gap.
