# Keyboard focus styling inventory: SGS theme and plugins (2026-10-17)

Read-only audit. Nothing in the repo was edited, built or deployed; nothing was created on the canary; the shared MCP browser was not used (all live measurements ran in separate headless Playwright processes against `https://sandybrown-nightingale-600381.hostingersite.com/`, which currently renders the Mama's Munches content). UK English, one line per paragraph.

GROUND-TRUTH: spec=.claude/specs/38A-SGS-MOTION-MODEL.md §10 + FR-38A-42, .claude/specs/32-COMPONENT-STYLING-TOKEN-CONTRACT.md §14.3 source=theme/sgs-theme/assets/css/*.css, plugins/sgs-blocks/{assets/css,src/blocks/*/style.css,includes}, framework DB (`sgs-db.py sql`), live canary evidence=the commands named in each section (a CSS scan script, `rg`, DB SQL, Playwright `getComputedStyle` and `document.styleSheets` probes).

## 0. Headline findings

1. There is no single focus system. 330 shipped front-end CSS rules concern focus (a `:focus*` selector, an `outline` declaration or a `--sgs-focus-*` definition); 168 of them draw a focus indicator, using 67 distinct declaration strings across 64 files (outline widths: 2px in 124 rules, 3px in 24, tokenised in 13; offsets from -4px to 4px; 22 rules use block-private colour tokens or literals).
2. The global default has two competing definitions. `core-blocks-critical.css` says 3px; `utilities.css` (`*:focus-visible`, loaded later, same specificity) says 2px and also forces `border-radius: 4px`. The live cascade proves the 2px one wins. The 3px rule is dead for every element that has no more specific rule.
3. The "disconnected" look is structural: the dominant indicator is an `outline` with a 2px gap (108 of the 161 outline rules that parse use `outline-offset: 2px`) plus a separate blurred glow (`0 0 8px 2px` at 40% of the accent) painted by `box-shadow`, and `*:focus-visible { border-radius: 4px }` changes the button's own corner shape while it is focused (measured: an `.sgs-button--primary` goes from 10px to 4px radius on focus, so the outline hugs a different shape from the resting button).
4. The default ring colour fails 3:1 on most of the page. Measured on the canary, the accent ring `#f5d050` against the surrounding background composites to 1.35:1 on cream, 1.5:1 on white and 1.04:1 on the pink band; it only passes (8.77:1) where the surrounding background is the dark footer. Against the dark button fills the ring itself reads 6.8 to 8.8:1, but the ring sits 2px outside the fill, so the adjacent colour is the page, not the fill. The 40%-alpha teal fallback used by 15 rules in 9 files measured 1.75:1.
5. Any element carrying `.wp-element-button` or `.wp-block-button__link` is locked to the theme's `!important` outline and `!important` glow. That includes the buybox add-to-cart, the buybox notify submit, the linked-flow modal CTA, WooCommerce cart/checkout buttons, and any `sgs/button` given the class `wp-block-button__link` (the shop archive template does this). On those elements 9 block or WooCommerce focus rules cannot change outline or shadow, and the Spec 38A hover ring and accent bar can never show on keyboard focus (documented as intentional in Spec 38A §10).
6. There is no inspector control for focus on any button block. The only focus-related attributes in the DB are `sgsFocusRing` (a boolean on 8 non-button blocks), `formFocusRing*` (4 attributes on `sgs/form`) and `focusRingColour` (2 blocks). There are no `sgs_focus_*` PHP helpers.
7. On sites whose snapshot omits `settings.custom.focus-ring` (six of the nine snapshots: `mamas-munches`, `helping-doctors` and the four `sgs-*` samples) the `--wp--custom--focus-ring--*` tokens are undefined at runtime; on the canary, which renders Mama's Munches content, all four read as empty on `:root`, consistent with `sites/mamas-munches/theme-snapshot.json` having no such key. Fifteen rules then fall back to a hard-coded 40%-alpha teal `rgba(31, 122, 122, 0.4)` from the SGS default palette. That is the colour the testimonial slider arrows and dots showed on the canary.
8. One visually hidden radio input in `sgs/option-picker` (1px by 1px, `tabindex` 0) receives the global ring, so a keyboard user sees a ring around a 1px point on the canary home page (the block also has a separate rule for the pill sibling, `input:focus-visible ~ .sgs-option-picker__pill`, whose rendering was not captured).

## 4. Fights: specificity and `!important`

GROUND-TRUTH: spec=n/a source=core-blocks-critical.css, utilities.css, core-blocks.css, woocommerce.css, motion.css, button/style.css evidence=rule texts from the scan plus the matched-rule lists in section 7 (specificity computed by hand: `:focus-visible` = (0,1,0), `*:focus-visible` = (0,1,0), `.a:focus-visible` = (0,2,0), `:root :where(.a:focus-visible)` = (0,1,0), `!important` outranks all normal rules).

1. Global duplicate. `core-blocks-critical.css::` global `:focus-visible` (3px, glow) and `utilities.css::*:focus-visible` (2px, glow, `border-radius: 4px`) have equal specificity; `utilities.css` is enqueued after (`functions.php`: critical, core-blocks, utilities) and so wins on outline width, offset and radius. Measured: every focusable on the canary that relies on the global rule shows 2px; none of the 25 shows the 3px global (the only 3px outlines are the slider's own rule).
2. Radius clobber. `*:focus-visible { border-radius: 4px }` beats any radius declared at (0,1,0) or lower and earlier in the cascade, such as the preset radius on `.sgs-button--primary`. Measured on fixture page 5310: radius 10px at rest and on hover, 4px while focus-visible. A per-instance `.sgs-btn-<uid>.sgs-button` radius (0,2,0) survives, which is why home-page buttons keep their shape.
3. The `!important` core-button rule. `core-blocks-critical.css::` `:root :where(.wp-element-button:focus-visible, .wp-block-button__link:focus-visible) { outline: 3px solid var(--sgs-focus-color) !important; box-shadow: var(--sgs-focus-shadow) !important }` has specificity (0,1,0) but is `!important`, so it overrides every normal rule for outline (colour, width, style) and box-shadow, including: `core-blocks.css` `is-style-sgs-primary|secondary|accent` (3px teal 40% plus amber glow), the four `woocommerce.css` button rules (mini-cart checkout, mini-cart cart, proceed-to-checkout, place-order; 2px FR1), `buybox/style.css` add-to-cart and notify-submit (2px FR1), the Spec 38A hover ring and accent bar, a block's own resting `box-shadow` while focused, and any editor-set shadow. Only `outline-offset` is not `!important`, so offsets from more specific rules still apply (3px on the WooCommerce buttons).
4. Redundant button rule. `core-blocks-critical.css::.wp-block-button__link:focus-visible` (3px `--sgs-focus-color` with a `primary-dark` fallback) duplicates the global and is beaten by the `!important` rule in every case.
5. `theme.json` `:focus` outline. `:root :where(.wp-element-button:focus, .wp-block-button__link:focus)` (2px accent) fires on mouse focus as well, and loses to the `!important` rule on keyboard focus.
6. Block rules vs global. A block rule such as `.sgs-button:focus-visible` (0,2,0) wins outline width, colour and offset against the (0,1,0) global rules, but the global rules still supply the glow (`box-shadow`) and the radius, because the block does not set them. So the final look is a splice of two rules, which is the root of the "outline plus faint glow" look on SGS buttons.
7. Motion composition. `motion.css::[data-sgs-mc~="box-shadow"]:focus-visible` (0,2,0, normal) beats the global glow and re-lists it first, then the ring, then the inset accent bar. It loses to the `!important` box-shadow on `.wp-element-button` and `.wp-block-button__link`. Measured on fixture page 5310 (`a.sgs-button.t1-btn`, ring 4px): the focused button's `box-shadow` is `[accent 40% glow 8px 2px], [ring rgb(46, 125, 79) 4px spread], [inset accent line 0]` and its outline is still 2px accent offset 2px.
8. Hover fill on focus. `button/style.css::.sgs-button:hover, .sgs-button:focus-visible` swaps colour and background to the hover values on focus, so the accent ring sits next to a changed fill, not the resting one.
9. `prefers-contrast: more`. `core-blocks-critical.css` `:focus-visible { outline-width: 4px !important; outline-style: solid !important; outline-color: var(--sgs-focus-color, #076a8e) !important }` overrides every block's width and colour at high contrast. This is an accessibility feature that a unified system must keep or replace with an equivalent token.
10. Token fallbacks disagree. The same token is read with seven different fallbacks (`var(--wp--preset--color--accent)`, `rgba(31, 122, 122, 0.4)`, `#076a8e`, `currentColor`, `primary-dark`, `rgba(245, 158, 11, 0.4)`, `#d8ca50`), so an unconfigured site renders a different colour per block. 15 rules in 9 files fall back to the 40%-alpha teal.
11. Suppression. Four rules set `outline: none` with a replacement (`woocommerce.css` text/select inputs: border colour plus a 2px 20% box-shadow ring; `sgs-client-notes` frontend: a 1px `#2271b1` ring; `choice-flow` showcase layout `:focus`). `box-shadow` is not drawn in Windows forced-colours mode (CSS behaviour, not measured here), so those replacements disappear there.
12. Two indicators on one control. `sgs/option-picker` draws the global ring on the 1px radio input and a second ring on the pill sibling.
13. Duplicated skip-link styling in three places (`utilities.css`, `wc-blocks.css`, `sgs-accessibility`).

## 5. Motion interplay (Spec 38A)

GROUND-TRUTH: spec=.claude/specs/38A-SGS-MOTION-MODEL.md §10 "Composition rules" (the `box-shadow` row), §12, FR-38A-30, FR-38A-42 source=plugins/sgs-blocks/assets/css/motion.css, plugins/sgs-blocks/includes/motion/class-sgs-motion-ring-guard.php, class-sgs-motion-focus-state.php evidence=Grep of the spec by the strings `focus`, `FR-38A-42` (never read whole); live probe on fixture page 5310.

Binding lines. §10, `box-shadow` row: "single owner: `box-shadow: 0 0 0 var(--sgs-mh-ring) var(--sgs-mh-ring-c), inset 0 calc(-1 * var(--sgs-mh-accent)) 0 0 var(--sgs-mh-accent-c)` (on `:focus-visible` the rule composes the theme's glow first (`--sgs-focus-shadow`, defined in each theme focus rule), then the ring and the accent line; an element carrying `.wp-element-button` or `.wp-block-button__link` keeps the theme's `!important` glow alone; offered only on an element with no shadow of its own, FR-38A-42; never `outline`, so the keyboard focus ring stays; ...)". §12 and FR-38A-30: "keyboard focus reproduces every hover effect". What this means for a button. The hover ring ("a thin ring inside") is `0 0 0 <spread> <colour>` painted by `box-shadow`, and the accent line ("a bottom bar") is `inset 0 -<width> 0 0 <colour>`; on focus they are appended after the theme glow, so a focused motion button shows outline + glow + ring + bar at once (measured on 5310). The ring guard (`Sgs_Motion_Ring_Guard`, `block.json::supports.sgs.elements.<el>.attrMap["css:box-shadow"]` and `restingShadow`) hides ring and accent fields on any element that has a shadow of its own, so a button with a resting shadow cannot have them; that is why they are offered on `sgs/button` only while its `boxShadow` is empty.

Blocks with motion parts on a button (DB `motion_targets`): `sgs/button` (`button`, wrapper), `sgs/buybox` (`add-to-cart`, `notifySubmit`; both wear `wp-element-button`, so ring and accent are overridden on focus), `sgs/form` (`prev-button`, `submit-button`, `submit-actions`; states only `invalid`, `step-changed`, `success`), `sgs/pricing-table` (`cta`), `sgs/product-card` (`cta`, `cta2`; `restingShadow` is declared on its `box` and `tag` elements, not on the CTAs), `sgs/theme-toggle` (`button`), `sgs/whatsapp-cta` (`button`; `restingShadow` is declared on that element, so ring and accent are refused there). `sgs/pricing-table` declares `restingShadow` on `plan-card`, not on `cta`. Other motion pieces that interact with focus: the form Focus state (`class-sgs-motion-focus-state.php`, fields only, never `outline`), `scale`/`opacity` channels that multiply `--sgs-focus-s` and `--sgs-focus-op` (horizontal-panel proximity, unrelated to keyboard focus), sheen sweep (FR-38A-35, on pointer entry and `:focus-visible`), `sgs-has-hover-indent:focus-within` and `sgs-has-img-zoom:focus-within` in `extensions.css`.

## Appendix B. Method and limits

- The scan tokenises CSS by braces and comments; selector lists are kept whole in the table, so one table row can cover several selectors. `.scss` nesting (for example `responsive-logo/style.scss`) is read as written, so a `&:focus-visible` row shows the nested selector only.
- Rules written by JavaScript do not exist (no `outline` CSS in any shipped `.js`). Rules written by PHP are in the table in section 1 (found by `rg`, not by the scan).
- Live results are for the canary's currently active snapshot (Mama's Munches) and its home page only; other snapshots, the WooCommerce cart and checkout, open drawers, mega panels and hover states were not exercised. Rows marked "inferred" in section 3 come from reading the CSS, not from measurement.
- Two of the 330 rules sit in `theme/sgs-theme/styles/mamas-munches.css`, a git-ignored local file (`.gitignore` line `theme/sgs-theme/styles/*.css`) that Spec 32 Part C says should stay empty; it is counted because it is in the working tree.
- Files written: this report only (plus scratch files under the session scratchpad: `scan.py`, `gen.py`, `tab.cjs`, `tab2.cjs`, `p3.cjs` to `p8.cjs`, JSON outputs).
