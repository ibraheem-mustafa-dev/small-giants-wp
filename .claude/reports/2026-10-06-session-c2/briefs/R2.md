# R2 - A normalised row key, so a cosmetic path change is not read as mass close-and-reopen

## Why this exists

Added 2026-10-06 by Bean's decision. **This defect will corrupt this session's own verification sweep** -
P1 and P2b3 both change emitted paths.

## Diagnosis

Row identity is `scripts/computed-route/lib/issue-classes.mjs::issueKey`:

```js
export const issueKey = ( x ) => `${ x.ref || x.pair }|${ x.path ?? '' }|${ x.kind }|${ x.key }`;
```

`path` carries positional selectors. Between two Session C2 sweeps `sgs/brand-strip` kept **exactly 51
rows** while **18 changed key**, because the walker's emitted path gained a `:nth-of-type(1)` on `__set` -
with **no verdict change on any of them**.

Gate TAIL's "at most 1 new row per 10 closed" cap reads that as a wave of closes plus a wave of opens, and
then passes or fails for the wrong reason.

## The fix - and it must be ADDITIVE

Add a **normalised-path key beside `issueKey`**, and compare on it where sweep-over-sweep deltas are
computed. **Do not change `issueKey` itself.** Changing it would re-key every existing ledger entry - which
is the very failure mode this task exists to prevent.

Normalisation strips positional selectors (`:nth-of-type(n)`, `:nth-child(n)`) from the path component,
leaving `ref`, `kind` and `key` untouched.

## Owned files

`scripts/computed-route/lib/issue-classes.mjs` (the new export),
`scripts/computed-route/lib/sweep.mjs` (the comparison site),
`scripts/computed-route/lib/solve-report.mjs` if a consumer needs it,
tests in `scripts/computed-route/tests/sweep.test.mjs`.

`issueKey`'s other importers are `triage.mjs` and `solve-report.mjs`; the additive design means neither
changes behaviour. **`triage.mjs` is owned by W3-G this wave - do not edit it.** If you believe it needs a
change, report that instead of making it.

## Negative control

- **Red on revert:** a case with two rows identical but for a `:nth-of-type(1)` in the path, asserting they
  share one normalised key and the delta reports **zero** closes and **zero** opens. Reverting must turn it
  red.
- **Not over-suppressing:** two rows on **genuinely different** paths (different elements, not a positional
  variation of one) must still be **distinct** keys. If normalisation over-collapses, real findings merge
  and vanish - strictly worse than the re-keying it fixes. Assert `issueKey` itself is **unchanged**.
