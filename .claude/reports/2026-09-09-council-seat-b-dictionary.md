## 0. Headline verdict

**The dictionary is not the binding constraint, and building a new one would make the
numbers worse, not better.** Three findings, in order of importance:

1. **[PROVEN] 143 of the 209 "declared in draft CSS but not extracted" entries are false
   positives generated by exactly THREE over-coarse rows in `property_suffixes`.** They are
   not transfer failures at all. The whole draft contains **one** gradient declaration, yet
   the report claims 100 gradient drops.
2. **[PROVEN] 44% of the real, live-rendered parity mismatches are on properties the
   dictionary already covers in BOTH tables.** This is Seat B's most important finding: for
   the largest class of genuine defects, the dictionary already has the row and something
   downstream ignores it. Spec 31 already says why (§13, line 332).
3. **[PROVEN] The honest gap channel already exists and already reports the truth.**
   `content-gaps.json` for this same run contains **25 entries**, of which ~11 are genuinely
   dictionary-addressable — and each already carries a `proposed_action`. The 209 is a
   second, cruder, reverse-inference channel that contradicts it.

The correct shape of the work is **repair + retire a duplicate reporter**, not **build a new
table**. A new table would be the project's documented most-expensive failure mode.

**Reconciled with Seat D (§7bis).** We agree on every overlapping point; three of my draft
claims were corrected by its evidence and are marked in place. The quantified answer to the

## 1. Where the "209" actually comes from — and why 68% of it is fiction

### 1.1 The mechanism [PROVEN]

`plugins/sgs-blocks/scripts/recogniser/leftover-bucket-router.py` is the sole producer
(`grep` → one hit, line 818). The logic:

- `route_extraction_failed()` (line 727) walks every slot a block *declares* and finds the
  ones the converter left empty — a **reverse inference from the block schema**, not an
  observation of a dropped declaration.
- `_has_draft_source_signal()` (line 561) then decides the reason string. It calls
  `_resolve_css_property()` (line 414), which maps the *slot name* to a CSS property by
  **longest-suffix match against `property_suffixes`**, then asks
  `_boundary_declared_properties()` (line 520) whether that property — or a shorthand family
  from `_property_families()` (line 460) — appears anywhere in the section's CSS.
- Present → `"declared in draft CSS but not extracted"`. Absent → `"no value extracted"`.

The check is **property-name presence at section granularity**. It cannot tell whether the
declaration's *value* was of the shape the slot wants, and it cannot tell *which element* in
the section carried it.

### 1.2 The three rows that manufacture 143 entries [PROVEN]

| `property_suffixes` row | resolves to | `_property_families` widens to | entries produced |
|---|---|---|---|
| `Gradient` → `background-image` (role `colour-gradient`) | `background-image` | `background` | **100** |
| `Colour` → `color` (role `color`) | `color` | — | **43** |
| `Duration` → `transition-duration` (role `motion`) | `transition-duration` | — | **8** |

**All nine boundaries declare `background`, `color` and `transition-duration`** (verified by
unioning `declarations` keys from `expected-rules-b1..b9.jsonl`). Because the family fallback
accepts the bare `background` shorthand as proof that `background-image` was declared, *every*
`*Gradient` slot on *every* section fires `True` automatically.

**The killer measurement:** across all nine `expected-rules-*.jsonl` files, exactly **ONE**
declaration in the entire draft has a gradient value —
`b4 .sgs-product-card--trial { background: linear-gradient(135deg, …) }`. Every other
`background:` value is a solid colour, `white`, `transparent` or `none`. So **at most 1–5 of
the 100 gradient entries can be real; ≥95 are provably fabricated.**

The `Colour` → `color` row is the same defect in a different family: `shadowColour`,
`backgroundOverlayColour`, `shapeDividerTopColour`, `iconCircleShadowColour` and
`splitMediaOverlayColour` all resolve to the *text* colour property, so any section that sets
`color:` (i.e. all of them) lights up every `*Colour` slot the block declares.

### 1.3 The 209, grouped and classified

| Class | n | % | Dictionary-addressable? |
|---|---:|---:|---|
| **A — Gradient false positive** (`Gradient`→`background-image`→`background` family) | 100 | 48% | No. Reporter defect. |
| **B — Colour false positive** (`Colour`→`color`) | 43 | 21% | No. Reporter defect. |
| **C — Duration false positive** (`Duration`→`transition-duration`) | 8 | 4% | No. Reporter defect. |
| **D — Un-routed slot: `block_attributes` row exists but `css_property` IS NULL** | 44* | — | **Yes** — but 35 of these overlap A/B above. |
| **E — Layout/box slots with a plausible real signal** (`maxWidth`, `justifyContent`, `alignItems`, `columns`, `margin`, `minHeight`, `borderRadius`, `shadow`, `textAlign`, `fontStyle`, `splitMedia*`, `title*`, `label*`) | ~58 | 28% | **Partly** — these need per-element proof, not a dictionary row. |

\* Class D overlaps A/B: `shapeDividerTop/BottomColour(+Gradient)` (28),
`gridItemShadowColour` (5), `gridItemTextColourGradient` (5) are already counted as false
positives; the genuinely-unrouted remainder is `bgSvgMinHeight` (4),
`labelTextColumns`/`titleTextColumns` (2).

**Net: 151/209 (72%) are reporter artefacts. The genuine residual is ≤58, and none of it is
proven to be a missing dictionary row** — Class E slots resolve fine; they were flagged
because the *section* declares `max-width`/`align-items` somewhere, not because *this
element's* declaration was dropped.

**[PROVEN] The honest channel disagrees by an order of magnitude.** `content-gaps.json` for
the same run holds 25 records (21 `dropped`, 4 `fuzzy_fallback`), containing just **three**
distinct dictionary-shaped issues:

- `sgs/container band:--content-width` × 4 — `[NO_DESTINATION] … (proposed_action: add attr
  or seed property_suffixes)` — a **custom property**, which the dictionary has no concept of.
- `*TextIndent` on `sgs/media`/`sgs/testimonial` × 8 — *"content-semantic string attr has no
  role/derived_selector — DB-data gap"*.
- `videoCaptionsLabel` / `videoCaptionsSrcLang` × 2 — same shape.

Plus 2 unmapped `::before`/`::after` `margin-top` drops and 4 BEM-recognition fallbacks
(not dictionary).

## 2. Coverage matrix — the 910 live parity prop-diffs

Method: every `diffs[].prop` across all three viewports of `computed-parity.json`
(910 instances, 56 distinct properties) checked against `property_suffixes.css_property`,
`block_attributes.css_property` (comma-split) and `excluded_properties`.

| Class | instances | % | Reading |
|---|---:|---:|---|
| **Covered in BOTH tables — still wrong on the live page** | **403** | **44%** | **The dictionary is not the constraint.** |
| **In `property_suffixes` only, no `block_attributes` consumer** | 249 | 27% | Data seeded, no destination attr / no resolver. |
| **Not in the dictionary at all** | 258 | 28% | Mostly SVG-intrinsic + `border-*-style`. |

### 2.1 "Covered but still dropped" — the important class [PROVEN]

`color` (57), `align-items` (38), `display` (37), `background-color` (33),
`background-position/repeat/size` (81), `margin-bottom` (21), `max-width` (19),
`justify-content` (16), `grid-template-columns/rows` (30), `font-size` (15).

The actual values prove these are **wrong-value defects, not transfer gaps**:

```
color              15x  draft rgb(58,46,38)   → clone rgb(197,106,122)
background-color    8x  draft rgb(255,255,255)→ clone rgb(251,243,220)
align-items        11x  draft normal          → clone center
border-top-style    8x  draft none            → clone solid
border-top-width    8x  draft 0px             → clone 1px
```

The clone is *painting something the draft never asked for*. That is a **block default
winning over an absent draft declaration** — precisely the failure mode already recorded in
memory as `a-schema-default-erases-the-absence-a-pipeline-preserved` (D1005). No dictionary
row can fix it; the dictionary has the row already.

### 2.2 "`property_suffixes` only" — seeded data, no lift path [PROVEN, with spec citation]

`border-*-width` (120), `row-gap`/`column-gap` (42), `overflow-x/y` (24), `flex-grow/basis`
(19), `border-*-radius` corners (24), `padding-*` (12), `grid-template-areas` (6).

**Spec 31 §13, line 332 already states this outright:**

> *"SEEDED = data rows exist in the DB; the LIFT-PATH for most is a later stage. Exceptions:
> `background-size`/`-position`/`-repeat`/`-attachment` DO lift now via `outer_box.py`; the
> rest (`order`/`grid-*`/`overflow`/`object-fit`/`position`/`flex`/`aspect-ratio`) are
> data-only — their resolver is a future stage-by-stage step."*

Cross-referencing that sentence against the parity table matches item-for-item. **This class
is a known, specced, unbuilt resolver backlog — not a discovery, and not a dictionary gap.**

Note also that `overflow-x`, `overflow-y`, `flex-grow`, `flex-basis` sit in
`excluded_properties` with the reason *"no block declares a consuming attribute — CSS
passthrough only (D2)"*. Those 55 instances are **deliberate exclusions still measuring as
parity failures** — i.e. the exclusion decision is correct but the measurement tool doesn't
know about it. That is a ruler bug (`a-measurement-tool-can-be-wrong-in-both-directions`).

### 2.3 "Not in the dictionary" — mostly not real [PROVEN]

- `stroke-linecap` (36), `stroke-linejoin` (36), `d` (9), `cx`/`cy`/`r` (18) = **99 (38%)** are
  SVG presentation attributes. `draft butt → clone round` means a *different icon* was
  substituted — an icon-resolver identity issue, not CSS transfer. Adding dictionary rows
  would do nothing.
- `border-image-slice` (27): `draft 100% → clone 1` is UA-default noise riding on the

- `border-bottom/left/right/top-style` (120) is the one **genuine dictionary hole** in this
  bucket — and the paired `border-*-width` rows *do* exist in `property_suffixes`, so the
  family is half-seeded.
- `overflow-block` (12): a logical-property alias nothing handles.

## 3. Two dictionaries already exist, and they disagree

**[PROVEN] `block_attributes.css_property` carries a strictly better vocabulary than
`property_suffixes` for exactly the slots that produced the false positives:**

| slot | `property_suffixes` says | `block_attributes` says | correct? |
|---|---|---|---|
| `shadowColour` | `color` | `box-shadow-color` | block_attributes |
| `backgroundColourGradient` | `background-image` | `background-color-gradient` | block_attributes |
| `borderColourGradient` | `background-image` | `border-color-gradient` | block_attributes |
| `bgAnimationDuration` | `transition-duration` | `anim:duration` | block_attributes |
| `textColumns` | `grid-template-columns` | `column-count` | block_attributes |
| `iconColourGradient` | `background-image` | `color-gradient`, `stroke` | block_attributes |

**The leftover-bucket router never consults `block_attributes`.** It only suffix-matches
`property_suffixes` (line 414). Repointing it at the per-block declarative column would kill
most of the 143 false positives with no new table and no new column.

### 3.1 Seeding state of the "Front-1" declarative columns [PROVEN]

```
block_attributes: 7348 rows
  css_property populated: 3035 (41%)
  css_element  populated: 2050 (28%)
  css_state    populated:  397 ( 5%)
  css_tier     populated:   10 (0.1%)
```

`css_tier` at 10 rows is worth flagging to the council. `db_lookup.py:1884-1892` explains
that tier-sibling rows *deliberately* carry NULL `css_property`/`css_tier` because the
sibling's property is derived from its base row at read time — and explicitly warns a future
session against "fixing" them. **Do not let the council propose backfilling `css_tier`.**

### 3.2 A likely reseed regression [PROVEN existence, ASSUMED cause]

D875 (2026-08-28) ran a census + migration
(`scripts/migrations/2026-08-27-gradient-family-synthetic-css-property-census-fix.py`)
correcting **78 rows** carrying synthetic gradient values (`background-color-gradient` 17,
`color-gradient` 28, `border-color-gradient` 33) to the real `background-image` longhand.

Querying the live DB today:

```
color-gradient          106 rows
border-color-gradient    94 rows
background-color-gradient 26 rows
box-shadow-color          27 rows
color-link-gradient       10 rows
```

**263 rows now carry those same synthetic values — more than before the migration.**
[ASSUMED] cause: `/sgs-update` reseeds `block_attributes` from block.json, so the migration
fixed rows rather than the declaration they derive from — the exact shape of the memory rule
`a-raw-db-update-does-not-survive-a-reseed`. **This needs verifying before the council
designs anything**, because if true it means *any* dictionary correction written as a row
update will evaporate on the next reseed, which invalidates several obvious design directions.

(Separately, `fx:*` and `anim:*` namespaced values — ~1050 rows — are deliberate motion
pseudo-properties, correctly outside `property_suffixes`. Not a defect.)

**Where a declaration can be silently dropped.** The CSS side is genuinely well-defended —
`unrouted` fails loud (`dispatch_table.py:165`, test `test_unrouted_fails.py`), residual

remaining silent-drop surfaces are:

1. **`_ALWAYS_STRIP_SHORTHANDS` (css_pass.py:167,177).** `background`/`border` are stripped
   unconditionally. If `expand_background_border_shorthand` fails to produce a longhand for
   any value shape, the declaration vanishes with no gap record. This is exactly the D875
   gradient bug — same line, one value shape. **[ASSUMED] other value shapes (`background`
   with multiple layers, `border` with a colour-first ordering) are untested.**
2. **`_NON_SIGNAL_PROPERTIES = {"display"}` (leftover-bucket-router.py:346)** — reporter-side
   only, but it means `display` (37 parity diffs) can never be reported as a gap.
3. **`_area_excluded` — a genuinely silent drop, and the highest-value one found.**
   `services/fold_helpers.py:302-304` defines
   `_area_excluded = _CROSS_NODE_EXCLUDED_PROPS | {grid-area, width, height, max-width,
   min-width, max-height, min-height}`, and line 437 skips them:
   ```python
   if css_prop in _area_excluded or css_prop.startswith("--"):
       continue
   ```

   The `continue` is **before** the `attr_base is None` branch that emits the
   `cross_node_gap_candidate` trace (line 447), so an excluded property is dropped with
   **no gap record at all** — it cannot appear in `content-gaps.json`, and the only place it
   surfaces is the crude 209 channel. **[CORRECTION to my earlier draft]** this line is also
   why `--content-width` gaps: custom properties are explicitly skipped here, not
   "inexpressible in the dictionary". Independently identified by Seat D as an unowned
   faithful-transfer hole; confirmed here at file:line, and it accounts for **15 of the 209**
   (§8).
4. **Stale gate comment:** `dispatch_table.py:112` says `excluded_properties` *"currently
   ships empty, D235"*; the table has 10 rows. Harmless but misleading.

## 5. Verdict on Bean's three proposed columns

### (a) "How to DECLARE it" — **YES, but it already half-exists; extend, don't add**

**Verdict: build it, as a value-shape/predicate column on `property_suffixes`.**

This is the genuinely missing datum and it is the direct cause of the 143 false positives.
The reporter can currently only ask *"was property P named?"*. It needs to ask *"was a
declaration matching this slot's VALUE SHAPE present?"* — `Gradient` needs `value matches
/gradient\(/`; `Colour` needs *"a colour-valued declaration on the shadow/overlay/divider
sub-property, not bare `color`"*.

`property_suffixes` already carries the seeds of this: `role` (18 values), `kind_override`
(`number_unitless` / `number_px_or_em` / `string`), `is_token_matched`, `token_source`. A
`value_predicate` column is a natural fourth. **Populate from:** the existing
`kind_override`/`role` pairs for the easy cases, and a one-off census of the ~15 families
that need a regex.

**Cost of not doing it:** the 209 stays 72% fiction and nobody can trust the number — the
project's documented `a-gate-that-always-fails-is-a-gate-nobody-reads` failure mode.

### (b) "How to PROCESS it" — **NO. It already exists and it is not property-keyed**

**Verdict: recommend AGAINST.**

Processing is **already** fully determined, and by design it is *not* a function of the
property alone. `dispatch_table.resolver_id()` (dispatch_table.py:124) keys on
`(layer, css_property)` where `layer` comes from `layer_detect` at runtime per element. The
module docstring is explicit that this is deliberate: *"It NAMES NO BLOCK (R-31-1 / R-31-9):
block-specific behaviour comes from the DB … never an `if slug ==`."*

A per-property "how to process" column would either (i) duplicate `role` +
`kind_override`, which already drive parsing/serialisation (Spec 31 §13 step 5), or
(ii) encode the resolver choice, which is **structurally wrong** because the same property
routes to different resolvers on different elements. `gap` is the worked example — the
docstring at `dispatch_table.py:87-90` says it is deliberately kept layer-ambiguous.

Adding this column would create a second, less correct copy of the dispatch table.

### (c) "Which FILES process it" — **NO. Recommend against, firmly**

**Verdict: recommend AGAINST — this is a maintenance liability that will rot, and the
project has already been burnt by exactly this.**

Three independent reasons:

1. **It is not a function of the property.** Same argument as (b): the file is picked at
   runtime by layer. A `processed_by` column would have to say
   `"outer_box.py | content_band.py | grid.py | typography.py"` for most rows — which is the
   `_LAYER_TO_RESOLVER` dict written out longhand, with no information added.
2. **It rots silently and there is no gate that can catch it.** `dispatch_table.py:112`
   already carries a stale claim (`excluded_properties` "ships empty") that has been wrong
   since the table gained 10 rows. The docstring also records `grid_area`/`GRID_AREA` being
   deleted in D642 and `scalar_media`/`scalar_content` in Step 12 — **the resolver roster has
   changed three times in three months.** A file-name column would have been wrong on each
   occasion, with no failing test.
3. **It contradicts a standing project rule.** `CLAUDE.md` says *"never cache a roster or
   count here; verify via the prebuild gates"* and `.claude/CLAUDE.md` says *"a summary
   sentence here is a copy that drifts"*. A DB column is the same anti-pattern with a
   schema around it. The equivalent live query already exists and is free:
   `grep -rn "css_property ==" converter/resolvers/`.

**If the council wants file-level traceability, the right instrument is the existing
runtime trace** — `convert-trace-b*.jsonl` is already written per boundary per run and
records the actual path taken. That is ground truth; a column would be a prediction.

## 6. Prior art — do NOT let the council design a duplicate

**[PROVEN] Three things already exist that the council is at risk of reinventing:**

1. **The dictionary itself.** `property_suffixes` (158 rows, 113 with `css_property`),
   `excluded_properties` (10), `modifier_suffixes` (19), `block_attributes` declarative
   columns. Spec 31 §13, line 289 names `property_suffixes` as *"THE property→attr-suffix→
   parse map (step 2/5/6)"*.

2. **The completeness instrument Bean is describing — already specified as MF-1, and
   [PROVEN] already BUILT.** `plugins/sgs-blocks/scripts/ledger/declare_input.py` exists
   (56,687 bytes), alongside `coverage_check.py` (47,279), `content_gap_check.py` (19,575),
   their goldens (`coverage-baseline.json`, `content-gap-baseline.json`) and a `tests/`
   directory. So does `plugins/sgs-blocks/scripts/coverage-matrix/generate-coverage-matrix.py`
   with an 854KB generated `coverage-matrix.json`. **[CORRECTION to my earlier draft, which
   called MF-1 "specified but unbuilt" — that was wrong.]** Spec 31 line 454 describes it:
   Spec 31 line 454: *"Draft-derived CSS Accounting Ledger (MF-1, the keystone).
   `declare_input` = the draft's parsed (selector, property, value) stream captured at Stage
   0.7 BEFORE any routing … `UNACCOUNTED = draft_decls − (transferred ∪ excluded-with-reason
   ∪ gap)`. Any UNACCOUNTED = hard fail."* The spec even anticipates this exact review:
   *"(Supersedes the §5 matrix as the primary completeness instrument — the matrix only sees
   cells it knows about; the ledger sees the whole draft.)"*
   **MF-1 is forward-keyed on the draft's actual declarations. The 209 is backward-keyed on
   the block's schema. Forward-keyed is the correct direction, it is already designed, and
   it is already written.** The only open scope is A2 (extend `declare_input` to content
   units), which is design-gated. **Any seat proposing to build a CSS-property census is
   about to rebuild these two files.**

3. **⛔ A DB-backed gap-candidate table — Bean has already rejected this.**
   Spec 31 line 625: *"D3 `attribute_gap_candidates` was never finished and **the project
   owner confirmed it was never wanted**; the honest-gap mechanism is preserved via
   in-memory ledger."* Retired 2026-09-02, one week ago. Spec 31 line 321 repeats it.
   **If any council seat proposes a `css_gap_candidates` / `css_dictionary_gaps` table, it is
   re-proposing a thing Bean killed seven days ago.**

Also relevant: **D875** (2026-08-28) already ran a census+migration triad over the synthetic
gradient `css_property` values — the pattern, the tooling shape and the detector all exist.
**D470** (2026-08-02) built the rebuild-from-git seeders for `property_suffixes`, `slots` and
`excluded_properties`, and documents that **row order is load-bearing** (`propose_attr_name()`
uses `ORDER BY rowid LIMIT 1`; `INSERT OR REPLACE` scrambles it). **D497** notes a new
`property_suffixes` entry needs **two** `/sgs-update` passes.

Nothing in `parking.md` or `decisions.md` matches the string "dictionary" — so the *framing*
is new even though every *mechanism* it names already exists.

| **(iii) `css_property` set, `css_element` NULL — the D643 danger state** | 1 | 0.5% | `sgs/container.textDecoration → ('text-decoration', None)` |

Read block-scoped rather than by cause, the same 209 splits **121 fully classified (58%) /
87 `css_property` NULL (42%) / 1 half-classified**.

**Direct answers to the revised ask:**

- **(i) missing data — 8 entries (3.8%).** Four slot names. This is the smallest category.
  **Seeding the dictionary would close under 4% of the 209.**
- **(ii) `_area_excluded` — 15 entries (7.2%).** Seat D's finding (a) confirmed at file:line,
  and it is worse than "unowned": the `continue` precedes the trace emitter, so these are
  the only truly *silent* CSS drops in the pipeline. Highest fix-value per unit of work.
- **(iii) the 54 NULL colour attrs / 15 undeclared blocks — 87 entries overlap, but only 8
  are causally attributable.** 79 of the 87 NULL-`css_property` entries are *also* class (vi)
  false positives: `shapeDividerTopColourGradient` on `sgs/container` is both NULL **and**
  fabricated by the `Gradient` row. Fixing the NULL would not remove the entry; fixing the
  reporter would. **Sequencing matters: repair the reporter first, or the colour-attr
  landing will be measured against a number that cannot move.**
- **(iv) reached a resolver and was dropped — 39 entries (18.7%).** These have `css_property`
  *and* `css_element` populated, i.e. the dictionary has said everything it can say. The
  cause is downstream (resolver coverage, or a further false positive from the section-
  granularity signal check). **This is the real converter backlog, and it needs per-element
  proof — the reporter cannot distinguish "dropped" from "the section declared it on a
  different element" at its current granularity.**
- **(v) genuine expressiveness limit — ONE, and it is real.** [PROVEN] 44 of the 209 carry a
  `block_attributes.css_property` value with **no counterpart in `property_suffixes` and no
  counterpart in real CSS**: `border-color-gradient` (15), `color-gradient` (15),
  `box-shadow-color` (8), `anim:duration` (6). Framework-wide that vocabulary covers 263
  rows (§3.2). **No reporter and no resolver can check a synthetic property against a draft's
  declared-property set, because the draft can never declare `box-shadow-color`.** The
  missing datum is a **decomposition**: synthetic → (real property, value-component) —
  `box-shadow-color` = the colour component of `box-shadow`; `anim:duration` =
  `animation-duration`; `*-gradient` = a `gradient()`-valued declaration on its family.
  That is the same datum as my §5(a) `value_predicate`, arrived at from the opposite
  direction, and it is **the only thing in this review that justifies a new column.**

### 7bis.2 Q3 verdicts after Seat D's evidence

- **(a) "how to DECLARE it" — verdict UNCHANGED (build it), and now better-motivated.** Seat
  D is right that `kind_override` / `is_token_matched` / `token_source` / `role` already are
  Bean's classification columns for *parsing*. What none of them expresses is **which draft
  declaration shape satisfies this slot** — the synthetic-vocabulary gap in (v). One column,
  one purpose, 64 distinct values to populate.
- **(b) "how to PROCESS it" — verdict UNCHANGED (against).** Strengthened: Seat D counts 10
  resolver files behind `dispatch_table.py` + `dispatch_spine.py`, i.e. Spec 31 §12.4's
  "per-resolver files behind ONE dispatch table" is built. A property-keyed processing column
  would be a second, less correct copy.
- **(c) "which FILES process it" — verdict UNCHANGED (against), now with a stronger reason.**
  My original argument was rot-risk. Seat D supplies the decisive one: the routing key is
  `(block, layer, property, tier)`, so a *property*-keyed file column is **not merely
  rot-prone, it is under-keyed** — it cannot represent the mapping even on the day it is
  written. Same failure class as D875's `AmbiguousLayerAttrError`.

### 7bis.3 Two constraints that bind every direction below

- **[Seat D, confirmed by my §3.2]** A raw `UPDATE block_attributes SET css_property=…` does
  not survive a `/sgs-update` reseed (D935). My finding that D875's 78-row gradient fix has
  since become 263 rows is consistent with exactly that. **Every dictionary correction must
  be written to the block.json declaration it derives from.** My earlier §3.2 [ASSUMED]
  cause is now corroborated by an independent seat; treat it as the working hypothesis and
  verify before any row-writing work is scheduled.
- **[Seat D + D470]** `property_suffixes` row ORDER is load-bearing (`ORDER BY rowid`,
  `propose_attr_name()` uses `LIMIT 1`). `INSERT OR REPLACE` scrambles precedence. Any new
  column must be added by `ALTER TABLE`, never by a rewrite.
- **[D643]** A `css_property` landed without a resolved `css_element` falls to ROOT routing
  and **misroutes on a clone** — 51 new F6 violations last time. My class (iii) shows the
  tree currently contains exactly one such row (`sgs/container.textDecoration`). Property and
  element land together or not at all.

## 7. Three candidate design directions

### Direction 1 — Repair the reporter; add one column. **(recommended)**

**Scope:** (a) add `value_predicate` to `property_suffixes`; (b) repoint
`leftover-bucket-router._resolve_css_property` at `block_attributes.css_property` for the
block in hand, falling back to suffix-match; (c) make `_property_families` stop treating the
`background` shorthand as proof of `background-image`.

- **Kills** ~143 of 209 false positives; makes the remaining number trustworthy.
- **Adds** one column with a clear population source and an obvious rot-test (a row whose
  predicate never matches anything on a real draft is dead data).
- **Risk:** low. Reporter-only — cannot change what the converter emits.
- **Does not fix** the 44% covered-but-still-dropped parity class. That is separate work.
- **Trade-off:** improves the *instrument*, not the *clone*. Bean should know that.

### Direction 2 — Adopt the ledger that already exists; retire the 209 channel. **(cheapest)**

**Revised after Seat D: this is not a build, it is a switchover.** `declare_input.py`,
`coverage_check.py` and `generate-coverage-matrix.py` are all present with goldens (§6.2).

**Scope:** run `declare_input` on this draft, compare its `UNACCOUNTED` set against the 209,
then retire `route_extraction_failed`'s Source-1 arm — the arm that produced all 209 —
leaving `content-gaps.json` and the ledger as the two honest channels.

- **Structurally cannot invent a drop.** It is keyed on declarations the draft actually
  contains, so 100-gradients-from-one-gradient is impossible by construction.
- **Removes a channel rather than adding one** — the opposite of the `attribute_gap_candidates`
  mistake Bean already ruled on.
- **Cost: the smallest of the three**, now that the code is known to exist. The open A2
  (content units) scope does not block the CSS side.
- **Trade-off:** needs a verification pass first — the goldens date from July, so confirm
  `declare_input` still runs green on a current draft before betting the reporting on it.

### Direction 3 — Attack the 44%: build the missing resolvers, not the missing rows.

**Scope:** work the Spec 31 line-332 backlog — `order`, `grid-*`, `overflow`, `object-fit`,
`position`, `flex`, `aspect-ratio` are seeded-but-data-only. Plus seed the one genuine hole
(`border-*-style`, 120 instances) and investigate the block-default-overriding-absence class.

- **Only direction that moves the live parity number.** 1 and 2 improve reporting only.
- **Trade-off:** it is the largest, and it needs the §2.1 defects triaged first — several
  ("draft `border-style:none` → clone `solid`") are block-default bugs, not converter bugs,
  and would be fixed in `block.json`/`style.css`, not the dictionary at all.

### Direction 4 — Close `_area_excluded`. **(smallest, and the only silent drop)**

**Scope:** `fold_helpers.py:302-304,437`. Either route the width/height family per-area, or —
if the exclusion is deliberate — move the `continue` *after* the `cross_node_gap_candidate`
trace so the drop is at least recorded. Accounts for 15 of the 209 and is the only place in
the CSS path where a declaration vanishes with no record anywhere.

- **Risk:** the exclusion looks deliberate (cross-node width routing is genuinely ambiguous),
  so the honest first move is the trace, not the routing. Design-gate the routing half.
