### Discovered finding (pre-existing mechanism, not a regression from this diff — disclosed, not hidden)

Per step 5's instruction to check specifically whether removing a declared attribute a stored
instance still carries could trigger recovery UI: it does not, but investigating *why* it does not
surfaced something worth recording precisely, because the reason is not "the attribute is genuinely
gone."

**`splitImage`/`splitImageMobile` remain live in the server-registered block schema after this
change**, independent of and unaffected by deleting their static `block.json` declaration. Verified
three ways, all against the live canary after a fresh, confirmed OPcache reset (ruling out stale
bytecode as the explanation):

1. `wp.apiFetch({ path: '/wp/v2/block-types/sgs/hero' })` from a real editor session — `splitImage`
   and `splitImageMobile` both present in the returned schema, `totalAttrs: 306`.
2. `WP_Block_Type_Registry::get_instance()->get_registered('sgs/hero')->attributes` via SSH — both
   present.
3. A fresh, isolated probe script (bootstrapped via `wp-load.php`, deployed and deleted within this
   session) that: read `build/blocks/hero/block.json` directly and confirmed **no** `splitImage` key
   on disk; called `unregister_block_type('sgs/hero')` then `register_block_type($path)` fresh in the
   same request; and still found `splitImage` in the resulting registry. This rules out any request-
   scoped or file-content caching explanation.

**Root cause, read from source, not inferred:** `includes/media-element-attrs-register.php`'s
`sgs_register_media_element_attrs()` (hooked on `register_block_type_args`, priority 20) reads
`supports.sgs.mediaElements` from the block's own `block.json` — untouched by this diff, still
declaring `{ "prefix": "split", "context": "element", "atoms": ["source", "media-type"] }` — and
independently re-derives the same attribute name family (`splitImage`, `splitImageId`,
`splitImageUrl`, …, each with `Tablet`/`Mobile` tiers) from that declaration, merging them in
wherever the block's own `attributes` object doesn't already declare the name
(`$args['attributes'] = array_merge($injected, $existing)`, comment: *"the block's own declaration
wins"*). This is a deliberate, documented mechanism (`Bean's ruling 2026-08-30`), not a bug — but its
practical consequence for this diff is that **deleting `splitImage`/`splitImageMobile` from
block.json's static `attributes` block has no observable effect on the live, server-registered
schema**: the same names are silently re-supplied by this filter from the still-present
`mediaElements` "source" atom declaration on the SAME block.json file.

This is why the editor opens with **zero** friction and `isValid: true` — the schema the editor
validates against still recognises `splitImage`. It also means the commit's own stated intent
("close the last reason these two dead declarations needed to survive... deleted") is accurate for
the *static declaration*, but the attribute names themselves remain part of the block's live schema
today, sourced from `mediaElements` rather than the deleted `attributes` entries. **Not a regression
— present identically before and after this diff** (the filter ran against the pre-diff block.json
too; it simply had nothing to inject then because the block's own declaration already won). Flagged
as a follow-up for whoever owns the `mediaElements`/attribute-declaration relationship, not fixed
here — this diff's own scope was the static `attributes` block only, and touching
`supports.sgs.mediaElements` is the DB-routing mechanism CLAUDE.md's comment on this exact diff
names as an "out-of-scope subsystem this migration must not touch blind."

## Capture 2 — decorative toggle + Alignment & grid panel + hover controls (later, same day)

### What changed

Three separate pieces of work landed on this file, layered on top of Capture 1's state:

1. **Decorative toggle** (detector item 18) — `splitMediaDecorative` (boolean, default
   `false`), scoped to the split-media element only (the block's one real `<img>`/
   `<video>`/svg — `backgroundImage` is a CSS background, never exposed to assistive tech,
   and correctly excluded). `render.php` blanks the split-media alt (covers the image tier)
   and adds `aria-hidden="true"` to the media wrapper (covers video/svg tiers, which carry
   no `alt` of their own).
2. **"Alignment & grid" panel** (detector item 21 appendix) — 7 attributes
   (`alignContent`/`justifyContent`/`flexDirection`/`flexWrap`/`gridAutoRows`/
   `gridTemplateRows`/`justifyItems`) were declared and consumed by the shared
   `SGS_Container_Wrapper` class but had no editor control at all. Built a new
   `PanelBody` + `ToolsPanel`, mirroring `sgs/site-footer-row`'s identical panel but scoped
   to hero's actual (smaller) attribute set — hero's `gridTemplateColumns`/`alignItems`
   attributes are unrelated (split-media ratio control; a confirmed-dead attribute) and were
   correctly excluded.
3. **Hover-state border + transition controls** — `borderColourHover`/
   `borderColourHoverGradient` (a new "Hover" tab on the existing `SgsBorderControl`) and
   `transitionDuration`/`transitionEasing` (a new "Hover" panel) — both previously declared
   and rendered with no control, per the block's own long-standing code comment admitting
   the gap.

A same-session QC pass also caught and fixed a real bug in this file, unrelated to the
three items above: five attributes (`splitMediaObjectPosition` + its two tiers,
`mediaBackground`, `mediaBackgroundGradient`) were referenced in two `ToolsPanelItem`
`hasValue()` callbacks but never destructured in the `Edit` function's scope — a
`ReferenceError` waiting to fire the first time either callback ran. Fixed by adding them
to the existing destructure block.
