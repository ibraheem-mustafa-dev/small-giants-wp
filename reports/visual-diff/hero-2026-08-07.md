## Live measurement (post-deploy, canary homepage)
Hero renders unchanged: 0 elements matching `[class*="badge"]`, innerText 217
chars, 953x1905px, headline "Made for the mum who needs it most", root `style`
attribute (none).

## Why zero visual change is the CORRECT result here
`badges` was vestigial — the capability is served by nesting `sgs/label` children
— and NO stored hero instance carried badge data. Verified on the canary with a
negative control before removing anything:
  wp post list --post_status=any --s='badges'   -> no posts
  wp post list --post_status=any --s='sgs/hero' -> 12 posts
The second proves the query works, so the first zero is real rather than a broken
search. With no stored data, nothing rendered before and nothing renders now.

## What else the removal covers
`supports.sgs.arrayContentLift` was removed with it: `badges` was hero's ONLY
array attribute, so the support declared a capability the block could not
exercise. That is what made the new single-item-array warning fire on EVERY hero
clone — fixed at source rather than by narrowing the gate.

## Limits

which was deliberately not run (shared DB, co-active track). Until then the
converter warning still fires — the code is ahead of the data.
