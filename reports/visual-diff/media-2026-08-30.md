# `sgs/media` — video playback flags routed through the video-behaviour atom

**Date:** 2026-08-30 · **Decision:** D909 · **Block:** `sgs/media`
**Change:** `src/blocks/media/render.php` — autoplay / muted / playsinline are now
resolved together by `sgs_media_atom_video_behaviour_requires()` instead of
independently.

---

## ⚠ What was NOT done, stated first

**No browser was opened. No deploy was run. There is no live DOM check, no
screenshot, and no pixel comparison in this report.**

That is deliberate, not an omission: Wave 4 builds the atom layer but wires it to
no surface, so there is nothing on the canary to look at yet. Wave 5 is the first
point at which a live check is possible, and the acceptance rule for this whole
programme is that **Wave 5 closes on paint** (STOP-CONSUMED-IS-NOT-PAINTED).

This report exists because the visual-diff gate correctly identified that
`render.php` deletes non-comment lines and therefore *could* change rendered
output. It documents what actually changes and the evidence that was gathered,
so a later session is not left guessing.

`check-markup-neutral.py media` reports:


## What changes in the rendered markup

Only the attribute list on the `<video>` element, and only when the client has
set an invalid combination. Nothing about layout, dimensions, sources, poster,
captions, or any other element changes.

**The defect being fixed.** A browser refuses to autoplay an unmuted video, and
iOS requires `playsinline` or the video takes over the screen. Before this
change, `render.php` built the three flags independently with no guard:

```php
$autoplay_attr = $video_autoplay ? ' autoplay' : '';
$muted_attr    = $video_muted    ? ' muted'    : '';
$inline_attr   = $video_inline   ? ' playsinline' : '';
```

The coupling existed in exactly one place — `view.js:148-152`, client-side only.
So a client setting autoplay-on with muted-off got server markup the browser
would not play, silently repaired on hydration. **A visitor without JavaScript
kept the broken state.**

## Measured, at the PHP level

Run directly against `sgs_media_atom_video_behaviour_requires()`:

| Stored attributes | desktop | tablet |
|---|---|---|
| autoplay ON, muted OFF, inline OFF | `autoplay=true muted=true inline=true` | `autoplay=true muted=true inline=true` |
| autoplay OFF, muted OFF | `autoplay=false muted=false inline=false` | `autoplay=false muted=false inline=false` |
| tablet-only autoplay | `autoplay=false muted=false inline=false` | `autoplay=true muted=true inline=true` |

Rendered attribute list, before and after, for the first row:

```
BEFORE:  <video autoplay …>
AFTER:   <video autoplay muted playsinline …>
```

Three things this establishes, each mattering separately:

1. **The coupling fires.** An unmuted autoplay is corrected.
2. **It is not blanket-forcing.** Row 2 — autoplay off — leaves `muted` off. A
   client who wants an unmuted, click-to-play video still gets one. Without this
   control the fix would be indistinguishable from "always mute everything".
3. **It is per-tier.** Row 3 — a tablet-only autoplay override — couples muted
   and playsinline on tablet while leaving desktop untouched. The flags are tier
   objects, so a fix applied only at desktop would have left the tablet markup
   broken.

Verified by the coordinator running the function directly, not taken from the
implementing agent's report.

⚠ **`check-dead-controls` needed broadening for this change, and the reason is
worth knowing.** The moment `render.php` stopped naming `videoPlaysInline` and
friends as literals, the detector reported all three as unrendered — they went
from *consumed* to *dead* while becoming more correct. The media layer composes
every attribute name from a prefix and a base, so a literal grep cannot see one.
The detector was broadened (not baselined, per the project rule) and checked for
overmatch: it derives exactly the 9 names this atom composes, no unrelated
attributes, and nothing at all from a corpus with no helper call.

## What Wave 5 must verify live

1. A `sgs/media` block with **autoplay on and muted off**, published, inspected
   in the browser: the `<video>` element carries `autoplay muted playsinline`
   **with JavaScript disabled**. That is the case that was broken.
2. The negative control alongside it: **autoplay off, muted off** must still
   render an unmuted video with no `autoplay` attribute. If both cases produce a
   muted video, the fix has over-applied and the first check alone would not
   reveal it.
3. Both at desktop and at a tablet width, since the coupling is per-tier.

## Measured live, 2026-09-01 (closes the three cases above)

Fixture built by `python plugins/sgs-blocks/scripts/probes/build-noJS-autoplay-fixture.py --apply`
(page 3147, `[GATE - DO NOT DELETE] no-JS autoplay probe`, two real-canary-video
instances). Measured by `node plugins/sgs-blocks/scripts/probes/probe-noJS-autoplay.mjs
https://sandybrown-nightingale-600381.hostingersite.com/?page_id=3147`, with
Playwright's `javaScriptEnabled: false` — genuinely disabled, not merely
un-interacted-with, because `view.js`'s `applyTierPlayback()` (L148-152)
forcibly sets `video.muted = true` on hydration whenever autoplay resolves
true and would mask a broken server fix if JS ran:

```
--- desktop (1280x900), JavaScript DISABLED ---
  [PASS] case A (autoplay-on, muted-off): server markup carries autoplay muted playsinline — autoplay=true muted=true playsinline=true
  [PASS] case B (negative control): NO autoplay attribute, video NOT muted — autoplay=false muted=false playsinline=true

--- tablet (768x1024), JavaScript DISABLED ---
  [PASS] case A (autoplay-on, muted-off): server markup carries autoplay muted playsinline — autoplay=true muted=true playsinline=true
  [PASS] case B (negative control): NO autoplay attribute, video NOT muted — autoplay=false muted=false playsinline=true

VERDICT: PASS — 4/4 assertions held
```

All three owed cases now hold: the broken case is fixed, the negative control
proves the fix did not over-apply, and both viewport widths produce identical
(desktop-tier) markup — confirming render.php's own comment that tablet/mobile
overrides are JS-time data-* behaviour only, and a no-JS visitor at any
viewport width gets the same correctly-coupled desktop markup, not a
half-applied tier-specific one.
