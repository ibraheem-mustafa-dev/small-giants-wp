## The assertion under test

Adding `.sgs-card-grid.sgs-has-hover-scale:hover { transform: none; }` stops the WHOLE GRID
scaling on hover, while leaving the per-card scale untouched.

## Why this is a fix and not a change

`render.php:636` puts `sgs-has-hover-scale` on the block ROOT from the block's **own** Scale
Hover control. `extensions.css:164` is an unqualified `.sgs-has-hover-scale:hover`, so it
matched that root. `style.css:237` separately scales `.sgs-card-grid__item`. Both fired.

⚠ **This was live with the universal hover panel switched OFF.** It is a shared class-namespace
collision, not a panel bug — which is why it survived unnoticed and why deleting the block's own
attribute would not have fixed it.

## Measurement — bug reproduced FIRST, then fixed

Isolated repro, both rules verbatim, measured in headless Chromium via `getComputedStyle`:

| | root, hovered in a GAP | item, hovered | root, while item hovered |
|---|---|---|---|
| **before** | `matrix(1.05, 0, 0, 1.05, 0, 0)` | `matrix(1.05, …)` | `matrix(1.05, …)` |
| **after** | `none` | `matrix(1.05, …)` | `none` |

Three things this shows:
1. **The bug reproduces** — hovering the grid's own padding, nowhere near a card, scaled the
   entire grid. That is the "feels a bit cheap" symptom a client would never file as a bug.
2. **It compounded** — hovering a card scaled the card *and* the grid underneath it.
3. **The fix is surgical** — gap-hover now does nothing; the card still scales exactly as before.

## Anti-vacuity

A "nothing happens now" result is the same shape a broken probe produces, so the `before` arm is
the control: it had to reproduce the failure before the `after` arm meant anything. It did, at
1.05, on all three measurements. The harness reads `getComputedStyle().transform` on the real
painted node rather than inferring from which rules exist.

⚠ The first version of a sibling harness this session was **vacuous** — it declared the rules in
an order where the bug could not occur, and read a clean result. Recorded so the same mistake is
not repeated: the ordering and the hover position (`{x:5,y:5}`, inside the root's own padding)
are both load-bearing here.

## Specificity, stated rather than assumed

The neutraliser is `(0,3,0)`; the generic rule is `(0,2,0)`. It wins deterministically, with no
`!important` and no dependence on which stylesheet loads first — which matters because the two
rules live in unrelated files consolidated at `render_block` priority 99.

## How `source_sha` was computed (shared-worktree trap)

`visual-report-sha.py` hashes the **default index**. A path-scoped commit
(`git commit -- <paths>`) instead builds a TEMPORARY index of `HEAD + the named
paths`, so on a shared worktree where another track has files staged under the same
block, the script and the gate compute DIFFERENT shas — and the gate is the one that
matters. That happened here: another track had `card-grid/render.php` and
`gallery/render.php` staged, so the script returned a sha the gate rejected as STALE.

This sha was computed the way the commit actually sees it, without disturbing the
other track's staging:

```bash
GIT_INDEX_FILE=/tmp/probe.idx git read-tree HEAD
GIT_INDEX_FILE=/tmp/probe.idx git add <only my paths>
GIT_INDEX_FILE=/tmp/probe.idx python scripts/visual-report-sha.py <block>
```
