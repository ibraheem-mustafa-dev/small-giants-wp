## ⛔ A real bug found and fixed during this capture

First live verification round found `opacity` computing as `1` despite the client
setting `0.5` in the editor. Root cause: `svg-presentation.css` also declares a bare
`opacity:` property on `.sgs-media-el` (its own `--sgs-media-svg-opacity` custom
property) — identical specificity (0,1,0) to the new `opacity.css` rule, and
`svg-presentation` sorts alphabetically AFTER `opacity` in the generator's cascade
order, so it always won outright and silently discarded the new atom's value on every
non-svg element. This is the exact same collision class `_base.css`'s existing
"Cross-atom rule: composed animation" section already documents for motion/
svg-presentation — just on a different property. Fixed the same way: both atoms now
write only to their own uniquely named custom property; the real `opacity` is composed
ONCE in `_base.css` by multiplying both values (`calc( var(--sgs-media-opacity,1) *
var(--sgs-media-svg-opacity,1) )` — opacity is naturally multiplicative, so this is the
physically correct combining rule, not an arbitrary tie-break). Re-verified live after
the fix: `getComputedStyle` read `0.5` correctly.
