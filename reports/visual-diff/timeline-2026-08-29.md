# sgs/timeline — phantom-token sweep + reached-milestone state

## What changed and what is asserted

Two changes in `1014fc9d8`:

1. `connectorColour`'s default moved from `border-subtle` (defined in NO palette) to
   `border`. **Assertion:** the milestone dot paints a real colour instead of
   `rgba(0,0,0,0)`.
2. A persistent `is-reached` class marks milestones the fill has passed.
   **Assertion:** dots at a fraction ≤ the current progress paint the fill colour;
   dots above it keep the resting colour.

This is an `intent_capture`, not a before/after diff, and deliberately so: the
before-state of assertion 1 is an **unpainted element**. There is no meaningful
"before" image of a colour that never rendered.

## Method

Live canary, Chrome (the NATIVE `animation-timeline: view()` driver — confirmed
`CSS.supports('animation-timeline','view()') === true`, so `view.js`'s rAF driver
feature-detects and returns early). `prefers-reduced-motion` confirmed `false`, so
the fill was not pinned to 1 by the reduced-motion rule.

⚠ **Viewport height had to be reduced to 420px to make the effect observable at
all.** See finding B.

## Result — both controls present in one uncontaminated sweep

Node fractions along the connector: `0.079, 0.299, 0.520, 0.740`.
Pure scrolling only; no animation object was touched (see "Instrument failures").

| measured progress | 0.079 | 0.299 | 0.520 | 0.740 |
|---|---|---|---|---|
| **0.337** | reached | reached | **NOT** | **NOT** |
| **0.696** | reached | reached | reached | **NOT** |
| **0.836** | reached | reached | reached | reached |

**Positive control:** dots below the head are marked.
**Negative control:** dots above the head are NOT — the check can fail.

Painted colour at progress 0.337, read from `::before` (the element that actually
paints), not the node box:

- reached dot → `rgb(245, 208, 80)` — the client's accent
- unreached dot → `rgb(232, 213, 192)` = **`#E8D5C0`**, exactly the `border` value
  in `sites/mamas-munches/theme-snapshot.json`

That second value IS the phantom-token fix, measured. Before the sweep this
computed to `rgba(0, 0, 0, 0)`.

**Painted geometry asserted, not just computed style:** every node measured
`16x16` with a non-zero bounding rect. A computed-style check cannot see a
zero-area element, which is how a 2px×2px SVG passed 69 gates during Stage A.

**Second, independent control on the same page:** section 2 of the probe page is a
timeline with the progress fill OFF. Its dots now render in pale `#E8D5C0` in the
screenshot. Before this commit they were invisible there too — so the fix is
visible in an instance that has nothing to do with the progress feature.

## Two findings that are NOT this commit's, both needing a decision

### A. `align-left` — the connector line misses every milestone by 107px

Measured on the live canary:

| | x centre |
|---|---|
| connector line | **17px** |
| every milestone dot | **124px** |

`style.scss` puts the connector at `left: var(--sgs-node-size)` (16px) for
`align-left`, but that variant's grid is `auto auto 1fr` with a ≥100px date column,
so the node column starts around 108px. The line therefore runs down the far left
of the block, connecting nothing.

This is **pre-existing Stage A**, not the token sweep — and it was known: the
comment at `view.js:254-263` cites "in the left-aligned variant the nodes sit
~100px to the side of the line" as the reason sparks anchor to nodes. It was
recorded as a fact to work around rather than raised as a defect.

### B. The fill is essentially complete before a desktop reader can see it

`animation-range: entry 0px exit` on a 405px-tall timeline in a 936px viewport
means the block has almost finished its transit as soon as it is on screen.
Measured: progress never dropped below **0.82** at ANY scroll position at
1440x900, and at 1440x760 **no mixed reached/unreached state exists at all** while
the block is visible. The reached-state animation is only perceptible on short
viewports or long timelines. Worth a decision on the range.

## Instrument failures during this capture — recorded, because all three were mine

1. **Read before the scroll settled.** The first sweep reported progress `1` at
   every position and `elTop: -1456` at `y=0` — stale layout. Frame waits fixed it
   and the fill animates correctly (60% → 100%).
2. **Pausing a scroll-linked animation to force a low progress produced readings
   the observer did not act on.** It made a working feature look broken — I twice
   concluded the observer was dead. The uncontaminated method is to shrink the
   viewport and scroll for real.
3. **Only the FIRST of three timelines on the page was being measured.**
   `querySelector` silently takes one; the page carries three variants.

None of these were caught by a gate. Two were caught by opening the screenshot.
