## The assertion under test

> Deleting `--sgs-modal-z-index` changes nothing on screen, because nothing ever read it and
> `z-index` does not apply to the element it was meant for.

## Why it was dead — two independent reasons, not one

**1. No reader existed.** `grep -rn 'sgs-modal-z-index'` over `plugins/` and `theme/` found the
name exactly **once**: `src/blocks/modal/style.css:9`, the declaration itself. Every other hit was
a build artefact re-emitting that same declaration. After removal, **0 source references remain.**
A custom property with a declaration and no `var()` consumer paints nothing.

**2. Even a consumer could not have worked.** `view.js` opens the modal with
`dialog.showModal()`, which promotes the element to the **top layer**. `z-index` has no effect
there at all — top-layer paint order is decided by the order elements were promoted, not by any
stylesheet. So the property was inert twice over, which is why removing it is safe rather than
merely untested.

This is the same root fact as the gallery half of D806, arrived at from the opposite direction:
the gallery needed the top layer and did not have it; the modal already had it and was carrying a
`z-index` that could never apply.

## Negative control — the probe CAN report the other state

With the dialog CLOSED, `elementFromPoint` at the same header-band coordinates returns `A` (a
header link) and the dialog computes `display: none`. The instrument therefore distinguishes
open from closed; the PASS is not an artefact of it always returning the dialog.

## Scope limit, stated rather than hidden

The dialog was opened by calling the same `showModal()` the shipped trigger handler calls, not by
clicking the trigger button. That exercises the rendering path this change could possibly have
affected — the only thing under test is whether a deleted custom property altered the paint. The
trigger wiring is untouched by this commit.
