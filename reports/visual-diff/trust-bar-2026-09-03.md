## What changed

`sgs/trust-bar` declared WordPress's native `__experimentalBorder` support. Like card-grid,
`migrate-border-shape-b.js --survey` refused it because `render.php` accumulates CSS into two
separately-named `*_css` variables (`tb_extra_scoped_css`, `typo_css`) and the script's
name-based disambiguation couldn't tell which one was the border sink. Fixed by the same
structural trace used for card-grid: the accumulator that receives the border
`wp_style_engine_get_styles()` call's output is `$tb_extra_scoped_css` — confirmed by reading
the file directly. Border width/style/colour/radius are now block-private attributes
(Shape B), matching `sgs/accordion`'s proven pattern.

**A second dead-code issue was found and fixed here too.** Once the native border reads were
stripped, `$tb_border_args`'s only consumer (`if ( ! empty( $tb_border_args ) ) {
$tb_style_engine_args['border'] = $tb_border_args; }`) became permanently unreachable —
`$tb_border_args` could no longer ever be non-empty, so `check-render-undefined-vars` correctly
flagged the guard as "always falsy". Removing that guard then made `$tb_style_engine_args`
itself vacuous too (its only write was the guard just removed), cascading to a second dead
guard around the `wp_style_engine_get_styles()` call. Both were pruned by proof (a variable
with zero remaining writes anywhere in the file makes `empty()` on it unconditionally true
forever, so the guard is unreachable regardless of what's inside it) — not a heuristic, and
not by deleting the variable declarations themselves (which the migration script's own
self-test explicitly requires to survive, matching the narrower scope of what this function is
meant to clean up).

## Also today: 37-media-no-handroll object-fit migration (separate track, second report section)

A different, unrelated change also landed on this block today: the badge image's `object-fit`
was migrated from a hand-rolled `render.php` declaration onto the shared media-atom system
(`badgeImageObjectFit` already matched the atom's own naming convention for the `badgeImage`

auto-generates a `badgeImageSize` attribute for the atom's `Size` base, which collides BY NAME
ONLY with this block's own pre-existing, unrelated `badgeImageSize` (a px dimension, not a
background-size keyword) — documented as an exception in `registry.js`, the same mechanism
already used for `sgs/container`/`sgs/hero`'s own naming collisions.

**Assertion:** the live canary serves the correct fallback CSS for the badge image, and the
badge no longer emits a competing literal `object-fit` declaration.

**Live result:** the compiled frontend stylesheet (`build/blocks/trust-bar/style-index.css`)
contains zero literal `object-fit` declarations (the old hardcoded `contain` fallback in
`style.css` was removed, replaced by an explicit `block.json` default that the atom now emits
as `--sgs-media-object-fit:contain` unconditionally, since `badgeImageObjectFit`'s default is
`contain`, not the shared `cover` fallback). The shared atom stylesheet
(`assets/css/media-atoms/object-fit.css`, compiled into the live `media-element.css` bundle,
`?ver=1788429270`) is confirmed live. No live `image-badge` variant instance was found on the
canary's current content to capture a rendered badge `<img>` directly — the icon-circle/
