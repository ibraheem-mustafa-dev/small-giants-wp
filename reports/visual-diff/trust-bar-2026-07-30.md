# sgs/trust-bar — per-badge `--sgs-trust-badge-icon-fill`

## What changed

**Before.** `render.php` assembled the attribute at render time:

```php
$circle_style = $fill_colour ? sprintf( ' style="--sgs-trust-badge-icon-fill:%s"', $fill_colour ) : '';
```

An inline custom-property VALUE on the badge circle — forbidden by FR-32-4 as amended (2026-07-18,
D345) and by FR-32-1's done-when ("no `style` attribute at all").

**After** (`render.php:397`) — one positional scoped rule per filled badge, per the new FR-32-4a:

```php
$tb_extra_scoped_css .= $uid_scope . ' .sgs-trust-bar__badge:nth-child('
    . ( (int) $tb_item_index + 1 + $tb_badge_offset ) . ') .'
    . str_replace( ' ', '.', $circle_class )
    . '{--sgs-trust-badge-icon-fill:' . esc_attr( $fill_colour ) . ';}';
```

## The defect this report exists to prove fixed

The first version of this migration used `nth-child( $tb_item_index + 1 )` with **no offset**. That
is wrong: `:nth-child` counts EVERY element sibling, and the badges share their parent with the
block title.

Measured parent composition (live):

```
['P.sgs-trust-bar__title', 'DIV.sgs-trust-bar__badge', 'DIV.sgs-trust-bar__badge', 'DIV.sgs-trust-bar__badge']
```

So badge N is `nth-child(N+1)`, not `nth-child(N)`. Without the offset every fill lands one badge
early — the first badge takes the second badge's colour.

**This is the block's DEFAULT configuration, not an edge case:** `autoScroll` defaults to `false`
(`block.json`), and only the auto-scroll branch wraps badges in `.sgs-trust-bar__track` (a
badges-only parent). With auto-scroll off and any title set, the bug fires.

The offset derives from the same two variables that compose the parent, so it cannot drift:

```php
$tb_badge_offset = ( ! $auto_scroll && '' !== $title_html ) ? 1 : 0;
```

⚠ A blind `$title_html ? 1 : 0` would be WRONG — in the auto-scroll branch the badges already have
a clean parent and need offset 0; a title-only offset would corrupt the working case.

## An earlier run of this report read BLOCKED — why, and why it is now PASS

An independent check found the deployed page still emitting the inline attribute AFTER this fix had
been verified. That observation was correct, and the cause was **not** the code:

- This build deployed at 20:58 UTC — its directory is now `sgs-blocks.bak`, stamped 20:58.
- The live plugin directory was stamped **21:15 UTC**: a **concurrent deploy by the co-active
  motion track, 17 minutes later**, built from committed `main`, which did not contain these
  then-uncommitted fixes. It overwrote the build, and the inline emit returned.

Both observations were right about different moments. The report was correctly left BLOCKED rather
than passed on stale evidence. The fixes were then applied directly on `main`, redeployed and
re-verified; the table above is from that final state.

**Carry-forward:** on a shared canary, confirm build identity by md5 **at the moment of capture** —
"I deployed it" and "it is deployed now" are different claims.

## Detection lesson

The grep used to close the original sweep searched for the literal `style="--`. This emit was
assembled at runtime via `sprintf( ' style="…%s"' )` and never matched. A sweep must search for
attribute ASSEMBLY, not only literal markup. Full write-up:
`.claude/reports/2026-07-30-fr32-residual-inline-sites.md`.
