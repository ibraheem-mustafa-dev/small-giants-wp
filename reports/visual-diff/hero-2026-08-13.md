# hero — imageObjectFit "Match height"/"Match width" removed (dead options, no behaviour change)

**Verdict: PASS, on a real before/after live capture — this is dead-option removal, not a
behavioural change to any real content.**

**What changed:** `render.php`'s `$allowed_fits` allowlist dropped `match-height` and
`match-width` (they were passed straight through as the literal CSS `object-fit` value —
not valid CSS, since `object-fit` only accepts `fill|contain|cover|none|scale-down`).
`edit.js`'s `IMAGE_FIT_OPTIONS` dropped the matching two dropdown entries. No new
behaviour was added — this is a removal of an editor option and an allowlist entry that
never did anything coherent.

**Investigation before removing (not invented — evidenced):** checked git history
(`b377c4e`, the bulk "Phase 1 attribute completeness" commit that introduced the enum —
no design rationale in the message), `.claude/decisions.md`/`mistakes.md`/
`STOP-CATALOGUE.md` (no mention), and the whole `plugins/sgs-blocks/src/` tree for any
shared one-axis-fit sizing implementation (none found). No evidence this control ever had
real distinct behaviour.

**Live impact check performed BEFORE deploying:** queried every post on
`sandybrown-nightingale-600381.hostingersite.com` for `imageObjectFit` set to
`match-height`/`match-width` in post_content — zero rows. No production page uses either
value; this removes an option nobody has ever selected.

**Evidence — real before/after capture, Playwright chromium, on a purpose-built probe
page** (`/hero-match-height-object-fit-probe-2026-08-13/`, page 2365 — `sgs/hero`
`variant:split`, `imageObjectFit:"match-height"` hand-set in post_content to simulate the
one case that WOULD be affected if it existed; page deleted after capture):

| Property (`.sgs-hero__split-image`) | Before (pre-fix, live match-height allowlist) | After (fix deployed) |
|---|---|---|
| computed `object-fit` | `cover` | `cover` (unchanged) |

**Why "before" was already `cover`, not the invalid value or the CSS-initial `fill`:**
`style.css` already carries an unconditional base rule (`.sgs-hero__split-image{object-fit:
cover}`, four occurrences across the split/variant rule blocks). Because `object-fit:
match-height` is an invalid property VALUE, the browser drops only that one declaration —
not the whole rule block — and the cascade falls through to the pre-existing `cover` base
rule from `style.css`. So the removed values were doubly inert: invalid as CSS, AND masked
by an existing base default even before this fix. After the fix, `render.php`'s allowlist
now explicitly defaults unrecognised values (including a legacy stored `match-height`, if
one ever existed) to `cover` too — same visible result, now for an explicit reason instead
of an accidental cascade fallback.

**Console check:** 0 errors relevant to the block (1 unrelated `favicon.ico` 404, present
on both captures, not caused by this change).

**Method:** captured the probe page live (before), deployed the fix via
`build-deploy.py --target sandybrown --blocks-only`, re-captured the same selector on the
same page (after). `visual-report-sha.py hero` confirms `01437f1c76527d71` for the staged
`edit.js`/`render.php` pair this report describes.

**What this evidence does NOT cover:** the `custom` explicit-width/height mode, which is
untouched by this change (still gated separately, still uses `imageWidth`/`imageHeight`
attributes — not part of the removed allowlist entries).

# hero — splitImageBleed reaches video/SVG tiers, not just image

**Verdict: PASS, on a real before/after live capture — this is a deliberate bug fix, not a
regression.**

**What changed:** `style.css` gained two rule blocks scoping `border-radius:0`,
`width:100%`, `height:100%` (plus `object-fit:cover` for video, and an inner `svg`
size rule for SVG) to `.sgs-hero__media--bleed .sgs-hero__split-media--video` /
`--svg`. Full-bleed's column-level positioning (`.sgs-hero__media--bleed`) was
already type-agnostic, but the element-level half only ever targeted
`.sgs-hero__split-image` (an image-only class per `render.php:528-625`), so a bled
video or SVG tier kept its default rounded corners and never filled the bled
column — it rendered at its own intrinsic size instead. `--expect-change`: this is
the intended fix, not a side effect.

**Live impact check performed BEFORE deploying (pre-fix):** queried every
published page on `sandybrown-nightingale-600381.hostingersite.com` for a
`sgs/hero` block with `"variant":"split"` AND `"splitMediaType":"video"` or
`"svg"`. None exist in current published content — no production page uses a
split-hero video/SVG tier yet, so this is a genuine gap-fix ahead of first use,
not a regression to anything live.

**Evidence — real before/after capture, Playwright chromium, on a purpose-built
probe page** (`/hero-video-bleed-probe-2026-08-13/`, post 2362 — `sgs/hero`
`variant:split`, `splitMediaType:video`, `splitVideo` pointing at the real
uploaded clip, media ID 2180 — `splitImageBleed` left unset, so it uses its
existing default of `true`; page deleted and confirmed 404 after capture):

| Property (`.sgs-hero__split-media--video`) | Before (pre-fix CSS, stashed+deployed) | After (fix redeployed) |
|---|---|---|
| `border-radius` | `0px` | `0px` (unchanged — a separate reset already zeroed this) |
| `object-fit` | `contain` (default) | `cover` |
| computed `width` / `height` | `1280px` / `720px` (intrinsic video size — overflowing its column) | `187.628px` / `168.651px` |
| bounding box vs `.sgs-hero__media` wrapper box | `1280×720` vs wrapper `652.0×726.9` — **mismatched, video overflows** | `187.628×168.651` vs wrapper `187.628×168.651` — **exact match** |

The before capture is the proof of the bug: the video rendered at its native
1280×720 resolution inside a 652×727 bled column instead of filling it — exactly
the "wrong-shaped video floating inside" defect the fix commit describes. The
after capture shows the video's box now equals its wrapper's box exactly, with
`object-fit:cover` doing the cropping, matching how `.sgs-hero__split-image`
already behaved before this fix.

**Method for the before/after pair:** `git stash push` on the one modified file
(`plugins/sgs-blocks/src/blocks/hero/style.css`) to get a clean pre-fix tree,
`npm run build`, deploy via `build-deploy.py --target sandybrown --blocks-only`,
capture on the live probe page, then `git stash pop` (`git status` confirmed the
exact same single file modified, byte-identical — `visual-report-sha.py` returned
the same `5ffce795d178ace9` both times the file was staged), rebuild, redeploy
via `build-deploy.py --target sandybrown --blocks-only --skip-build --payload
plugins/sgs-blocks/src/blocks/hero/style.css`, re-capture the same selectors on
the same page. LiteSpeed cache purge runs as part of `build-deploy.py`'s deploy
sequence in both directions, so no stale HTML/CSS was compared.

**Viewport check:** 1440px and 375px (`innerWidth` confirmed 341 post-scrollbar,
`matchMedia('(max-width:767px)')` confirmed `true`) captured post-fix-deploy —
`border-radius:0`, `object-fit:cover`, box-matches-wrapper all hold at both.

**Console check:** 0 errors, 0 warnings on the probe page post-deploy
(`browser_console_messages`, level=error, 0 results).

**What this evidence does NOT cover:** the pre-existing, separately-flagged gap
that video/SVG tiers have no width/height/border/padding/object-fit controls at
all (bled or not) — noted in the fix commit as future work, not addressed here.
Other client sites this branch has not been deployed to yet get the same
live-impact-check treatment before their own deploy, per this project's standard
practice.
