# hero — the split MEDIA element gets its own parallax + Ken-Burns pair

**Verdict: PASS**, on a live before/after computed-style measurement against the
sandybrown canary, covering all three staged behaviours: the two new opt-in
media-level effects, the `@keyframes` rename, and a compound-gate fix that stops
a phantom (invisible, CPU-wasting) animation from running.

⚠ This report replaces the same-day report describing the earlier D596 commits
(`0917bcf3`/`89857e39`/`0c270af7`) — those are still fully described in
`decisions.md` D596; this file's `source_sha` now describes ONLY the currently
staged bytes (block.json, edit.js, render.php, style.css), which is a distinct,

## What changed and why

1. **`sgs-hero__media` gains its own opt-in `--parallax` / `--ken-burns`
   modifiers**, driven by new attrs `mediaParallax`, `mediaKenBurns`,
   `mediaAnimationDuration` (defaults `false`/`false`/`20`). Bean spotted the gap
   unprompted at the end of the previous session (LEDGER "Open" item): the
   SECTION background already had parallax/Ken-Burns via the shared
   `BackgroundPanel`, but the split-media column had neither — the same
   asymmetry the overlay had before `89857e39` fixed it for overlays.
2. **The keyframes were renamed** to block/element-scoped identifiers
   (`sgs-ken-burns` → `sgs-hero-ken-burns` for the section; a new
   `sgs-hero-media-ken-burns` for the media column; `sgs-hero-media-parallax`
   for the media parallax) so the media effect's own timing/transform profile
   never collides with the section's.
3. **A compound gate on the section's own Ken-Burns rule**: the animation now
   requires BOTH `.sgs-hero--ken-burns` AND `.sgs-container--has-bg-image`.
   Previously it required only the first, so a split hero with `bgKenBurns:true`
   and no root `backgroundImage` had the animation RUNNING against
   `background-image:none` — invisible (nothing to animate) but not free: the
   browser was still computing the keyframe every frame. Measured directly,
   below.

## H1 — the phantom-animation fix, measured directly

`sgs/hero`, split variant, `bgKenBurns:true`, root `backgroundImage` unset.
Wrapper element (`.sgs-hero.sgs-container...`), `::before` pseudo-element:

| | animation-name | background-image |
|---|---|---|
| **before** | **`sgs-ken-burns`** (running) | `none` |
| **after** | **`none`** | `none` |

Before: the class `.sgs-hero--ken-burns` was present and its rule fired the
animation regardless of whether there was anything to animate — a real, measured
CPU/DOM behaviour change, not a guess. The background was `none` in both cases
(nothing painted, so no visual difference either way) — this is a dead-weight
fix, not a rendering fix, exactly as the module docstring for this class of
change describes.

## H2 — `mediaKenBurns:true` (positive control, split media)

| | mediaClasses | split-media animation-name | duration |
|---|---|---|---|
| **before** | `sgs-hero__media` | `none` | `0s` |
| **after** | `sgs-hero__media sgs-hero__media--ken-burns` | **`sgs-hero-media-ken-burns`** | **`20s`** |

Before: the attribute did not exist in `block.json`, so WordPress silently
discarded it (D338) — no class, no binding possible. After: the new class
attaches and its keyframe animation genuinely binds at the default 20s
duration. This is the positive control proving the new attribute is not inert.
