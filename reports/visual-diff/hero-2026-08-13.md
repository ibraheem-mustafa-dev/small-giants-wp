# hero — dead video/svg-animated variant removal + dead control cleanup

**Verdict: PASS, on live capture evidence gathered directly on the sandybrown canary during this
change (Playwright, logged-in admin session — not a synthetic/offline diff).**

**What changed:**
1. `variant` enum: removed `video`/`svg-animated` (block already had these superseded by the shared,
   container-mirrored `BackgroundPanel`, which exposes video/SVG backgrounds on every variant, D93).
2. Removed the matching `supports.sgs.variants.video`/`svg-animated` entries, the `svgContent` attr,
   the SVG/video editor panels + canvas preview markup, and the `.sgs-hero--video`/`.sgs-hero__svg-bg`
   CSS rules.
3. Removed the now-orphaned `hero-video`/`hero-animated` block-variation entries from
   `includes/variations/sgs-hero-variations.php` (they populated the block inserter's "Video
   Background Hero"/"Animated SVG Hero" quick-insert options, both of which silently inserted the now
   -invalid `variant: 'video'`/`'svg-animated'` value).
4. Removed the message-only "Buttons" `PanelBody` (dead — CTAs are child InnerBlocks now).
5. Removed `supports.color` (native colour panel — scoped to the wrapper, could never reach the
   heading/sub-headline child blocks) and `supports.spacing` (native Dimensions panel — a duplicate of
   the custom "Padding & margin" `ResponsiveBoxControl`, which is kept as the one interface, base +
   tablet + mobile).

**Evidence (live, this session, sandybrown canary):**

1. **Legacy content regression check** — a real draft page (#2143) already carrying
   `{"variant":"video"}` in stored `post_content` was opened in the editor post-deploy: no "invalid
   block" warning, editor Variant dropdown showed only Standard/Split (value silently unmatched, no
   crash). Viewed on the frontend: both hero instances on that page rendered with class
   `sgs-hero--standard` and identical bounding-box height (297.997px each) — WordPress's own
   attribute-schema validation coerces the out-of-enum stored value to the default at render time, so
   no visual regression exists for any pre-existing content. Screenshotted
   (`.playwright-mcp/qc-hero-legacy-video-page2143.png` in the working tree during the session).
2. **Block inserter** — before the `sgs-hero-variations.php` fix, `/SGS Hero` quick-insert listed
   "Video Background Hero"/"Animated SVG Hero"; after, only "Standard Hero"/"Split Hero (image +
   text)" remain, both insert correctly (`sgs-hero--standard`/`sgs-hero--split` classes confirmed).
3. **Background panel replacement mechanism** — confirmed the Styles-tab "Background" panel exposes
   Image/Video/SVG tabs with working desktop/tablet/mobile video pickers on the Standard variant (the
   capability the removed variants duplicated).
4. **Native panel removal** — post-fix inspector census: Settings tab = Hero Settings / Visibility
   conditions / Advanced only (no Buttons panel); Styles tab = Typography / Border / Container-Entire-
   Block / Image styling / Section (outer) / Content band / Padding & margin / Background / Shadow /
   Shape Dividers / Animation / Click Effects / Element parallax / Scroll & effects (no native Colour
   panel, no separate native Dimensions panel).
5. **Padding/margin round-trip** (the risk this change carried — removing `supports.spacing` could
   have caused WordPress to silently discard `style.spacing.padding`/`margin`, per the D338 failure
   class): set desktop padding = 77px via the sole remaining "Padding & margin" panel, saved, reloaded
   the editor (value persisted), viewed the live frontend — `getComputedStyle('.wp-block-sgs-hero')
   .padding === '77px'` on all four sides. Console: 0 errors on both surfaces.
6. **Confirmed-working controls left untouched, verified NOT to have regressed**: set `style.typography
   .fontSize`/`lineHeight` directly via `wp.data`, saved, confirmed on the live frontend the matched
   CSS rule (`.sgs-hero-{uid}.wp-block-sgs-hero .sgs-hero__headline{font-size:clamp(...,100px)}`) and
   the computed value (100px / 300px line-height) — these native typography controls are unaffected by
   this change and still function correctly.

**What this evidence does NOT cover:** other sites this branch has not been deployed to yet (only
sandybrown was touched this session) — those get the same live-verification treatment before their own
deploy per this project's standard practice.
