# hero — splitImageBleed default flip (false -> true)

**Verdict: PASS, on a real before/after live capture — this is a deliberate, expected rendering
change, not a regression.**

**What changed:** `block.json`'s `splitImageBleed` attribute default changed from `false` to `true`
(Bean-instructed: full-bleed should be the standard split-hero look, not opt-in). The editor
`ToggleControl` itself was already wired (shipped this morning in `6cd683d9`) — this change only
flips which state a NEW split hero starts in, and re-syncs `edit.js`'s two `resetAll`/`onDeselect`
defaults + the `hasValue` divergence check to match.

**--expect-change reason (hero):** deliberate — split heroes with `splitImageBleed` unset in stored
content now render with the media column bleeding flush to the container edge (no border-radius, no
inner padding, negative-margin breakout past the block's own padding) instead of inset. This is the
intended effect of the default flip, not a side effect.

**Live impact check performed BEFORE deploying:** queried every published page on
`sandybrown-nightingale-600381.hostingersite.com` for a `sgs/hero` block with `"variant":"split"`.
Two published pages matched — post 2334 ("T3 hero split probe") and post 2337 ("Hero bg baseline") —
both dev/QA fixture pages, neither is real client content. The live Mama's Munches homepage (front
page) has zero `wp-block-sgs-hero` elements at all (`document.querySelectorAll('.wp-block-sgs-hero')`
returns `[]`). No production content is affected by this default flip.

**Evidence — real before/after capture on post 2334 (`/t3-hero-split-probe/`), Playwright chromium:**

| Property | Before (pre-deploy, default=false) | After (post-deploy, default=true) |
|---|---|---|
| Root `<section>` classes | `sgs-hero sgs-hero--split …` (no `--split-bleed`) | `sgs-hero sgs-hero--split … sgs-hero--split-bleed` |
| `.sgs-hero__media` classes | `sgs-hero__media` | `sgs-hero__media sgs-hero__media--bleed` |
| `.sgs-hero__media` computed `margin-right` | `0px` | `-24px` |
| `.sgs-hero__media` computed `max-width` | (unset / normal) | `calc(50% + 24px)` |
| `.sgs-hero__split-image` classes | `… sgs-hero__split-image` (no `--bleed`) | `… sgs-hero__split-image sgs-hero__split-image--bleed` |
| `.sgs-hero__split-image` computed `aspect-ratio` | (ratio-constrained) | `auto` |

Both split-hero instances on the probe page moved identically, confirming the change is
attribute-driven (block.json default), not a one-off.

**Viewport check:** 1440px and 375px, both screenshotted post-deploy — the media column bleeds flush
to the container edge at both breakpoints; no overflow, no layout break, mobile stacking unaffected.

**Console check:** 0 errors, 0 warnings on the probe page post-deploy
(`browser_console_messages`, level=error, 0 results).

**Method:** Playwright (chromium), computed styles + screenshots, before deploy and after deploy,
same live page (`https://sandybrown-nightingale-600381.hostingersite.com/t3-hero-split-probe/`), same
selectors, cache purged (LiteSpeed `wp litespeed-purge all`) between captures so no stale HTML/CSS was
compared.

**What this evidence does NOT cover:** other sites this branch has not been deployed to yet (e.g. a
future `mamasmunches.com` production deploy) — those get the same live-impact-check treatment before
their own deploy per this project's standard practice.
