# hero — split media gains per-device TYPE (image / video / SVG), and the legacy `splitMedia` slot is deleted

**Verdict: PASS**, on a first-paint capture at two viewports plus a full editor
session against the live canary.

⚠ **This block's split media has been reworked and REVERTED TWICE** (`8598ac73`,
and D594 where the live editor was found broken — split squashed to quarter-width,
controls inert). Both prior attempts replaced the split media with a **child
block**. This one does not: it wires the already-declared typed attributes to the
shared `sgs_tier_media_render()` helper. The editor checks below exist
specifically because a passing front end did not catch either previous failure.

## What was wired

`splitMediaType` / `Tablet` / `Mobile`, `splitVideo*` and `splitSvg*` were
DECLARED in block.json and READ into PHP variables, then used by nothing — each
appeared exactly once (its own assignment), and `hero/edit.js` had zero controls
for any of them. The server could not render them and no client could set them.
All nine now resolve through `includes/helpers-tier-media.php`, and each has an
inspector control.

## Legacy REMOVED, not preserved (Bean, 2026-08-13)

Deleted outright — no deprecation, no fallback (D270: pre-production, nothing to
migrate; R-22-14 in this file's own header already said "NO legacy scalar
fallback"; R-31-14 bans exactly the `if ( empty($new) && !empty($legacy) )` shape):

- the `splitMedia` attribute, its `_comment_splitMedia`, and its editor picker
- the two synthesise/hydrate bridges keeping `splitMedia` and `splitImage` in sync
- the `splitMedia` → `splitVideo` alias bridge
- the alt-text fallback through `splitMedia`
- the type resolver's `'image'`-falls-through-to-inference branch, whose only
  justification was a legacy `splitMedia` video. `'image'` is now STRICT, exactly
  like `'video'` and `'svg'`. The `''` (inherit) inference stays — that is the
  canonical cascade, not legacy.

The client previously saw **two media pickers for one slot** ("Split media source"
and "Split image") writing different attributes and hand-synced. Now one.

**Verified before deleting, not assumed.** Across ALL post statuses the only rows
carrying `splitMedia`/`splitImage` were one leftover DRAFT from the reverted D594
session (2294, "D6 hero split-media QC") and this session's own probe, plus their
revisions — zero real content. 2294 was trashed on Bean's instruction; the
`oldshape-audit` gate then went from **1 NEW HIGH → 0** and the deploy proceeded.
⛔ That gate ABORTED the first deploy attempt, correctly: it is what stands between
removing an attribute and silently deleting stored content on next save (D338).

# hero — the section background now paints on the SPLIT variant (it previously painted nothing)

**Verdict: PASS**, on a pre/post computed-style measurement against the live
canary, with a three-part commit gate including a double-paint check.

## The defect

`sgs/hero` builds `$hero_helper_attrs` and NULLS a list of attributes before
handing them to `SGS_Container_Wrapper::render()`. That nulling is a **double-emit
guard**: the STANDARD variant paints its own private
`<img class="sgs-hero__bg-img">` (carrying `fetchpriority`/`loading`/`decoding` for
LCP), so the wrapper must not also paint a background for it.

The loop was **not gated on variant**. The SPLIT variant has no private `<img>`
(that is gated by `$has_standard_bg_image = ! $is_split && …`), so a split hero
had **no background painter at all** — the attributes were discarded before the
one component that could have used them ever saw them.

**Origin, from git blame, not guesswork:** the null-loop arrived in `bacbde57`
(2026-06-04, "WS-4 composite-wrapper mirror — hero's `<section>` becomes an
sgs/container"), when hero adopted the shared wrapper and the wrapper's background
was still section-kind gated. **D6 (2026-08-11) made wrapper backgrounds
universal** and nobody revisited hero's guard. It is a stale guard, not a decision
that split should have no background — searched `decisions.md` and `parking.md`:
no recorded decision exists either way.

## The fix

`render.php` ~1162: only `backgroundImage` / `backgroundImageTablet` /
`backgroundImageMobile` become conditional on `! $is_split`. `bgVideo`,
`bgVideoMobile`, `bgSvgContent` and `minHeight` keep being nulled for BOTH
variants, unchanged. 17 insertions, 5 deletions, one file.

## Measurement — same `backgroundImage` on both variants, canary page 2337

| | standard | split |
|---|---|---|
| **BEFORE** private `<img class="sgs-hero__bg-img">` | 1 | 0 |
| **BEFORE** `::before` `background-image` | none | none |
| **BEFORE** any background painted | true | **false** |
| **AFTER** private `<img>` | **1** (unchanged) | 0 |
| **AFTER** `::before` `background-image` | **none** (unchanged) | **`url("https://…")`** |
| **AFTER** any background painted | true | **true** |

The baseline carries its own positive control: standard painted a background
before the fix, so the measurement provably CAN detect one. Split's `false` was
therefore a real absence, not a dead probe.

## Commit gate — all three required, all passed

| # | Gate | Result |
|---|---|---|
| 1 | split `::before` contains `url(...)` | **PASS** |
| 2 | standard keeps exactly 1 private LCP `<img>` | **PASS** |
| 3 | standard `::before` still `none` (no double-paint) | **PASS** |

Gate 3 is the important one: it proves the standard variant did not gain a second
background painter. Without it, "split works now" would have hidden a regression
on every existing standard hero.

## Why the originally-proposed fix location was wrong

An earlier diagnosis targeted `render.php:352` and `:971` — the two other places
testing `! $is_split`. A `/qc-council` code-path rater falsified that: those two
gate only the STANDARD variant's private `<img>` and its overlay span, and have
nothing to do with whether the wrapper paints. **Had the change been made there,
split would have gained a second background painter layered over the wrapper's —
plausibly reproducing the "background bleeding through" symptom recorded in D594**,
and it would have looked correct on any page where no wrapper background was set.

# hero — a SECOND overlay, targeting the split MEDIA element

**Verdict: PASS**, on a live measurement covering both the positive and the
negative case.

One overlay per element, which is the owner's requirement: the section already had
`backgroundOverlayColour`; the media column had none. New attrs `mediaOverlayColour`,
`mediaOverlayGradient`, `mediaOverlayGradientAngle`, `mediaOverlayGradientFrom`,
`mediaOverlayGradientTo` (types mirroring the section-overlay family), one
`GradientOverlayControl` in the split-only Image panel, and a
`.sgs-hero__media-overlay` span emitted inside the media column.

⚠ `mediaBackground*` could NOT be reused: it paints a background-colour on the media
wrapper, which sits BEHIND an `object-fit:cover` image and is therefore invisible
whenever media is present. A real overlay is a separate element layered on top.

## Measurement — canary page 2337, 1440px

| | overlay element | overlay background | overlay z-index | media z-index | covers media |
|---|---|---|---|---|---|
| A — no overlay set | **absent** | – | – | 1 | – |
| B — `mediaOverlayColour` set | **present** | `rgb(230,138,149)` | 1 | 1 | **true** |

Row A is the negative case: with neither colour nor gradient set, NO element is
emitted at all — an empty decorative span never reaches the page.

## `z-index: 1` is load-bearing, not cosmetic — and the controller got this wrong first

`.sgs-hero--ken-burns .sgs-hero__media` is raised to `position:relative; z-index:1`
(`style.css:453-457`). Measured live, the media column reports `z-index: 1`. An
overlay left at the section overlay's `0` would therefore render **behind** the
media on those heroes.

⛔ The controller initially called the implementer's justification "fabricated",
having run `grep -n z-index style.css | head -8` — the ken-burns rule is the 10th
match, so the truncated search manufactured a false absence. The task reviewer
caught the error. The comment has been rewritten to cite the correct line and to
warn against "harmonising" the value back to 0.

## Review

Task reviewer (cross-model): spec compliance ✅; code quality approved with two
Minor comment-accuracy findings, both fixed (the misleading "mirrors
.sgs-hero__overlay's z-index" phrasing and the off-by-14 line reference).
