## Why this needed a real capture rather than an auto-skip

The gate refused the auto-skips, correctly: `check-editor-only.py` reported *"block.json is
staged and is not JavaScript — PHP, CSS and block.json all change what the visitor sees"*, and
the change is not `supports.sgs`-only either. So it was captured rather than argued.

## Why identical is the expected result, not a missed capture

- `render.php` and `style.css` are **untouched** — `git diff` over both is empty, so the
  frontend render path did not change at all.
- The two new attrs default to `{}`, and the wrapper's owned-spacing read only contributes a
  side when it is a non-empty string, so an unset hero emits nothing new.
- The migrated pattern authoring moved between two keys the shared wrapper **both** read
  (`style.spacing.padding` legacy → owned `padding`), with the same `{top,right,bottom,left}`
  shape and the same values. A key move, not a reshape.

## What actually changed, and where it is visible

The EDITOR, not the frontend. Hero declares no `supports.spacing`, so its Padding/Margin control
was writing the BASE tier to `style.spacing.*` — an attribute WordPress drops from the editor
schema, and therefore **discarded on save**. A client set base padding and it vanished; only the
tablet/mobile tiers survived. That surface is not capturable by a first-paint diff, which is
exactly why this report asserts frontend parity and names the editor as the changed surface
rather than claiming a visual improvement it cannot show.
