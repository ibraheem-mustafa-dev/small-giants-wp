## Fix 1 — dropdown + mega panels had no block-axis bound

`.sgs-nav-menu__submenu-wrap` and `.sgs-nav-menu__mega-panel-wrap` are emitted as uid-scoped CSS
in `plugins/sgs-blocks/src/blocks/nav-menu/render.php` (NOT in `style.css` — the original council
finding pointed at the wrong file; the defect was real, the location was not). Both were
`position:absolute; top:100%` with no `max-height` and no `overflow`.

Verified absent before: `grep -c "max-height"` returned 0 for both `render.php` and `style.css`,
with a positive control of 1 in `mega-panel/style.css` proving the search would have found it.

Consequence: a long panel rendered past the viewport bottom with nothing to scroll, on a surface
that closes on pointer-leave. The links were simply unreachable.

**After, measured live on the canary:**

| | Value |
|---|---|
| `max-height` | `741px` (was `none`) |
| `overflow-y` | `auto` (was `visible`) |
| `overscroll-behavior` | `contain` |

741px reconciles: `calc(100dvh - var(--sgs-header-height, 80px) - 16px)` against the live inner
height. The header term uses the theme's own published variable; `overscroll-behavior: contain`
stops a scroll reaching the panel's end from chaining to the page behind it, matching what the
drawer already does.

## Fix 2 — drawer labels could not wrap

The drawer reuses `.sgs-nav-menu__link`, which carries `white-space: nowrap`. That is correct for
the HORIZONTAL bar (which is `flex-wrap: wrap`, so a long label keeps its item intact and the ITEM
moves to a second row) and wrong for the drawer's VERTICAL stacked list, which has no second row
to move to — the label could only push sideways.

**Before, measured live at 375px** with one ordinary label ("Frequently Asked Questions About
Delivery And Returns"): drawer `scrollWidth` **460** against `clientWidth` **360** — 100px of menu
outside its own box, painted over the page behind it, reachable only via a horizontal scrollbar
the drawer should not have. In drill-down mode the bar is `overflow: hidden`, so the same label is
CLIPPED with no scrollbar at all.
Capture: `drawer-long-label-375.png`.

**After, same label, same viewport:**

| | Before | After |
|---|---|---|
| `white-space` | `nowrap` | `normal` |
| `overflow-wrap` | (unset) | `break-word` |
| Drawer horizontal overflow | **100px** | **0px** |
| Link height | 44px | 67px (wrapped to two lines) |

Capture: `drawer-long-label-AFTER-375.png` — label wraps to two lines inside the drawer, and the
horizontal scrollbar present in the before-shot is gone.

Specificity is deliberate: the override is `:where(.sgs-nav-menu__bar--drawer) .sgs-nav-menu__link`,
which keeps it at 0,1,0 — identical to the base rule, so it wins on source order alone and never
competes with the operator's `itemTextWrap` control, which `render.php` emits at 0,2,0.

## Fix 3 (nav-drawer track, later same day) — drawer sub-accordion laid out beside its parent

**Assertion:** the drawer's sub-accordion should render as a full-width row beneath its parent
menu item (Bean's report + a Spectra/Astra Pro reference screenshot), not constrained to the
leftover flex space beside the parent's label.

**Root cause:** `.sgs-nav-menu__accordion-row` is `display:flex` with the label and the whole
`<details class="sgs-nav-menu__accordion">` as its two flex children. `<summary>` + the submenu
`<ul>` both live INSIDE that `<details>` flex item, so opening it laid the submenu out inside the
item's own flex-allotted box rather than as a block below the row.

**First fix attempt — landed, then corrected same day.** `flex-wrap: wrap` on
`.sgs-nav-menu__accordion-row` + `flex-basis: 100%` on `.sgs-nav-menu__accordion[open]` fixed the
submenu's width correctly (verified live: accordion went from left:86px/width:253px to
left:21.6px/width:316.8px, matching the row) — but Bean caught what the live-width measurement
missed: `<summary>` (the caret toggle) is INSIDE that same `<details>` flex item, so it moved onto
the new full-width line too, extending the row by a whole line and re-centring the caret in the
middle of it, instead of leaving it in place next to the label flipping orientation. A measurement
of accordion/sublink WIDTH never captured the caret's own position — a real gap in the first
verification pass.

**Second CSS approach tried and REFUTED before shipping** (tested live via injected CSS, not
guessed): `display: contents` on `.accordion[open]`, to hoist `<summary>`/`<ul>` out as direct flex
items of the row (so `<summary>` could stay put while only `<ul>` got `flex-basis:100%`). Measured
live: Chrome gives `<details>` special internal box treatment and silently ignores
`display:contents` on it — the child never actually became a flex item of the row (explicit
`flex:0 0 100%` on the `<ul>` had no effect either; it stayed 143px wide instead of the row's
427px). Refuted before it reached source.

**Fix that measured correctly, shipped:** `.accordion-row` is a normal BLOCK (not flex) container,
`position:relative` as the caret's anchor. The link fills the row's full width
(`padding-inline-end:56px` reserved for the caret). `<details>` is a normal block too, so when open
its content (`<ul>`) flows as a full-width block right after the link. `<summary>` (the caret) is
`position:absolute; inset-inline-end:0; top:0` — removed from flow entirely, so it never
contributes to the row's height in either state and never moves.

**Live result — canary, drawer open, submenu expanded (viewport reported 485px wide by the
devtools tool this pass, not the earlier 375px session — relative box relationships are what's
being verified, not the absolute figures):**

| Measure | Value |
|---|---|
| Row / label width | 427px (both — label fills the row) |
| Caret position | left:412px, top:109px (flush with the label's own top, at the row's trailing edge) |
| Submenu (`ul`) | left:29px, top:153px, width:427px — full row width, flush below the label |
| Drawer `scrollWidth`/`clientWidth` | 485/485 — no overflow |
| Caret on close | returns to the same position, row height returns to single-line — confirmed via a second live screenshot |

Screenshots: `reports/visual-diff/nav-drawer-accordion-caret-fix-2026-09-10.png` (open — caret
stayed in place, flipped to point up, Ingredients/Our Promise full-width with a chevron marker
each) and a second closed-state capture confirming no leftover row height. Intent-capture (not

**Also added, same fix (Bean's reference-site feedback):** a small `chevron-right` marker in each
sub-item's indent (`sgs-nav-menu__sublink-marker`, `render.php`), matching the reference's
convention of a static right-pointing marker for leaf items versus the rotating chevron-down for
the expander. Drawer-scoped sublink padding changed from a fixed 32px left indent to
`12px padding + 14px icon + 8px gap` (≈34px, visually unchanged) so the marker sits inside the
existing indent rather than needing new horizontal space.

**Risk:** scoped to the plain (non-drill-enhanced) accordion path only. The JS-enhanced drill-down
slide-over (`[data-drill-enhanced]`) uses a separate `position:absolute` rule set, untouched. The
`padding-inline-end`/`inset-inline-end` logical properties are RTL-correct by construction (the
project's `nav-qa-logical-props` gate enforces this — both were caught and fixed by that gate
before this shipped).
