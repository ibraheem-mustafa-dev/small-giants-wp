# sgs/hero — live intent capture, 2026-09-05

Discharges the manual visual-gate skip taken during the render change. Captured
AFTER deploy against the live canary, probe page 3297
(`[PROBE 2026-09-05] hover-colour + bgSvg render check`).

**Method note.** This project LIFTS block CSS into
`wp-content/uploads/sgs-css/*.css` rather than emitting it inline, so grepping
page HTML proves nothing about the emitted rules. Every assertion below was
read from the LIFTED stylesheet the page links, not from the page source. An
earlier pass of this verification wrongly reported ABSENT for all values by
grepping the HTML; that was a method error, corrected here.

## Assertion

After removing `bgSvgContent` from `$sgs_hero_null_attrs`, hero must paint the
shared wrapper's decorative SVG layer — the same layer the seven other
wrapper-adopting blocks get (eight declare `bgSvgContent` in total, hero included). Before this change it painted nothing: the
wrapper's `$has_bg_svg` gate was permanently false, so seven declared
attributes offered in the Background panel had no effect anywhere.

## Result — PASS

Probe set `bgSvgContent` (an inline `<svg>`), `bgSvgOpacity:42`,
`bgSvgPosition:"foreground"`. Live page output:

```
<div class="sgs-container__svg-bg" aria-hidden="true">
```

with the wrapper carrying both `sgs-container--has-bg-svg` and
`sgs-container--svg-foreground` — confirming the layer renders AND that
`bgSvgPosition` is honoured (foreground, not the `background` default).

## Negative control

The same markers were checked on the site homepage first: `sgs-container__svg-bg`
appeared there, but NOT inside the `sgs-hero` element — it belonged to a
different wrapper block on the page. That ruled out a false positive from a
neighbouring block before the probe was built.
