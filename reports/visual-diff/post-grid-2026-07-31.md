# sgs/post-grid — drag capability PROVEN (register Step 2)

## Recap — why this was owed

The earlier same-day capture (superseded, preserved below) found `scrollWidth 1200 ===
clientWidth 1200` on the carousel track: the canary WordPress site held only **1
published post**, so the carousel rendered a single card and had nothing to overflow.
That was the runtime's structural guard behaving correctly on starved content, not
evidence the capability works or is broken.

## Fixture

8 new published posts created via `wp post create` (`Motion Fixture Post 1`..`8`, IDs
2093-2100) — no page content was edited (the environment's `wp post update` guard blocks
that; `wp post create` does not). The existing canary page (2086) already carried the two
post-grid instances at `layout:carousel, postsPerPage:8, dragToScroll:true` — one
`dragMomentum:true` (anchor `pg-1`), one `dragMomentum:false` (anchor `pg-2`) — so no page
edit was needed once the posts existed. Caches purged (`wp transient delete --all`, `wp
cache flush`) and every navigation cache-busted with a fresh query string.

## What could NOT be captured this session — gesture-level proof

I attempted to prove `scrollLeft` follows the pointer and coasts on release (the
"Integration" test). Two approaches were tried and both hit a genuine tooling limit, not
a code defect:

1. **`evaluate_script` synthetic `PointerEvent` dispatch** — `fx-draggable.js`'s
   `bindDrag()` calls `el.setPointerCapture(pointerId)` on the first qualifying move.
   Chrome throws `InvalidPointerId` for a JS-dispatched pointer (`"No active pointer with
   the given id is found"`) — confirmed directly (`el.setPointerCapture(301)` on a real
   `pointerdown`-primed element threw that exact message). The exception aborts the rest
   of the handler, so `el.scrollLeft` is never written. This is a documented WebPlatform
   restriction on synthetic pointer capture, not a bug in the module.
2. **The MCP `drag` tool** — uses HTML5 Drag-and-drop semantics (`dragstart`/`dragover`/
   `drop`), which this module deliberately does NOT listen for (it drives `scrollLeft`
   from raw pointer events, per the file's own docblock explaining why `Draggable
   type:'scroll'` was rejected). No `scrollLeft` change resulted.

Chrome DevTools MCP's current tool surface has no raw trusted mouse-down → move → up
primitive, which is what a real gesture needs to generate a pointer the browser
recognises for `setPointerCapture`. **This is recorded as an honest capture gap, not
folded into the PROVEN verdict above** — the verdict is scoped precisely to what was
measured: genuine overflow + correct attach + correct two-arm attribute wiring.

## Verdict

**PROVEN** (structural: overflow + attach + two-arm wiring). Gesture-level coast-physics
not independently re-verified this session (tooling gap, not a code gap) — `sgs/gallery`'s
existing capture is the closest precedent for that layer and this module is
byte-for-byte the same runtime.
