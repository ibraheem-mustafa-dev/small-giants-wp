# PART 1 (staged now) — D806, the lightbox reaches the top layer


## The assertion under test

> With the lightbox OPEN, the topmost painted element over the lightbox area is the lightbox —
> not the site header.

## The failure was reproduced FIRST, on the same page, before the fix

Bug-first, per the project's standing rule. Same page, same viewport, same probe point.

| | BEFORE (div + `z-index:100000`) | AFTER (`<dialog>` + `showModal()`) |
|---|---|---|
| `elementFromPoint(720, 72)` with lightbox open | **`a.sgs-nav-menu__link`** | **`dialog.sgs-gallery__lightbox`** |
| resolves to | **HEADER** | **LIGHTBOX** |
| lightbox rect | 0,0 → 1440×900 | 0,0 → 1440×900 |
| authored `z-index` | `100000` | `auto` (the number is gone, not lowered) |

The probe point is the centre of the sticky header's own bounding box, which lies inside the
lightbox's `inset:0` rect — so both elements genuinely overlap there and the winner is decided by
paint order, not by geometry.

## Why the old number could never have won — and why no bigger one would have

The lightbox is sealed inside an ancestor stacking context. Measured by walking the ancestor chain
and reporting every element that creates one:

- On page 2242: `div.sgs-container__inner` ×2, **and `div.entry-content.wp-block-post-content`**,
  each `position:relative; z-index:1`.
- On page 2158: `div.entry-content.wp-block-post-content` alone.

`.entry-content` is present on **every** page. A descendant's `z-index` is resolved *within* its
nearest stacking context, so `100000` only ever competed against the lightbox's siblings — while
the site header's `z-index:100` sits in the ROOT context and outranks the whole `.entry-content`
subtree. ⛔ This is why the briefed cause ("it sits inside a container child at z-index:1") was
only half right, and why a container-scoped fix would also have failed: `.entry-content` is not
ours to de-specify.

The top layer is the only escape, which is what `showModal()` provides.

## Negative control — the probe CAN report the failing state

With the dialog CLOSED on the fixed build, `elementFromPoint` at the same coordinates returns
`a` (the header link) and the dialog computes `display:none`. The instrument therefore
distinguishes the two states; a PASS is not an artefact of the probe always returning the dialog.

## Collateral checks on the same capture

| Check | Result |
|---|---|
| element is a real `HTMLDialogElement` | `true` |
| `role` / `aria-modal` authored | `null` / `null` — the UA supplies both for a modal dialog; authoring them is redundant |
| closed → `display` | `none` (UA `dialog:not([open])`; no `display:none` is authored, which would have hidden it when open too) |
| open → `display` | `flex`, filling 1440×900 |
| focus after `showModal()` | inside the dialog, on `.sgs-gallery__lightbox-close` — UA focus trap working, and the old manual `.focus()` call (which queried a class not yet applied) is deleted |
| `close()` clears `[open]` | `true` |
| console errors attributable to this change | **0** |

## One pre-existing error observed and NOT introduced here

The page logs `Failed to resolve module specifier "@sgs/gsap-draggable"`. That belongs to the
gallery's **carousel drag-scroll** effect (`render.php` emits `data-sgs-fx="draggable"` for
carousel layouts), not to the lightbox. This commit touches only the lightbox markup, the lightbox
CSS and the lightbox actions — no gsap module, no import map, no registration. It is the
"registers and does nothing" shape D452/D789 describe and is reported for a separate investigation
rather than folded in here.

## Scope limit, stated rather than hidden

No canary page currently renders gallery **tiles** (`.sgs-gallery__item` count is 0 on both 2158
and 2242), so the lightbox could not be opened by clicking. It was opened by calling the same
`showModal()` the shipped `openLightbox()` action calls, on the deployed build. That exercises the
real code path for the stacking claim under test; it does not exercise tile-click wiring, which is
unchanged by this commit.

## The assertion under test

Adding `.sgs-gallery.sgs-has-hover-scale:hover { transform: none; }` changes **nothing today**,
and prevents a future double-fire if the universal hover panel is ever switched on for this block.

## Why this is a NO-OP right now — the honest claim

Unlike `sgs/card-grid`, this is **not** a live defect, and the report does not claim it is.

`gallery/render.php` never emits `sgs-has-hover-scale` — verified by grep; the only hover class it
emits is `sgs-has-hover` (`render.php:342`). The added selector therefore **cannot match any
element this block renders today**, so it cannot change any pixel.

## Why add it at all

`style.css:283` is **unconditional**:

```css
.sgs-gallery__item:hover { transform: scale( var( --sgs-hover-scale, 1 ) ); }
```

It has no gate class — it simply falls back to `scale(1)` while the variable is unset. So the
moment the universal panel is enabled for `sgs/gallery`, the panel would both set
`--sgs-hover-scale` **and** put `sgs-has-hover-scale` on the root. The generic
`extensions.css:164` rule would then scale the whole tile grid, while the inherited variable
would simultaneously feed this per-tile rule. That is exactly the card-grid failure, arriving
silently as a side effect of an unrelated opt-in decision.

Neutralising now means that decision cannot reintroduce it.

## Evidence

1. **Reachability** — `grep 'sgs-has-hover-scale' gallery/render.php` → no match. The rule is
   inert; a live capture would measure the absence of a class, which proves nothing about the
   rule and is exactly the "no-evidence result" trap.
2. **The mechanism is proven on its sibling** — the identical neutraliser was measured in
   headless Chromium on `sgs/card-grid`, where the class IS emitted: gap-hover went
   `matrix(1.05,…)` → `none` with the per-item scale preserved. Full measurement table in
   `reports/visual-diff/card-grid-2026-08-26.md`.

Specificity here is `(0,2,0)` against the generic `(0,1,0)` — one class fewer than the card-grid
case because `.sgs-gallery` carries no extra qualifier, but the same deterministic margin.

## What would falsify this later

If `gallery/render.php` ever starts emitting `sgs-has-hover-scale` (i.e. the panel is enabled
here), this rule stops being a no-op and becomes load-bearing. At that point it needs the same
live measurement card-grid got — gap-hover `none`, tile-hover still scaling. Recorded so the
next person does not inherit a PASS that was only ever true of the inert case.

## How `source_sha` was computed (shared-worktree trap)

`visual-report-sha.py` hashes the **default index**. A path-scoped commit
(`git commit -- <paths>`) instead builds a TEMPORARY index of `HEAD + the named
paths`, so on a shared worktree where another track has files staged under the same
block, the script and the gate compute DIFFERENT shas — and the gate is the one that
matters. That happened here: another track had `card-grid/render.php` and
`gallery/render.php` staged, so the script returned a sha the gate rejected as STALE.

This sha was computed the way the commit actually sees it, without disturbing the
other track's staging:

```bash
GIT_INDEX_FILE=/tmp/probe.idx git read-tree HEAD
GIT_INDEX_FILE=/tmp/probe.idx git add <only my paths>
GIT_INDEX_FILE=/tmp/probe.idx python scripts/visual-report-sha.py <block>
```
