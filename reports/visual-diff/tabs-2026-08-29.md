# sgs/tabs — border colour default no longer resolves to nothing

## What changed

`block.json:200` default moved from `border-subtle` to `border`. The same commit
also swept three `var( --wp--preset--color--border-subtle )` declarations in
`includes/variations/sgs-tabs-variations.php` (lines 40, 45, 64) — the tab-strip
border, the panel border, and the panel's top rule.

## Why this is an intent capture and not a before/after diff

`border-subtle` is defined in no palette, so every one of those four declarations
was dropped by the browser. The before-state is a **missing border**. Diffing an
absent border against a present one tells you less than measuring whether the
token resolves, which is the actual mechanism.

## Assertion

> The slug this block and its variations now use resolves to a real colour on the
> live canary; the slug they used to use does not.

## Measurement — live canary, in-page, with a negative control

| token | computed `background-color` | |
|---|---|---|
| `--wp--preset--color--border` | `rgb(232, 213, 192)` | ✅ resolves — the NEW value |
| `--wp--preset--color--border-subtle` | **`rgba(0, 0, 0, 0)`** | ❌ does not resolve — the OLD value |
| `--wp--preset--color--border-light` | `rgb(229, 231, 235)` | resolves (discriminating control) |
| `--wp--preset--color--accent` | `rgb(245, 208, 80)` | resolves (sanity control) |

**Negative control:** the old token returns fully transparent, so this probe can
report failure.
**Discriminating control:** `border-light` also resolves, so the probe is
distinguishing real palette entries from phantom ones rather than returning
"resolves" for any input.

## Corroboration from a rendered element

`sgs/timeline`'s milestone dot, on the same page load and through the identical
`sgs_colour_value()` path, computed `rgb(232, 213, 192)`. Screenshot in
`timeline-2026-08-29.md`.

## Honest scope limit

⚠ **No `sgs/tabs` instance was located on the canary, so no tabs block was
photographed.** What is proven is the mechanism the block depends on, measured on
the live site, plus the same mechanism rendering correctly on a sibling block in
the same page load. What is NOT proven is a tabs-specific layout regression — the
change is a value-only swap inside existing declarations (no selector, no
property, no markup changed), so the risk of one is low, but it is not zero and it
is not claimed.
