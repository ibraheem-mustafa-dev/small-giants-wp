Covers the colour-conformance codemod's addition of `triggerBackgroundGradient` and
`modalBackgroundGradient` as gradient siblings to `triggerBackground`/`modalBackground`. Deploy
method identical to card-grid's 2026-09-03 section — see that file for the full "Deploy notes".

## Assertions — stated before measuring

1. `triggerBackgroundGradient` set to a test gradient paints `background-image` on
   `.sgs-modal__trigger`, at its own scoped selector, independent of `modalBackgroundGradient`.
2. `modalBackgroundGradient` set to a DIFFERENT test gradient paints `background-image` on
   `.sgs-modal__dialog`, independently.
3. **Negative control:** default instance (neither gradient set) paints plain
   `background-color`/none at both selectors.
4. **Edge case (added after the first pass surfaced a code-read concern):** `triggerBackgroundGradient`
   set ALONE, with `triggerBackground` left completely unset (its schema default — `block.json`
   declares no default, so it resolves to `''`), still paints the gradient.

## Live results — measured on the canary (lifted stylesheet)

```
positive (uid sgs-modal-1020791a, both triggerBackground:"primary" AND triggerBackgroundGradient set):
  .sgs-modal-1020791a .sgs-modal__trigger{background-image:linear-gradient(90deg,#ff00aa 0%,#00ffaa 100%)}
  .sgs-modal-1020791a .sgs-modal__dialog{background-image:linear-gradient(90deg,#00ffaa 0%,#ff00aa 100%)}

negative (uid sgs-modal-ebb0fad2, neither set): no background-image rule for this uid at all
  (trigger/dialog fall through to style.css's plain `.sgs-modal__trigger--primary` default).

edge case (uid sgs-modal-b1a0a434, triggerBackgroundGradient SET, triggerBackground UNSET):
  .sgs-modal-b1a0a434 .sgs-modal__dialog{background-color:white}   <- modal's own default, unaffected
  NO .sgs-modal-b1a0a434 .sgs-modal__trigger rule anywhere in the lifted stylesheet at all.
```

| Assertion | Result |
|---|---|
| 1 — trigger gradient paints at its own selector | ✅ PASS (when `triggerBackground` is also set — see assertion 4) |
| 2 — dialog gradient paints at its own selector, independent direction | ✅ PASS |
| 3 — negative control clean | ✅ PASS |
| 4 — gradient-only (no flat `triggerBackground`) still paints | ❌ FAIL — confirmed by explicitly adding a THIRD live instance with `triggerBackground` completely absent from the block markup: zero CSS emitted for `.sgs-modal-b1a0a434 .sgs-modal__trigger` at all, not even a fallback. Root cause read in `render.php:43`: `if ( $trigger_background ) { $trigger_rules[] = sgs_background_paint_decl( $trigger_background, $trigger_background_gradient ); }` — the gate checks ONLY the flat colour, never the gradient, so when `triggerBackground` is unset (its `block.json` entry has no `default` key, unlike `modalBackground`'s `"white"` default) the whole rule is skipped regardless of the gradient. `modalBackgroundGradient` does NOT have this defect only because `modalBackground` happens to default to `"white"` (truthy), which is incidental, not a designed protection — the same gate pattern (`if ( $modal_background )` at `render.php:49`) would have the identical bug if that default were ever removed. |

## What this means practically

`modalBackgroundGradient` works reliably for any real-world use (the dialog panel always has a
resting background). `triggerBackgroundGradient` only works when the operator ALSO sets a flat
`triggerBackground` colour alongside it — setting the gradient alone (a legitimate, expected use
case — "I want a gradient trigger button, I don't care what the flat fallback is") silently does
nothing. Same root-cause SHAPE as card-grid's collision bug and pricing-table's misrouting below
— all three are render.php CSS-emission defects introduced or exposed by this wave's codemod,
none of them fixable from this dispatch (render.php off-limits per brief).
