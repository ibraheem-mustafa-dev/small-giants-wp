## What changed

Added one new rule to `style.css`:

```css
:where(.sgs-multi-button) .sgs-button {
	border-width: var(--sgs-mb-btn-border-width-default);
	border-style: var(--sgs-mb-btn-border-style-default);
}
```

Consumes two new group-default custom properties from `sgs/multi-button` (see that
block's own report). Deliberately NOT added to the `.sgs-button` base rule directly —
that rule has carried no border-width/style declaration since the 2026-08-27 fix that
stopped a hardcoded `2px solid` painting through every preset-less button.

## A real bug caught and fixed before this ever reached deploy

The first version of this rule was `.sgs-multi-button .sgs-button { ... }` (no
`:where()`), specificity (0,2,0) — HIGHER than every preset selector
(`.sgs-button--primary`/`--secondary`/`--outline`, each (0,1,0)). Static specificity
analysis before any live check showed this would silently override a preset's own
border-width/style with the unset group-default var's initial value the moment a
multi-button shipped with no group default configured — i.e. on every existing
multi-button on the framework, immediately. `:where(.sgs-multi-button)` costs zero
specificity, so the shipped rule ties with presets at (0,1,0) and, being declared
BEFORE the preset rules in the same file, always loses that tie to them.

## Live result — canary, computed styles

Post-deploy (commit `51be3c847`), both live multi-button instances on the canary
(homepage page 2742: primary + secondary; `tc-multibutton-margin-probe` page 1473:
primary) compute `border-width: 2px; border-style: solid` unchanged — presets are
unaffected. A disposable probe with a preset-less child and the new group default set
computed `border-width: 3px; border-style: dashed` as configured. Full detail and
screenshots: `reports/visual-diff/multi-button-2026-08-30.md`.
