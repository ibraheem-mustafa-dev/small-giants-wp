# sgs/gallery — migration to the Spec 37 FR-37-16 object model

⚠ **Unlike the sibling `container-2026-08-10.md` report, this change IS frontend-affecting.**
It is not editor-only and is not claimed as such. Below is what changes on the painted
page, why it is safe, and the one stored instance that had to be migrated for it to be
safe.

## Why

`sgs/gallery` was the LAST mount of `ResponsiveSpacingPanel`, which was defective two ways:

1. **16 inert controls.** It rendered tablet/mobile padding + margin controls writing
   `paddingTopTablet` / `marginLeftMobile` / etc. **No `block.json` anywhere declares those
   attributes**, and WordPress silently DISCARDS an undeclared attribute — so a client
   could set tablet padding on a gallery, save, and watch it vanish with no error, no
   warning and no failing gate. Verified three ways before deletion: no declaration in any
   `block.json`, no consumption in any `render.php` or the shared wrapper, and exactly one
   live mount.
2. **Two hollow desktop tiers.** Both its Padding and Margin `ResponsiveControl`s returned
   a `<p>` reading "set in the Dimensions panel above" instead of a control, because
   desktop spacing came from WP-native `supports.spacing` while the tiers came from SGS
   attrs. `inspector-scan` rule 26 flagged both.

Deleting the panel therefore required giving gallery a real replacement — Bean's call was
the full FR-37-16 object model, matching `site-header-row` / `site-footer-row` / `nav-menu`.

## What changed

| File | Change |
|---|---|
| `block.json` | `supports.spacing` REMOVED. `maxWidth` + `contentWidth` string → `object`. `padding` + `margin` added as `object`. Element-manifest `attrMap` repointed: `css:padding`/`css:margin` from `native:spacing.*` to the new `padding`/`margin` attrs |
| `edit.js` | `WidthPanel` + `ResponsiveSpacingPanel` mounts replaced by one `ResponsiveBoxControls` |
| `render.php` | `'responsive_model' => 'object'` added to the `SGS_Container_Wrapper::render()` opts |
| `ContainerWrapperControls.js` | `ResponsiveSpacingPanel` DELETED (last mount gone), replaced by a tombstone comment |

## Why flipping `responsive_model` is safe for gallery's OTHER responsive attrs

Verified in `class-sgs-container-wrapper.php`, not assumed. The flag only diverts a value
that is **actually array-shaped**: `$object_grid = $object_model && is_array( gridTemplateColumns )`,
and every scalar read is guarded `is_array($x) ? default : $x`. Gallery's `gap` is the
string `"16"` and its `gridTemplateColumns*` family are strings, so all of them stay on the
legacy scalar path, byte-identical. The wrapper's own comment states the contract: flipping
the flag "never breaks an un-migrated instance's columns".

## Frontend deltas, disclosed

1. **`container-type: inline-size` is newly applied** to gallery's outer element — the
   object model establishes a query container so the inner band can adapt to the block's
   own width when nested narrow (FR-37-16). Gallery is a block-level element at full width
   in every observed instance, so inline-size containment is expected to be a no-op; it is
   nonetheless a real CSS addition and is called out rather than buried.
2. **Padding/margin now emit through `sgs_emit_responsive_css()`** on `.{uid}` with
   `@media`, instead of through the wrapper's native `style.spacing` read.
3. **Everything else is unchanged** — gap, grid, columns, colours, borders, band background.

## The one stored instance, and why it had to be migrated

⚠ **This is the part that could have silently broken a live page.** WordPress coerces a
type-mismatched attribute value back to its default. A stored `contentWidth: "1200px"`
read against an object-typed attribute becomes `{}` — **the cap vanishes, with no error and
no failing gate.** `audit-post-content-blocks.py` does NOT catch this class: it checks
attribute NAMES and stranded content, never value TYPES.

Measured on the canary (the only live site), 194 pages+posts scanned:

| | Count |
|---|---|
| `sgs/gallery` instances | 5 |
| with `maxWidth` | 0 |
| with `contentWidth` | **1 — page 1591, `"1200px"`** |
| with `style.spacing` | **1 — page 1591, padding 48/24/24/48** |
| POSITIVE CONTROL: `wp:sgs/*` openings parsed | **1706** |

The positive control matters: a zero from a broken query is indistinguishable from a
genuinely clean tree. 1706 openings parsed proves the census could see content, so the
zeros above are real measurements.

Migration: `plugins/sgs-blocks/scripts/migrate-gallery-object-model.js` — **dry-run by
default**, `--live` required to write, idempotent (an already-object value is left alone),
and it refuses to write if any byte outside the gallery block comments differs. It uses
brace-balanced JSON extraction rather than a non-greedy regex, because a non-greedy regex
truncates at the first `}` and would mangle nested `style.spacing.padding`.

Dry-run output:
```
page 1591 — 1 gallery instance(s) to migrate
  contentWidth: "1200px" -> {"desktop":"1200px"}
  padding: undefined -> {"desktop":{"bottom":"48px","left":"24px","right":"24px","top":"48px"}}
  style.spacing: removed (gallery no longer declares supports.spacing)
```

**Graceful window, verified not assumed:** the wrapper's base-spacing read at
`class-sgs-container-wrapper.php:1056-1076` is NOT gated by `$object_model` — it reads
`style.spacing` unconditionally. So an un-migrated instance keeps rendering its old padding
after deploy rather than losing it instantly. That makes deploy-then-migrate safe, and it
is why the migration removes `style.spacing` when it writes the object form — otherwise
both paths would emit to the same `.{uid}` selector and be resolved only by source order.

## Evidence

- `inspector-scan` rule 26: **5 → 3**. Both padding/margin `hollow-tier` findings resolved
  by deleting `ResponsiveSpacingPanel`. The remaining 3 (`backgroundImage`, `bgVideo`,
  `sgsHeight`) are unrelated and separately tracked.
- `check-dead-controls`: **zero** gallery findings — the four new object attrs are consumed
  by the shared wrapper, so none is a dead control.
- Line endings preserved: all three gallery files are 100% CRLF (353/353, 743/743, 661/661),
  so the diffs are real changes and not a whole-file rewrite.
- `block.json` parses.
