## What changed and why

D540 reserves `contentWidth` for a block that renders a genuine inner band. `sgs/info-box` renders
none — it dropped `SGS_Container_Wrapper` under D294 and emits `width:` from `contentWidth` onto the
**same root selector** its `maxWidth` emits `max-width:` to (`render.php:299-304`). Two widths on one
element, the second under a name promising a second layer that does not exist. That is verbatim the
shape D540 deleted from five other blocks.

It was **renamed, not deleted** (Bean, 2026-08-10). D540's own text says a block that genuinely
wants a fixed width says `width` — and this one demonstrably does: two published canary pages set it
to 900px and 480px. Deleting would have changed real pages; renaming makes the name tell the truth
and changes nothing a visitor sees.

## Stored content was migrated BEFORE deploy, and the migration was scoped

WP silently discards an attribute a block.json does not declare (D338), so the next editor save
would have deleted the stored value outright. 6 rows migrated (2 published pages + 4 revisions).

The rewrite was scoped to `wp:sgs/info-box` block comments only — a blanket replace would have hit
`sgs/container` and `sgs/site-footer`, which legitimately keep the name because they DO render an
inner band. Proven after the run:

- `info-box` + `contentWidth`: **0** remaining
- `container` + `contentWidth`: **140** — unchanged
- 122 other rows containing an info-box but no `contentWidth`: untouched

The migration script also asserted per row that the count of removed occurrences equalled the count
of info-box instances, and skipped any row where it did not — so an over-reaching regex would have
refused to write rather than silently corrupted content.
