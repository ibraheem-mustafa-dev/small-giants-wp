# sgs/hero — de-duplicating the two split-image height families

**Verdict: PASS**, on a measured before/after capture of a real published hero, plus a
positive control proving the surviving control still works. Details below.

## What changed

Two attribute families were writing `height` to the SAME element
(`.sgs-hero__split-image`), each with its own inspector control:

| Family | Unit | Gate | Side-effect | Mobile attr |
|---|---|---|---|---|
| `splitImageHeight` / `…Tablet` / `splitImageMobileHeight` | hardcoded `px` | none | forces `object-fit:cover` | **breaks the suffix convention** |
| `imageHeight` / `…Tablet` / `…Mobile` | `imageHeightUnit` | `custom` object-fit only | none | conventional |

The `splitImageHeight` family is REMOVED. `imageHeight` survives, is converted to the Spec 35
tier-object model (`{desktop,tablet,mobile}` in one attr), and its emission is **ungated** so
it keeps the removed family's unconditional reach. Width stays gated — it never had an
ungated equivalent. The editor's two controls collapse to one, using `ResponsiveOverride`.

## Why — and why it was invisible until today

The two families genuinely contended for one routing slot. The DB gate states the cost
exactly: the live resolver *"silently picks the first by rowid order"*, and the column-first
resolver *"raises AmbiguousLayerAttrError at clone time"*. So cloning a hero produced an
arbitrary winner or an error.

Nothing had computed that collision before. The css-property classifier that populates the
routing columns had to be run **by hand** and evidently had not been for a long time; wiring
it into `/sgs-update` (commit `e86dbd04`) surfaced the collision immediately.

`splitImageHeight`/`splitImageHeightTablet` were themselves added **earlier the same day** by
the Phase 1.4c tier promotion (report preserved at
`hero-2026-08-10-phase-1.4c-tier-promotion.md`). That change was correct on its own terms and
explicitly additive; it could not have seen that `imageHeight` already covered the same
property on the same element, because the routing data was stale. This is largely a same-day
revert of that addition.

## Capture — measured, not argued

Page: `/art-direction-tiers-canary-hero-media/` (post 2161), a published page carrying real
`sgs/hero` instances. Captured at **1440 / 900 / 390 px** before and after deploying the
change to the sandybrown canary.

**39 measurements across 3 viewports — every one identical.** Measured per viewport: hero
`height` / `minHeight` / `gridTemplateColumns`, and for every `.sgs-hero__split-image` its
computed `height`, bounding-box height and `objectFit`, plus a count of emitted stylesheet
rules touching split-image height.

| Viewport | hero height | split-image height (bound instance) | height rules |
|---|---|---|---|
| desktop 1440 | 405px → 405px | 405px → 405px | 1 → 1 |
| tablet 900 | 391.984px → 391.984px | 391.984px → 391.984px | 1 → 1 |
| mobile 390 | 836.109px → 836.109px | 693.328px → 693.328px | 1 → 1 |

Console errors: **0 → 0.** PHP diagnostics in the served HTML (`Fatal error`, `Warning:`,
`Notice:`, `Deprecated:`, `Array to string conversion`): **none → none.**

## ⛔ The positive control — because identical numbers alone would be vacuous

Identical measurements are exactly what a **completely inert** control would also produce. No
published hero sets either attribute, so "nothing moved" could have meant "nothing can move".

Control: a temporary clone of post 2161 with the OBJECT-shaped
`"imageHeight":{"desktop":222}` + `imageHeightUnit:px` injected into its hero.

Result: `.sgs-hero__split-image` computed height = **222px** on all three matched elements,
bounding box 222. **The new object attr demonstrably applies.** The probe page was purged
with `wp post delete --force` after measurement.

(The `height:222` rule does not appear in any inline `<style>` — SGS block CSS is lifted into
`uploads/sgs-css/`. The computed value is the evidence.)

## Stored-content safety — and a correction to an earlier claim

⚠ **An earlier draft of this work asserted "zero hero instances, zero stored values". That
was measured against the wrong site** — a `ls ~/domains/*/public_html | head -1` resolved to
`feldeluxe.com`, which has no SGS blocks at all. The server hosts **11 WordPress sites**, not
one. Re-measured per site:

| Site | hero blocks | `splitImage*Height` rows | flat `imageHeight` rows |
|---|---|---|---|
| sandybrown (canary) | 175 | 3 | 11 |
| palestine-lives.org | 165 | 0 | 0 |
| the other 9 | 0 | 0 | 0 |

Every one of those 14 rows is a **revision or trash**, never a published post:
`splitImageMobileHeight` in 3 revisions (IDs 51, 223, 752); `imageHeight` in 10 revisions plus
one trashed post (ID 65). **Zero published posts hold either attribute**, which is why all 175
live heroes measured byte-identical — they leave both unset, so nothing is emitted either way.

The pre-deploy `oldshape-audit` independently agreed: *"PASS: stored content is compatible with
the schemas being deployed."*

**Residual risk, stated rather than hidden:** restoring one of those 13 revisions after this
change would silently drop the value, because WordPress discards an attribute the block.json
no longer declares, and `wp_restore_post_revision` copies `post_content` verbatim. This is the
`inert-unless-restored` finding from the same session. No automated path resurrects them.

⚠ Also worth recording: `palestine-lives.org` is **live with 165 hero blocks**, while
`CLAUDE.md` states it is gone and sandybrown is "the ONLY site". That doc claim is wrong and
should be corrected — this change does not deploy there, but a future one might assume it away.
