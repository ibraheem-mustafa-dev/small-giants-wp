## CHECK 2 — motion-path skew

Page: `/motion-canary-wave-c/` (post 2083). Scrolled ~2 viewport-heights past
the element's top before sampling (its ScrollTrigger range spans several
viewport-heights per the house probe's own prior measurement), so this is a
genuine mid-animation sample, not the untouched initial state.

Measured:
```
href: .../motion-canary-wave-c/?cb=...  (re-asserted, no hijack)
preserveAspectRatio: null
svgRect: { x: 120, y: -5668.6, width: 1200, height: 7933.7 }
transform: matrix(0.501335, 0.865253, -0.865253, 0.501335, 527.58, 578.119)
```

- **`preserveAspectRatio` is now `null` (removed) — CONFIRMED, matches the
  expected fix.**
- Transform decomposition: for a pure rotation with no skew, `a=d` and
  `c=-b`. Here `a=d=0.501335` and `c=-0.865253=-(b)` — **exact match, zero
  skew component.** Scale is uniform on both axes: `√(a²+b²) = √(c²+d²) = 1.0`.
  This is a clean rotation matrix.

**Caveat (measurement honesty):** the pre-fix example matrix given in the
brief, `matrix(0.0937, -0.9956, 0.9956, 0.0937, -528.5, 2418.6)`, *also*
satisfies `a=d` and `c=-b` when decomposed the same way — i.e. a single
matrix snapshot's algebra can't by itself distinguish "skewed" from
"not skewed" at a different sample point, because the two matrices weren't
sampled at the same scroll position/animation phase. The mechanism (per the
task's framing) is that `preserveAspectRatio` was non-uniformly distorting
the SVG's own coordinate space, which fed MotionPathPlugin's tangent/rotation
calculation a distorted frame of reference even though the resulting CSS
`transform` matrix could still individually decompose as "clean." **The
direct, load-bearing evidence for this fix is the attribute removal
(`preserveAspectRatio: null`)**, not the matrix numbers alone — the matrix is
supporting evidence (consistent scale/no-skew at this sample) but not
independently conclusive against a different pre/post pair.

**The oversized route box (~1200×7934) and its large translate are KNOWN-OPEN
per the brief — not re-litigated here, not counted as a failure of the skew
fix.**

**Verdict: PASS on the skew-specific fix** (`preserveAspectRatio` removed;
sampled transform shows no skew component).

### `/motion-canary-wave-c/` sweep (30 steps, scroll settled + polled each step)

`pinAttr` (`canvas.getAttribute('data-sgs-fx-pin')`) = **`null`** — pin is OFF
on this instance. `render.php` only emits `data-sgs-fx-pin="true"` when the
block's `fxPin` attribute is set, so this confirms the *toggle exists as a
documented mechanism in source* (verified by reading `render.php` — emits
`data-sgs-fx-pin="true"` conditionally) but **this specific canary instance
does not have it enabled, and no instance with pin=true was found on either
tested page, so the pin-ON rendering path was NOT observed live.** Flagging
as **OPEN** — recommend a canary instance with `fxPin` toggled on if that
specific behaviour needs live proof.

Sweep results (canvas content-signature — a checksum over sampled RGB bytes,
used instead of luma because these are real photographic frames, not a
synthetic brightness ramp; a changed signature = a different frame painted):

| fraction of visibility window | scrollY | signature changed? |
|---|---|---|
| −2.40 → −0.08 (13 samples, before window) | 4664–5186 | constant (`86563105`) — poster/first frame held, correct |
| 0.11 | 5230 | → `96986423` (new) |
| 0.31 | 5273 | → `111153004` |
| 0.50 | 5317 | → `122355780` |
| 0.69 | 5360 | → `129861197` (reached final value) |
| 0.89 → 3.40 (remaining 17 samples, through and past window end) | 5404–5969 | constant at `129861197` — frozen at last frame, correct once scrub is done |

The frame content progressed gradually across four distinct values
(0.11 → 0.31 → 0.50 → 0.69 of the window), not bunched at the very start —
**this is NOT the documented mirror defect** (which would show everything
happening in the first ~10-20% of the window). `distinctSigsInWindow: 4`,
`firstReachFinalFractionInWindow: 0.69`.

**One measurement caveat, resolved analytically:** my computed
"fully-visible window" end used `exitFull = elTop` (no header-offset
subtraction), because I don't have access to the page's live
`chromeOffsetPx()` value from outside the bundle. The real code subtracts a
sticky-header offset from `exitFull`, which would make the *real* window end
earlier than mine. Back-solving: if the real end were where my sweep shows
the plateau starting (scrollY 5360, i.e. my fraction 0.69 of my
over-estimated window), that implies a header offset of roughly
`5429 − 5360 ≈ 69px` — a plausible sticky-header height. In other words, the
apparent "reaches final value at 69% of my window" is very likely actually
"reaches final value at ~100% of the REAL window," once corrected for the
header I couldn't measure from this harness. **Treating this as PASS with
that caveat stated**, not as a defect — the shape (gradual progression, no
early-plateau) is the important signal either way.

Mid-scrub screenshot: `assets/check3-waveC-midscrub.png` — shows a partial
"pac-man" wedge (the canary's synthetic frame-index fixture), i.e. a genuine
intermediate frame, not frame-0 or the final frame — direct visual
confirmation the scrub is live mid-sweep.

**Verdict: PASS (no mirror defect observed) on `/motion-canary-wave-c/`, with
the header-offset caveat above. Pin-ON rendering: OPEN, not observed live on
either tested page. `/motion-roster-canary/`: UNTESTABLE, block absent.**

## CHECK 4 — scramble presets

Page: `/fx-preset-comparison/` (post 2103). `pageHeight: 1861`, `vh: 900`,
**`maxScroll: 961`** — confirms the brief's own description that this page is
short and the three demo blocks sit close together near the bottom
(measured docTop spacing: 1302.9 / 1379.7 / 1456.5 — **76.8px apart each**,
matching "~77px apart").

| Heading (top→bottom = Subtle/Standard/Dramatic per page labels) | `data-sgs-fx-start` (as-rendered) | Matches CURRENT preset JSON? | Scroll Y where text first differed |
|---|---|---|---|
| index 0 (Subtle) | `top 85%` | Yes (`subtle.fxStart = "top 85%"`) | 544.6 |
| index 1 (Standard) | `top 70%` | Yes (`standard.fxStart = "top 70%"`) | 752.8 |
| index 2 (Dramatic) | **`top bottom`** | **No — current JSON says `"top center"`** | 560.6 |

**All three headings DID fire** and all three settled back to their exact
original text (`settledMatchesOriginal: [true, true, true]`) — no stuck
scrambled state.

**The Dramatic heading on this live page is carrying a STALE stored value**
(`top bottom`, the pre-rework value) rather than the current preset JSON's
`top center`. That's why it fired at scrollY 560.6 — very close to Subtle,
and *before* Standard — `top bottom` means "fires as soon as any part of the
element enters the viewport," which is much earlier than `top 70%`/`top 85%`.
This is expected re-application-required staleness, exactly as the brief
predicted ("presets bake their values into a block when applied in the
editor... an EXISTING block may still carry the OLD stored value") — **not a
bug in the new preset**, but it does mean **the live page did not exercise
the new Dramatic value at all.**

**Analytical check of the specific risk flagged in the brief** (does the NEW
`top center` value fall beyond this page's max scroll?): `top center` fires
when the element's top crosses the viewport's vertical centre, i.e. at
`scrollY = docTop − vh/2 = 1456.5 − 450 = 1006.5`. This page's `maxScroll` is
**961** — **1006.5 > 961, so the new Dramatic trigger point IS unreachable on
this page as currently laid out, by about 45px.** This confirms the
coordinator's predicted risk is real, even though it couldn't be observed
directly (the live block hasn't been re-applied to the new value). **If the
Dramatic block on this page is re-saved with the current preset, it will
never fire, and the fix will look broken when the preset itself is fine.**
Recommend adding roughly 100px of vertical spacing below the scramble
section on this canary page (cheap, page-only change, not a preset-value
change) before re-testing with a freshly re-applied Dramatic block.

Screenshot: `assets/check4-fx-preset-comparison-top.png` (top of page — the
scramble demo section is further down, not visible in this shot; the
per-effect label rows visible in the shot confirm this is the right page and
row order).

**Verdict: PASS on Subtle/Standard triggering + all firing + all settling
correctly. Dramatic: OPEN — untested against its real new value (stale stored
attribute); analytically CONFIRMED the predicted "trigger point beyond max
scroll" risk, so the canary page needs the spacing fix before Dramatic can be
verified live.**
