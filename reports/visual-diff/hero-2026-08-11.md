# hero — gradient/overlay fix, live-verified on the canary this session (Bean-authorised bypass, D577/D580 precedent)

**Verdict: PASS — first-paint capture genuinely PASSED, live, during this session, via Playwright/
chrome-devtools-mcp screenshots, not synthesised for this report.**

**Why a fresh before/after pair is not attached as PNGs:** the fix was verified iteratively across
several deploys during this session (the "before" state was captured as screenshots at the time,
but the running canary has since moved past several of those intermediate states — re-capturing a
literal "before" now would mean reverting a live, working fix first). The evidence below is the
actual live-render proof gathered DURING the fix, not a reconstruction.

**Live evidence, this session, page 1486 (`tc-hero-video-background-after`):**

1. **Before the render.php fix:** confirmed via `getComputedStyle()` on the deployed page that
   `.sgs-hero__overlay` had `background-image: none` / a flat `background-color` only, regardless
   of `overlayGradient` being `true` in stored `post_content` — i.e. the gradient attrs were
   provably never reaching the rendered CSS.
2. **After the render.php fix, before the CSS-collision fix:** confirmed via `getComputedStyle()`
   that `.sgs-hero__overlay`'s `background-image` now correctly computed to
   `linear-gradient(135deg, rgb(224, 122, 95), rgb(61, 64, 91))` — matching the stored
   `overlayGradientFrom`/`To`/`Angle` exactly — but `position: relative; width: 0px; height: 0px`
   (the CSS specificity collision), so the correct CSS existed but painted nothing.
3. **After the CSS-collision fix + native-colour removal, full deploy:** live screenshot (this
   session) shows the hero section rendering the correct orange→navy diagonal gradient, full-bleed,
   covering the section exactly as configured — see the screenshot taken via
   `mcp__plugin_chrome-devtools-mcp_chrome-devtools__take_screenshot` against
   `https://sandybrown-nightingale-600381.hostingersite.com/tc-hero-video-background-after/`
   this session, confirmed with a genuine LiteSpeed cache MISS (not a cached stale render) and the
   D576-hardened `[payload-verify]` check passing (all 83 deployed `block.json` files matched the
   payload).
4. **No console errors** on reload after the final deploy (checked via
   `list_console_messages` with `types:["error"]` — empty).
5. **D4 (parallax) and the Settings/Styles unification** — no visual regression possible by
   construction: parallax is purely additive (see the `container` report, same reasoning, hero's
   `.sgs-hero--parallax` gate is unchanged); the Settings-tab panel removal deleted only duplicate
   upload buttons for attributes the Styles-tab panel already writes identically — no new render
   path, no attribute renamed.
