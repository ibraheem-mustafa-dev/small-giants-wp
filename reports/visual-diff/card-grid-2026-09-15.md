## What changed

D1061 follow-up (sc_var_responsive_correlator.py -> a real block attribute). Added a
new, editor-controllable, responsive `cardPadding` attribute (tier-object
`{desktop,tablet,mobile}`, each `{top,right,bottom,left}` — mirrors `sgs/hero`'s
`mediaPadding`) to `sgs/card-grid`. Previously the per-card body padding was a
hardcoded `style.css` default (`padding: var(--wp--preset--spacing--30)`) with no
attribute and no control at all — confirmed by reading the block's own code before
building anything (`render.php` had zero padding-reading logic; grepped `style.css`
directly). `block.json` (new attr + `boxFamilies`/`elements.body` entries),
`render.php` (new scoped-CSS emission, base + tablet + mobile), `edit.js` (new
`ResponsiveBoxControl`).

## Why intent capture, not before/after

There is no meaningful "before" state for a brand-new, opt-in attribute — no existing
instance anywhere sets `cardPadding` (it didn't exist before today), so a before/after
diff of an existing page would show nothing to compare. The real question is: (1) does
an UNSET instance still render byte-identically to the old hardcoded default, and (2) does
a SET instance actually produce the correct, correctly-tiered CSS. Both are single live
assertions against the canary, not a diff against a prior state.

## Assertions (stated before measuring)

1. An existing live `sgs/card-grid` instance with `cardPadding` unset must emit **no**
   `.sgs-card-grid__body{padding:...}` rule at all in its lifted CSS — the pre-existing
   static `style.css` default must be the only source of that property, unchanged.
2. A `sgs/card-grid` instance with `cardPadding` set to distinct desktop/tablet/mobile
   values must emit exactly those values, at the project's standard device-tier
   breakpoints (`max-width:1023px` tablet, `max-width:767px` mobile).
