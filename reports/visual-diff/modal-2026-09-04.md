## What changed

Phase 3 of the golden-colour staged rollout (finishing commit `778879732`'s text-colour
gradient work). Wires a `triggerColourGradient` sibling onto `sgs/modal`'s `triggerColour`
attribute (the trigger button's text colour) so the row stops being flagged by inspector
rule 31 (`missing-gradient`).

- `block.json` — added `triggerColourGradient` (string, default `""`); added
  `"css:color-gradient": "triggerColourGradient"` to the `trigger` element's `attrMap`
  (alongside the pre-existing `"css:background-image": "triggerBackgroundGradient"` entry —
  the two gradient siblings use different css: keys because they paint different properties
  on the same element).
- `render.php` — reads `triggerColourGradient`, resolves via
  `sgs_resolve_text_colour_or_gradient()`, emits via `sgs_text_colour_decl()` onto the
  existing `.{uid} .sgs-modal__trigger` scoped rule, and unconditionally calls
  `sgs_text_colour_gradient_fallback_rule()` on that same selector. The pre-existing D942
  background-cancel logic (`background-color:transparent` when no explicit
  `triggerBackground`/`triggerBackgroundGradient` is set) is preserved untouched — its own
  comment already anticipated and reserved this slot for the gradient sibling.
- `edit.js` — destructured `triggerColourGradient`; the `triggerText` row in
  `SgsColourPanel` gained `gradientCapable: true` + `gradientValue`/`onGradientChange`;
  the canvas preview (`triggerButtonStyle`) now spreads
  `resolveTextColourPreviewStyle(triggerColour, triggerColourGradient, resolveColourToken)`
  instead of a bare `color:` line, so a gradient shows in the editor exactly as it will on
  the frontend.

## Why intent capture, not before/after

This is an additive `block.json` attribute with default `""`. No existing content has ever
been able to set `triggerColourGradient` (it didn't exist before this change), so a
before/after diff on any real page shows no difference by construction — the flat-colour
path is provably unchanged (same helper call chain, same selector, same D942 cancel logic).
The real question is "does the new gradient sibling actually paint", which needs one
instance with a gradient set, not a before-state.

## Known edge case (flagged, not fixed here)

`.sgs-modal__trigger` can ALSO receive `background-color`/`background-image` from the
separate `triggerBackground`/`triggerBackgroundGradient` attributes on the SAME selector
(a different rule block, same selector, combined via CSS cascade at render time). When an
operator sets BOTH `triggerColourGradient` AND an explicit `triggerBackground`,
`background-clip:text` (a whole-element background clip, not just the image) will clip the
button's own background fill to the glyph shapes. The task brief pre-verified this
attribute against `textSharesElementWithBackground()` (the rule-31 exemption check, which
reads only `block.json`'s *explicit* `attrMap` entries) and that check reports no conflict,
because `triggerColour`/`triggerBackground` resolve via the *implicit* prefix convention
and never appear as explicit `attrMap` values on the `trigger` element — a real blind spot
in that automated check, not evidence the interaction is safe. The interaction only
manifests when an operator deliberately sets both a text gradient AND a background on the
trigger button; flagging for awareness rather than blocking, since the D942 background-cancel
already handles the far more common "no background set" case correctly.
