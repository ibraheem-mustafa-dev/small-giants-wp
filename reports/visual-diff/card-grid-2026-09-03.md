  border-color:var(--wp--preset--color--primary);color:#ff00aa;color:#00ffaa

| Assertion | Result |
|---|---|
| 1 — title/subtitle hover colours paint independently | ❌ FAIL — both attrs write a `color:` declaration to the SAME selector, `.sgs-card-grid__item:hover` (not `.sgs-card-grid__title:hover`/`.sgs-card-grid__subtitle:hover`). CSS keeps only the LAST declaration when two properties collide on one rule — `subtitleColourHover`'s value (`#00ffaa`) silently wins for the whole card item, and `titleColourHover`'s value (`#ff00aa`) is dead the moment both are set. Root cause read directly in `render.php:278-290`: both `$attributes['titleColourHover']`/`$attributes['subtitleColourHover']` push a `color:` string into the SAME `$card_grid_hover_decls` array, which is then emitted as ONE rule scoped to `.sgs-card-grid__item` (the card wrapper), not to the title/subtitle elements individually. |
| 2 — negative control clean | ✅ PASS — no `color:` declaration present when neither attr is set; the existing `border-color` hover rule is unaffected. |

## What this means practically

If a client sets ONLY `titleColourHover` (the common case — most cards don't also set
`subtitleColourHover`), it DOES work, because `$card_grid_hover_decls` then holds exactly one
`color:` declaration. The bug only manifests when BOTH are set on the same card-grid instance —
but that is exactly the scenario this codemod was built to support (two independent Hover
siblings), and it fails silently: no error, no console warning, just the wrong element painting
the wrong colour. This is a fix at the render.php CSS-emission layer (route each attr to its own
selector — `.sgs-card-grid__title:hover` / `.sgs-card-grid__subtitle:hover` — rather than
collapsing both into one `.sgs-card-grid__item:hover` rule), not something this verification
dispatch was authorised to change (source files off-limits per brief).

## What changed

`sgs/card-grid` declared WordPress's native `__experimentalBorder` support (radius, width,
colour, style). `migrate-border-shape-b.js --survey` had refused to migrate it because
`render.php` accumulates CSS into three separately-named `*_css` variables
(`card_grid_native_css`, `sgs_grid_typo_css`, `card_grid_stagger_css`) and the script's
name-based disambiguation couldn't tell which one was the border sink. The script was widened
to trace which accumulator structurally receives the output of the border-specific
`wp_style_engine_get_styles()` call — `$card_grid_native_css`, confirmed by reading the file
directly before touching anything. Border width/style/colour/radius are now block-private
attributes (`borderWidth`, `borderStyle`, `borderColour`, `borderColourGradient`,
`borderRadius`/`Tablet`/`Mobile`) with their own `render.php` emission (Shape B), matching
`sgs/accordion`'s proven pattern.
