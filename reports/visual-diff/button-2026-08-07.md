## What was broken

Bean reported that `sgs/button`'s "Transform to variation" control (Primary /
Secondary / Outline) did nothing. The variations were never the fault: measured
live, each click DOES dispatch and `inheritStyle` cycles correctly. The presets
were invisible, by two independent editor-side writers.

1. `src/blocks/button/edit.js:259-261` — the preview built
   `blockClasses = ['sgs-button']` and never appended
   `sgs-button--{inheritStyle}`, which `render.php:614-617` DOES emit on the
   frontend. That modifier is the entire preset mechanism: it SETS the six
   `--sgs-btn-*` custom properties from the client's
   `--wp--custom--button-presets--*` tokens, which base `.sgs-button` consumes.
2. `src/blocks/button/editor.css:15` — `border: 2px solid transparent` under
   `.editor-styles-wrapper .sgs-button`, specificity (0,2,0) vs style.css's
   (0,1,0), pinning border colour to transparent in the editor. Secondary and
   Outline are both border-led, so fixing only (1) would have left them still
   looking identical to Primary.

## Negative control (old build, real "Transform to variation" UI)

Class string identical across all three selections:
`block-editor-block-list__block wp-block is-selected sgs-button wp-block-sgs-button`
— no modifier in any state. Computed background `rgba(0, 0, 0, 0)` and colour
`rgb(58, 46, 38)` unchanged throughout. `inheritStyle` did change each time
(primary → secondary → outline), proving the probe could detect a difference and
that the data layer was healthy.

## After (new build served into the real editor, no hand patching)

Driven through the actual "Transform to variation" menu; styles read with
`getComputedStyle` on the rendered canvas element.

| Preset | inheritStyle | emitted class | background | border colour |
|---|---|---|---|---|
| Primary | `primary` | `sgs-button--primary` | `rgb(230, 138, 149)` | `rgb(230, 138, 149)` |
| Secondary | `secondary` | `sgs-button--secondary` | `rgba(0, 0, 0, 0)` | `rgb(230, 138, 149)` |
| Outline | `outline` | `sgs-button--outline` | `rgba(0, 0, 0, 0)` | `rgb(232, 213, 192)` |

Text colour is `rgb(58, 46, 38)` for all three. That is not a defect: this
client's snapshot deliberately sets dark text on pink (the axe-passing pairing
already recorded in `theme/sgs-theme/assets/css/woocommerce.css`). The presets
differ on background and border, which is what these three presets are.

Confirmed the intercepted editor stylesheet was the one in force — the canvas
rule read `.editor-styles-wrapper .sgs-button { align-items: center;
border-radius: 10px; box-sizing: border-box; cursor: default; display:
inline-flex; font-size: 15px; font-weight: 600; justify-content: center;
min-height: 48px; padding: 14px 24px; text-decoration: none; }` with no `border`
declaration.

## Anti-vacuity

The probe was proven able to detect the difference before the fix existed: the
negative control above shows the same script reading identical class strings and
identical computed colours across all three presets on the old build. A check
that could not distinguish the states would have reported the same "PASS" on the
broken build, so the negative control is what makes this verdict meaningful.
The block was also confirmed to render real text (`label: "Preset Proof"`) —
an absent or empty block scores a false pass on any computed-style sweep.

## Scope / what is NOT claimed

- Frontend is untouched by this change. `render.php` and `style.css` were not
  edited; the frontend already emitted the modifier correctly.
- Not deployed. The canary still serves the previous bundle. Every "after"
  number above comes from the locally built artefacts executed in the real
  editor via interception — that is a real capture of the real build, but it is
  not a post-deploy capture.
- `editor.css` still overrides `padding`, `border-radius`, `font-weight` and
  `font-size` at (0,2,0). Those are not part of this bug (no preset sets them as
  `--sgs-btn-*` vars) but they are the same latent trap and are flagged, not
  fixed here.
