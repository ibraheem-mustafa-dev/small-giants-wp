## The defect this block actually had, and why no earlier check saw it

**The "carousel" was not a horizontal scroller at all.** `grid-auto-flow` defaulted to `row`,
so with more images than `--sgs-columns` the items wrapped onto extra ROWS: measured
`scrollWidth 1200 === clientWidth 1200` with 8 items at 3 columns. Everything downstream was
silently inert — `goToItem()`'s `scrollIntoView({ inline: 'start' })`, the prev/next arrows,
the dots, and the whole FR-38-13 Draggable upgrade, because `fx-draggable.js` asks the
structural question "is this a genuine native horizontal scroller?" and was correctly
answering **no**.

Fix: `grid-auto-flow: column` + `grid-auto-columns` matching the explicit column width.
Post-fix measurement on the same track: **`scrollWidth 3227` vs `clientWidth 1200`**.

Two further causes were each proven, not inferred, before being fixed:

1. **`scroll-snap-type: x mandatory` reverted every programmatic write.** `el.scrollLeft = 200`
   read back as `0`; with snapping switched off it read back as `200`. The module now suspends
   snapping for the gesture and restores it when the coast ends.
2. **The browser's native image drag stole the gesture.** Event trace read
   `pointerdown → pointermove (scrollLeft 0→30) → dragstart`, then nothing. `dragstart` is now
   suppressed while a drag of ours is in progress.

## Named observable signal — measured

| Arm | before | during drag | at release | settled | coast |
|---|---|---|---|---|---|
| momentum ON, no-preference | 0 | **360** | 360 | **1862** | **+1502** |
| momentum OFF, no-preference | 0 | **360** | 405 | 405 | **0** |
| momentum ON, reduce | 0 | **360** | 405 | 405 | **0** |

`cursor` computes to `grab` on both instances.

**Negative controls, all discriminating.** Momentum-OFF is instance 2 of the SAME page under
the SAME build, so "coasts 1502px" vs "stops dead" is a within-page control, not a cross-run
comparison. The reduce arm independently reproduces the momentum-OFF result while drag itself
still moves 360px — which is exactly Spec 38 §10's SIMPLIFY contract for this effect (drag is
user-driven input and must survive reduced motion; only the physics is dropped).

## Registry correctness

`fx_effects.draggable.plugin_set` corrected `["Draggable","Inertia"]` → `["Inertia"]`. The
module no longer uses the `Draggable` class (its `type: 'scroll'` mode re-parents a scroller's
children into a wrapper div — `gsap/Draggable.js:536` — which destroyed this very track,
collapsing 8 slides to one 389px column). Net page cost for a page using this effect falls by
about 12.7 KB gzip.

## What this report does NOT claim

- No human eye has judged the FEEL of the momentum curve (R-31-13 is co-authoritative and not
  yet given). The numbers say it coasts; they do not say it coasts *nicely*.
- Touch devices are unmeasured. The module gates itself behind `(pointer: fine)` and never
  binds on touch, so the native scroll path is untouched by construction — but "by
  construction" is a reading of the code, not a device measurement.
