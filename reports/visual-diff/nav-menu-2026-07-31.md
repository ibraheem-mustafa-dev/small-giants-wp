## The colour decision (defect 3) — BEAN-RULED

Submenu rows default to the palette's **LINK token**, so they follow the theme
and every style variation exactly as the rest of the site's links do.

Measured ratios on this client, recorded for the record, NOT as a gate:

| Foreground | On panel | Ratio |
|---|---|---:|
| `primary` `#e68a95` (rest) | `#fff9f0` | 2.25 |
| `primary-dark` `#c56a7a` (hover/focus) | `#fff9f0` | 3.32 |
| `text` `#3a2e26` (rejected alternative) | `#fff9f0` | 11.86 |

**Bean ruled the WCAG AA floor not applicable to this pairing** (2026-07-31):
pink on cream is easily discernible, legible, and an intended aesthetic pairing.
That is the owner's call on his own brand palette. A contrast ratio measures
luminance distance, not legibility, and the framework should honour the palette
the client chose rather than silently substituting a different colour — which is
what the earlier `text`-token version did.

I raised the AA figure once; Bean confirmed. Recorded here so the number is not
lost and so nobody "fixes" this back without knowing it was a decision.
`P-MAMAS-PRIMARY-CONTRAST` stands on its own merits and is unaffected.

## Drawer defects — found by Bean, not by me

I shipped the drawer path with the accordion recorded as "INDICATIVE, not proven"
and no visual check. Bean opened it and found it plainly broken. Both regressions
were mine, and both came from rules that are correct for a FLOATING header panel
and wrong once the panel joins the normal flow:

| Symptom | Cause | Fix |
|---|---|---|
| Submenu opened to the RIGHT of its parent | `.sgs-nav-menu__submenu-root{display:flex}` makes the root a flex ROW; in the header the wrap is `position:absolute` so it never applied, but in the drawer it is `position:static` and became a flex SIBLING | drawer root is `display:flex;flex-wrap:wrap` with a full-width wrap, so the row stays a row and the panel wraps BELOW |
| Submenu text invisible | my own rule forced `background:transparent` in the drawer, deleting the surface the pink link token was chosen against — pink on pink | drawer children inherit the DRAWER's colour (`color:inherit`), and every drawer value derives from `currentColor`, so it works on a light, dark or brand drawer |
| Caret dropped onto its own line | my first fix over-corrected to `display:block` | `flex-wrap:wrap`, link takes the free space, toggle sits at the right edge |
| No separators, no structure | never implemented | `currentColor`-derived rules between every row, main and sub |
| No hover feedback on main items | `itemColour`/`itemBg`/`itemColourHover`/`itemBgHover` all default to `""`, so nothing is emitted unless the operator sets one — a real gap, NOT a suppressed default | a `currentColor` tint as the drawer default, which any operator-set colour still beats |
| Current page looked identical to hover | `render.php` put `[aria-current="page"]` in the SAME selector list as `:hover` | current-page removed from that list; it now gets weight + a solid left rule, so "where I am" and "what I'm pointing at" are different answers |

**Verified at 390px after the fix:** panel top 108 = row bottom 108 (below, not
beside) · same left edge as the trigger · caret on the same row at the right edge
· sublinks indented 32px · text 8.43:1 on the pink drawer · separators present ·
current page bold with a left bar. Screenshot `nav-drawer-final-390.png`.

## Known limit — NOT fixed, and cannot be from this block

A nav placed inside **page content** still has its dropdown overlapped by the
sticky header and the footer. The theme's `.entry-content{position:relative;
z-index:1}` creates a stacking context the block cannot escape; the header is
`z-index:100` and the footer's positioned rows are `z-index:1` but later in
document order. Raising `.entry-content` would put all page content above the
sticky header, which is worse.

**The normal HEADER placement is unaffected and fully correct** — verified above.
Tracked as `P-NAV-DROPDOWN-STACKING-IN-PAGE-CONTENT`.
