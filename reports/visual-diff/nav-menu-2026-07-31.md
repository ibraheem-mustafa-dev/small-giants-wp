# Visual-diff — `sgs/nav-menu` submenu / dropdown

Satisfies the visual-diff gate for the dropdown work. The gate correctly refused
to treat this as markup-neutral (it adds output and touches JS/CSS/JSON), so a
deploy and a live check were required — and that requirement earned its keep:
**five real defects were found live that every offline gate passed.**

## Defects found LIVE (all offline gates were green on every one)

| # | Defect | Cause | Status |
|---|---|---|---|
| 1 | Panel opened 89px right of its menu item | anchored on `[data-sgs-mega-trigger]`, which in the has-URL branch is the small caret BUTTON after the link, not the item | FIXED — anchors on the disclosure root; measured offset now **0px** |
| 2 | Panel hardcoded `#fff` + black shadow | literal fallbacks instead of palette tokens — ignored the client's `surface` `#fbf3dc` entirely, in every style variation | FIXED — `surface-alt` / `--wp--preset--shadow--md` / `border-subtle` |
| 3 | Submenu links ignored the palette | my rule out-specified the theme's global link rule and forced inherited body text | FIXED — see the contrast note below |
| 4 | "Black underline" on click | focus ring set to `currentColor`, which resolves to near-black body text | FIXED — `--wp--preset--color--primary` |
| 5 | Dropdown children could never be marked as the current page | `markCurrentPage()` selected `.sgs-nav-menu__link` only; children emitted `data-sgs-nav-path` that nothing read | FIXED — selector widened; verified live |

## The contrast decision (defect 3)

Letting the theme's link colour apply IS palette-driven, but measured on this
client it fails accessibility:

| Foreground | On panel | Ratio | AA (4.5:1) |
|---|---|---|---|
| `primary` `#e68a95` | `#fbf3dc` | **2.25** | FAIL |
| `primary-dark` `#c56a7a` (focus) | `#fbf3dc` | **3.32** | FAIL |
| `text` `#3a2e26` | `#fff9f0` | **11.86** | PASS |

So submenu rows default to the **`text` token** — palette-driven, follows every
style variation and per-client snapshot, and accessible. A dropdown row is
navigation text on a panel, not an inline body link. Pre-existing issue
`P-MAMAS-PRIMARY-CONTRAST` is the reason the link tokens fail here; this work
does not fix that, it declines to ship into it.

## Verified live (1440)

- Negative control on every open check: panel `display:none`, `aria-expanded=false`, rect 0×0 BEFORE each click.
- Opens: painted 200×150, below the trigger, fully on-screen.
- **Alignment 0px offset** from the menu item (was 89px).
- ESC closes AND returns focus to the trigger.
- Toggle closes on second click (single-open behaviour).
- Children: 2 of 2 (then 3 of 3) present, correct hrefs, 44px minimum height.
- Current page: only `/t1-dropdown-verify/` carries `aria-current="page"` + weight 600; the other two carry neither. Built-in negative control.
- Panel bg `rgb(255,249,240)` ≠ page bg `rgb(251,243,220)` — genuine separation.
- Stacking, HEADER placement: **all 5 sampled points return the panel as topmost**.

## Known limit — NOT fixed, and cannot be from this block

A nav placed inside **page content** still has its dropdown overlapped by the
sticky header and the footer. The theme's `.entry-content{position:relative;
z-index:1}` creates a stacking context the block cannot escape; the header is
`z-index:100` and the footer's positioned rows are `z-index:1` but later in
document order. Raising `.entry-content` would put all page content above the
sticky header, which is worse.

**The normal HEADER placement is unaffected and fully correct** — verified above.
Tracked as `P-NAV-DROPDOWN-STACKING-IN-PAGE-CONTENT`.
