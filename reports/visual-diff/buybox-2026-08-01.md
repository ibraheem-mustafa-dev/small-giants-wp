# Job 1 — per-breakpoint motion disable, runtime gate (Step 15): PASS

## Method

Created a real canary page (`wp post create`, post 2115) with two `sgs/heading`
blocks carrying `fx:"scrub"` — a CONTROL with no disable attribute (anchor
`fx-control`) and a TEST with `fxDisableMobile:true` (anchor
`fx-disabled-mobile`) — separated by tall spacers so both start below the
fold. Measured `getComputedStyle().opacity`/`visibility`/`display` with
Playwright at 375px and 1440px, before and after scrolling each element into
view, with a fresh cache-busting query string per run.

## Results (real numbers)

**375px (mobile, disable-mobile should suppress the TEST block only):**

| Element | Pre-scroll opacity | Opacity once scrolled to it | visibility | display |
|---|---|---|---|---|
| `#fx-control` (no disable) | 0 | 0.8628 | visible | block |
| `#fx-disabled-mobile` | 1 | 1 | visible | block |

The control's opacity dropped to 0 pre-scroll (GSAP's `immediateRender`
applying its `fromTo` from-state before the element enters view) and rose to
0.86 once scrolled to — direct proof `bootEffect` initialised it. The
disabled block's opacity never left 1 and its `visibility`/`display` never
changed — proof `isDisabledAtThisTier()` skipped it entirely, and per FR-38-2
the skipped element is fully visible throughout (fail-open confirmed, not
just asserted).

**1440px (desktop — `fxDisableMobile` must NOT suppress at this tier):**

| Element | Pre-scroll opacity | Opacity once scrolled to it | Opacity once further scrolled past |
|---|---|---|---|
| `#fx-control` | 0 | 0.7159 | 0.9999 |
| `#fx-disabled-mobile` | 0 | (not yet reached) 0 | 0.7702 |

Both elements start hidden pre-scroll and progress toward 1 as they enter the
scroll range — the `fxDisableMobile` attribute correctly has NO effect at the
desktop tier; both effects ran identically.

## Verdict: PASS

The Step 15 gate behaves exactly as specified: disabled at its declared tier,
running normally at every other tier, and fail-open (never invisible) when
skipped. This is genuine live-browser evidence, not unit-test inference.

# Job 2 — buybox thumbnail-strip drag (Step V)

## What was checked, and a mid-session correction

**Constraint:** the live product `/product/mamas-test-box-48-sku-fixture/`
(post 540) carries the buybox block via a SHARED theme template part
(`parts/sgs-pdp-buybox.html`, `<!-- wp:sgs/buybox /-->` with no attributes —
`dragToScroll` defaults `false`). Editing that template part would change the
drag behaviour of **every product on the site**, is outside "a canary page I
create myself", and `wp post update` is hook-blocked regardless. So the
literal target URL's own buybox instance could not be, and was not, modified
this session — it renders exactly as before, `dragToScroll` still off.

To test the mechanism honestly rather than fabricating a positive, a
**canary page bound to the SAME real product (540)** was created via
`wp post create`, with `<!-- wp:sgs/buybox {"dragToScroll":true} --> `
composed inside a block that supplies WooCommerce's `postId` context —
exercising the identical `render.php` / `gallery-col.php` /
`fx-draggable.js` deployed on production, against real WooCommerce data, with
a real trusted pointer gesture. No JS injection, no hand-edited DOM, no
forced attribute.

**First attempt failed and surfaced a genuine, separate, unreported bug.**
Wrapping `sgs/buybox` in a plain `core/query` + `core/post-template` loop
(post 2116) resolved `context.postId` correctly (price rendered as real
£4.99) but the manifest's gallery data came back **entirely empty for every
combo** (`sgs-buybox-galleries` island `[]`), where the SAME product on its
real PDP carries populated per-combo galleries. Re-checked twice minutes
apart — reproducible, not a cache race. `Product_Manifest::build()`'s cache
key (`sgs_manifest_v6_{id}_{tax_fingerprint}`) is product-ID-only and has no
`is_product()`/query-context branch in its source, so this looks like a
context-dependent difference in how per-variation gallery meta resolves
depending on whether `woocommerce_setup_product_data()`-style hooks have run
— **flagging this as a new finding for the block/manifest owner; not
investigated further or fixed, per this session's read-only scope on block
source.** Switching the wrapper to `woocommerce/product-collection` +
`woocommerce/product-template` (post 2117) — which does call WooCommerce's
own per-item setup — fixed it: the gallery populated identically to the real
PDP.

## Measure 1 — does the attribute now appear in rendered HTML from a real render?

**Yes, confirmed on the working canary (post 2117).** Fetched HTML shows:

```html
<div class="product-card__thumbs" role="list" aria-label="Product images"
     data-wp-bind--hidden="context.thumbsHidden" data-sgs-fx="draggable">
```

This is the first time `data-sgs-fx="draggable"` has been observed coming
from a real PHP render (`gallery-col.php` echoing
`$buybox_thumbs_fx_attr`) rather than hand injection — the specific gap the
2026-08-01 (earlier) and 2026-07-31 reports both left open. **On the literal
`/product/mamas-test-box-48-sku-fixture/` URL, the attribute is still
absent** — correctly, because `dragToScroll` is false there by design/default,
not because the emit is broken.

## Measure 2 — genuine pointer drag, 1:1 tracking

Used the committed harness's own pattern (`page.mouse.move/down/up`, trusted
CDP events — confirmed via `event.isTrusted: true` and `pointerType: "mouse"`
in an in-page listener), 12 steps of 30px each, over the real overflowing
strip (`scrollWidth 712 / clientWidth 616 / maxScroll 96`):

| Step | Cumulative pointer delta (px) | `scrollLeft` (px) |
|---|---|---|
| 1 | 30 | 30 |
| 2 | 60 | 60 |
| 3 | 90 | 90 |
| 4 | 120 | 96 (clamped — correct, `maxScroll` is 96) |
| 5–12 | 150–360 | 96 (held at max, no drift, no overshoot) |

Steps 1–3 track the pointer **exactly 1:1, zero offset** — the same signature
the committed harness recorded for `sgs/gallery` (which has no
`scroll-behavior: smooth` race) and the opposite of the sibling bug this
brief warned about (`sgs/post-grid` drifted to 14px because
`scroll-behavior: smooth` raced the drag's writes). `cursor` toggled
`grab → grabbing → grab` in step with pointerdown/pointerup. On release,
`scrollLeft` stayed at 96 through the 250ms and 1.5s follow-up reads — no
momentum overshoot past the real boundary (`InertiaPlugin`'s `max` clamp is
working).

(First run of this measurement returned an all-zero trail with an empty
pointer-event log — the strip was below the fold and the mouse coordinates
landed outside the actual viewport. Re-run after `scrollIntoViewIfNeeded()`
produced the trusted-event trail above. Recorded here so the zero-movement
result is not mistaken for a second finding — it was a probe defect, fixed
before drawing any conclusion, not a claim.)

## Measure 3 — keyboard and wheel alternatives

Both still work, natively, with no JS from this feature required:

- **Keyboard:** focused the first thumb button, pressed `ArrowRight` —
  `scrollLeft` moved 0 → 72px (browser-native scroll of the focused element's
  scrollable ancestor; nothing in `fx-draggable.js` intercepts or needs to
  intercept this, per its own "keyboard: never sets tabindex, never moves
  focus" contract).
- **Wheel:** dispatched a horizontal wheel delta over the strip — `scrollLeft`
  moved 72 → 96 (clamped at max), again native `overflow-x: auto` behaviour,
  untouched by the drag module.
