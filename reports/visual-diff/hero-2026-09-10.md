# Visual diff — sgs/hero — hover-spill-scale (stacking + transition fix) — 2026-09-10

Fixes two confirmed live bugs on the split hero's hover-zoomed split-media image
(page 2742, sandybrown canary): (1) the hover-zoomed image painted BEHIND the
following `sgs/trust-bar` section instead of above it, because `.sgs-hero--split`'s
own `overflow-x:clip` created a stacking context that trapped the media's borrowed
`z-index:1` inside it; (2) the scale transition was instant instead of smooth,
because the shared `.sgs-media-el` shadow atom's `transition: box-shadow 0.3s`
SHORTHAND reset `transition-property` and silently overwrote hero's own
`transform 0.35s ease-in-out`.

Built as reusable shared infrastructure per Bean's direction: a new
`hoverSpillScale` capability on `SGS_Container_Wrapper` (opt-in via
`supports.sgs.enabledExtensions`, same mechanism as `width`/`background`/
`shapeDividers`), plus a longhand fix in `assets/css/media-atoms/shadow.css`
that benefits every `.sgs-media-el` consumer, not just hero. "Before" isn't
meaningful for the capability half — it's a new, isolated, opt-in mechanism
with no prior state to diff against on any block except hero, whose own
private CSS it supersedes; the real question is "does the current live state
match what was intended?", answered below by direct measurement.

## Assertions — stated before measuring

1. The hero root (`.wp-block-sgs-hero`) carries `position:relative`, an explicit
   non-auto `z-index`, `overflow-x:clip`, `overflow-y:visible`.
2. `.sgs-hero .sgs-media-el`'s computed `transition-property` includes `transform`
   (not `box-shadow`, not reset to nothing).
3. While the split-media image is genuinely `:hover`ed, `document.elementFromPoint()`
   at coordinates 5px/15px/25px BELOW the hero's own bottom edge — physically
   inside the following `sgs/trust-bar` section's box — resolves to the hero's
   own `<img>`, not the trust-bar.
4. No horizontal-scroll regression while hovered (`document.documentElement.
   scrollWidth <= clientWidth`).
5. Other live `.sgs-media-el` consumers on the same page (`sgs/product-card`,
   `sgs/media`) still show `transition-property:box-shadow` — the shorthand fix
   does not disturb their own transition.
6. Composites that do NOT declare `hoverSpillScale` (`sgs/container` — 15 live
   instances on the page, `sgs/trust-bar`) render byte-identical: `z-index:auto`,
   `overflow-x:visible`, no `.sgs-container--hover-spill-scale` marker class.

## Live result — measured against the canary (page 2742, post-deploy)

1. `getComputedStyle(hero)` → `position:"relative"`, `zIndex:"2"`,
   `overflowX:"clip"`, `overflowY:"visible"`. Matches.
2. `getComputedStyle(mediaEl).transitionProperty` → `"transform"`,
   `transitionDuration` → `"0.35s"`. Matches.
3. Real hover triggered via Playwright CDP click (confirmed `mediaBox.matches(':hover')
   === true`, `getComputedStyle(mediaEl).transform === "matrix(1.05, 0, 0, 1.05, 0, 0)"`).
   `elementFromPoint` at heroBottom+5/+15/+25 all returned the hero's own `IMG`
   (`el.closest('.sgs-hero') === true`, `el.closest('.sgs-trust-bar') === false`)
   for all three offsets. Screenshot confirms the zoomed cookie image visibly
   painting over the pink trust-bar strip. Matches.
4. `scrollWidth === clientWidth` (1425 === 1425) while hovered. Matches.
5. `sgs/product-card` (2 instances) and `sgs/media` (1 instance) on the same page
   all show `transitionProperty:"box-shadow"`. Matches — zero regression.
6. All 15 `sgs/container` instances and the page's `sgs/trust-bar` show
   `zIndex:"auto"`, `overflowX:"visible"`, `classList.contains('sgs-container--hover-spill-scale')
   === false`. `document.querySelectorAll('.sgs-container--hover-spill-scale')` returns
   exactly 1 element on the whole page (the hero itself). Matches — the opt-in
   leaks to nothing that doesn't declare it.

## Why before/after doesn't apply

The capability is new and opt-in (nothing else on the live page has ever carried
`hoverSpillScale`), and the shorthand fix in `shadow.css` is a bug fix whose
"before" state (instant transition, wrong stacking) is precisely the defect being
removed — a diff against it would only re-confirm the bug existed, not that the
fix landed correctly. The six assertions above are a direct, stated-then-measured
check against the live rendered/interactive output, which is the stronger proof
for an interaction-state (`:hover`) change that a static before/after screenshot
pair cannot capture anyway.
