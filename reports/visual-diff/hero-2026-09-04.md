## What changed

Tier-migration residual (D777): `textAlignDesktop`/`textAlignTablet`/`textAlignMobile`
(3 flat scalars) collapsed into one object attr `textAlign: {desktop,tablet,mobile}`.
S1 (block.json) + S2 (edit.js, LEGACY attrMap → `<ResponsiveOverride>`) + S3 (render.php,
raw bracket reads → `sgs_responsive_normalise_object()`). Behind an editor control that was
already broken for the block's live shape — `migrate-tier-object.py`'s detector couldn't
see a `<prop>Desktop`-suffixed base, so this was silently mis-scanned before today.

## Why before/after doesn't apply

No stored page on the canary has ever set `textAlignDesktop`/`Tablet`/`Mobile` to a
non-default value (verified: mama's-munches page 2742's hero, the only live hero instance,
carries no `textAlign*` key at all in its stored attrs) — so there is no meaningful
"before" render to diff against. The real question is whether the migrated control now
works at all, which "does the current output match intent" answers directly.

## Assertions (stated before measuring)

1. With `textAlign` unset (`{}`, the live default), `.sgs-hero__content` should render
   with NO explicit `text-align` rule (inherits the variant's own alignment) — i.e. no
   regression to the untouched, common case.
2. With `textAlign: {desktop:"center", tablet:"right"}`, the live page should render
   `text-align:center` on `.sgs-hero__content` at desktop width, and `text-align:right`
   at tablet width (≤1023px) — proving the object round-trips through block.json →
   edit.js → render.php → real browser-computed style.
3. No `text-align:Array` (or any literal "Array" string) anywhere in the rendered
   `<style>` — the PHP array-to-string-coercion bug class this whole migration exists to
   prevent (D569/D570).

## Known unrelated finding (not fixed here, flagged separately)

`render.php:905-906` (unchanged by this migration) reads a bare `$attributes['textAlign']`
expecting a flat scalar (`'left'|'center'|'right'`) to paint `.sgs-hero__headline` directly.
This attribute name was never declared bare in block.json before today, so this line has
always been dead (isset() false). After this migration `isset()` now returns true (the
object exists), but `in_array($object, [...strings], true)` still evaluates false (strict
type mismatch) — so it remains a silent no-op, not a new live defect. Pre-existing,
unrelated to this migration's target property; not touched here.
