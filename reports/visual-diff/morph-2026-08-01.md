## Condition 2 — root cause (why it fails)

Confirmed against `sgs/heading` with `fx=morph`, `fxShape=circle-square`, `fxTrigger=load` — one of the 28 newly-qualifying blocks, not one of the original 3 SVG-shape blocks.

`includes/fx-shape-routes.php::sgs_expand_fx_shape_pair()` builds the "FROM" shape markup as:

```html
<svg class="sgs-fx-shape-visual" data-sgs-fx="morph" data-sgs-fx-morph-target="#sgs-fx-shape-1" viewBox="0 0 100 100" ...>
  <path d="M 50 6 A 44 44 0 0 1 50 94 A 44 44 0 0 1 50 6 Z"></path>
</svg>
```

`data-sgs-fx="morph"` is placed on the **`<svg>` wrapper**, not the inner `<path>`. Confirmed live via `document.querySelector('.sgs-fx-shape-visual')`:

```json
{ "visualTag": "svg", "visualDataSgsFx": "morph", "visualHasDAttr": false,
  "pathD": "M 50 6 A 44 44 0 0 1 50 94 A 44 44 0 0 1 50 6 Z" }
```

`fx-morph.js`'s own docblock (item 1 of its authoring contract) requires the element carrying `data-sgs-fx="morph"` to itself be "a real SVG shape node (`<path>`, or anything MorphSVGPlugin can `convertToPath()` itself: `<rect>`/`<circle>`/`<ellipse>`/`<polygon>`/`<polyline>`/`<line>`)". An `<svg>` container is not in that list and is not itself convertible. `resolveMorphTarget()` in that same file validates the **TARGET's** geometry (it correctly resolved — the hidden `#sgs-fx-shape-1` `<path>` carries the square's `d`) but never validates the **source** (`el`) — so the asset gate passes and GSAP is asked to morph the `<svg>` element itself, which GSAP refuses outright:

```
[WARNING] Cannot morph a <SVG> element. Use MorphSVGPlugin.convertToPath() to convert to a path before morphing.
  @ .../build/vendor-modules/gsap-morphsvg.js
```

No tween is created. Geometry evidence — sampled the visual `<path>`'s `d` attribute on every animation frame for 1.6 seconds (well past the 0.8s default `fxDuration`) after `load` trigger fired:

- t=0ms through t=1603ms: `d` is `"M 50 6 A 44 44 0 0 1 50 94 A 44 44 0 0 1 50 6 Z"` at **every single sample** — never once moved toward the square target. (Full 148-sample series captured; identical value throughout, so it is reproduced here once rather than pasted in full.)

**This is not a one-off misconfiguration on my test page** — `sgs_expand_fx_shape_pair()` is the ONLY code path that expands a curated `fxShape` preset for any of the 28 qualifying blocks, and it always emits `data-sgs-fx="morph"` on the `<svg>` wrapper (see `fx-shape-routes.php:346`: `$visual_attrs = ' data-sgs-fx="morph" ...'` is concatenated directly onto the `<svg class="sgs-fx-shape-visual"...>` tag, unconditionally). Every one of the 28 blocks will hit this identical failure the moment an operator picks a shape pair — the 3 original SVG-shape blocks (`sgs/icon`, `sgs/responsive-logo`, `sgs/separator`) are not exempt either, since the same expansion function runs for them too once they use the curated-shape picker path rather than hand-authored inline SVG.

**Fix shape** (for whoever owns `fx-shape-routes.php` — not proposing this as the fix, just naming what's wrong): the `data-sgs-fx="morph"` + `data-sgs-fx-morph-target` attributes need to land on the inner `<path>` element, not the `<svg>` wrapper, OR `fx-morph.js` needs `convertToPath()`-style handling for an `<svg>` root (unlikely to be what MorphSVGPlugin supports — it works on shape primitives, not container elements).

## Condition 3 — fail-safe check (met)

Built a second instance directly in a Custom HTML block (not touching any plugin file — page content only): a `<svg>` with `data-sgs-fx="morph"` pointing at a selector that resolves to nothing on the page.

```html
<svg data-sgs-fx="morph" data-sgs-fx-morph-target="#sgs-morph-qa-missing-target" ...>
  <path d="M 50 6 A 44 44 0 0 1 50 94 A 44 44 0 0 1 50 6 Z" fill="currentColor"></path>
</svg>
```

Console, on load:

```
[WARNING] [sgs-fx-morph] data-sgs-fx-morph-target "#sgs-morph-qa-missing-target" matched no element —
  morph skipped, element stays at its rendered shape.
  @ .../build/shared/effects/gsap/fx-morph.js
```

Element geometry: unchanged (never touched — `resolveMorphTarget()` returns `null` before any tween is created, per its own documented fail-safe design). This path works exactly as `fx-morph.js`'s docblock describes — no silent failure, no destructive partial state, one clear console warning identifying the exact selector and element.

Note: I could not reproduce the "deliberately mismatched TOPOLOGY pair" framing literally — per the module's own docblock, MorphSVGPlugin **re-samples** a topology mismatch rather than refusing to run (it "still animates, just with more redistribution"), so a bad-topology pair is not a warn-and-fail case by design; only a genuinely *unresolvable* target (invalid selector, no match, no usable geometry) is. I tested the unresolvable-target path since that's the one the code actually gates on.

## Also worth knowing (relaxation side-effect, not gated by the brief but real)

The condition-2 failure above IS the concrete case of the brief's own worry: "if `requires: none` lets morph attach to blocks where it can do nothing meaningful... that is a real finding." `sgs/heading` has zero inherent morphable geometry — the relaxation's entire premise is that the render-layer shape injection (`fx-shape-routes.php`) supplies geometry to blocks that have none of their own. That supply mechanism is what's broken. So the relaxation isn't merely reaching blocks that "can't do anything with it" in the abstract — the concrete delivery mechanism for ALL 28 blocks (including the original 3) is non-functional for the curated-preset path tested here.
