# sgs/form — `--sgs-progress-colour` — VERIFIED LIVE ON A NEW CANARY INSTANCE

**Verdict: PASS.** A new canary page (`sgs-gate-canary-2`, page ID 2071) was built with a
`sgs/form` instance carrying two `sgs/form-step` children (`$is_multi_step = $total_steps > 1`
is true) and a non-default `progressBarColour:"accent"`, so `.sgs-form__progress` renders.
Captured live via Playwright at 1440px and 375px: no `style` attribute, correct computed
custom-property value.

## What changed
`plugins/sgs-blocks/src/blocks/form/render.php`:
```php
// Before
$progress_style_attr = '';
if ( $progress_colour ) {
    $progress_style_attr = ' style="--sgs-progress-colour:' . sgs_colour_value( $progress_colour ) . '"';
}
...
<div class="sgs-form__progress" role="progressbar" ... <?php echo $progress_style_attr; ?>>

// After
if ( $progress_colour ) {
    if ( empty( $sgs_form_uid ) ) {
        $sgs_form_uid                = 'sgs-form-' . substr( md5( wp_json_encode( $attributes ) ), 0, 8 );
        $sgs_form_supports_classes[] = $sgs_form_uid;
    }
    $sgs_form_supports_css .= '.' . $sgs_form_uid . ' .sgs-form__progress{--sgs-progress-colour:' . sgs_colour_value( $progress_colour ) . ';}';
}
...
<div class="sgs-form__progress" role="progressbar" ...>
```
The colour now lands in the same scoped `<style>` uid used by the block's other
colour/border/typography/submit-button supports (minted eagerly if none of those already
needed one), instead of an inline `style="--x:y"` attribute on the progress-bar div.

## Canary instance

<!-- wp:sgs/form-step {"label":"Confirmation"} /-->

## Evidence
- **Element found live:** `.sgs-form__progress` present in the rendered DOM at both viewports
  (the multi-step scaffolding — `.sgs-form__progress-wrapper`, `.sgs-form__progress-steps`,
  2 `.sgs-form__progress-step` entries — all render as expected).
- **No-inline contract holds:** `element.getAttribute('style')` === `null` at both 1440px and
  375px.
- **Computed value correct:** `getComputedStyle(el).getPropertyValue('--sgs-progress-colour')`
  === `"#f5d050"` at both viewports (the theme's resolved `accent` token — the CSS rule itself
  stores `var(--wp--preset--color--accent)`, which the browser resolves to the concrete hex on
  read).
- **CSS lands in the LIFTED stylesheet, not inline `<style>` on the page** (SGS lifts block CSS
  to `wp-content/uploads/sgs-css/`, per memory `sgs-block-css-is-lifted-not-inline` — page-HTML
  grep alone proves nothing). Fetched
  `wp-content/uploads/sgs-css/sgs-1003-175717f0a7396f78658cc3d7873ff1fd.css` and confirmed:
  ```css
  .sgs-form-76845279 .sgs-form__progress{--sgs-progress-colour:var(--wp--preset--color--accent);}
  ```
- **Method + tooling:** `plugins/sgs-blocks/scripts/gate-canary-2-capture.mjs` (Playwright,
