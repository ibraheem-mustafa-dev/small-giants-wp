# label — `borderRadius` migrated from a px-only number to a CSS-length string

**Verdict: PASS**, on a live server-emitted-CSS capture against the canary after
a real deploy. This is a **deliberate rendering change** for any instance using a
non-px unit, and it repairs two silent value losses. Existing instances are
byte-identical.

## What was measured, and where

- **Page:** https://sandybrown-nightingale-600381.hostingersite.com/t1b-border-radius-unit-probe/ (page 2363)
- **Deploy:** `--blocks-only`, `--payload`-scoped to this wave's four paths, from
  an isolated worktree. `payload-verify` matched all 83 live `block.json`
  against the payload. No `--allow-dirty`, no `--skip-verify`.
- **Method:** the block's CSS is **lifted** to `uploads/sgs-css/sgs-*.css`, so a
  grep of the page HTML proves nothing — it was followed to the lifted
  stylesheet and asserted there. The probe page carries four `sgs/label`
  instances covering every value shape, authored via the REST API and confirmed
  in `context=edit` raw `post_content` before measuring.

## Result — all four cases

| Stored value | Shape | Emitted after | Emitted BEFORE this change |
|---|---|---|---|
| `16` | legacy int | `border-radius:16px` | `border-radius:16px` (unchanged) |
| `"1.5rem"` | new string | `border-radius:1.5rem` | `border-radius:1px` — truncated |
| `"0.5rem"` | new string | `border-radius:0.5rem` | **nothing — silently dropped** |
| `0` | legacy int | *(no declaration)* | *(no declaration)* (unchanged) |

PHP diagnostics in the served HTML: **0**.

## Why the change is deliberate (`--expect-change` reason)

The shared emitter `sgs_label_box_css_rule()` did `intval( $radius ) . 'px'`.
`intval('1.5rem')` is `1`, so every non-px unit was silently truncated to `1px`.
The zero-is-absent guard used `intval()` too, and `intval('0.5rem')` is `0`, so
any sub-1 rem/em radius was dropped entirely. Both are now correct: the emitter
sanitises a real CSS length, and the guard uses `floatval()`.

## ⛔ A REAL BUG THIS CAPTURE CAUGHT — recorded, not smoothed over

The first deployed revision declared `borderRadius` as `"type": "string"`. The
probe then showed the legacy int `16` stored correctly in `post_content` but
rendering **no radius at all**: WordPress validates a stored value against the
declared type and silently falls back to the default on a mismatch (D338).

**Every existing label with a radius would have silently lost it.** The
back-compat claim in the first commit message was false, and only a live capture
falsified it — the build was green, all 43 prebuild gates passed, and the
editor-side change looked correct throughout.

Fixed by declaring `"type": [ "string", "number" ]`, so both the legacy number
and a new CSS-length string validate. Re-deployed and re-measured: the table
above is the post-fix state.

## Positive control

The three explicitly-set values each bind to a distinct emitted declaration
(`16px` / `1.5rem` / `0.5rem`), and the zero case emits none — so the probe
distinguishes "renders correctly" from "renders at all", rather than reporting
presence.
