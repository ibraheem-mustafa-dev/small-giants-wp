# sgs/timeline — phantom-token sweep + reached-milestone state

## What changed and what is asserted

Two changes in `1014fc9d8`:

1. `connectorColour`'s default moved from `border-subtle` (defined in NO palette) to
   `border`. **Assertion:** the milestone dot paints a real colour instead of
   `rgba(0,0,0,0)`.
2. A persistent `is-reached` class marks milestones the fill has passed.
   **Assertion:** dots at a fraction ≤ the current progress paint the fill colour;
   dots above it keep the resting colour.

This is an `intent_capture`, not a before/after diff, and deliberately so: the
before-state of assertion 1 is an **unpainted element**. There is no meaningful
"before" image of a colour that never rendered.

## Method

Live canary, Chrome (the NATIVE `animation-timeline: view()` driver — confirmed
`CSS.supports('animation-timeline','view()') === true`, so `view.js`'s rAF driver
feature-detects and returns early). `prefers-reduced-motion` confirmed `false`, so
the fill was not pinned to 1 by the reduced-motion rule.

⚠ **Viewport height had to be reduced to 420px to make the effect observable at
all.** See finding B.

## Result — both controls present in one uncontaminated sweep

Node fractions along the connector: `0.079, 0.299, 0.520, 0.740`.
Pure scrolling only; no animation object was touched (see "Instrument failures").

| measured progress | 0.079 | 0.299 | 0.520 | 0.740 |
|---|---|---|---|---|
| **0.337** | reached | reached | **NOT** | **NOT** |
| **0.696** | reached | reached | reached | **NOT** |
| **0.836** | reached | reached | reached | reached |

**Positive control:** dots below the head are marked.
**Negative control:** dots above the head are NOT — the check can fail.

Painted colour at progress 0.337, read from `::before` (the element that actually
paints), not the node box:

- reached dot → `rgb(245, 208, 80)` — the client's accent
- unreached dot → `rgb(232, 213, 192)` = **`#E8D5C0`**, exactly the `border` value
  in `sites/mamas-munches/theme-snapshot.json`

That second value IS the phantom-token fix, measured. Before the sweep this
computed to `rgba(0, 0, 0, 0)`.

**Painted geometry asserted, not just computed style:** every node measured
`16x16` with a non-zero bounding rect. A computed-style check cannot see a
zero-area element, which is how a 2px×2px SVG passed 69 gates during Stage A.

**Second, independent control on the same page:** section 2 of the probe page is a
timeline with the progress fill OFF. Its dots now render in pale `#E8D5C0` in the
screenshot. Before this commit they were invisible there too — so the fix is
visible in an instance that has nothing to do with the progress feature.

# ADDENDUM — sparkler replaces the per-milestone burst

Second deploy, same day. Owner's feedback on the Stage A sparks: *"I really dislike
the sparks, it hides the nice halo ring effect when it hits the dot. And, my
request was for sparks like from a sparkler (the little firework stick) visually
on the progress after circle."*

## What changed

- `burst()` -> `flashRing()`: the milestone dot keeps its halo ring and throws NO
  particles. The ring is now unobstructed, which was the complaint.
- New continuous emitter on the travelling fill head — the lit sparkler tip. Own
  rAF loop (a sparkler burns continuously; it is not an event), gated on
  IntersectionObserver + `0 < progress < 1` + not-reduced-motion, with a 26-spark
  ceiling.
- Spark size 11px -> 6px, life 1100ms -> 520ms. Many small fast motes, not a
  seven-particle firework.

## Anchoring — the opposite rule to the ring, deliberately

A burst belonging to a DOT must anchor to the dot (in `align-left` the dots sit
~107px off the line — see finding A). A sparkler belonging to the HEAD anchors to
the LINE, because the head is on the line. Verified live:

| | x centre |
|---|---|
| spark | **713px** |
| connector | **713px** |

`.sgs-timeline__progress` is the correct parent in every alignment: it is the same
positioning container the head's own `::after` uses, and it is deliberately
UNMASKED (the mask lives on its two child layers), so a spark thrown past the head
is not clipped.

## What is proven, and what is NOT

**Proven live:** sparks are created while the head travels (peak 4 concurrent),
they sit exactly on the connector centre line, the halo ring still fires, and
`liveSparks` returns to 0 when progress reaches 1.

⛔ **NOT proven: that a spark is legibly painted.** `getComputedStyle().opacity`
returned `0` for every spark at every age — including for a control spark injected
at the OLD node location, which is Stage A code the owner confirms he can see. The
same element reported `display: block`, `visibility: visible`,
`animation-play-state: running` and a `DocumentTimeline`. The instrument, not the
feature, is the thing that failed: opacity/transform animations are composited,
and this headless Chrome reports the base value rather than the animated one.

That is the inverse of the usual trap and worth keeping: a computed-style check
cannot see a painted element here any more than it could see a zero-area one
during Stage A.

**Therefore the aesthetic AND the legibility of the sparkler both sit with the
owner's eye (R-31-13).** Screenshot: `timeline-sparkler-2026-08-29.png` — it shows
the filled connector, accent dots, the head, and rings with nothing covering them.

Three knobs, one number each, if it wants tuning:
`--sgs-timeline-spark-size` (6px), `--sgs-timeline-spark-life` (520ms), and
`EMIT_EVERY_MS` (45ms) in `view.js`.

## ⛔ THE MEASUREMENT FINDING THAT MATTERS MOST — Lenis owns the scroll

Every anomaly in this session's live work traced to one cause, found only at the
end: **this framework runs Lenis smooth-scroll** (`html.lenis`, `window.lenis`,
`scroll-behavior: smooth`). `window.scrollTo()` is therefore ANIMATED, and any read
taken after a fixed delay is a read of the WRONG scroll position.

Proof: a probe asked for `top - 120` (~1080), read `scrollY: 0`, and moments later
the same page reported `scrollY: 1041` — still in flight.

What it caused, all of it false:
- the connector fill looking frozen at progress 1, then at 0;
- the milestone observer looking DEAD (twice);
- sections 1 and 4 looking as if their reveal never fired — they read `0/4` and
  `1/4` under fixed waits and `4/4` once the scroll actually settled.

⭐ **Any Playwright probe against this framework must wait for the scroll to STOP
MOVING, not for a fixed delay.** The pattern that works:

```js
window.scrollTo( { top: y, behavior: 'instant' } );
let last = -1, stable = 0;
for ( let i = 0; i < 60; i++ ) {
  await wait( 50 );
  if ( window.scrollY === last ) { if ( ++stable >= 3 ) break; }
  else { stable = 0; last = window.scrollY; }
}
```

With it, stops land exactly (0, 300, 600, 900, 1200) and every section reports 4/4.
⚠ `window.lenis.scrollTo` is NOT a function on this build — do not reach for it.

# ADDENDUM 3 — two defects the owner caught by eye that every probe had passed

Both reported against probe page 3079: *"4's whole appear on scroll effect are not
working. 6 has botched design. The picture has been placed in a really weird place
on the left so it overlaps the progress line."* Both were real. Screenshot:
`timeline-alignleft-media-fixed.png`.

## Defect 1 — reading the fill progress back through `getComputedStyle` is QUANTISED

The connector-triggered reveal fired in clumps: three milestones appeared at once
instead of one at a time. My own earlier probe had reported it working, because it
sampled at exactly the scroll positions where the staircase happened to step.

Sampling every 50px of scroll shows what the observer was actually reading:

| element top | progress reported |
|---|---|
| 900 → 700 | 0 |
| 650 → 400 | **0.223** |
| 350 → 150 | **0.635** |
| 100 → -100 | **0.836** |
| -150 → -400 | 0.942 |

Flat for 200-250px at a time — and it reports `1` while the block is still BELOW
the viewport. The painted fill is smooth; the value handed back to JS is not.

**Fix:** the milestone observer no longer reads the custom property at all. It
computes progress from GEOMETRY, using the same window the CSS animates over
(`animation-range: entry 0% exit 100%`), which is the function the rAF driver
already had. One shared `computeViewProgress()`, continuous, driver-agnostic, and
in step with the painted line by construction rather than by reading its output.

**Verified after:** milestones now reveal ONE AT A TIME at four distinct scroll
positions — 0 → 1 → 2 → 3 → 4 at element-top 1000 / 750 / 500 / -50 / -300.

⭐ This is the general lesson, not a timeline quirk: **a scroll-driven registered
custom property is for the browser to paint with, not for JS to read back.**
Anything keyed off such a read fires in steps.

## Defect 2 — the align-left rail did not move with its column

Measured before:

| | x |
|---|---|
| connector rail | **16** |
| media slot | **0 → 180** (drawn straight across the rail) |
| milestone dots | **196** |

The rail had always been pinned at `var(--sgs-node-size)` (16px) while the dots sit
in the node COLUMN — the same 107px misalignment already recorded in Addendum 1's
finding A. Widening column 1 to hold the media turned a long-standing
misalignment into a visible collision.

**Fix:** a new `--sgs-timeline-rail-offset` (default `var(--sgs-node-size)`, so
nothing changes without media) which, for an align-left timeline WITH media,
resolves to the node column's centre — derived from the three values that define
the grid (column 1 width + column gap + half the node), so it cannot drift from
the layout the way a magic number would.

**Verified after:** rail centre **205**, node centre **204** — aligned to 1px, and
`mediaCrossesRail: false`.

⚠ Scoped to the has-media case deliberately. Without media, column 1 is `auto` and
there is no expression for its width, so the rail keeps its existing position and
its existing misalignment rather than being moved on a guess. **Addendum 1's
finding A therefore remains open for the no-media case** and still needs a
decision.

## Not a defect — the media sitting flush to the page edge

Measured: the block has `padding-left: 0`, its parent `.entry-content` has
`padding-left: 0`, and the block spans the full 1425px. The probe page drops the

## Why the probes missed both

# ADDENDUM 4 — `left` was not a layout, it was `alternating` with the flip removed

Owner's observation: *"Doesn't that left design overlap with the normal variant?
Shouldn't the left variation have all of the content on the right of the timeline
bar?"* Correct on both counts. Screenshot: `timeline-left-vs-gutter.png`.
Probe rebuilt: canary page 3079, eight sections.

## The measurement that proved the duplication

| | rail x | row 1 | row 2 |
|---|---|---|---|
| `alternating` | 713 | date `0→689`, content `737→1425` | **mirrored** |
| `left` (before) | 205 | date `0→180`, content `228→1425` | identical to row 1 |

Both put date left of the rail and content right of it. `left` differed from
`alternating` only by not flipping — so a single row of each was the same shape.

## What the research said (research-check, default tier, 2 agents, 6 sources)

Full finding: `~/.claude/memory/research/2026-08-29-timeline-left-alignment-vs-date-gutter.md`.

**4 of 4 component libraries model "which side the content sits on" and "does the
date get its own gutter" as SEPARATE controls** — MUI `TimelineOppositeContent`,
Ant Design `label` (its LESS source literally switches on a second absolutely
positioned column), PrimeReact `opposite`, Vuetify's `opposite` slot. **None
forces a gutter when you pick `left`.** Welding them together was the defect.

Both patterns are real and named:
- **inline stack** — rail hard left, everything right (Flowbite/Preline default)
- **opposite content / date-gutter** — date in its own fixed column (MUI et al.,
  Preline's separately-named "Side timestamps")

The two agents disagreed on which to ship; the owner chose to split them properly,
which is what every library does.

Supporting: NN/g gazeplots found zig-zag layouts cause wasted fixations; every
vertical timeline collapses to rail-left-single-column on mobile anyway; and a
gutter that flips sides is what tempts the `order`/absolute-position hacks that
break WCAG 1.3.2 meaningful sequence.

## After — measured on the live canary

| section | align | rail x | row 1 | row 2 |
|---|---|---|---|---|
| 1 | alternating | 713 | date `0→689`, content `737→1425` | mirrored |
| 2 | **left (new default)** | **9** | date **and** content `32→1425` | same |
| 3 | **left + date column ON** | 205 | date `0→180`, content `228→1425` | same |
| 5 | left, no media | 9 | date and content `32→1425` | same |

`left` is now a genuinely distinct layout, and the gutter is available on it as an
opt-in rather than being forced.

## ⚠ NEW FINDING — `centre` now duplicates `left`, and needs the owner's decision

| section | align | rail x | row 1 |
|---|---|---|---|
| 2 | left | **9** | date and content `32→1425` |
| 4 | **centre** | **17** | date and content `32→1425` |

## Defect 1 — sparks 304px behind the head

Measured on canary 3079, timeline index 1:

| | value |
|---|---|
| CSS fill fraction | **0.931** |
| head, viewport y | **644** |
| first spark, viewport y | **340** |
| gap | **−304px** |

The head is `::after` on `.sgs-timeline__progress`, placed by CSS at

problem (Addendum 3) rather than working around it.

⚠ Note the split this leaves, deliberately: **position** comes from CSS, while the
**reveal/reached** decisions still come from geometry. Each uses the source that is
correct for it — CSS is where the head actually is; geometry is continuous where
the property read is stepped.

single active timeline every frame — its head must be on screen, and of those it
is the one nearest the viewport centre. Election is per frame, so the active

cost nothing.

## Addendum 7 — viewport reveal re-keyed onto `.is-js`

`:392` hid entries via `[data-reveal-on-scroll]`, an attribute authored into the markup,
so it matched whether or not `view.js` ran — with JS off those entries were unreachable
permanently. The connector reveal (`:1364`) already solved this by gating on `.is-js`,
which only a running script adds. `.is-js` was confirmed present on all 8 timeline roots
in the live DOM before relying on it.

⚠ **The reduced-motion override carries `.is-js` too, and that is load-bearing.** Adding
it to only the hiding rule would put that rule at (0,5,0) against the override's (0,4,0)
— the override loses the cascade and reduced-motion users are left with permanently
hidden entries. A losing rule is indistinguishable from an absent one. Both now sit at
(0,5,0), mirroring how the connector reveal pairs its own rules at `:1364`/`:1383`.

## Addendum 9 — a WCAG claim this session got WRONG, corrected before it propagated

Mid-session I told the owner that a horizontal timeline could not use a mobile carousel
because it fails WCAG 1.4.10 Reflow. **That was wrong, and the owner's own instinct
("it basically works the same as a carousel") was right.**

The error: asking whether a timeline qualifies for 1.4.10's *two-dimensional-layout
exception* (maps, diagrams, video, games, data tables), finding it doesn't, and
concluding it fails. **A contained horizontal scroller never needed the exception — it
passes on the main criterion.** W3C publishes **Technique G225**, a *Sufficient*
technique for 1.4.10, describing exactly this pattern; its Example 1 is a product
carousel and its Figure 6 is labelled **Pass**. The Understanding doc states plainly:
*"Reflow does not prohibit web pages from presenting both horizontal and vertical
scrollbars for individual sections of content."*

**The rule to bank: failing to qualify for an exception is not the same as failing the
criterion.** Check the Sufficient Techniques list before declaring a common pattern
non-conformant.

Two criteria that DO bite a horizontal scroller, and which the first pass missed:

- **SC 2.1.1 Keyboard** — a native overflow scroller with no focusable children cannot
  be reached or operated by keyboard in Chromium before 127, and in Safari *at all*.
  Fix: `tabindex="0"` + `role="region"` + accessible name, scoped to the breakpoint
  where it actually scrolls.
- **SC 2.5.7 Dragging Movements** — native `overflow` scrolling is **exempt** because the
  user agent provides the mechanism. Content that *suppresses* native scrolling and
  implements its own is **not** exempt. That is the precise boundary between a native
  `scroll-snap` carousel (conformant) and a GSAP `ScrollTrigger` pinned/scrubbed
  horizontal section (inherits 2.5.7 + 2.5.1 obligations) — and it decides the
  implementation for any future horizontal-timeline work.
