# sgs/timeline — phantom-token sweep + reached-milestone state

## What changed and what is asserted

Two changes in `1014fc9d8`:

1. `connectorColour`'s default moved from `border-subtle` (defined in NO palette) to
   `border`. **Assertion:** the milestone dot paints a real colour instead of
   `rgba(0,0,0,0)`.
2. A persistent `is-reached` class marks milestones the fill has passed.
   **Assertion:** dots at a fraction ≤ the current progress paint the fill colour;
   dots above it keep the resting colour.

This is an `intent_capture`, not a before/after diff, and deliberately so: the
before-state of assertion 1 is an **unpainted element**. There is no meaningful
"before" image of a colour that never rendered.

## Method

Live canary, Chrome (the NATIVE `animation-timeline: view()` driver — confirmed
`CSS.supports('animation-timeline','view()') === true`, so `view.js`'s rAF driver
feature-detects and returns early). `prefers-reduced-motion` confirmed `false`, so
the fill was not pinned to 1 by the reduced-motion rule.

⚠ **Viewport height had to be reduced to 420px to make the effect observable at
all.** See finding B.

## Result — both controls present in one uncontaminated sweep

Node fractions along the connector: `0.079, 0.299, 0.520, 0.740`.
Pure scrolling only; no animation object was touched (see "Instrument failures").

| measured progress | 0.079 | 0.299 | 0.520 | 0.740 |
|---|---|---|---|---|
| **0.337** | reached | reached | **NOT** | **NOT** |
| **0.696** | reached | reached | reached | **NOT** |
| **0.836** | reached | reached | reached | reached |

**Positive control:** dots below the head are marked.
**Negative control:** dots above the head are NOT — the check can fail.

Painted colour at progress 0.337, read from `::before` (the element that actually
paints), not the node box:

- reached dot → `rgb(245, 208, 80)` — the client's accent
- unreached dot → `rgb(232, 213, 192)` = **`#E8D5C0`**, exactly the `border` value
  in `sites/mamas-munches/theme-snapshot.json`

That second value IS the phantom-token fix, measured. Before the sweep this
computed to `rgba(0, 0, 0, 0)`.

**Painted geometry asserted, not just computed style:** every node measured
`16x16` with a non-zero bounding rect. A computed-style check cannot see a
zero-area element, which is how a 2px×2px SVG passed 69 gates during Stage A.

**Second, independent control on the same page:** section 2 of the probe page is a
timeline with the progress fill OFF. Its dots now render in pale `#E8D5C0` in the
screenshot. Before this commit they were invisible there too — so the fix is
visible in an instance that has nothing to do with the progress feature.

# ADDENDUM — sparkler replaces the per-milestone burst

Second deploy, same day. Owner's feedback on the Stage A sparks: *"I really dislike
the sparks, it hides the nice halo ring effect when it hits the dot. And, my
request was for sparks like from a sparkler (the little firework stick) visually
on the progress after circle."*

## What changed

- `burst()` -> `flashRing()`: the milestone dot keeps its halo ring and throws NO
  particles. The ring is now unobstructed, which was the complaint.
- New continuous emitter on the travelling fill head — the lit sparkler tip. Own
  rAF loop (a sparkler burns continuously; it is not an event), gated on
  IntersectionObserver + `0 < progress < 1` + not-reduced-motion, with a 26-spark
  ceiling.
- Spark size 11px -> 6px, life 1100ms -> 520ms. Many small fast motes, not a
  seven-particle firework.

## Anchoring — the opposite rule to the ring, deliberately

A burst belonging to a DOT must anchor to the dot (in `align-left` the dots sit
~107px off the line — see finding A). A sparkler belonging to the HEAD anchors to
the LINE, because the head is on the line. Verified live:

| | x centre |
|---|---|
| spark | **713px** |
| connector | **713px** |

`.sgs-timeline__progress` is the correct parent in every alignment: it is the same
positioning container the head's own `::after` uses, and it is deliberately
UNMASKED (the mask lives on its two child layers), so a spark thrown past the head
is not clipped.

## What is proven, and what is NOT

**Proven live:** sparks are created while the head travels (peak 4 concurrent),
they sit exactly on the connector centre line, the halo ring still fires, and
`liveSparks` returns to 0 when progress reaches 1.

⛔ **NOT proven: that a spark is legibly painted.** `getComputedStyle().opacity`
returned `0` for every spark at every age — including for a control spark injected
at the OLD node location, which is Stage A code the owner confirms he can see. The
same element reported `display: block`, `visibility: visible`,
`animation-play-state: running` and a `DocumentTimeline`. The instrument, not the
feature, is the thing that failed: opacity/transform animations are composited,
and this headless Chrome reports the base value rather than the animated one.

That is the inverse of the usual trap and worth keeping: a computed-style check
cannot see a painted element here any more than it could see a zero-area one
during Stage A.

**Therefore the aesthetic AND the legibility of the sparkler both sit with the
owner's eye (R-31-13).** Screenshot: `timeline-sparkler-2026-08-29.png` — it shows
the filled connector, accent dots, the head, and rings with nothing covering them.

Three knobs, one number each, if it wants tuning:
`--sgs-timeline-spark-size` (6px), `--sgs-timeline-spark-life` (520ms), and
`EMIT_EVERY_MS` (45ms) in `view.js`.

testing it, this would have shipped as content that vanishes with JS disabled.**

## ⛔ THE MEASUREMENT FINDING THAT MATTERS MOST — Lenis owns the scroll

Every anomaly in this session's live work traced to one cause, found only at the
end: **this framework runs Lenis smooth-scroll** (`html.lenis`, `window.lenis`,
`scroll-behavior: smooth`). `window.scrollTo()` is therefore ANIMATED, and any read
taken after a fixed delay is a read of the WRONG scroll position.

Proof: a probe asked for `top - 120` (~1080), read `scrollY: 0`, and moments later
the same page reported `scrollY: 1041` — still in flight.

What it caused, all of it false:
- the connector fill looking frozen at progress 1, then at 0;
- the milestone observer looking DEAD (twice);
- sections 1 and 4 looking as if their reveal never fired — they read `0/4` and
  `1/4` under fixed waits and `4/4` once the scroll actually settled.

⭐ **Any Playwright probe against this framework must wait for the scroll to STOP
MOVING, not for a fixed delay.** The pattern that works:

```js
window.scrollTo( { top: y, behavior: 'instant' } );
let last = -1, stable = 0;
for ( let i = 0; i < 60; i++ ) {
  await wait( 50 );
  if ( window.scrollY === last ) { if ( ++stable >= 3 ) break; }
  else { stable = 0; last = window.scrollY; }
}
```

With it, stops land exactly (0, 300, 600, 900, 1200) and every section reports 4/4.
⚠ `window.lenis.scrollTo` is NOT a function on this build — do not reach for it.

# ADDENDUM 3 — two defects the owner caught by eye that every probe had passed

Both reported against probe page 3079: *"4's whole appear on scroll effect are not
working. 6 has botched design. The picture has been placed in a really weird place
on the left so it overlaps the progress line."* Both were real. Screenshot:
`timeline-alignleft-media-fixed.png`.

## Defect 1 — reading the fill progress back through `getComputedStyle` is QUANTISED

The connector-triggered reveal fired in clumps: three milestones appeared at once
instead of one at a time. My own earlier probe had reported it working, because it
sampled at exactly the scroll positions where the staircase happened to step.

Sampling every 50px of scroll shows what the observer was actually reading:

| element top | progress reported |
|---|---|
| 900 → 700 | 0 |
| 650 → 400 | **0.223** |
| 350 → 150 | **0.635** |
| 100 → -100 | **0.836** |
| -150 → -400 | 0.942 |

Flat for 200-250px at a time — and it reports `1` while the block is still BELOW
the viewport. The painted fill is smooth; the value handed back to JS is not.

**Fix:** the milestone observer no longer reads the custom property at all. It
computes progress from GEOMETRY, using the same window the CSS animates over
(`animation-range: entry 0% exit 100%`), which is the function the rAF driver
already had. One shared `computeViewProgress()`, continuous, driver-agnostic, and
in step with the painted line by construction rather than by reading its output.

**Verified after:** milestones now reveal ONE AT A TIME at four distinct scroll
positions — 0 → 1 → 2 → 3 → 4 at element-top 1000 / 750 / 500 / -50 / -300.

⭐ This is the general lesson, not a timeline quirk: **a scroll-driven registered
custom property is for the browser to paint with, not for JS to read back.**
Anything keyed off such a read fires in steps.

## Defect 2 — the align-left rail did not move with its column

Measured before:

| | x |
|---|---|
| connector rail | **16** |
| media slot | **0 → 180** (drawn straight across the rail) |
| milestone dots | **196** |

The rail had always been pinned at `var(--sgs-node-size)` (16px) while the dots sit
in the node COLUMN — the same 107px misalignment already recorded in Addendum 1's
finding A. Widening column 1 to hold the media turned a long-standing
misalignment into a visible collision.

**Fix:** a new `--sgs-timeline-rail-offset` (default `var(--sgs-node-size)`, so
nothing changes without media) which, for an align-left timeline WITH media,
resolves to the node column's centre — derived from the three values that define
the grid (column 1 width + column gap + half the node), so it cannot drift from
the layout the way a magic number would.

**Verified after:** rail centre **205**, node centre **204** — aligned to 1px, and
`mediaCrossesRail: false`.

⚠ Scoped to the has-media case deliberately. Without media, column 1 is `auto` and
there is no expression for its width, so the rail keeps its existing position and
its existing misalignment rather than being moved on a guess. **Addendum 1's
finding A therefore remains open for the no-media case** and still needs a
decision.

## Not a defect — the media sitting flush to the page edge

Measured: the block has `padding-left: 0`, its parent `.entry-content` has
`padding-left: 0`, and the block spans the full 1425px. The probe page drops the
timeline straight into post-content with no container, and per the project's own
rule a block placed straight into a page is intentionally full-width. On a real
page inside a container it is inset. Stated rather than "fixed".

## Why the probes missed both

Defect 2 was measured and REPORTED in Addendum 1 as a 107px misalignment — but as

Both were caught by the owner looking at the page. That is R-31-13 doing exactly
what it is for, and the third time this session that a screenshot or an eye beat

# ADDENDUM 4 — `left` was not a layout, it was `alternating` with the flip removed

Owner's observation: *"Doesn't that left design overlap with the normal variant?
Shouldn't the left variation have all of the content on the right of the timeline
bar?"* Correct on both counts. Screenshot: `timeline-left-vs-gutter.png`.
Probe rebuilt: canary page 3079, eight sections.

## The measurement that proved the duplication

| | rail x | row 1 | row 2 |
|---|---|---|---|
| `alternating` | 713 | date `0→689`, content `737→1425` | **mirrored** |
| `left` (before) | 205 | date `0→180`, content `228→1425` | identical to row 1 |

Both put date left of the rail and content right of it. `left` differed from
`alternating` only by not flipping — so a single row of each was the same shape.

## What the research said (research-check, default tier, 2 agents, 6 sources)

Full finding: `~/.claude/memory/research/2026-08-29-timeline-left-alignment-vs-date-gutter.md`.

**4 of 4 component libraries model "which side the content sits on" and "does the
date get its own gutter" as SEPARATE controls** — MUI `TimelineOppositeContent`,
Ant Design `label` (its LESS source literally switches on a second absolutely
positioned column), PrimeReact `opposite`, Vuetify's `opposite` slot. **None
forces a gutter when you pick `left`.** Welding them together was the defect.

Both patterns are real and named:
- **inline stack** — rail hard left, everything right (Flowbite/Preline default)
- **opposite content / date-gutter** — date in its own fixed column (MUI et al.,
  Preline's separately-named "Side timestamps")

The two agents disagreed on which to ship; the owner chose to split them properly,
which is what every library does.

Supporting: NN/g gazeplots found zig-zag layouts cause wasted fixations; every
vertical timeline collapses to rail-left-single-column on mobile anyway; and a
gutter that flips sides is what tempts the `order`/absolute-position hacks that
break WCAG 1.3.2 meaningful sequence.

## After — measured on the live canary

| section | align | rail x | row 1 | row 2 |
|---|---|---|---|---|
| 1 | alternating | 713 | date `0→689`, content `737→1425` | mirrored |
| 2 | **left (new default)** | **9** | date **and** content `32→1425` | same |
| 3 | **left + date column ON** | 205 | date `0→180`, content `228→1425` | same |
| 5 | left, no media | 9 | date and content `32→1425` | same |

`left` is now a genuinely distinct layout, and the gutter is available on it as an
opt-in rather than being forced.

## ⚠ NEW FINDING — `centre` now duplicates `left`, and needs the owner's decision

| section | align | rail x | row 1 |
|---|---|---|---|
| 2 | left | **9** | date and content `32→1425` |
| 4 | **centre** | **17** | date and content `32→1425` |

Identical column spans; the rails sit 8px apart. `centre` was ALREADY the inline-
stack pattern (node column 1 spanning both rows, date row 1 and content row 2 in

⛔ **Deliberately NOT resolved here.** Retiring or repurposing an alignment value

# ADDENDUM 5 — sparks trailed the head; every visible timeline burned

Owner, on the live probe page: *"The sparkle effect is far behind the
progress:after marker … and additionally the sparkle is always active so multiple
timelines will have the sparkle effect playing even though it should only be the
active timeline."* Both real. The page was NOT stale — this was the deployed code.

## Defect 1 — sparks 304px behind the head

Measured on canary 3079, timeline index 1:

| | value |
|---|---|
| CSS fill fraction | **0.931** |
| head, viewport y | **644** |
| first spark, viewport y | **340** |
| gap | **−304px** |

The head is `::after` on `.sgs-timeline__progress`, placed by CSS at
`calc(var(--sgs-timeline-fill-progress) * 100%)`. `emitHeadSpark()` was instead
handed a JS percentage from `computeViewProgress()`. Two different numbers for the
same point, so they could never agree — and the divergence grows with progress.

**Fix:** the spark is now positioned with the *same CSS expression* the head uses.
The property inherits, so the browser resolves the identical `calc` and the two
coincide BY CONSTRUCTION — on either driver, whatever `animation-range` is set,
with no JS number in the position at all. That also sidesteps the staircase
problem (Addendum 3) rather than working around it.

⚠ Note the split this leaves, deliberately: **position** comes from CSS, while the
**reveal/reached** decisions still come from geometry. Each uses the source that is
correct for it — CSS is where the head actually is; geometry is continuous where
the property read is stepped.

## Defect 2 — two timelines burning at once

Measured: **2 of 8** progress timelines emitting simultaneously, each running its
own rAF loop. The old gate was "block on screen and 0 < progress < 1", which
several timelines satisfy at once on a long page.

**Fix:** N per-instance loops replaced by ONE page-level coordinator that elects a
single active timeline every frame — its head must be on screen, and of those it
is the one nearest the viewport centre. Election is per frame, so the active
timeline changes as the reader scrolls with no handover code, and idle timelines
cost nothing.

## Addendum 6 — the rail's two halves sat 171px apart at mobile (source_sha fc91654b6632ced4)

`.sgs-timeline` draws its rail as TWO elements: the static line is the block's own
`::before`, the animated fill is a separate `.sgs-timeline__progress`. The
`align-alternating` mobile collapse (`style.scss:1039`) moved only the `::before`.

Measured live at 375px on the deployed build, BEFORE:

| Element | x |
|---|---|
| Static connector line (`::before`) | 16px |
| Animated progress fill | **179px** |
| Node dots | 8px |

Three positions for what reads as one rail. The horizontal variant's own mobile
collapse (`:961-981`) moves BOTH halves and is correct; the base horizontal rule at
`:159` even carries the warning — *"The SAME offset as the base track — a second
literal is how the two silently drift apart."* The alternating block ignored it.

**Second defect in the same rule:** the offset was `var(--sgs-node-size)` = 16px, but
column 1 is `auto`, sized to the 16px node, so the dots' centre is at **8px**. The line
sat on the node's right EDGE, not through the dots. `align-left` already derives it as
`calc(var(--sgs-node-size) / 2)` (`:595`).

**Fix:** `--sgs-timeline-rail-offset` is declared ONCE on the alternating mobile block
and both halves read it. Single source of truth, in the block's own existing vocabulary.

## Addendum 7 — viewport reveal re-keyed onto `.is-js`

`:392` hid entries via `[data-reveal-on-scroll]`, an attribute authored into the markup,
so it matched whether or not `view.js` ran — with JS off those entries were unreachable
permanently. The connector reveal (`:1364`) already solved this by gating on `.is-js`,
which only a running script adds. `.is-js` was confirmed present on all 8 timeline roots
in the live DOM before relying on it.

⚠ **The reduced-motion override carries `.is-js` too, and that is load-bearing.** Adding
it to only the hiding rule would put that rule at (0,5,0) against the override's (0,4,0)

## Addendum 9 — a WCAG claim this session got WRONG, corrected before it propagated

Mid-session I told the owner that a horizontal timeline could not use a mobile carousel
because it fails WCAG 1.4.10 Reflow. **That was wrong, and the owner's own instinct
("it basically works the same as a carousel") was right.**

The error: asking whether a timeline qualifies for 1.4.10's *two-dimensional-layout
exception* (maps, diagrams, video, games, data tables), finding it doesn't, and
concluding it fails. **A contained horizontal scroller never needed the exception — it
passes on the main criterion.** W3C publishes **Technique G225**, a *Sufficient*
technique for 1.4.10, describing exactly this pattern; its Example 1 is a product
carousel and its Figure 6 is labelled **Pass**. The Understanding doc states plainly:
*"Reflow does not prohibit web pages from presenting both horizontal and vertical
scrollbars for individual sections of content."*

**The rule to bank: failing to qualify for an exception is not the same as failing the
criterion.** Check the Sufficient Techniques list before declaring a common pattern
non-conformant.

Two criteria that DO bite a horizontal scroller, and which the first pass missed:

- **SC 2.1.1 Keyboard** — a native overflow scroller with no focusable children cannot
  be reached or operated by keyboard in Chromium before 127, and in Safari *at all*.
  Fix: `tabindex="0"` + `role="region"` + accessible name, scoped to the breakpoint
  where it actually scrolls.
- **SC 2.5.7 Dragging Movements** — native `overflow` scrolling is **exempt** because the
  user agent provides the mechanism. Content that *suppresses* native scrolling and
  implements its own is **not** exempt. That is the precise boundary between a native
  `scroll-snap` carousel (conformant) and a GSAP `ScrollTrigger` pinned/scrubbed
  horizontal section (inherits 2.5.7 + 2.5.1 obligations) — and it decides the
  implementation for any future horizontal-timeline work.

## Addendum 19 — Step 2: the marker moves to a reading line, and two fill drivers become one (source_sha ffb7ee51045367dd)

**What changed.** `--sgs-timeline-fill-progress` was mapped to the block's transit through the
viewport (`animation-range: entry 0% exit 100%`, spanning `viewportHeight + blockHeight`). It is now
computed from a READING LINE:

```
chrome      = chromeOffsetPx()                                   // live sticky-header height, 0 when unpinned
readingLine = chrome + 0.38 * ( innerHeight - chrome )           // 38% of the USABLE viewport
fill        = clamp( (readingLine - blockTop) / blockHeight, 0, 1 )
```

The head dot is positioned at `top: calc(var(--sgs-timeline-fill-progress) * 100%)` of the rail
(three rules, all identical: `style.scss` vertical / horizontal / mobile). So `marker y = blockTop +
fill × blockHeight = readingLine` — **the dot lands on the reading line by construction, with no
`position: sticky` anywhere.** Sticky was considered and rejected: the dot IS the fill head, and
pinning it separately would detach it from the fill and float it in an unfilled line, while adding a
second mechanism doing the first one's job.

`CSS.supports` early-return is gone from `view.js`. One rAF driver now runs everywhere.

**Two candidate fixes were tried against the live page first, and BOTH changed nothing:**

1. `align-content: stretch` — no effect. The tracks already summed to exactly 720px, so there was
   no free space to distribute. My stated diagnosis ("176px of dead space") was wrong: the space
   was not dead, it was the date's row.
2. `grid-template-rows: auto 1fr` at (0,2,0) — no effect, and this is the one that matters.

⭐ **A losing rule is indistinguishable from an absent one, and this build has now hit that three
times.** Enumerating every rule that actually matched the element found the owner:

| Selector | Specificity | Declares |
|---|---|---|
| `.sgs-timeline--vertical .sgs-timeline__entry` | (0,2,0) | `grid-template-rows: auto` |
| **`.sgs-timeline--media-under.sgs-timeline--vertical.sgs-timeline--content-alternating .sgs-timeline__entry--has-media`** | **(0,4,0)** | **`grid-template-rows: auto auto` ← the owner** |
| the attempted fix | (0,2,0) | out-ranked, silently |

Same shape as D894, which cost a session: a `--media-under` rule out-ranking a newer rule.

**The fix repeats its own class once to reach (0,5,0)** — a deterministic one-class margin over the
(0,4,0) owner. Matching it at (0,4,0) and relying on source order would work today and flip the day
any rule is appended elsewhere; the carousel block lower in this file uses the same device for the
same reason and says so. Repeating the class also covers `same-side` by construction instead of
hand-listing every content-layout combination.

Post-fix, deployed and re-measured: rows `19.6px / 700.4px`, media 700px, `slot === entry − date`
exactly.

### A second finding, from the build gate rather than the browser

`inspector-scan` rule 03 (dense-panel-candidate) failed the build: adding `milestoneSize` to the
**Layout** panel took it from 6 controls to 7, one over the threshold, and the ratchet reds on a
single new finding. The design doc had specified Layout as its home; the client-experience rater had
flagged exactly this risk and been right.

Moved into **"Milestone size & media"** — the panel named for this setting, where a client would
look for it, and where it also sits directly above the control it gates. Layout back to 6, gate
green. Panel COUNT unchanged at 8, so the prior sign-off's ceiling still holds.

### The cross-track DB reseed the design predicted was NOT needed

§8 said three new attributes would need `/sgs-update` to reseed `block_attributes` — a shared-DB
action that reds every other track's build. `check-element-manifest-conformance` did fail, and
regenerating `attr-role-map.json` alone did **not** clear it (the map derives from the DB, which
does not know a brand-new attribute).

Root cause was neither: the `entry` element declared `"clusters": []`, so an attrMap entry on it had
no cluster member to be claimed by. Declaring `"clusters": [ "layout" ]` cleared it — `UNCLASSIFIED:
0`, exit 0, no DB write, no cross-track disruption. `milestoneMinHeight` and `entryGap` now route as
`layout/css:min-height` and `layout/css:margin-bottom`.

⚠ **A first draft invented a bare `variant` attrMap key** for `milestoneSize`. Measured across the
tree: 46 of the 47 non-`css:`/`native:` attrMap keys are `anim:*`, and `variant` had zero precedent
and no reader in either the audit or `sgs-update`. Removing it changed the gate's output **not at
all**, confirming it was inert. `milestoneSize` is a layout-MODE selector and now sits in the
ORPHAN:BY-DESIGN bucket the audit already uses for `connectorStyle`, `iconPosition`, `tileShape` —
where its siblings `orientation`/`contentLayout`/`mobileLayout` already are.

## Addendum 21 — Step 4a: the root becomes a `<div>`, and the `<ol>` moves inside it (source_sha a61fa3893dcb7210)

**Why.** `fx-horizontal-panel.js:69` resolves its track with `:scope > [data-sgs-fx-track]` — a
single DIRECT child. The root was an `<ol>`, and an `<ol>` may contain only `<li>`/`<script>`/
`<template>`; the block's own comment already states that rule, which is why the progress connector
is itself an `<li>`. No valid markup could satisfy the effect. Owner's call: change the root.

**Shape.** `<div class="sgs-timeline …">` (wrapper attrs + every modifier class) → `<div
class="sgs-timeline__track">` → `<ol class="sgs-timeline__list">` → the unchanged `<li>` entries
with the progress `<li>` still last. Track emitted ALWAYS, not conditionally — one shape beats two
code paths.

**List semantics preserved, which was the whole risk.** Measured: `lists: 1` per timeline across all
eight on page 3079, five `<li>` children, progress last, track carries no role. A screen reader
hears one list with N items — exactly as before. The two rejected alternatives (a `<div>` inside the
`<ol>`, or an `<li>` wrapping the other `<li>`s) would each have produced "list, 1 item".

**Two couplings that would have broken silently, both handled in the same commit:**

- The mobile carousel made the ROOT the horizontal scroller, so after the restructure its entries
  would have stopped being flex items. The layout/scroll properties moved onto `.sgs-timeline__list`
  while the modifier class stays on the root — (0,5,0) → (0,6,0), so the deliberate 5x class
  repetition keeps its margin over the (0,5,0) ceiling rather than falling back to source order.
- `initCarouselA11y()` set `tabindex`/`aria-label` on the root and listened for `scroll` there.
  A `tabindex` on a non-scrolling wrapper is a focus stop that goes nowhere and the listener would
  never fire, so both now target the list.

### ⛔ A REGRESSION THE STRUCTURE CHECKS PASSED, CAUGHT ONLY BY A GEOMETRY BASELINE

First deploy of 4a: root a `<div>` ✅, track present ✅, list a direct child ✅, entries are list
children ✅, progress last ✅, one list ✅, no role on the track ✅. Seven green structural assertions.

| | Pre-restructure | After 4a | After the fix |
|---|---|---|---|
| Entry columns | 688.5px 16px 688.5px | **668.5px 16px 668.5px** | 688.5px 16px 688.5px |
| Node centre | 712.5 | **732.5** | 712.5 |
| Rail centre | 712.5 | 712.5 | 712.5 |

**The dot sat 20px off its own line** — the same "two halves disagree" defect the mobile-rail fix
(Addendum 6) exists to close.

Cause: while the root WAS the `<ol>`, `.sgs-timeline--vertical`'s `padding: … 0` / `margin: 0` /
`list-style: none` killed the UA list defaults as a side effect. Moving the `<ol>` inside a `<div>`
left those resets on the wrapper and the browser's default `padding-inline-start: 40px` returned.
Verified directly: `paddingInlineStart` read **40px**, and injecting the reset into the live page
took it to 0px with columns and node centre snapping back to the baseline exactly.

⭐ **No structural or accessibility check could have caught this.** It was found only by comparing
geometry against numbers recorded before the change — which existed because Addendum 18 measured
them. That is the argument for baselining before restructuring, not after.

**Full regression sweep, all 8 timelines on page 3079, post-fix:** every list at `padding: 0`, one
list each; alternating / same-side / carousel all back to `688.5px 16px 688.5px` with node and rail
identical at 712.5.

⚠ **A pre-existing 1px offset found while sweeping, NOT introduced here.** The four `single-column`
timelines put the node centre 1px left of the rail centre (8 vs 9; 204 vs 205). That variant's rail
uses `left: var(--sgs-timeline-rail-offset, var(--sgs-node-size)); transform: none` — the rail's
LEFT EDGE lands on the node's centre offset, so its own 2px width is uncorrected, unlike
alternating/same-side which centre with `translateX(-50%)` and align exactly. The rule is untouched
by this session's diff. Recorded, not fixed here.

**Deliberately NOT in this step:** `data-sgs-fx-track`, the `scrollEffect` attribute, and any effect
wiring. The structure is now the shape `fx-horizontal-panel` expects; step 4b attaches to it.

## Addendum 22 — Step 4b: the scrollEffect picker, and the horizontal effect finally moving (source_sha 450e0e6740f8280f)

**What shipped.** `scrollEffect`: `basic` (today's fade reveal) · `scrub` ("Move with the scroll") ·
`pinned-journey` ("Pin and reveal") · `pinned-horizontal` ("Pin and slide sideways"). Options are a
function of `orientation` — hidden, never disabled. No new fx slug: the existing `scrub` /
`pin-scrub` / `horizontal-panel` modules are reused, and `providesNatively` removes all three from
the generic "Scroll & effects" picker so the block has ONE surface instead of two that can fight.

### Result — all four verified on the deployed build (page 3141)

| effect | `data-sgs-fx` | disable-mobile | entries revealed | opacity |
|---|---|---|---|---|
| basic | (none) | — | 4/4 | 1 |
| scrub | `scrub` | ✅ | 4/4 | 1 |
| pinned-journey | `pin-scrub` | ✅ | 4/4 | 1 |
| pinned-horizontal | `horizontal-panel` | — (self-gates) | 12/12 | 1 |

**D896 guard holds.** `pinned-journey` emits NO `data-reveal-on-scroll`, so the
`[data-reveal-on-scroll].is-js … { opacity: 0 }` rule cannot match and a suppressed driver cannot
leave entries invisible. Positive control: `basic` DOES emit it and reveals normally.

⚠ **A false alarm worth recording.** At scroll 0 the lower timelines read opacity 0 and 0/4 revealed
— which looks exactly like D896. It was the viewport reveal simply not having reached them.
Re-measured by scrolling each into view: 4/4 everywhere. **A reveal-on-scroll block cannot be

### ⛔ THE ROOT RESTRUCTURE WAS NECESSARY BUT NOT SUFFICIENT — and my own design was wrong

Step 4a created `<div class="sgs-timeline__track">` for `fx-horizontal-panel` to attach to. It
attached: module loaded, track marked, ScrollTrigger created a pin-spacer. **And it slid nothing.**
Measured with 12 entries and the list genuinely overflowing (scrollWidth 2640 vs clientWidth 1410):
**0px of travel across 30 scroll samples.**

Reading the module rather than guessing again found the cause. It imposes TWO constraints:
1. `resolveTrack()` matches `:scope > [data-sgs-fx-track]` — the marked element must be a DIRECT
   child of the element carrying `data-sgs-fx`.
2. `getTravelDistance()` measures the marked element's own `children` as the panels and **returns 0
   when there are fewer than two** — the module's own comment calls that the correct outcome.

The track div satisfied (1) and broke (2): its only child was the `<ol>`. One panel, zero travel.

**The fix removed the div entirely.** Marking the `<ol>` itself satisfies both — it is a direct child
of the root AND its children are the `<li>` panels. That is legal only because Step 4a made the root
a `<div>`; the original blocker was an `<ol>` ROOT. So the restructure was still required — the
intermediate wrapper never was.

**Post-fix, measured:** list marked ✅, direct child of root ✅, 12 panel children, width 2640
(`max-content`), **22 distinct positions and 2,266px of travel** (0 → −304 → −964 → −1624 → −2266)
while the control timeline's list never moved. Screenshot `screenshots/timeline-pinned-horizontal-midslide.png`
shows milestones 6–11 mid-slide with partial cards at both edges.

⚠ Native scrolling and the pinned effect are MUTUALLY EXCLUSIVE and now made so: the horizontal
timeline is normally its own `overflow-x: auto` scroller (which is what meets SC 2.5.7 with no JS),
and leaving that on kept the list viewport-width so GSAP slid a box whose content could not follow.
Keyed off `[data-sgs-fx="horizontal-panel"]` — the attribute is already the single source of truth.

### ⛔ A SECOND STEP-4A REGRESSION, FOUND ONLY BECAUSE THE EFFECT DIDN'T MOVE

`.sgs-timeline--horizontal` set `display: flex` + `overflow-x: auto` on the ROOT. After 4a the
entries are grandchildren, so **horizontal orientation stopped laying out entirely** — measured at
1440px: track 394px wide, list `display: block`, four 394px entries stacked vertically.

This is the identical coupling as the mobile carousel, which WAS re-pointed in the 4a commit. It was
missed because only the carousel was looked for. The row now lives on `.sgs-timeline__list`, with
`position: relative` / padding / `--sgs-timeline-h-line-top` staying on the root where the `::before`
rail and `.sgs-timeline__progress` are positioned against it. The ≤767px override that UNDOES the
row had the same problem and follows it.

Post-fix: list `display: flex`, `flex-direction: row`, track full width, four entries at one top
(2630) and four distinct lefts (0/220/440/660).

⭐ **The lesson: a shared coupling is rarely singular.** The 4a brief named the carousel explicitly
and it got fixed; horizontal had the same shape and no one enumerated for it. The question to ask
was "what ELSE makes the root a layout container?", which a single grep answers.

### Mobile — inert, and one more content-clipping fix

At 375px: no effect initialises (no transforms, no pin-spacers, no GSAP objects on any of the four),
horizontal collapses to a column, all 12 entries reach opacity 1 when scrolled to, no horizontal
page scroll.

⚠ **First attempt clipped content.** The `width: max-content` / `overflow: hidden` pair is CSS and
applied at every width even though the effect never runs below 768px: measured at 375px the list was
**461px inside a 375px viewport**, clipped by the root, cutting ~86px off every milestone with no
scrollbar to reach it. Now gated to `min-width: 768px`. Re-measured: list 360px, root 360px, zero
entries clipped. Degrade to MORE content, never less.

### ⚠ A CLAIM IN THE DESIGN DOC THAT IS FALSE, CORRECTED HERE

§9 required "**no GSAP loads at 375px**". Measured: `fx-scrub.js`, `fx-pin-scrub.js`,
`fx-horizontal-panel.js` and `gsap-scrolltrigger.js` **are all still enqueued on mobile**. They
download and do nothing.

The suppression is BEHAVIOURAL, not byte-level, and cannot be otherwise as built: the registry
sniffs `data-sgs-fx` out of rendered markup server-side at `render_block` priority 99, where the
viewport is unknowable, while `data-sgs-fx-disable-mobile` is a client-side gate inside
`bootEffect()`. This is framework-wide behaviour for every block using that flag, not something this
change introduced — but the design doc asserted a stronger guarantee than the framework provides,
and that assertion is withdrawn.
