# sgs/buybox — product-page fixture built, scroller proven, toggle shipped in source but NOT deploy-verified (register Step 3)

## Why this could not be captured on 2026-07-31 originally

`sgs/buybox` requires a WooCommerce variable product IN CONTEXT — `render.php` falls back
to core WC blocks when `postId` resolves to nothing or a non-variable product, so it
renders no `.sgs-buybox` markup at all on an ordinary page. The shared roster canary page
carried two placeholder `sgs/buybox` instances precisely to record that "renders nothing"
honestly rather than claim a capture. This step's job was to build the real fixture the
capability actually needs.

## Fixture built

Used the existing variable product **540** ("Mama's Test Box — 48 SKU fixture",
`https://…/product/mamas-test-box-48-sku-fixture/`) — no new product needed, it already
carries per-variation image galleries via `_sgs_variation_gallery` postmeta (FR-30-10
Step-10a / A4). Its DEFAULT variation (confirmed live via the rendered
`data-wp-context.selectedVariationId` = **541**, not 576 as first assumed from
alphabetic post order — read the live context before acting, did not guess) originally
carried only 3 gallery images. At `.sgs-buybox .product-card__thumbs`'s CSS (64px thumb +
0.5rem gap, `flex-wrap:nowrap`, `overflow-x:auto` — confirmed genuine scroller CSS,
`buybox/style.css:571-579`), 3 thumbs (208px) sit well inside the ~644px gallery column
at 1440px viewport — no overflow. Expanded variation 541's `_sgs_variation_gallery`
postmeta to **10** real media-library image IDs (reused existing product photography,
no fabricated assets) via `wp post meta update` (a metadata write, not the blocked `wp
post update` post-content path) — 10 x 64px + 9 x 8px gap = 712px > the measured 644px
column width.

## Session 2 — the deploy deadlock, and the injection-based measurement (2026-07-31, later same day)

**Why still no deploy.** Two safety gates correctly deadlock on this block: the pre-commit
visual-diff gate refuses to commit until `verdict: PASS` (this file), and the deploy
dirty-tree gate refuses to deploy while `buybox` is uncommitted (`--allow-dirty` is banned
project-wide since D336). To commit needs a PASS; to reach the canary for evidence needs a
deploy; deploy needs a commit. Circular — so the orchestrator directed a non-destructive
**live-injection measurement** instead of a deploy: prove the RUNTIME independently of
proving the EMIT.

**Method — nothing on the server was touched.** Using an isolated Playwright process
(`page.mouse.down/move/up`, NOT the shared Chrome DevTools MCP session, which has no
trusted pointer primitive):

1. Navigated to the live PDP with a cache-busting query param.
2. Measured baseline BEFORE any injection.
3. Injected `data-sgs-fx="draggable"` onto `.product-card__thumbs` client-side — exactly
   the attribute `render.php`'s new `$buybox_thumbs_fx_attr` logic emits.
4. **Discovered and worked around a real gap in the naive injection plan:**
   `SGS_Motion_Registry` decides which effect JS bundles to enqueue by scanning
   SERVER-RENDERED markup for `data-sgs-fx` before the page ever loads. Since this
   product's real `render.php` doesn't (pre-deploy) emit the attribute, and no other block
   on this page uses the `draggable` effect, **the runtime module was never enqueued on
   this page at all** — confirmed: `window.gsap` undefined, zero matching `<script>` tags.
   `bootEffect()` also only ever runs one `querySelectorAll` at module-evaluation time (no
   `MutationObserver`), so a late-injected attribute would be invisible to it regardless.
   Attribute injection alone therefore could not have exercised anything — it would have
   produced a false "nothing happens" reading with no diagnostic value.
5. Fixed this properly, not by reimplementing the effect: confirmed the actual compiled
   runtime files are already live static assets on this canary (200 OK from an earlier
   Wave C deploy — `build/shared/effects/gsap/fx-draggable.js`,
   `build/vendor-modules/gsap-{core,draggable,inertia}.js`,
   `build/shared/effects/gsap/provider.js`), built a browser import map matching
   `class-sgs-motion-registry.php`'s own dependency table
   (`@sgs/gsap` / `@sgs/gsap-draggable` / `@sgs/gsap-inertia` / `@sgs/motion-provider`),
   loaded the REAL deployed `fx-draggable.js` module, and called its real exported
   `initDraggable(el)` directly on the injected element — the identical call
   `bootEffect()` makes internally. This tests the shipped runtime, not a rewrite of it.

### What this proves, and what it explicitly does NOT

**Proves:** the shipped `fx-draggable.js` runtime, when the exact attribute our PHP change
emits is present on `.product-card__thumbs`, genuinely recognises it as a draggable
scroller, sets `cursor:grab`, and moves `scrollLeft` in response to a real trusted pointer
gesture — with zero interference to the variant picker's own click handling immediately
after a drag on the same element.

**Does NOT prove:** that `render.php` / `gallery-col.php` actually emit
`data-sgs-fx="draggable"` in a real server render. That PHP path has never executed this
session — no build, no deploy, ever. The attribute was hand-set via `page.evaluate()`, not
produced by the block's own render output. The logic is short and readable
(`$buybox_thumbs_fx_attr = ' data-sgs-fx="draggable"'` echoed via `<?php echo
$buybox_thumbs_fx_attr; ?>` in `gallery-col.php`, gated on the same
`! $buybox_thumbs_hidden` condition the strip's own visibility already uses), but "reads
correctly" is not "observed live" — R-31-11 (verify rendered output, not internal
metrics) still applies to the emit half of this feature.

**Also NOT proven:** the block-editor "Gallery interaction" `ToggleControl` panel
(`edit.js`) — zero editor-surface testing happened this session (frontend only). And the
momentum "two-arm control" was not comparatively verified against a live `sgs/gallery`
instance — the drag here was short, `endScrollLeft` stayed at 53 with no observed coast,
which is consistent with low release velocity on a short synthetic drag rather than
evidence the momentum layer is broken, but it is not a positive proof either way.
