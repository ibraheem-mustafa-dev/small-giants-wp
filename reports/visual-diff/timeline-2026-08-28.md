## ⛔ CORRECTION — this report first claimed "6 of 7 PASS". That was WRONG.

An earlier revision of this file recorded a PARTIAL verdict on the strength of the computed-style
measurements below. **Then a screenshot was opened, and the connector was not there at all.**

`getComputedStyle` reported `display: block`, the correct per-instance `stroke`,
`stroke-dasharray: 1px`, and a `stroke-dashoffset` animating smoothly through
`0.992 → 0.753 → 0.345 → 0.108`. Every one of those numbers was true. The element they described
measured **2px × 2px inside a 383px-tall timeline** and painted zero pixels.

**Cause (mine, not the drivers'):** an `<svg>` carrying a `viewBox` has an INTRINSIC ASPECT RATIO
and sizes like a replaced element. Given an explicit `width: 2px` and no explicit height, the
height resolved from the 1:1 ratio to 2px — `top: 0; bottom: 0` does not stretch a replaced
element with an intrinsic ratio, and `preserveAspectRatio="none"` does not help (it governs how
CONTENT scales inside the viewport, not how the element is sized). The build plan specified
`height: 100%`; it was dropped during implementation.

**Worse than not shipping it:** because the `::before` suppression works correctly, switching the
feature ON currently REMOVES the connector line rather than animating it. Blast radius is
contained — the attribute defaults to `false`, and this is the canary, not a client site.

**Why every gate and the first probe pass missed it:** all 69 prebuild gates are static; the probe
asserted computed style and `display`, never painted geometry. **A style check cannot see a
zero-area element.** The probe now asserts the SVG spans ≥60% of the block along its own axis (a
deliberately loose floor — the real defect was 0.5%), so this exact failure cannot pass again.

This is the `a-green-measurement-is-not-fidelity` rule and R-31-13 in one incident: the numbers
were internally consistent, correct, and describing nothing. **Bean's eye — here, one screenshot —
was the only thing that caught it.**

## What changed

`sgs/timeline` gains an optional scroll-driven connector: the line joining the milestones fills
progressively 0→1 as the block scrolls through the viewport. Spec 38 **FR-38-35**, Tier V,
block-private. Commit `72825d07c`; the 767px fix below is a follow-up commit.

Contract: one `@property`-registered number `--sgs-timeline-fill-progress`, consumed once as
`stroke-dashoffset: calc(1 - var(…))` on an `aria-hidden` SVG path with `pathLength="1"`. Two
drivers write it — native `@supports (animation-timeline: view())`, and a vanilla rAF loop in
`view.js` which is the PRIMARY path for Firefox (no `animation-timeline` in any stable build).

## Fixture — 5 instances, deliberately including 2 negative controls

vertical ON (accent) · vertical OFF · vertical align-left ON (primary) · horizontal ON (accent) ·
horizontal OFF. **The two OFF instances are the negative control**: without them, "one line
renders" is unfalsifiable — a rule that hid every line would pass just as well.

## Assertions — stated before measuring

1. Fill tracks scroll **smoothly**, not a 0→1 jump-cut. *(The C1 regression test.)*
2. **Both** drivers work, including the forced `@supports` negative branch.
3. Reduced motion renders the line **fully filled**, never empty. *(C7.)*
4. **Exactly ONE line** in every on/off × orientation combination. *(C3.)*
5. Correct at 375 / 768 / 1440, including the 767px horizontal→vertical re-layout.
6. Fill colour is per-instance and token-driven.
7. `stroke-dasharray` is actually applied. *(C11.)*

## Results

### ✅ 1 — Smooth fill, NOT a jump-cut (the C1 regression test)

`strokeDashoffset` sampled at 8 scroll positions, native driver:

```
sgs-tl-2da0410a  0:1.000  0.15:1.000  0.3:0.814  0.45:0.360  0.6:0.124  0.75:0.023  0.9:0.000  1:0.000
sgs-tl-8b0c73e4  0:1.000  0.15:1.000  0.3:1.000  0.45:1.000  0.6:0.684  0.75:0.221  0.9:0.041  1:0.003
```

5–6 **distinct** values per instance, 3–4 of them strictly between 0 and 1. A discrete jump-cut —
the failure mode an unregistered custom property produces — would show exactly two values. It does
not. **`@property` is doing its job.**

⚠ Note the method: sampling only the endpoints would have PASSED a jump-cut. The intermediate
count is the assertion; the endpoints are not.

### ✅ 2 — Both drivers, negative branch forced

`CSS.supports('animation-timeline', …)` stubbed to `false` in an `addInitScript` **before any page
script runs**, forcing the `@supports` negative branch and the rAF path:

```
native    0.3:0.814  0.45:0.360  0.6:0.124  0.75:0.023
forced-JS 0.3:0.808  0.45:0.360  0.6:0.124  0.75:0.022
```

Two independently-written implementations agree to ~3 decimal places. That is a much stronger
result than either passing alone.

### ✅ 3 — Reduced motion = FULLY FILLED

```
sgs-tl-683bd668 progress=true  offset=0%  var=1  ::before=none
sgs-tl-2da0410a progress=true  offset=0%  var=1  ::before=none
sgs-tl-8b0c73e4 progress=true  offset=0%  var=1  ::before=none
sgs-tl-e198b476 progress=false offset=null var=0 ::before=block   <- control, untouched
sgs-tl-2620cb6d progress=false offset=null var=0 ::before=block   <- control, untouched
```

`offset: 0` = fully drawn, and the controls are unaffected. C7 satisfied, and the
`animation: none !important` is doing its job (an animation would otherwise outrank the
declaration).

### ✅ 4, 6, 7 — One line, per-instance colour, dasharray applied

```
OK  sgs-tl-683bd668 progress=true  ::before=none  visiblePaths=1  dasharray=1px stroke=rgb(245,208,80)
OK  sgs-tl-e198b476 progress=false ::before=block visiblePaths=0  dasharray=null
OK  sgs-tl-2da0410a progress=true  ::before=none  visiblePaths=1  dasharray=1px stroke=rgb(230,138,149)
OK  sgs-tl-8b0c73e4 progress=true  ::before=none  visiblePaths=1  dasharray=1px stroke=rgb(245,208,80)
OK  sgs-tl-2620cb6d progress=false ::before=block visiblePaths=0  dasharray=null
```

`::before` is `none` **iff** the progress class is present — the C3 double-render check, with the
controls proving the rule discriminates. Two different strokes (accent vs primary) confirm the
colour control writes real per-instance values. `dasharray=1px` confirms C11 landed; without it
`stroke-dashoffset` would be inert and the line permanently full.

Colour also confirmed in the **lifted** stylesheet, not the page HTML — SGS block CSS is lifted to
`uploads/sgs-css/`, so a page-HTML grep proves nothing:
`--sgs-timeline-fill-colour:var(--wp--preset--color--accent)` on the ON instances, and **absent** on
both OFF instances.

### ❌ 5 — 375px horizontal rendered TWO paths (found live, fixed, awaits redeploy)

⚠ Read this together with the correction at the top: this defect is real and was fixed, but the
same instance was ALSO painting nothing, so `visiblePaths=2` meant two invisible paths.


```
 375px sgs-tl-8b0c73e4 horizontal=true  visiblePaths=2   <- DEFECT
 768px sgs-tl-8b0c73e4 horizontal=true  visiblePaths=1
1440px sgs-tl-8b0c73e4 horizontal=true  visiblePaths=1
```

**A doubled line at mobile — the exact defect the `::before` suppression exists to prevent,
reintroduced by specificity alone.** At ≤767px the horizontal timeline re-lays out vertically, so
the override must swap which path shows. The base orientation rule nests the path inside
`.sgs-timeline__progress` → `(0,3,0)`; the override sat one level shallower → `(0,2,0)`. The
override LOST, so the horizontal path never hid, while the vertical path's own `(0,2,0)` rule beat
the `(0,1,0)` base hide and switched on. Both visible.

Fixed by nesting the override inside `.sgs-timeline__progress` so both are `(0,3,0)` and source
order decides, with the measured symptom recorded in a comment so the depth is not "tidied" away.

⛔ **No gate caught this** — not the 69 prebuild gates, not the inline-styling audit, not
dead-controls. It is a cascade-resolution defect, visible only in a real browser at a real width.
This is R-31-13 earning its place: a green measurement is not fidelity.

  tightening to something like `contain`, but that is a look decision, not a correctness one.
