## ⛔ CORRECTION — this report first claimed "6 of 7 PASS". That was WRONG.

An earlier revision of this file recorded a PARTIAL verdict on the strength of the computed-style
measurements below. **Then a screenshot was opened, and the connector was not there at all.**

`getComputedStyle` reported `display: block`, the correct per-instance `stroke`,
`stroke-dasharray: 1px`, and a `stroke-dashoffset` animating smoothly through
`0.992 → 0.753 → 0.345 → 0.108`. Every one of those numbers was true. The element they described
measured **2px × 2px inside a 383px-tall timeline** and painted zero pixels.

**Cause (mine, not the drivers'):** an `<svg>` carrying a `viewBox` has an INTRINSIC ASPECT RATIO
and sizes like a replaced element. Given an explicit `width: 2px` and no explicit height, the
height resolved from the 1:1 ratio to 2px — `top: 0; bottom: 0` does not stretch a replaced
element with an intrinsic ratio, and `preserveAspectRatio="none"` does not help (it governs how
CONTENT scales inside the viewport, not how the element is sized). The build plan specified
`height: 100%`; it was dropped during implementation.

**Worse than not shipping it:** because the `::before` suppression works correctly, switching the
feature ON currently REMOVES the connector line rather than animating it. Blast radius is
contained — the attribute defaults to `false`, and this is the canary, not a client site.

**Why every gate and the first probe pass missed it:** all 69 prebuild gates are static; the probe
asserted computed style and `display`, never painted geometry. **A style check cannot see a
zero-area element.** The probe now asserts the SVG spans ≥60% of the block along its own axis (a
deliberately loose floor — the real defect was 0.5%), so this exact failure cannot pass again.

This is the `a-green-measurement-is-not-fidelity` rule and R-31-13 in one incident: the numbers
were internally consistent, correct, and describing nothing. **Bean's eye — here, one screenshot —
was the only thing that caught it.**

## What changed

`sgs/timeline` gains an optional scroll-driven connector: the line joining the milestones fills
progressively 0→1 as the block scrolls through the viewport. Spec 38 **FR-38-35**, Tier V,
block-private. Commit `72825d07c`; the 767px fix below is a follow-up commit.

Contract: one `@property`-registered number `--sgs-timeline-fill-progress`, consumed once as
`stroke-dashoffset: calc(1 - var(…))` on an `aria-hidden` SVG path with `pathLength="1"`. Two
drivers write it — native `@supports (animation-timeline: view())`, and a vanilla rAF loop in
`view.js` which is the PRIMARY path for Firefox (no `animation-timeline` in any stable build).

same instance was ALSO painting nothing, so `visiblePaths=2` meant two invisible paths.


```
 375px sgs-tl-8b0c73e4 horizontal=true  visiblePaths=2   <- DEFECT

1440px sgs-tl-8b0c73e4 horizontal=true  visiblePaths=1
```

**A doubled line at mobile — the exact defect the `::before` suppression exists to prevent,
reintroduced by specificity alone.** At ≤767px the horizontal timeline re-lays out vertically, so
the override must swap which path shows. The base orientation rule nests the path inside

override LOST, so the horizontal path never hid, while the vertical path's own `(0,2,0)` rule beat
the `(0,1,0)` base hide and switched on. Both visible.

Fixed by nesting the override inside `.sgs-timeline__progress` so both are `(0,3,0)` and source
order decides, with the measured symptom recorded in a comment so the depth is not "tidied" away.

⛔ **No gate caught this** — not the 69 prebuild gates, not the inline-styling audit, not
dead-controls. It is a cascade-resolution defect, visible only in a real browser at a real width.

## Update — rebuilt on a mask, with glow + head + sparks (same day)

**Bean's decision (both points):** ship the fill as a CSS **mask** now and bring the SVG path in at
Stage B when curved vine/tree connectors actually need it; and build **all three** effects now.

### Why the SVG route was abandoned for Stage A — three defects, one root cause

A unit `viewBox` stretched non-uniformly, which is what QC correction C9 prescribed to avoid a JS
resize rebuild. Measured:

1. **`vector-effect="non-scaling-stroke"` resolves dash lengths in SCREEN space**, defeating
   `pathLength="1"` normalisation completely — it painted a **1px dotted line** (460 alternating
   runs) with no relationship to progress at all.
2. Removing `vector-effect` fixes the maths but the non-uniform transform then **doubles the stroke
   to 4px** and leaves a 20px wraparound stub.
3. The same viewBox sized the SVG **2px × 2px** (the zero-area bug at the top of this report).

**C9's no-JS escape hatch is therefore closed.** The real fork was never "mask vs SVG" — it was
"mask, no JS, exact" vs "SVG *plus* a JS ResizeObserver to generate path coordinates". Stage B will
pay that JS cost knowingly, at its own design gate.

### Measured, against the compiled stylesheet and the real markup

| config | p=0 | 0.25 | 0.5 | 0.75 | 1 | box |
|---|---|---|---|---|---|---|
| vertical / alternating | 1% | **26%** | **51%** | **76%** | 100% | 2×584 |
| vertical / left | 2% | **26%** | **51%** | **76%** | 100% | 2×584 |
| horizontal | 2% | **26%** | **51%** | **76%** | 100% | 600×2 |

(The consistent +1% is the head dot's own pixels. Head measured 12×12 in every case.)

Glow + head measured separately: **head error 0px at every progress value**, glow halo 8px — the
blur radius, intended, and it does not leak past the head.

⚠ **A false failure the harness produced first, worth recording:** horizontal initially read
`box=2x208` (vertical geometry) and reported DRIFT. The viewport was 700px — *below* the 767px
breakpoint — so horizontal was correctly re-laying out to vertical and the harness was walking the
wrong axis. The code was right; the test was wrong. Re-run at 1100px, it passes.

### Two structural fixes that came out of the rebuild

- **The progress element is now a `<li>`, emitted LAST.** It was an `<svg>` emitted FIRST, which is
  invalid (`<ol>` may only contain `<li>`/`<script>`/`<template>`) **and** shifted every entry's
  `:nth-child` index by one — measured: `firstEntry is nth-child(2)` with progress on vs `(1)` off.
  `:nth-child(odd|even)` drives the alternating layout, so that is a real inversion risk.
  ⚠ The direct test for visible inversion was **vacuous** — both the progress instance and the
  control measured `RRRR` (no alternation on that page at all), so it could not have detected a
  flip. Emitting last is a *cause-agnostic* fix: correct whether or not the inversion was visible.
- **The mask lives on the child layers, not the container** — a mask applies to an element's
  pseudo-elements and children too, so masking the container would have clipped the head dot in
  half exactly at the progress boundary.

### Effects — what shipped and why

- **Glow:** a wider, blurred duplicate layer sharing the *same* mask declaration (via a Sass
  placeholder), so it cannot desync from the crisp fill. **Blur is set once and never animated** —
  animating `filter`/`box-shadow` blur per frame is a documented cross-engine jank source (WebKit
  #22102, Mozilla #1514384 where the shadow is visibly *clipped* mid-animation, Safari flicker in
  mdn/browser-compat-data #17726).
- **Head:** a 12px dot with a **static** `box-shadow` halo, positioned from the same number. Repaint
  cost scales with blur radius × area, so the halo belongs on a small dot, never smeared down a
  full-height trail.
- **Sparks:** short-lived 3px DOM elements on transform+opacity only, self-removing on
  `animationend`, rate-limited to one per 60ms. **No particle library** — tsparticles is 20-100KB
  against a 50KB page budget; canvas-confetti is built for one-shot bursts, not a continuous trail.

### Accessibility

- **SC 2.2.2 does not engage, and the spark gate is what keeps it that way.** Sparks spawn ONLY
  while progress is actually changing (`delta >= 0.004`). Motion that continued while the user sat
  still would be *autonomous*, and autonomous motion past five seconds owes a pause control. No
  scroll, no sparks, nothing owed. This gate is a requirement, not an optimisation.
- **Reduced motion:** glow and head stay (they carry the journey's state); **sparks switch off
  entirely** — they are pure decoration. Removing the glow/head instead would be
  `degrade-to-more-content-never-less` in reverse.

### Still outstanding

- **None of this is live.** `build-deploy.py` still refuses on ~20 files belonging to other

- **Bean's eye has not been on the effects** (R-31-13). Everything above is instrument output.
- Perf claims come from bug reports plus a local harness, **not** a real-device profile. Run

## Owner-reported defect, 2026-08-29: *"Only a surrounding glow around the dot. No spark."*

He was right on both counts, and the verification above had missed both.

### 1. The sparks could never have fired for him — an architecture error

`maybeSpark()` lived **inside** `initProgressDriver()`, which returns early on any browser with
native `animation-timeline` support. So the spark layer existed **only on the JS fallback path —
i.e. only on Firefox** — the exact inverse of what was wanted. Measured live:
`CSS.supports('animation-timeline','view()') === true`, sparks created `0`.

⛔ **The generalisable rule: a decorative layer must never live inside a fallback driver.** It has
to observe the progress VALUE, whoever wrote it. Sparks are now an independent `initSparks()` that
boots on every progress timeline and polls the computed custom property once per animation frame
while scrolling — one read per frame, only while moving.

⚠ **Why no gate or probe caught it:** the prior probe asserted `sparks=0` *under reduced motion*
and read that as the suppression working. It never asserted sparks were non-zero when they should
be — a check with no positive control. The new probe counts every spark **created** via a
`MutationObserver`, not those alive at one instant.

### 2. The trail glow was rendering correctly and was still invisible

Computed style was exactly as authored: 14px box, `blur(5px)`, `opacity: 0.75`, correct gradient and
mask, 407px tall. **Correct and imperceptible** — a pale rose smudge 14px wide on a cream ground,
beside the head's much punchier `box-shadow` halo. "Only a glow around the dot" was an accurate
description of what the code produced.

Widened and strengthened, and the three knobs are now custom properties
(`--sgs-timeline-glow-spread` / `-blur` / `-opacity`) so a client build can tune them without a
rebuild. **This is `measurement-vs-eye` exactly: every number said the layer was fine; the eye said
it wasn't there. The eye was right.**
