# sgs/gallery — `loopCarousel`, an INDEPENDENT looping control

## What changed

`sgs/gallery` gains `loopCarousel` (boolean, **default `false`**) plus an
inspector toggle that sits alongside — and is independent of — "Drag to scroll".
When on, `render.php` emits `data-sgs-loop="1"` on the scroller, and the new
Tier V module `src/shared/effects/fx-carousel-loop.js` clones leading/trailing
items and re-seats `scrollLeft` at the boundary so the track never dead-stops at
the last card.

`view.js`'s item selection now excludes clones (`:not([data-sgs-loop-clone])`),
so the dot count and `goToItem()` keep working against the REAL cards.

**`src/shared/effects/gsap/fx-draggable.js` is not modified — not one line.**

## Why this shape (D460)

Bean asked for looping carousels. The original plan said "add looping to
`fx-draggable.js`, universal across the drag roster". That fix-shape was
**falsified by the docblock of the file it proposed to edit**, which records a
prior decision rejecting exactly it: *"re-deriving such a block's own wrap-around
maths inside a block-agnostic module is exactly the per-block hyperfocus R-31-9
forbids"*, alongside a contract that the module never creates a wrapper, never
transforms, and never reorders DOM — all three of which looping a native
scroller requires.

Bean's ruling dissolved the conflict rather than resolving it: *"looping should
not be tied to the drag effect — they should be independent controls"*, and
*"we're not setting the default behaviour in all carousels, just making the
functionality available to those who want it."* A separate module owns
wrap-around as its explicit job, so the drag module's contract is never touched.

## Live verification — `scripts/motion-qa/probe-carousel-loop.mjs`, 8/8 PASS

Run against `/loop-carousel-canary/` (6 real images, `layout: carousel`, with
**both** `dragToScroll` and `loopCarousel` on — the interesting state):

| Assertion | Measured |
|---|---|
| Track genuinely overflows (loop has work to do) | `scrollWidth=7280 > clientWidth=1200`, `overflow-x: auto` |
| Clones inserted | 12 clones |
| Every clone `inert` + `aria-hidden` | 0 not neutralised |
| **Dot count keys to REAL cards, not the cloned length** | real=6, with clones=18, **dots=6** |
| Past-the-end does not dead-stop | `max=6080`, after pushing past → `3648` (re-seated) |
| Drag AND loop both live on the same element | `data-sgs-fx=draggable`, `cursor: grab` |
| Drag bounds derive from post-clone `scrollWidth` | 7280 (unchanged between reads — clones exist before any gesture) |
| A REAL pointer drag moves the track | `scrollLeft = 5118` after a 320px gesture |

**The dots row is the load-bearing one.** Bean's eye caught last wave's defects
because the automated checks asked "did it move?" rather than "did the dots
follow the cards?". Cloning makes that failure mode concrete — a naive count
reads 18. It reads 6.

### Vacuity guard

The probe exits `INCONCLUSIVE` (never PASS) if the track does not overflow, since
a non-overflowing carousel cannot loop and every assertion below would hold
without exercising anything.

## What this report does NOT claim

- **Only `sgs/gallery` carries the control.** The other five drag-roster blocks
  (`buybox`, `google-reviews`, `post-grid`, `testimonial-slider`,
  `trustpilot-reviews`) still need the same mechanical pattern. Gallery is the
  exemplar, not the rollout.
- **No screenshot pixel-diff was taken.** The verdict rests on measured DOM and
  geometry plus a real pointer gesture, not on image comparison.
- **Keyboard arrow wrap-around at the boundary was not separately exercised** —
  arrows are present and do not disable, but the wrap was driven via pointer and
  `scrollLeft`, not by repeated arrow activation.
- **Reduced-motion behaviour for the loop is untested here.** The drag module's
  own reduced-motion contract is unchanged; the loop module's needs its own pass.
